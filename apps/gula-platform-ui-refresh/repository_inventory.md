# جرد المستودع: الخلفية والعقود والهوية

## النطاق الذي تم فحصه

تمت مراجعة نقطة دخول FastAPI ومصنع التطبيق وتسجيل المسارات وطبقة عميل واجهة v3 ومساراتها ومنطق الدخول والتفويض. لم يُشغّل أي مكوّن من المستودع الأصلي ولم تُغيّر منه ملفات خلال هذا الجرد.

## حقائق معمارية مؤكدة

| العنصر | الدليل في المستودع | الأثر على الواجهة |
|---|---|---|
| الخلفية | `backend/app/main.py` ينشئ التطبيق عبر `factory.create_app()` | التطبيق الخلفي مركزي واسع النطاق وليس خدمة مختبر منفردة. |
| تجميع API | `backend/app/factory.py` يسجل مسارات أساسية وسريرية ومختبرية ومالية وهوية ووطنية وتكاملات | لا ينبغي اختزال السطح المرئي إلى قائمة ثابتة واحدة لجميع الأدوار. |
| الدخول | `backend/app/routes/login.py` يقدّم `/login` و`/logout` و`/session` | الجلسة تستخدم زوج JWT وملفات تعريف ارتباط آمنة، وتعيد دور المستخدم والمختبر عند دخوله. |
| الحماية | تسجيل الدخول يفرض التحقق للحسابات المناسبة، ويتطلب MFA لبعض الأدوار ذات الامتيازات | واجهة الدخول يجب أن تستوعب حالات التحقق وMFA وعدم القبول، لا نجاح/فشل فقط. |
| التفويض | `backend/app/routes/authorization.py` يقدّم `/authz/me` و`/authz/me/permissions` و`/authz/me/menu` | يمكن بناء سياق هوية وقائمة تنقل حقيقية من الخلفية بدلاً من أحكام محلية على الدور. |
| هوية أوسع | `IdentityService` يوفّر سياق المؤسسة والـtenant والمنشأة والأدوار المعيّنة | توجد قابلية خلفية لمفهوم مساحة العمل والسياق التشغيلي، لكنها غير مستثمرة بالكامل في واجهة v3. |
| واجهة v3 | `frontend-v3/src/routes/index.tsx` يحتوي مسارات محمية كثيرة موزعة على مجموعات أدوار | المسار المرئي واسع ويتطلب جردًا على مستوى الصفحة والإجراء، لا مراجعة صفحة لوحة التحكم فقط. |

## عقود أولية ذات أولوية للواجهة

| القدرة | العقد | الاستخدام الملائم في الواجهة |
|---|---|---|
| جلسة المستخدم | `GET /session` | استعادة جلسة مبسطة ودور الحساب ومختبره. |
| هوية السياق | `GET /authz/me` | شريط سياق المؤسسة/tenant/المنشأة والأدوار المتاحة. |
| الصلاحيات الممنوحة | `GET /authz/me/permissions` | حراسة الإجراءات وعرض أسباب المنع بدون الاعتماد على مفردات محلية. |
| قائمة التنقل | `GET /authz/me/menu` | قائمة وسياق تنقل محسوبان في الخلفية بحسب الصلاحية. |
| الفحص الجماعي | `POST /authz/check/batch` | اختبار قابلية مجموعة أوامر أو إجراءات ضمن سياق معيّن. |
| المرضى | `GET/POST /patients` وما يتصل بها | صفحات البحث والإدارة، وفق الأدوار المعتمدة من الخلفية. |
| الطلبات | `GET/POST /orders` والإجراءات المساندة | قائمة العمل المختبرية وعمليات التحقق والإلغاء. |
| النتائج | `GET/POST /test-results` والتحقق | مراجعة النتائج والتسلسل التشغيلي عند توفر الصلاحية. |

## فجوات موثقة تحتاج معالجة لاحقة

| الفجوة | الحالة الحالية | اتجاه المعالجة |
|---|---|---|
| سياق مساحة العمل | حالة المصادقة في v3 تحتفظ بمعلومات محدودة عن المستخدم والمختبر | استهلاك `/authz/me` وإدخال نموذج سياق موحّد قبل إنشاء مبدّل مساحة عمل. |
| قائمة التنقل | الشريط الجانبي يولد عناصر ثابتة ويرشحها بمصفوفة أدوار محلية | جعل `/authz/me/menu` مصدر القائمة، مع fallback آمن وواضح عند التعذر. |
| مفردات الصلاحية | ملف RBAC المحلي يستخدم مفاتيح مختلفة جزئيًا عن خدمات الخلفية | توحيد مفردات العقد أو إنشاء محوّل واحد مُختبر، مع منع القرارات الموزعة في المكونات. |
| تجربة الدخول | العقد يميز التحقق وMFA وتعطيل المختبر، بينما واجهة الدخول تحتاج تمثيل هذه الحالات بوضوح | بناء state machine للمصادقة في الواجهة بعد تدقيق عقود التحقق وMFA. |

## أساس البيانات والتشغيل المخبري

| المجال | أدلة البيانات والعقود | نتيجة تصميمية |
|---|---|---|
| الهوية والمؤسسة | توجد نماذج `users` و`lab_users` و`roles` و`role_assignments` و`organizations` و`facilities` و`tenants` | يجب عدم مساواة دور نصي واحد بمساحة العمل أو المؤسسة أو المنشأة. |
| السجل المختبري الأساسي | توجد نماذج للمرضى والطلبات والنتائج والعينات وأنواع الفحوصات | يمكن إسناد صفحات العمل الأساسية إلى موارد حقيقية، لا إلى بطاقات ثابتة. |
| LIMS المتقدم | توجد جداول ومسارات للأقسام والأجهزة والمعايرة وضبط الجودة والكواشف والعينات وسلسلة الحيازة والتقارير | واجهات المختبر يمكن أن تمتد إلى سير عمل متكامل، لكن يلزم جرد دقيق للصفحات والعقود قبل إظهاره لكل دور. |
| عزل المستأجر | تعليقات ومسارات LIMS تشير إلى JWT و`lab_id` وعزل حسب المختبر وتدقيق وoptimistic locking | يجب أن تبرز الواجهة سياق المختبر/المنشأة ولا تسمح بتغيير ظاهر لا يقابله عقد آمن. |
| حالة النظام | الخلفية تسجل مؤشرات الصحة والاستعداد والتدهور وتدعم عدة وحدات تشغيلية | صفحة حالة إدارية محتملة، بشرط حجب التفاصيل الحساسة عن الأدوار غير المخولة. |

## سطح LIMS المؤكد

تتضمن وحدة `/lims` عقودًا مثبتة للأقسام ومحطات العمل والأجهزة وحالات الاتصال والمعايرة والصيانة، وتسجيل العينات وحالتها، والطلبات وحالتها، والنتائج والتحقق والإصدار، وضبط الجودة، والمخزون، والتقارير وتوقيعها، والتكامل ASTM وHL7، وسلسلة الحيازة، ولوحة LIMS. تُعامل هذه القائمة كخريطة قدرة أولية لا بوصفها واجهة مكتملة؛ ويستلزم عرض أي عملية منها ربطها بدور المستخدم وصلاحيته وسياقه وحالات النجاح والخطأ الواقعية.

## الهوية والثقة والخصوصية: تقييم تعاقدي أولي

| المجال | القدرة المكتشفة | ما يصح عرضه | القيد أو الفجوة |
|---|---|---|---|
| ربط السجل الصحي | `POST /identity/link` يربط معرفًا وطنيًا مجزأً بسجل مريض ويمنع الازدواج ضمن الاستعلام المتاح | حالة «مرتبط بمعرّف» دون كشف المعرف الخام | لا يعرض هذا العقد مصدر تحقق أو مستوى ثقة أو صلاحية أو دليل؛ كما أن ربطه لا يعلن فحص صلاحية مخصصًا في تعريف المسار. |
| البحث بالمعرف | `GET /identity/lookup` يتطلب `patients:read` ويعيد سجلًا محدودًا ضمن المختبر | بحث مهني محدود الصلاحية مع رسائل عدم العثور | ليس تجربة تحقق وطني ولا يثبت صحة الوثيقة. |
| OCR للوثائق | `POST /id-scan/scan` يستخرج حقولًا من صورة ويعيد `needs_confirmation: true` ولا يحفظ الصورة بحسب تعليق المسار | «بيانات مستخرجة تحتاج مراجعة» فقط | لا يجوز وضع شارة «تم التحقق» أو «رسمي» بناءً على هذه النتيجة. |
| التحقق الوطني | `POST /national-id/verify` يمر عبر بوابة تكامل | يمكن إظهار وضع تكامل إداري صريح فقط عند وجود صلاحية | البوابة تعمل بأوضاع `STUB/LIVE/SHADOW`، والافتراضي لا يصلح دليلاً نهائيًا للتحقق ولا لقرار سريري. |
| الموافقات | `/consent/grant` و`/consent/revoke` و`/consent/check` تدعم نطاقًا ومتلقيًا وانتهاءً | شاشة منح/سحب وفحص موافقة محدودة | لا يوجد في العقد المراجع سجل وصول أو مركز خصوصية شامل أو تصحيح بيانات أو تصدير. |
| سياق الواجهة | backend يملك `/authz/me` و`/authz/me/menu` و`/authz/me/permissions` | شريط سياق وقائمة حسب الصلاحيات عند استهلاكها | طبقة API في v3 لا تستدعي هذه العقود بعد، وتبقى على `session()` ومصفوفات محلية. |

> **قرار واجهة ملزم:** تُصنّف نتائج OCR بأنها «مستخرجة»، وتُصنّف بوابة الهوية الوطنية حسب وضعها الفعلي، ولا يُعرض أي ادعاء تحقق رسمي أو وطني قبل توافر تكامل مصرح ومُثبت وعقد يزود مصدر الدليل ودرجة الثقة وصلاحيته.

## مصفوفة التغطية: الهوية والخصوصية والأدلة

| المجال الحساس | التنفيذ أو المصدر القائم | سطح واجهة v3 المكتشف | الحالة القابلة للاستخدام | الفجوة المؤكدة |
|---|---|---|---|---|
| هوية المريض والربط | `routes/identity.py` و`services/identity.py` | `pages/identity/IdentityPage.tsx` | ربط وبحث محدودان في الخلفية | صفحة الهوية قالب نصي بلا استدعاء API أو حالة أو صلاحية ظاهرة. |
| التحقق الوطني | `routes/national_identity.py` وبوابة `STUB/LIVE/SHADOW` | لا سطح تحقق موثوق مكتشف | فحص إثراء غير حرج فقط | لا دليل مصدر أو صلاحية أو موصل معتمد افتراضيًا؛ يمنع ادعاء التحقق الرسمي. |
| OCR للوثائق | `routes/id_scan.py` | لا مسار مستخدم نهائي موثق | استخراج حقول مع تأكيد مطلوب | لا وجود لعقد دليل أو provenance أو واجهة مراجعة واعتماد محكومة. |
| الموافقة | `routes/consent.py` | صفحة قدرات عامة تستخدم `/healthcare-consent` بدل العقد المؤكد | منح وسحب وفحص محدود بنطاق وانتهاء | لا قائمة موافقات أو عرض متلقٍ/نطاق/انتهاء أو سجل وصول؛ ومسار وطني ثانٍ تمثيلي فقط. |
| تدقيق الوصول | `AuditLog` و`/compliance/audit-summary` و`/compliance/audit-integrity` | لا صفحة مستخدم مكتشفة | ملخص للمختبر وفحص سلامة إداري | لا سجل وصول موضوعي يشرح للمواطن أي جهة استخدمت أي بيانات ولأي غرض. |
| الخصوصية والتصحيح والتصدير | لا مسارات تنفيذية مؤكدة للمركز أو التصحيح أو التصدير الشخصي | لا صفحة خصوصية مكتشفة | غير متاح كمسار مستخدم | يلزم عقد جديد وقرارات سياسة وصلاحية قبل بناء واجهة. |
| كتالوج API | `contracts/api/v1/catalog.json` يعلن بعض مجموعات أوسع | غير كافٍ لإثبات القابلية التشغيلية | مرجع نظري فقط | توجد فروق اسمية وبنيوية عن مسارات الخلفية المنفذة، فلا يعتمد وحده لبناء الواجهة. |

> **قاعدة مصدر الحقيقة:** تستخدم الواجهة مسار الخلفية المنفذ والمختبر، لا تعريفًا في الكتالوج أو نوعًا مولّدًا أو صفحة قالبية. وعند اختلاف المصادر، تُسجل الفجوة بدل تخمين عقد بديل.

## قيود التنفيذ

لا تُعرض بيانات تشغيلية أو صحية نموذجية على أنها حقيقية، ولا تُعرض أوامر أو إجراءات غير متاحة عبر عقد وخدمة خلفية. لا تحل حماية الواجهة محل التفويض الخلفي، وتُستخدم المعلومات الحساسة وفق الحاجة والدور والسياق فقط.
