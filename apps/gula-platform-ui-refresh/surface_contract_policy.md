# سياسة ربط الواجهة بالعقود

تُعامل واجهة العرض الحالية باعتبارها نموذج تجربة وليس نظام تشغيل طبي متصلًا. لذلك لا يجوز لأي صفحة أن تعرض رقمًا سريريًا أو حالة طلب أو هوية مستخدم أو نتيجة تحقق ما لم يكن لها عقد خلفي فعلي، وسياق مساحة عمل، وصلاحية مستخدم قابلة للتحقق.

| السطح | الحالة الآمنة الحالية | شرط التفعيل التشغيلي |
|---|---|---|
| تسجيل الدخول | يعرض النموذج رسالة عدم توفر الربط ولا ينشئ جلسة محلية | عقد جلسة ومصادقة فعلي مع حالات خطأ وموافقة واضحة |
| الرئيسية والطلبات | تعرض حالة عدم ربط بدل مؤشرات أو طلبات تمثيلية | عقد قراءة نطاقي مع سياق مساحة عمل وصلاحية ملائمة |
| الإجراءات المرئية | لا تنفذ إضافة أو تصديرًا أو تغيير حالة دون اتصال معلن | عقد إجراء موثق، تحقق إدخال، وحالة تحميل ونجاح وفشل |
| الهوية والثقة | لا تعرض ادعاء تحقق وطني أو OCR أو NFC أو مطابقة حيوية | مزود تحقق معتمد، مصدر دليل، طريقة إثبات، درجة ثقة، وتاريخ تحقق قابل للتدقيق |
| الخصوصية وسجل الوصول والتصحيح | لا تُنشأ واجهات وظيفية لها لأن العقود الشاملة غير متاحة | عقود قراءة وطلب وقرار مقيّدة بالصلاحية وسياق مساحة العمل |

تبقى بيانات الاختبار محصورة في اختبارات الوحدات. لا تُستخدم لإيحاء أن عمليات المختبر أو نتائج المرضى أو سجل الهوية تعمل في بيئة العرض.

## ضابط قابل للتشغيل

يتحقق الأمر `pnpm verify:contracts` من توليد **مصفوفة إجراءات الواجهة** ومن وجود أعمدة **مراجع API داخل المعالج** و**معرف العقد الأساسي** و**العقود التابعة الموثقة** و**صلاحية الخلفية** و**يتطلب سياق منشأة** وملخص التغطية فيها، كما يراجع السياسة وسجل الصفحات ويمنع إدخال استدعاءات تشغيلية مباشرة إلى أسطح العميل ومكوناته دون مراجعة عقد وصلاحية وسياق منشأة.

يعد ملف `scripts/backend-contract-registry.json` **سجل العقود المرجعي** للواجهة. لا يصبح أي سطح تشغيلي مقبولًا لمجرد وجود طلب شبكة؛ إذ يلزم أن يعلن معرفًا مسجلًا بـ`data-contract-id` أو `contractId`، وأن يعرض مؤشر الصلاحية الخلفية المتفق عليه بالاسم عبر `data-permission` أو `requiredPermission`، وأن يعلن سياق مساحة العمل عند اشتراط العقد لذلك. وفي جرد واجهة v3 لا تعد المطابقة مقبولة إلا إذا تتبع المولد الاستدعاء من **معالج العنصر نفسه** إلى عميل API واسم عملية العميل ونوعها، بحيث تقود هذه العناصر معًا إلى **عقد أساسي واحد** مسجل. إن احتوى المعالج على طلبات لاحقة، فتسجل في عمود «العقود التابعة الموثقة» ولا تحل محل العقد الأساسي ولا تختفي من الدليل. يفشل الضابط عند بقاء أي معالج تشغيلي بلا عقد أساسي أو عند وجود عقد تابع غير مسجل. لا يكفي حارس مسار عام أو فحص صلاحية محلي لتفعيل الإجراء. يبقى تفويض الخادم مصدر القرار النهائي، ولا تُستخدم هذه المؤشرات لإيحاء بأن التفويض أو السياق قد تحققا محليًا.

## استثناء حالة تهيئة طبقة الربط

يعامل `trpc.integration.connectionStatus` كاستعلام حالة محلي آمن فقط. لا ينفذ هذا الإجراء طلبًا إلى الخلفية، ولا يعيد بيانات تشغيلية أو عنوان خدمة أو رمزًا أو صلاحيات مستخدم. لذا يستثنيه الضابط صراحة من إلزام عقد سطح تشغيلي. أي إجراء tRPC آخر في العميل يعامل تشغيليًا ويتطلب العقد والصلاحية وسياق المنشأة وفق هذه السياسة.
