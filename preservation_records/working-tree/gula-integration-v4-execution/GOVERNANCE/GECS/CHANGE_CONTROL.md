# GECS — CHANGE CONTROL

**Purpose (canonical):** the authorization boundary for every proposed change. A change may not
start until its category's authority has granted it. **A documentation task does not authorize code;
a test task does not authorize production change; an architecture recommendation does not authorize
implementation.**
**Created:** 2026-11-17

## Categories and boundaries

| Cat | Scope | Examples | Authorization boundary | Current permitted? (this phase) |
|---|---|---|---|---|
| **A** | Documentation-only (governance, reports, registries under `GOVERNANCE/`) | GECS files, decision-package addenda, blocker-register appends | Governance phase mandate; append-only; no historical rewrite | **YES — only this category is active** |
| **B** | Test and tooling changes | fixtures, conftest, test files, CI workflows, harnesses | explicit QA/tooling authorization; never to make a failing gate pass | **NO** |
| **C** | Application code changes | `backend/app/**`, frontend src, scripts that alter behaviour | Program Director + review; after D-001…D-004 where schema-dependent | **NO** |
| **D** | Database and migration changes | `backend/migrations/**`, `migrations/env.py`, schema objects | D-003 (env.py) / D-001 (revisions) approval first; zero DDL for NR-011 | **NO** |
| **E** | Architecture changes | ownership model, service boundaries, Shared Core, ADR adoption | Architecture + Program Director; implements D-001/D-002/D-010 only after approval | **NO** |

## Required declaration (every proposed change)

1. Target files · 2. Reason · 3. Related work IDs (`WORK_REGISTRY`) and finding IDs
(`FINDINGS_REGISTRY`) · 4. Expected effect · 5. Risk · 6. Reversibility · 7. Required approval
(category + named authority, `DECISION_REGISTRY`) · 8. Validation plan (evidence to be produced,
with the E-ID it will receive).
