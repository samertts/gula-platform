### 2.2 Two disjoint, incompatible session families

| Family | Table | Owner key | Device link | Auth claims |
|---|---|---|---|---|
| NIAM | `niam_sessions` (`identity/models/session.py:11-25`) | `account_id` String(26) → `niam_accounts.id`, NOT NULL | `device_id` String(26) → `niam_devices.id`, nullable, **SET NULL** (:25) | `{jti, account_uuid, identity_id}` — **no `user_id`, no `perm_ver`** (`authentication_service.py:64-74`) |
| Legacy/MFA | `mfa_sessions` (`models/mfa_device.py:31-40`) + enforced JWT | `user_id` Integer → `lab_users.id` | `MFADevice.credential_id` is a WebAuthn credential, not an account link | `user_id` (int) + `perm_ver` (`security/auth.py:73-80`) |

The NIAM login route `backend/app/identity/api/auth.py:27-42` passes only
login/password/ip/user-agent — **`device_id` is never supplied**, so
`niam_sessions.device_id` stays NULL. Separately, `security/auth.py:88-93`
`create_token()` overwrites `jti` with a fresh `uuid4()`, so the JWT `jti` never
equals the stored `UserSession.token_jti`.

**Enforced request auth is the legacy path.** `security/dependencies.py:37-124`
requires `payload["user_id"]` (:71), queries `LabUser.id`/`User.id` (:77-83),
then checks JTI blacklist (:55-69) and `perm_version` (:93-107). It performs
**no device check, no NIAM session check, no account_id check**. A NIAM token
(without `user_id`) is rejected at `dependencies.py:72-75`. NIAM sessions are
consulted only by a separate authorization decision engine
(`identity/services/authorization_decision.py:216-221`), not by main API auth.

### 2.3 Device revocation today does nothing to sessions or credentials
`backend/app/identity/services/device_service.py:79-85`:
```python
device = await self.repo.get_by_id(device_id)
if not device:
    return False
device.is_active = False
await self.repo.session.flush()
return True
```
That is the entire behaviour: flip `niam_devices.is_active`. The sole route
`identity/api/devices.py:44-54` calls it via `get_by_uuid`. There is **no**
session termination, JWT blacklist, credential invalidation, `bump_perm_version`
call, or audit entry.

`Device.account_id` consumers (exhaustive): definition (`device.py:16`);
write-only in `device_service.py:34,41-42,50`; and
`DeviceRepository.find_by_account_id()` (`device_repository.py:31-40`) which has
**zero callers**. The registration route `identity/api/devices.py:21-27` never
sets `account_id`, so API-registered devices have `account_id = NULL`.

Session-termination APIs exist but are **not** called by device revocation and
are keyed on a NIAM account ULID, not a device:
`SessionService.terminate_all(account_id)` (`session_service.py:37-38`),
`AuthenticationService.logout_all_sessions(account_id)` (`authentication_service.py:144-148`),
`adaptive_auth.terminate_previous_sessions(account_id)` (`adaptive_auth/services.py:559-593`).

Related methods `attest_device`, `report_health`, `calculate_risk_score`,
`mark_compromised`, `transfer_device`, `report_lost` (`device_service.py:87-183`)
query **`MachineIdentity.uuid`** (`models/machine_identity.py`, table
`niam_machine_identities`, `String(36)`) — a different namespace; do not conflate
with `niam_devices`.

Side effect: `DeviceRepository.find_by_fingerprint` filters `is_active=True`
(`device_repository.py:12-18`) while `device_fingerprint` is UNIQUE —
re-registering a revoked fingerprint attempts a duplicate insert. (Evidence
only; no change made.)

### 2.4 Why `bump_perm_version` cannot consume a NIAM device
`backend/app/security/session.py` `bump_perm_version(user, db, *, ...)` needs a
**legacy `LabUser` ORM instance** with numeric `.id`, `.perm_version`, `.email`
and a sync `Session`. It cannot accept a NIAM `Account` (String(26) id, no
`perm_version`). All its callers are legacy flows (`password_reset.py`,
`labs.py`, `admin.py`, `login.py`, `admin_service.py`, `mobile_service.py`,
`lab_service.py`).

Legacy↔NIAM linkage is deliberately inert: `LegacyAccountLink`
(`identity/models/legacy_account_link.py:39-43`) maps `legacy_account_id:int`
↔ `canonical_account_id:String(26)` by HMAC fingerprint, and
`legacy_mapping_service.py:51-57` explicitly states it never creates canonical
accounts, copies credentials, runs backfills or changes authorization decisions
without "separate approved waves and an explicit feature-flagged cohort."

## 3. Existing relationship diagram (as implemented)

```
[FORCED AUTH PATH — legacy]
  JWT(user_id:int, perm_ver:int) ──> get_current_user() ──> LabUser/User(id:int)
        │                                                     │
        └─ blacklist(jti) in Redis ──┐                         └─ perm_version (Redis cache + primary DB)
                                      └── revocation OUTSIDE device domain

[NIAM REGISTRY — inert wrt forced auth]
  Device(person_id NOT NULL, account_id NULLABLE) ──FK──> Account(String26)
  UserSession(account_id NOT NULL, device_id SET NULL) ──FK──> Account / Device
        │ (device_id never populated by live NIAM login)
        └─ consulted only by authorization_decision.py, NOT by main API auth
  LegacyAccountLink(int ↔ String26 by HMAC) — registry only, not an auth bridge

  NO runtime edge connects niam_devices → enforced JWT / perm_version today.
```

## 4. Proposed ownership model (documentation only — NOT implemented)
1. Decide and enforce whether a device is owned by a NIAM **Person** (current
   `person_id` NOT NULL) or an **Account**. If account-scoped revocation is
   desired, make `Device.account_id` authoritative (populate on registration,
   likely NOT NULL + a controlled backfill) — an ownership/schema change.
2. Populate `UserSession.device_id` from the NIAM login path so a device→session
   link exists, and reconcile the stored `token_jti` with the JWT `jti`.
3. Define an authoritative, active NIAM-account ↔ `LabUser/User` runtime mapping
   if revoking a NIAM device must terminate **enforced legacy JWTs**. `LegacyAccountLink`
   is a pending registry, not such a bridge; activating it is a cross-domain
   migration / separate approved wave with a feature-flagged cohort.
4. Define revocation scope (this device's sessions vs all account sessions),
   whether legacy JWTs are blacklisted / `perm_version` bumped, who is
   authorized to revoke, and how the numeric user is derived.

## 5. Migration proposal (documentation only — NO DDL executed)
- Backfill `Device.account_id` from a verified person→account ownership source;
  add NOT NULL only after reconciliation.
- Backfill `UserSession.device_id` where attribution is reliably known; fix
  `create_token()`/`token_jti` desynchronisation.
- Establish and validate an account↔legacy-user link table before any
  cross-domain credential revocation.
- All of the above require database-owner sign-off and an authorized migration
  wave. **None was executed. `backend/migrations/env.py` remains +49/-0.**

## 7. Backward-compatibility risks
- Changing `Device.account_id` to NOT NULL / backfilling may break existing
  API-registered devices that currently have it NULL.
- Populating `UserSession.device_id` changes session attribution semantics.
- Introducing an account↔legacy-user bridge is a cross-domain policy change with
  privacy/blast-radius implications; must not be inferred from ULID format.
- Re-registering a revoked fingerprint collides with the UNIQUE constraint
  (evidence in §2.3).
