# GLOSI Security and License Policy

**Version:** 1.0.0
**Date:** 2026-11-15
**Status:** Mandatory for every registry entry and every proposed decision.

---

## 1. المبادئ

1. لا ترخيص مفترض. المصدر العام لا يعني إعادة استخدام حرة.
2. لا اعتماد مع ترخيص مجهول.
3. لا اعتماد مع خطر أمني حرج غير معالج.
4. الفحص الأمني والقانوني البشري شرط للاعتماد، وليس درجة آلية.
5. الدرجة العالية لا تتجاوز نقض الأمن أو القانون.

## 2. مراجعة الترخيص

### 2.1 الأسئلة الإلزامية

| السؤال | الحقل |
|---|---|
| ما الترخيص الفعلي؟ | `legal.license` |
| هل يسمح بالاستخدام التجاري؟ | `legal.commercial_use_permission` |
| هل يسمح بالتعديل؟ | `legal.modification_permission` |
| هل يسمح بإعادة التوزيع؟ | `legal.redistribution_permission` |
| ما التزامات الإسناد وNOTICE؟ | `legal.attribution_requirements` |
| هل يوجد copyleft؟ وما نطاقه؟ | `legal.copyleft_obligations` |
| هل توجد مخاطر براءات/علامات تجارية؟ | `legal.patent_trademark_considerations` |
| هل توجد قيود على البيانات/المصطلحات؟ | `legal.data_licensing_restrictions` |
| هل الترخيص متوافق مع سياسة GULA؟ | `legal.license_compatibility` |

### 2.2 أولوية التراخيص (من `OPEN_SOURCE_POLICY.md`)

Apache 2.0 → MIT → BSD → MPL 2.0 → LGPL → GPL → AGPL → Proprietary (استثناء موثق).

### 2.3 قواعد خاصة

- **MPL 2.0:** مقبول مع الالتزام بنشر تعديلات الملفات المرخّصة عند التوزيع.
- **GPL/AGPL:** يتطلب مراجعة قانونية بشرية وتحليل أثر التوزيع/الشبكة.
- **NOASSERTION:** لا يُعتبر ترخيصاً. يجب فحص LICENSE يدوياً.
- **التراخيص المزدوجة:** يجب تحديد المسار المختار وعدم افتراض الأفضل.
- **المعايير والمصطلحات:** ترخيص الكود لا يغطي محتوى SNOMED/LOINC/ICD؛ يلزم ترخيص منفصل.
- **البيانات:** لا تُسجّل بيانات مرضى حقيقية أو مجموعات بيانات مقيّدة دون مراجعة.

## 3. مراجعة الأمن

### 3.1 الحد الأدنى قبل الاعتماد

| الفحص | الحد المطلوب |
|---|---|
| سياسة الأمن | موجودة ومعلنة أو تعويض موثق |
| الإفصاح عن الثغرات | قناة واضحة |
| CVE | لا ثغرة حرجة نشطة غير معالجة |
| الاعتماديات | SBOM أو فحص سلسلة توريد |
| المصادقة | نموذج واضح لا يتجاوز NIAM |
| التفويض | صلاحيات دقيقة ورفض افتراضي |
| التشفير | نقل وتخزين مناسب |
| التدقيق | سجلات غير قابلة للتلاعب أو تكامل مع سجل GULA |
| الصيانة | إصلاحات أمنية خلال فترة معقولة |

### 3.2 شروط رفض فورية

- ثغرة حرجة مفتوحة بلا معالجة.
- اعتماد على مكوّن مهجور أو غير مدعوم.
- غياب مصدر رسمي أو مستودع موثوق.
- سلوك غير موثوق (تنفيذ أوامر، اتصال خارجي خفي، أسرار مضمّنة).
- عدم القدرة على عزل المكوّن أو تدقيقه.
- مخالفة خصوصية البيانات الصحية.
- فرض خدمة سحابية أو مزوّد واحد.

### 3.3 التعامل مع CVE

- تُسجل الثغرات المعروفة في `security.known_cves` مع تاريخ التحقق.
- `CRITICAL` أو `HIGH` غير معالجة → `security_review_status = BLOCKED` ومنع الاعتماد.
- `MEDIUM`/`LOW` تُوثّق مع خطة معالجة.
- عند صدور إصلاح، يُعاد التقييم وتضاف نسخة جديدة إلى `evaluation_history`.

## 4. خصوصية البيانات والذكاء الاصطناعي

- لا بيانات مرضى حقيقية في السجل أو الاختبارات أو الأدلة.
- لا إرسال بيانات صحية إلى خدمات AI خارجية.
- يُفضل النماذج المحلية أو المعالجة الحتمية.
- أي مكوّن AI يحتاج تقييم تحيّز، شرح، وأمان سريري قبل أي استخدام.
- لا تُسجل مفاتيح API أو أسرار في المستودع.

## 5. الترخيص مقابل القرار

| الحالة | النتيجة |
|---|---|
| ترخيص غير متوافق | `REJECT` أو `STUDY` (بدون كود) |
| ترخيص مجهول | لا اعتماد؛ يمكن `STUDY` مؤقتاً |
| ترخيص متوافق مع مراجعة بشرية | يمكن المضي في التقييم |
| خطر أمني حرج | `BLOCKED` بغض النظر عن الدرجة |
| خطر سريري غير معالج | `BLOCKED` حتى مراجعة السلامة السريرية |

## 6. سجل القرار

يجب أن يتضمن قرار الاعتماد:
- مرجع الترخيص وNOTICE.
- مرجع المراجعة الأمنية وتاريخها.
- الثغرات المفتوحة وخطة معالجتها.
- شروط إعادة التوزيع.
- خطة الرجوع والاستبدال.
- اسم المراجع البشري (وليس وكيلاً آلياً).

## 7. عدم الادعاء

لا يقدم GLOSI شهادة قانونية أو أمنية. التقييمات الآلية مساعدة، والاعتماد النهائي يحتاج مراجعة بشرية مستقلة وتوثيقاً رسمياً.
