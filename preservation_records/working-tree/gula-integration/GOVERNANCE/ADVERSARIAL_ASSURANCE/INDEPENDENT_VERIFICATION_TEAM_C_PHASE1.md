## 4. Overall verdict

Four of five remediations survived falsification at narrow engineering scope: **AUD-SEC-001, AUD-SEC-002, AUD-API-002, AUD-ARCH-003 → INDEPENDENTLY VERIFIED** (the latter two remain strictly owner-gated; no production claim). **AUD-SEC-003 → BLOCKED** because its own targeted test fails 2/13 and the privileged-MFA happy path crashes with an `AttributeError` — a real, reproducible functional defect in the remediation, not a test artifact. Security posture of SEC-003 is fail-closed (no tokens leaked), but the staged login does not actually work end-to-end, and the implementer's reported pass count is contradicted by direct observation.

**No `PRODUCTION READY` status was awarded to any finding.** Owner-gated items (AUD-API-002, AUD-ARCH-003) remain owner-gated; all owner decisions remain BLOCKED; `production_ready` counters remain 0. All listed invariants PASS.

**Prominent residual vulnerabilities / defects for the owner:**
1. **SEC-003 functional break (BLOCKED):** `login.py:77` `datetime.now(datetime.UTC)` — correct factor verification leads to HTTP 500 and no token issuance; legitimate privileged login is unavailable.
2. **Legacy domain ambiguity (API-002 / SEC-002 interaction):** tokens lacking `account_kind` fall back to `lab_id` derivation (→USER when absent), so a legacy OAuth2 subject tied to a LabUser can resolve to the wrong family on ID collision.

## 5. What I could NOT verify (honest gaps)

- **No operational database / runtime deployment:** all DB-backed behavior was observed via the repository's in-memory SQLite test fixtures; no PostgreSQL, Redis, or containerized runtime was exercised. Cross-worker single-use of MFA pending tokens (Redis vs in-memory blacklist) is therefore unverified.
- **No external/OIDC relying-party validation:** OAuth2 tokens were validated against a local protected route (`/labs/me`) only; JWKS/OIDC discovery is intentionally fail-closed (503) and was not exercised as a real RP flow.
- **Priority/trust-status:** whether NIAM `RoleAssignment`s for `master_admin`/`ministry_admin` actually exist in a seeded production-like catalog (they are shared-RBAC platform roles) was checked only against code/migration seeds, not a live directory.
- **Full semantic equivalence of the two authorization engines** (ARCH-003) is not proven by a 5-situation corpus; only the pinned decision contract was verified.
- **SEC-003 fix was not re-run after any correction** (none was permitted): the verdict reflects exactly the working tree observed at verification time.
