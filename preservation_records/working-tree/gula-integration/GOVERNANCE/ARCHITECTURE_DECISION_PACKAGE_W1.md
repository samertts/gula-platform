## 3. Problem statement

The repository can build a migration-only schema (433 tables), and that schema can be torn down and
rebuilt with an identical fingerprint. It cannot, however, **run the backend test suite** against
that schema. The 119 reproduced failures are dominated by two structural defects:

1. **Missing tables** — 340 ORM tables have no migration, including `national_patients`,
   `national_citizens`, `national_encounters`, all 18 `EHRBase` tables, all 45 `CareContinuumBase`
   tables, all 36 `DataPlatformBase` tables and all 24 `HealthDataBase` tables.
   `national_encounters`, `ehr_conditions` and `exam_code` appear in no migration at all.
2. **Column drift** — 82 migrated tables lack 664 ORM columns; e.g. `fin_providers.provider_type`
   (29 failures), `radiology_exams.exam_code` (4), `pharmacy_drug_catalog.code` (3),
   `organizations.org_type` (2), `fin_subscriptions.billing_cycle` (2).

A third defect, **NR-011**, prevents Alembic autogenerate from even describing the gap: cross-
`MetaData` foreign keys raise `NoReferencedTableError`, so `alembic check` cannot become the
regression gate until metadata is repaired.

Two observed failures are **not** schema migration gaps and must not be folded into ADR-A:
20 `RUNTIME_GUARD` failures (`test_edge_platform` raising `RuntimeIsolationError`) and 4
`HARNESS_PATH_ARTEFACT` failures (test-side source reads relative to the external harness). These
need their own disposition before a green gate can be claimed.

**Criterion 5 / `MIG-EXISTING` remains NOT MET.**

## 4. ADR-A — National migration strategy

### 4.1 Decision to be made

How should the 340 missing ORM tables (per-base) / 426 (per-context) and the 82 table / 664 column
drift be brought under Alembic control, in what order, and with what release-scope policy?

### 4.2 Options considered

| Option | Approach | Cost | Reviewability | Risk | Reversible |
|---|---|---|---|---|---|
| **A — Incremental by bounded context** (refines original A1 + A3) | Fix NR-011; author one migration per bounded context with a strict-schema round trip; register a per-context "shipping / non-shipping" flag and feature-gate non-shipping surfaces | High (17 bases / ~40 contexts) | **High** — each diff attributable, gated independently | Low per step; long programme | Yes — each revision independent; feature flags revertible |
| **B — Centralised baseline with ownership gates** | One programme baseline revision per meta-domain (core clinical, operational, governance, analytics), each reviewed by a named domain owner and gated by a strict sub-suite | Medium | Medium — 4 large but domain-coherent diffs | Medium — larger blast radius, cross-domain FK ordering | Yes, but rollback granularity coarser |
| **C — Hybrid, patient-critical first** | Migrate the minimum patient-critical closure (`national_patients`, `national_citizens`, `national_encounters`, `ehr_*`, `care_continuum`, pharmacy/radiology ordering tables) plus their column drift; mark everything else non-shipping | Medium–High | High for the critical subset | **Medium-high** — partial closure can create a false sense of release readiness; requires an explicit interim feature freeze | Yes |
| **Original A2 — single bulk baseline** | One revision covering everything currently in ORM | Medium | **Unreviewable** | High | Theoretically, practically no |
| **Original A4 — deploy-time `create_all()`** | Let deployment synthesise missing tables | Low | None | **Empirically rejected** — the 872/0 SQLite control proves this masks exactly the gap W1 measures | No |

### 4.3 Recommendation

**Adopt Option A (incremental by bounded context) with the A3 release-scope rule, and reject A2 and
A4.** Do not adopt Option C as the programme strategy; it may be used only as an *emergency release
sequence* if the Programme Director explicitly accepts a reduced, documented release scope and a
feature freeze on all unmigrated surfaces.

Operational meaning of "shipping": a surface is shipping only if (a) its route/worker is enabled in
the target release configuration, (b) every ORM table and column it touches exists in the
migration-only schema, and (c) its strict-schema module set is green. Everything else is
**non-shipping**, feature-gated off, and listed by name in the release notes. The current code
already references most missing tables from live modules (e.g. `national_practitioners` 96 refs,
`national_citizens` 84, `national_patients` 71, `national_encounters` 55, `hospitals` 40); therefore
"non-shipping" must be enforced by configuration, not by documentation alone.

Recommended context order (derived from measured live coupling and FK depth, not from a Ministry
requirement):

1. Reference/master data and identity closure (`national_organizations`, `national_departments`,
   `national_practitioners`, `gov_hierarchy_nodes`) — after ADR-B.
2. Patient/citizen registry and encounters (`national_citizens`, `national_patients`,
   `national_encounters`, `national_admissions`, `national_observations`, `national_referrals`).
3. Clinical records (`EHRBase` 18 tables, `ClinicalBase` 39 missing, `CareContinuumBase` 45).
4. Hospital / nursing / pharmacy / radiology operational tables.
5. Governance, audit and analytics (`governance_admin` 67, `analytics_dw` 60, `legacy` 21).

Order 1 and 2 are constrained by the 236 unresolved FK edges in `core_clinical`: the cross-metadata
FKs cannot resolve until NR-011 is fixed, and target tables must exist before dependent tables.

### 4.4 Required attributes of the recommendation

* **Evidence.** §2.2–2.5; 340 missing tables / 7,368 columns; 82 tables / 664 missing columns; four
  P0 patient-workflow modules fail only under strict schema (ICU/LIMS 6/7, emergency surgery 2/4,
  pharmacy/radiology 1/3, pharmacy POS 0/3); SQLite control 872/0.
* **Assumptions.** (i) A release owner can name, per release, the surfaces it serves; (ii) feature
  flags exist or can be added without schema change; (iii) each context has a test subset that can
  be run against the strict schema; (iv) NR-011 is approved and completed first; (v) no Ministry
  mandate fixes the whole 340-table surface as a single release scope.
* **Benefits.** Every migration diff is attributable and revertible; strict-schema green can be
  claimed per context instead of waiting for the entire platform; drift is fixed where it is
  measured; the non-shipping register makes an honest release note possible; A4's masking behaviour
  is eliminated.
* **Risks.** Long duration and repeated migration authoring; context boundaries may not align with
  FK topology (mitigate by ordering on FK depth, not folder name); a non-shipping surface can be
  accidentally enabled (mitigate with CI assertion over the shipping register); 20 `RUNTIME_GUARD`
  and 4 harness-path failures remain independent of this decision; the two small table groups
  (`duplicate`, `unresolved_ownership`) need ADR-B or separate rulings.
* **Reversibility.** Yes — one Alembic revision per context, additive only; each can be reverted
  with a single `downgrade <revision>` provided §7's full-teardown rule is observed for full
  rollback. No destructive migration is proposed.
* **Approval authority.** Programme Director (architecture scope and release honesty) + Chief
  Architect (context ordering and migration design) + Release Manager (shipping register and
  feature-gate enforcement).
* **Acceptance criteria.** (1) NR-011 green before the first context revision; (2) for each context,
  `alembic upgrade head` on an empty PG16 database produces the expected tables/columns; (3) the
  strict suite subset for that context passes against the migration-only DB; (4) fingerprint
  comparison shows only the intended DDL; (5) the shipping/non-shipping register is committed and CI
  enforces it; (6) zero `MIGRATION_MISSING_TABLE` and zero `MIGRATION_COLUMN_DRIFT` failures for
  shipping contexts; (7) release notes name every non-shipping surface; (8) full `downgrade base` +
  `upgrade head` still passes after each context revision (§7).

## 5. ADR-B — Ownership of `facilities`, `organizations`, `national_facilities`

### 5.1 New evidence that refines the carried B1 premise

The carried recommendation (B1 + single ORM owner) is **not changed in direction**, but its stated
premise was incomplete and is corrected here. Measured on the migration-only database and on the
migration sources:

| Table | DB columns (measured) | ORM owner | Migration history | Downgrade |
|---|---:|---|---|---|
| `facilities` | 11 — matches `Base` ORM exactly | `app/models/organization.py` (`Base`) | Conditionally created in `20260813_0003`; FKs added in `20260813_0003` | **No `drop_table` anywhere** |
| `organizations` | 17 — has legacy `organization_id` + `organization_type` and new `org_id`; **no `org_type`** | `app/models/organization.py` (`Base`, maps `org_type`) | Conditionally created in `20260722_0001`; bootstrap columns added in `20261114_0001`; `org_type` never added by any migration | **No `drop_table` anywhere** |
| `national_facilities` | **6** — matches `app/models/clinical_scope.py::NationalFacility` (`Base`): `id, facility_code, name, status, created_at, updated_at` | Dual: `Base` (6-col) and `NationalBase` (28-col, `extend_existing=True`) | Created in `20260813_0004` with exactly the 6-column shape | **No `drop_table` anywhere** |

Additional measured facts:

* These three tables are **created by migrations on a fresh build**; they are not merely inherited
  pre-existing infrastructure. Describing B1 as "leave pre-existing tables alone" is factually
  incomplete. The correct statement is: *migration-created reference tables whose downgrade was
  omitted, with ambiguous ownership and possible pre-existing rows in long-lived databases.*
* The 28-column `NationalBase` `Facility`
  (`backend/app/national/domain/facility.py`) is imported only by
  `backend/app/national/domain/__init__.py` as a re-export. There are **no queries, routes or
  services** using it. Because the physical table has 6 columns, any query through this mapping
  would fail on missing columns. It is a dormant duplicate, not a second live owner.
* `insurance_coverages` (`Base`, `app/billing/models.py`) matches its 14-column DB shape exactly
  and is **not** part of the residual problem; it is listed here to prevent scope creep.
* `organizations.org_type` is the direct cause of 2 strict failures; it is a column-drift item
  (ADR-A context 1), not an ownership item.
* After `downgrade base`, 4 tables remain: `alembic_version` (expected) plus these three. Version
  rows are 0. This is an **asymmetric conditional-create/no-drop defect**, not proof that the tables
  predate the migration chain.

### 5.2 Options considered

| Option | Approach | Fit to evidence | Risk |
|---|---|---|---|
| **B1 (corrected) — single `Base` owner + explicit baseline-owned exclusion** | Declare `facilities`, `organizations` and `national_facilities` as **migration-created, baseline-owned reference tables excluded from `downgrade base` by design**; one authoritative ORM owner per table (`Base`); retire the 28-col `NationalBase` duplicate; record the exclusion in an ADR and assert it in CI | **Best** — matches measured DB shapes and migration history | Long-lived databases may hold rows whose provenance is unknown → never drop automatically |
| **B2 — migration-owned, add to downgrade path** | Make all three droppable by `downgrade base` | Simple symmetry | **High** — may destroy national reference data in long-lived deployments; requires a data-ownership survey that does not exist |
| **B3 — split** | `national_facilities` migration-owned; the other two baseline-owned | Partial | `national_facilities` is used by `clinical_ehr_facility_bindings` FKs; splitting creates a second asymmetry without new evidence |
| **B4 — dedicated master-data service owns all three** | Introduce a service boundary and API-mediated access | Strategically interesting for a future national deployment | **Out of scope now** — adds a new service, contracts and migration of writes; unproven by W1 evidence |
| **B5 — federated ownership with sync contracts** | Multiple owners, synchronised reference data | Matches an eventual ministry/hospital hierarchy | **Rejected now** — duplicates write authority and cannot be verified with current evidence |

### 5.3 Recommendation

**Adopt B1 with corrected wording**, plus a single ORM owner:

* `facilities` → `app/models/organization.py::Facility` (`Base`), 11 columns.
* `organizations` → `app/models/organization.py::Organization` (`Base`), with a reviewed migration
  adding `org_type` (or a documented compatibility view) to close the 2 strict failures — sequenced
  under ADR-A context 1, **not** under this ownership decision.
* `national_facilities` → `app/models/clinical_scope.py::NationalFacility` (`Base`), 6 columns — the
  mapping that actually matches the physical table and the FK target used by
  `clinical_ehr_facility_bindings`.
* The 28-column `NationalBase` `Facility` in `backend/app/national/domain/facility.py` is marked for
  **retirement or re-pointing** after approval: either delete the dormant mapping (append-only
  archive preferred per repository policy) or migrate the table to the 28-column shape in a reviewed
  revision. Deleting the mapping is the lower-risk option; it requires no DDL.
* The exclusion from `downgrade base` is **explicit and asserted**, not incidental: a CI check must
  verify that these three tables are the only non-`alembic_version` residuals and that no migration
  gained a `drop_table` for them without a new ADR.

### 5.4 Required attributes of the recommendation

* **Evidence.** DCR §9.7; §10.3; measured DB column sets above; migration grep showing conditional

## 6. NR-011 — Alembic metadata registration and merged `MetaData`

### 6.1 Decision to be made

Which metadata strategy will allow `alembic check` / autogenerate to describe the ORM↔migration gap
instead of aborting, and what validation proves it works?

### 6.2 Measured defect

`backend/migrations/env.py` currently exposes a **10-entry** `target_metadata` list (lines 116–127):
`Base`, `NationalBase`, `EHRBase`, `CitizenPlatformBase`, `ClinicalBase`, `HealthDataBase`,
`TrustBase`, `GovernanceBase`, `CareContinuumBase`, `IdentityBase`.

Seven declarative bases are omitted: `HospitalBase`, `DataPlatformBase`, `NHDWBase`, `NursingBase`,
`PharmacyBase`, `RadiologyBase`, `FinBase`. National domain modules (notably
`app.national.domain.encounter`) are not imported at all.

`ehr_allergies` has four FKs crossing `EHRBase.metadata → NationalBase.metadata`
(`national_citizens`, `national_encounters`, `national_patients`, `national_practitioners`). SQLAlchemy
cannot resolve them in any single metadata, so:

* **Probe A** (baseline): `NoReferencedTableError: ehr_allergies.patient_id → national_patients`.
* **Probe B** (import `app.national.domain`): error moves to `national_patients`; import order cannot
  fix it.
* **Probe C** (7 omitted bases imported + one merged `MetaData`): `NoReferencedTableError` eliminated;
  a real diff becomes visible — **284 distinct missing tables, 68 add / 70 remove columns**. Index
  counts from probe C are inflated by `to_metadata()` and are explicitly **not** drift evidence.

Therefore a one-line import is **not** a fix. The fix is two-part: **(1)** register the missing
metadata (national domain models plus the seven omitted bases); **(2)** give Alembic a single merged
`MetaData` (or an equivalent, documented strategy that resolves cross-base FKs deterministically).

### 6.3 Options considered

| Option | Approach | Assessment |
|---|---|---|
| **N1 — Two-part fix (recommended)** | Import all model surfaces; merge into one `MetaData`; pin merge order; assert probe-C behaviour in a regression test | **Recommended** — the only measured option that removes the abort |
| **N2 — Import-only fix** | Add missing imports, keep the 10-entry list | **Rejected** — probe B proves the error merely moves |
| **N3 — Replace FK strings with no-FK columns** | Remove cross-base FKs to make autogenerate work | **Rejected** — destroys referential integrity to make a tool green; violates clinical safety |
| **N4 — Keep multiple `target_metadata`, generate revisions manually** | Skip autogenerate | **Rejected** — leaves `alembic check` permanently red; no regression gate |

### 6.4 Required attributes of the recommendation

* **Evidence.** `env.py` lines 116–127; probe A/B/C logs
  (`/tmp/opencode/remediation/w1/alembic_check_probe_{a,b,c}.log`),
  `ALEMBIC_PROBE_EVIDENCE.md`, `alembic_probe_{b,c}_env.diff`,
  `alembic_check_probe_c_summary.json`; DCR §10.4 / §11.7; W1_CHECKPOINT §§5–6.
* **Assumptions.** (i) Merging metadata for *autogenerate detection only* does not change runtime DDL;
  (ii) merge order can be made deterministic; (iii) `to_metadata()` index inflation is understood and
  excluded from drift assertions; (iv) ADR-A will subsequently resolve the real diff.
* **Benefits.** `alembic check` becomes a usable, deterministic regression gate; the true 284-table
  / 68-add / 70-remove-column diff is visible; no referential integrity is sacrificed; enables
  per-context migration authoring under ADR-A.
* **Risks.** A large merged metadata can be slow; a future new base may be forgotten again (mitigate
  with a test asserting every declarative base discovered under `backend/app` is registered);
  autogenerate may propose destructive operations from the 70 "remove column" findings — these must
  be reviewed, never applied automatically.
* **Reversibility.** Yes — `migrations/env.py` is a single file; reverting restores the previous
  detection behaviour. No database change occurs.
* **Approval authority.** Chief Architect + Migration Owner; Programme Director must sequence it
  before ADR-A authoring.
* **Acceptance criteria.** (1) `alembic check` runs to completion (red is acceptable **until** ADR-A
  lands; aborting is not); (2) no `NoReferencedTableError` for any table in any base; (3) a test
  asserts all 17 bases and the national domain models are registered; (4) probe-C counts reproduced
  and recorded; (5) no DDL executed by the fix itself; (6) fingerprint of a fresh build unchanged;
  (7) the 70 proposed column removals are triaged and explicitly rejected or accepted — never

## 7. Rollback and recovery policy (decision R-01)

### 7.1 Measured evidence

| Procedure | Result | Verdict |
|---|---|---|
| Fresh `upgrade head` | PASS, 433 tables, rev `20261114_0006` | baseline |
| `alembic downgrade base` | exit 0, 25 s, version rows **0**, 4 residuals (`alembic_version` + 3 reference tables) | **supported** as part of full rebuild |
| `alembic upgrade head` after full teardown | exit 0, 81 s, 433 tables, fingerprint **identical** to fresh build | **supported** |
| Partial `alembic downgrade 20260815_0022` | exit 0 but **2 `alembic_version` rows** + 7 residual tables (`blood_bank_*` ×6, `clinical_command_receipts`) → 412 tables instead of 405 | **UNSAFE — not a rollback** |
| Per-branch partial stepping | not exercised | **not claimed** |
| Pre-upgrade snapshot restore | not exercised in this repo | **not measured; not claimed** |

Cause of the partial-downgrade defect: `20260815_0022` is not an ancestor of the blood-bank branch
(`20260901_0001…20260908_0002`), so Alembic unwinds only the target's ancestry. **Exit 0 does not
prove state restoration.**

No RPO or RTO target has been measured in this repository. Prior documents that cite RPO/RTO values
are separate planning claims and are **not** evidence of achieved capability here.

### 7.2 Recommendation

Record as the **only supported rollback procedures** for this history:

1. **Restore the pre-upgrade database snapshot** (preferred where a verified, restorable snapshot
   exists); or
2. **`alembic downgrade base` followed by `alembic upgrade head`** in a maintenance window, with
   the 3-table residual set explicitly expected and asserted (§5).

**Prohibit** partial `downgrade <revision>` as a rollback, including `20260815_0022`, until the
branch topology is reconciled and a state-equivalence assertion exists. Treat any exit-0 partial
downgrade with 2 version rows as a failed procedure.

A snapshot restore is only claimable after a restore drill on this repository's chain; until then it
is a *policy option*, not a verified capability.

### 7.3 Required attributes of the recommendation

* **Evidence.** DCR §10.2–10.3; §9.7; fingerprint comparison; branch ancestry of `20260815_0022`.
* **Assumptions.** A maintenance window is available for a 106 s full teardown/rebuild; the 3-table
  residual set is accepted (§5); snapshot tooling exists but is not yet drilled here.
* **Benefits.** Removes an unsafe procedure that currently returns exit 0; makes rollback outcome
  testable by table count, version-row count and fingerprint.
* **Risks.** Full rebuild is slower than a partial rewind; accepted residual set must be re-verified
  after every new migration.
* **Reversibility.** The policy itself is documentation; changing it requires a new ADR and a new
  rehearsal.
* **Approval authority.** Programme Director (policy), DBA / Platform Operations (execution),
  Release Manager (maintenance-window commitment).
* **Acceptance criteria.** (1) Policy recorded in an ADR and linked from `FINAL_DECISION.md` §10 by
  append-only addendum; (2) CI assertion rejects a partial downgrade with >1 version row;
  (3) a rehearsal after each migration wave reproduces 433 tables and identical fingerprint;
  (4) a snapshot-restore drill is scheduled before any restore capability is claimed;
  (5) no RPO/RTO number is asserted without measurement.

## A6. NR-011 technical design (required §5 detail)

### A6.1 Root cause (both parts)

1. **Missing model registration:** `backend/migrations/env.py` exposes a 10-entry `target_metadata`
   (lines 116–127) and omits **7 declarative bases** (`HospitalBase`, `DataPlatformBase`, `NHDWBase`,
   `NursingBase`, `PharmacyBase`, `RadiologyBase`, `FinBase`); national domain modules (e.g.
   `app.national.domain.encounter`) are not imported. Autogenerate therefore cannot see those tables.
2. **Cross-`MetaData` FK resolution:** `ehr_allergies` declares four FKs to `national_citizens`,
   `national_encounters`, `national_patients`, `national_practitioners`, which live in
   `NationalBase.metadata`. `EHRBase.metadata is not NationalBase.metadata`, so SQLAlchemy raises
   `NoReferencedTableError` on **72 tables / 239 references** — no import order fixes this (probe B
   moves the error to `national_patients`).

### A6.2 Minimal technical design (approval-only; not implemented)

1. In `env.py`, import the 7 omitted bases and the national domain model surface.
2. Build a single merged `MetaData` used **only for autogenerate detection**: iterate bases in a
   **fixed, documented order**, attach each base's tables (and resolve FK strings across namespaces);
   never reuse it for runtime DDL.
3. Keep `target_metadata` pointing at the merged object; keep `compare_type=True`.
4. Register a regression test asserting: every declarative base discovered under `backend/app` is
   registered, and `alembic check` completes without `NoReferencedTableError`.
5. Record that probe C's index counts are inflated by `to_metadata()` and must be excluded from drift
   assertions.

### A6.3 Import-cycle risks

* Importing all model surfaces inside `env.py` runs package `__init__` chains (national domain
  imports base modules, enums, mixins). Any future circular import surfaces **at migration time**,
  i.e. before deploy. Mitigation: keep imports inside `env.py` in a stable order, wrap optional
  surfaces in `suppress(ImportError)` **only if** the regression test then proves they registered —
  silent suppression is otherwise a false green.
* `env.py` sets `RUNTIME_MODE=migration` and default secrets; broader imports may read config earlier
  than today → validate that no new secret/network dependency is introduced (no I/O at import).
* `configure_mappers()` currently fails unless `app.services.mpi.models` is imported (body §11.6) —
  merged metadata must import that surface too or mapper configuration may fail during autogenerate.

### A6.4 Model registration requirements (checklist for approval)

17 bases total: 10 already registered (`Base`, `NationalBase`, `EHRBase`, `CitizenPlatformBase`,
`ClinicalBase`, `HealthDataBase`, `TrustBase`, `GovernanceBase`, `CareContinuumBase`, `IdentityBase`)
+ 7 to add (`HospitalBase`, `DataPlatformBase`, `NHDWBase`, `NursingBase`, `PharmacyBase`,
`RadiologyBase`, `FinBase`) + national domain modules (`app.national.domain.*`, incl.
`encounter.py`, `facility.py`) + `app.services.mpi.models` for mapper configuration.

### A6.5 Autogeneration risks

* 70 "remove column" findings in probe C — **never auto-apply**; triage individually (many are
  tables whose ORM column is absent, i.e. the opposite direction of our fix).
* Merged metadata may emit duplicate or index-count noise (see A6.2.5).
* `alembic revision --autogenerate` against a live database must never be run without review; this
  package authors no revisions.
* Drift from the merged view includes objects outside ADR-A scope (85 DB-only extra columns) —
  autogenerate proposals must be filtered by the shipping register.
