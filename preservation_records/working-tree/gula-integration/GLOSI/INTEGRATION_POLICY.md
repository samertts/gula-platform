# GLOSI Integration Policy

**Version:** 1.0.0
**Date:** 2026-11-15
**Applies to:** أي استفادة من مكوّن أو فكرة أو معيار خارجي في GULA.

---

## 1. القاعدة الأساسية

لا يدمج GLOSI أي شيء تلقائياً. كل استفادة تمر بمسار موثق، وكل دمج داخل GULA يخضع لـADR ومراجعة بشرية واختبارات. GLOSI ينتج **أدلة وتوصية**، وGULA تنتج **قراراً وتنفيذاً**.

## 2. مسار المراجعة الإلزامي

```
DISCOVER → SOURCE VERIFICATION → LICENSE REVIEW → SECURITY REVIEW
→ ARCHITECTURE REVIEW → FUNCTIONAL EVALUATION → TESTING
→ COST ANALYSIS → IRAQI CONTEXT ASSESSMENT → ADR
→ APPROVAL OR REJECTION
```

لا يُختصر أي مسار. لا يُنتقل إلى التنفيذ لأن المشروع مشهور أو لأن درجته مرتفعة.

## 3. أنماط الاستفادة

| النمط | التعريف | شرط الحد الأدنى |
|---|---|---|
| `ADOPT` | استخدام المكوّن كما هو | ترخيص متوافق + أمن واضح + صيانة مستدامة + اختبار داخل GULA |
| `INTEGRATE` | ربطه عبر واجهة/موصل دون نسخ كود | عقد API/معيار + عزل + فشل آمن + مراقبة |
| `ADAPT` | تعديل مكوّن مرخّص | توافق الترخيص مع التعديل + إدارة Fork + التزامات copyleft |
| `REIMPLEMENT` | إعادة تنفيذ الفكرة دون نسخ كود | دليل على عدم نسخ كود/بنية محمية + مراجعة قانونية |
| `STUDY` | الاستفادة من التصميم/البحث فقط | لا كود إنتاجي ولا اعتمادية |
| `MONITOR` | متابعة التطورات | مراجعة دورية؛ لا التزام |
| `REJECT` | رفض موثق | سبب فني/قانوني/أمني/سيادي |

## 4. قواعد الدمج

1. **لا تعديل تلقائي:** ممنوع أي سكربت ينسخ كوداً خارجياً إلى `backend/` أو `frontend-v3/`.
2. **مكوّن واحد مسؤول:** لا تكرار تنفيذ لنفس المسؤولية الأساسية.
3. **عزل:** كل موصل خارجي في حزمة/طبقة مستقلة، مع حدود واضحة واختبارات رفض.
4. **عقد قبل كود:** يجب تثبيت إصدار API/المعيار وCapabilityStatement أو العقد قبل التنفيذ.
5. **فشل آمن:** timeout، circuit breaker، retry محدود، idempotency، ورفض افتراضي.
6. **قابلية الاستبدال:** لا يُسمح باعتماد مباشر يجعل إزالة المكوّن مستحيلة.
7. **قابلية التراجع:** كل دمج له خطة rollback وخطوة تحقق.
8. **لا صلاحيات موروثة:** الهوية أو التفويض الخارجي لا يمنح صلاحية داخل GULA تلقائياً.
9. **لا بيانات مرضى خارجية:** لا إرسال بيانات حقيقية إلى خدمة خارجية أو نموذج AI سحابي.
10. **التوثيق:** كل دمج يحتاج وثيقة تكامل واختبارات وملكية تشغيلية.
11. **الترخيص:** الالتزام بـ`OPEN_SOURCE_POLICY.md` وأولوية Apache/MIT/BSD قبل MPL/GPL/AGPL.
12. **السيادة:** يجب أن يعمل الحل محلياً داخل العراق قدر الإمكان، دون اعتماد إلزامي على SaaS.

## 5. إدارة الاعتماديات

- أي اعتمادية جديدة تحتاج مبرراً مكتوباً وبديلاً مفتوحاً تم تقييمه.
- يمنع إضافة اعتمادية لحل مشكلة يمكن حلها بأدوات stdlib أو مكوّن قائم.
- يجب توثيق النسخة والترخيص وطريقة التحديث ومخاطر السلسلة الغذائية.
- يمنع إدخال اعتمادية بلا صيانة أو بترخيص غير واضح.
- لا تُثبّت اعتماديات في GLOSI نفسه؛ أدواته تعتمد Python stdlib فقط.

## 6. التكامل مع GULA

| المكوّن | العلاقة |
|---|---|
| `backend/app/` | الكود التشغيلي الوحيد؛ لا استيراد خارجي مباشر بلا ADR |
| `frontend-v3/` | العميل الأساسي؛ لا مكتبات UI خارجية بلا مراجعة |
| قاعدة البيانات | لا تغيير بسبب GLOSI؛ migrations لا تُلمس |
| الهوية والصلاحيات | تبقى تحت سيطرة NIAM؛ لا نقل سلطة |
| Platform-Core | مستقل؛ لا تعديل بسبب GLOSI |
| Audit/Security | كل دمج يخضع لضوابط GULA الأمنية |

## 7. معايير قبول الدمج

قبل أي دمج في GULA يجب توفر:
- قرار GLOSI مرجعي (وليس مجرد ملاحظة).
- ADR معتمد داخل GULA.
- مراجعة أمنية وقانونية بشرية.
- اختبارات وحدة/تكامل/رفض صلاحيات.
- خطة رجوع ومراقبة.
- وثائق تشغيل ودعم محلي.
- إثبات أن المكوّن لا يفرض تبعية دائمة.

## 8. الرفض

يُرفض المورد إذا:
- ترخيصه غير متوافق أو مجهول.
- أمنه غير كافٍ أو به ثغرة حرجة غير معالجة.
- يعتمد على خدمة سحابية إلزامية أو مزوّد واحد.
- لا يمكن استضافته محلياً أو تدقيقه.
- غير قابل للاستبدال أو الصيانة محلياً.
- يخالف سيادة البيانات أو الخصوصية.

يُوثّق الرفض وسببه وأي بدائل، ويبقى السجل قابلاً لإعادة التقييم عند تغير الأدلة.

## 9. ما لا يفعله GLOSI

- لا يعدل قاعدة بيانات أو ترحيلات.
- لا يغيّر API أو الهوية أو الصلاحيات.
- لا ينشر كوداً خارجياً.
- لا يعتمد مشروعاً نيابة عن الجهة المعمارية.
- لا يستخدم خدمات مدفوعة أو مفاتيح API.
- لا يعتبر نفسه مراجعاً أمنياً أو قانونياً بشرياً.
