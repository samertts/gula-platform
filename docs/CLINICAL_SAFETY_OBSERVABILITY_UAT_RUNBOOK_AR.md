# دليل تشغيل المراقبة وUAT لضوابط السلامة السريرية

**النطاق:** الدفعات الأولى والثانية والثالثة من ضوابط السلامة السريرية.  
**قاعدة النشر:** لا يُنشر أي تغيير سريري قبل نجاح بوابة الانحدار، تفعيل مراقبة آمنة، وتنفيذ قبول مستخدم موثق.

## 1. تفعيل المراقبة من دون كشف بيانات صحية

تعرّض المنصة مقاييس Prometheus عبر `GET /metrics/prom`. في الإنتاج يجب تعيين `METRICS_BEARER_TOKEN` عشوائي وطويل، ثم تقييد نقطة النهاية على شبكة المراقبة أو الوكيل العكسي. إذا لم يوجد الرمز في الإنتاج، تفشل النقطة مغلقةً (`503`) بدلاً من كشف قياسات المنصة.

```bash
export METRICS_BEARER_TOKEN='<secret-from-vault>'
# لا تضع الرمز في مستودع الشفرة أو ملف واجهة أو سجل تشغيل.
```

تُصدر مؤشرات سلامة الأوامر التالية فقط بوسوم محدودة: `operation` و`resource_type` و`outcome` و`reason_code`. لا تضع أسماء مرضى أو معرفات مستخدمين أو معرفات موارد أو محتوى طلب أو مفتاح عدم التكرار أو قيم سريرية في Prometheus أو Grafana أو Sentry.

| المؤشر | القرار عند تغيره |
|---|---|
| `gula_clinical_audit_write_failure_total` | أي قيمة موجبة: P0؛ أوقف الكتابات الحرجة المتأثرة واتبع SOP البديل. |
| `gula_clinical_command_total{outcome="rejected"}` | حلل حسب `reason_code`؛ الارتفاع بعد نشر يعني عميلاً قديماً أو حالة بيانات غير متوقعة. |
| `gula_clinical_command_total{outcome="completed"}` | راقب خط الأساس والتغير المفاجئ في التدفق. |
| `gula_db_up` و`gula_db_latency_ms` | صحة PostgreSQL وزمنه؛ لا تعطل الأقفال لتحسين الأداء. |
| `gula_queue_backlog` | تحقق من تسليم الأحداث وموظفي الخلفية. |

يمكن تفعيل Sentry فقط بعد اعتماد موقع تخزين البيانات واتفاقية حماية البيانات. المنصة تنقح تلقائياً بيانات الطلب والمستخدم والسياق والنص الحر قبل الإرسال؛ ويبقى سجل التدقيق الداخلي مصدر الحقيقة السريري.

## 2. قواعد التنبيه والتصعيد

| المستوى | الشرط | الإقرار | مالك الاستجابة | الإجراء الأول |
|---|---|---:|---|---|
| P0 | فشل تدقيق، أثر جانبي مكرر، أو انتقال حالة ممنوع نجح | 5 دقائق | قائد الحادث + ممثل سريري | أوقف المسار المتأثر بأمان، فعّل SOP البديل، واحفظ الأدلة. |
| P1 | ارتفاع 5xx أو أقفال طويلة أو نتيجة حرجة متأخرة | 15 دقيقة | on-call التطبيق + مالك المجال | شخّص، خفف بأمان، وحدّث الحادث كل 30 دقيقة. |
| P2 | تضارب نسخة أو محاولة انتقال مرفوضة تتجاوز الخط الأساسي | يوم العمل | فريق المنتج/الدعم | راجع العميل والتدريب والبيانات التاريخية. |

لا تُرسل إشعارات تحتوي على PHI عبر البريد أو أدوات المحادثة. استخدم معرف حادث ورابطاً مقيداً للوحة، ثم راجع السجل السريري من خلال مستخدم مخول.

## 3. بوابة CI المحلية والمستضافة

تشغّل CI بوابة `Run clinical safety regression gate` بعد ترحيلات PostgreSQL وقبل حزمة الاختبارات العامة. يمكن تشغيلها محلياً من `backend`:

```bash
pytest -q --timeout=60 \
  tests/test_clinical_command_guard_p0.py \
  tests/test_clinical_operational_readiness_p0.py \
  tests/test_pharmacy_radiology_workflow_p0.py \
  tests/test_pharmacy_pos.py \
  tests/test_radiology_tenant_isolation.py \
  tests/test_emergency_surgery_workflow_p0.py \
  tests/test_icu_lab_workflow_p0.py
```

لا يعتمد نجاح الاختبار المحلي على بيانات إنتاجية؛ تستخدم التهيئة قاعدة SQLite مؤقتة معزولة. قبل الإنتاج، كرر سيناريوهات التزامن في PostgreSQL مماثل للإنتاج.

## 4. إجراءات UAT الإلزامية

### الدفعة الأولى: LIMS والحارس السريري

يشارك فني مختبر وأخصائي اعتماد وطبيب مستلم نتيجة ومهندس منصة. اختبر دورة العينة القانونية، ورفض العينة غير المتحققة، تضارب نسختين لنفس النتيجة، إعادة الإرسال بنفس المفتاح، عميل بلا رؤوس الحارس، نتيجة حرجة من الإنشاء إلى الإقرار، عزل مؤسستين، ورؤوس منع التخزين المؤقت. القبول يتطلب نجاح كل الحالات، وعدم وجود فشل تدقيق أو تكرار أثر جانبي أو وصول عبر المؤسسة.

### الدفعة الثانية: الصيدلة والأشعة

يشارك صيدلي منفذ وصيدلي مراجع مستقل واختصاصي أشعة وفني. اختبر صرفاً قانونياً، منع المخزون السلبي في طلبين متزامنين، منع التحقق الذاتي، إعادة الإرسال، العزل المؤسسي، دورة تقرير أشعة قانونية، منع تعديل النهائي، ونتيجة حرجة حتى الإقرار. القبول يتطلب رصيداً غير سالب دائماً، وعدم نجاح تحقق ذاتي أو تعديل نهائي غير قانوني.

### الدفعة الثالثة: EMS والعمليات والأسرّة

يشارك مرسل وطاقم إسعاف ومنسق عمليات وجراح وتمريض ومسؤول أسرّة. اختبر توزيع حادث قانوني، رفض مركبة أو طاقم غير صالح، سباق توزيع لنفس المركبة، فرز غير قانوني، اعتماد ePCR ناقص، قائمة تحقق جراحية مكتملة وناقصة، تشغيل غرفة متزامن، تخصيص سرير، نقل ذري، وسباق نقل إلى السرير نفسه. القبول يتطلب: توزيع مزدوج صفر، تشغيل غرفة بلا قائمة مكتملة صفر، وسرير لا يحمل أكثر من مريض نشط صفر.

## 5. قرار النشر والرجوع

يوقع مالك المجال السريري وممثل التمريض/الصيدلة/المختبر أو EMS وهندسة المنصة وأمن المعلومات على سجل UAT. لا يُنشر إذا بقي عيب P0 أو P1، أو فشلت بوابة الانحدار، أو لم يعرض Alembic رأساً واحداً، أو لم تتوافق واجهات العملاء مع الرؤوس المطلوبة.

الرجوع ليس دائماً إعادة نشر نسخة سابقة: عند وجود كتابات بمخطط جديد، أوقف المسار السريري المتأثر بشكل آمن وفعّل SOP البديل، ثم نفّذ إصلاحاً أمامياً بعد حفظ الأدلة. لا تُعطّل حواجز الأوامر أو سجل التدقيق كحل لتقليل الضغط.
