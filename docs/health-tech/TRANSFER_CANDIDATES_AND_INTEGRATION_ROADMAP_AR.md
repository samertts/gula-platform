# تقييم تقنيات صحية وطبية عالمية قابلة للنقل إلى GULA

**الحالة:** دراسة معمارية وتوصية تنفيذية؛ لا تفعيل سريري ولا تغيير لصلاحيات P5.

**التاريخ:** 17 آب 2026

## الخلاصة التنفيذية

يمكن لـGULA الاستفادة من تقنيات عالمية، لكن النقل الآمن يكون عبر **المعايير، والموصلات، والأنماط المعمارية، والمكونات مفتوحة المصدر ذات الترخيص الواضح**، وليس عبر نسخ منتجات أو بيانات أو واجهات مملوكة. أفضل ترتيب عملي هو: اعتماد FHIR R4 كعقود تبادل، واستخدام نمط OpenHIE لطبقة التكامل، ثم إضافة موصلات منفصلة للمختبر والتصوير والصحة العامة، مع إبقاء الهوية الوطنية، والتحقق، والحوكمة، والتفويض، والقيود الوزارية، وسجل التدقيق تحت سيطرة GULA.

هذا الترتيب منسجم مع مذكرة GULA المحلية التي توصي بنموذج تبادل وطني هجين: تبقى السجلات التشغيلية في المؤسسات، بينما تنسق GULA الهوية والفهرسة والتفويض والتدقيق والتبادل المنظم. [1]

**لا أوصي حالياً بنسخ أي نظام كامل إلى GULA، ولا بتفعيل أوامر سريرية أو وصفات أو صرف أو تطعيم أو قراءة واسعة للنتائج.** حالة P4 ما زالت حاجزاً سابقاً لـP5، ولذلك يجب أن تبقى البوابات السريرية والميزات الحساسة مغلقة حتى إتمام معالجة الدين النوعي والمراجعة البشرية الرسمية.

## المبادئ غير القابلة للتفاوض

تظل **هوية الجهة** منفصلة عن **صلاحياتها**. تسجيل وزارة أو نقابة أو شركة أو مختبر أو جهة دولية لا يمنحها أي وصول؛ تبدأ الجهة في حالة `PENDING_VERIFICATION`، ثم يحدد التحقق نوع المؤسسة ونطاقها ومستوى الثقة والعلاقات. وبالمثل لا يكفي اسم الطبيب أو عضويته الاسمية؛ صلاحية الطبيب السريرية لا تصبح فعالة إلا بعد تحقق وزارة الصحة والنقابة معاً، وتعيين نشط، ومنشأة أو نطاق تشغيلي مثبت.

يجب أن يمر كل طلب تقني أو سريري بالتسلسل التالي: إثبات الهوية، حل التعيين النشط، فحص الصلاحية الدقيقة، تثبيت سياق المؤسسة والمنشأة، تحميل المورد ضمن ذلك السياق، ثم تسجيل قرار السماح أو الرفض. هذا هو القرار المحلي الملزم في GULA، ولا يجوز لأي معيار خارجي تجاوزه. [10]

## المعمارية المقترحة للنقل

تقسم GULA عملية التكامل إلى أربع طبقات. في المركز توجد **بوابة تكامل GULA** التي تطبق سياسات الوصول، وتتحقق من CapabilityStatement، وتفرض تحديد المعدل، وتتحقق من التوقيع والإصدار، وتوجه الرسالة إلى الموصل المناسب. بجانبها توجد الخدمات المشتركة: سجل المؤسسات والكوادر، MPI، خدمة المصطلحات، خادم التفويض، وسجل التدقيق المقاوم للعبث. ثم تأتي موصلات مستقلة لـOpenELIS وPACS/DICOM وDHIS2 وOpenMRS. أما السجل التشغيلي الأصلي فيبقى لدى المؤسسة المالكة.

هذا التصميم يمنع أن تتحول تقنية منقولة إلى سلطة مستقلة. فـOpenELIS لا يمنح الطبيب صلاحية طلب فحص، وDICOM لا يمنح حق رؤية الصور، وDHIS2 لا يمنح حق قراءة ملف مواطن، وFHIR لا يساوي تفويضاً. كلها قنوات أو عقود بيانات تعمل فقط بعد قرار GULA.

## الترتيب المرحلي المقترح

| المرحلة | التنفيذ | شرط الانتقال |
|---|---|---|
| 0. التأسيس | تثبيت FHIR R4، CapabilityStatement، أخطاء موحدة، إصدارات، SBOM، وبيانات اصطناعية | مراجعة أمنية وتوافقية، وإغلاق معايير النطاق |
| 1. الوثائق | MHD/DocumentReference لتبادل التقارير الموقعة دون فتح قراءة واسعة | نجاح التوقيع، التدقيق، الإبطال، والعزل بين المؤسسات |
| 2. المختبر | موصل OpenELIS أو LIS عام: ServiceRequest، Specimen، Observation، DiagnosticReport | إثبات تحويل المنشأة، سلسلة حيازة، منع النتائج غير الموثقة، واختبارات رفض |
| 3. التصوير | موصل DICOM/PACS محدود للبيانات المطلوبة والتقرير والصورة المصرح بها | ربط الطلب بالمريض والمنشأة، تدقيق كل قراءة، ومنع البحث المفتوح |
| 4. الصحة العامة | موصل DHIS2 للمؤشرات المجمعة أو المسموح بها | فصل البيانات المجمعة عن السجل الفردي ومراجعة الخصوصية |
| 5. تطبيقات موثوقة | SMART on FHIR لتطبيقات محددة الغرض بعد جاهزية IAM | رموز قصيرة العمر، scopes دقيقة، إبطال فوري، واختبارات تجاوز |
| 6. توسع تدريجي | OpenMRS ومؤسسات أخرى عبر Gateway | اعتماد مؤسسي، مراقبة، دعم محلي، وخطة رجوع |

## المخاطر والضوابط

| الخطر | مثال | الضابط المطلوب |
|---|---|---|
| الخلط بين المعيار والتفويض | اعتبار FHIR أو SMART إثباتاً لصلاحية الطبيب | التفويض يبقى خادميّاً في GULA ومبنياً على التعيين والتحقق والمنشأة |
| تسرب عبر المعرفات | استخدام `lab_id` القديم بوصفه `Facility.id` | محول خادمي موثق أو منع آمن؛ لا يُقبل التطابق العددي وحده. [10] |
| نقل كود بترخيص غير مناسب | دمج مكتبة دون معرفة التزاماتها | فحص الترخيص، NOTICE، SBOM، التبعيات، والثغرات قبل إدخالها للمستودع |
| اختلاف الدلالة | نفس اسم الفحص بمعنى مختلف بين مختبرين | خدمة مصطلحات وإصدارات وخرائط، واختبار دلالي قبل الإنتاج |
| الدمج الخاطئ للهوية | مطابقة شخصين بسبب تشابه الاسم | MPI احتمالي مع عتبات ومراجعة بشرية، ودمج قابل للعكس. [1] |
| اتصال غير مستقر | تكرار طلب أو نتيجة بعد انقطاع الشبكة | idempotency، outbox، retry محدود، تعارض صريح، وسجل تدقيق |
| توسيع النطاق مبكراً | جعل الطبيب يقرأ كل موارد المؤسسة | scopes دقيقة بصيغة `clinical.<domain>.<resource>.<action>` ورفض افتراضي |
| الاعتماد على منصة خارجية | توقف مشروع أو تغير API | موصل معزول، عقد نسخة محددة، مراقبة، وخطة فصل/رجوع |

## ما لا ينبغي نقله في المرحلة الحالية

لا ينبغي نقل أو تفعيل التسجيل المدني بالـOCR أو NFC أو القياسات الحيوية، ولا فتح حساب المواطن من طبيب بوصفه توثيقاً نهائياً، ولا منح الطبيب صلاحيات تلقائية لأي فحص أو أشعة أو لقاح أو علاج. يمكن لاحقاً تصميم هذه الخدمات، لكن قرارها يتطلب سياسة وطنية واضحة، تحققاً مستقلاً، موافقات قانونية، واختبارات أمان وسلامة. إنشاء الحساب أو تسجيل المؤسسة أو ربط التطبيق لا يساوي توثيقاً ولا يساوي entitlement.

كما لا ينبغي نسخ قواعد بيانات مرضى، أو بيانات تجريبية حقيقية، أو واجهات تجارية، أو شعارات، أو أسرار تكامل. الاختبارات الأولى يجب أن تستخدم بيانات اصطناعية، وأن تظل كل البوابات السريرية خلف أعلام خادمية مغلقة.

## خطة العمل التنفيذية المقترحة

الخطوة البرمجية الأولى هي إنشاء حزمة عقود FHIR R4 داخل GULA تشمل `CapabilityStatement` وملفات تعريف للموارد الأولية: `Organization` و`Practitioner` و`PractitionerRole` و`Patient` و`ServiceRequest` و`Specimen` و`Observation` و`DiagnosticReport` و`DocumentReference` و`Provenance` و`AuditEvent`. لا ينبغي أن تضيف هذه الحزمة صلاحيات جديدة؛ بل تصف البيانات والتوافق فقط.

بعد ذلك ينشأ **محول تكامل مختبري read-only أولاً** يقرأ نتائج اصطناعية من موصل تجريبي، ويتحقق من المنشأة والمريض والطلب والعينة، ثم يسجل AuditEvent ويرفض أي مورد خارج النطاق. المرحلة التالية هي موصل DICOM/PACS للقراءة المقيدة، ثم مؤشرات DHIS2. كل مرحلة تحتاج اختبارات رفض عابرة للمؤسسة والمنشأة والمستأجر، واختبارات إبطال وتعارض وإعادة إرسال.

ولا يُعتبر أي من ذلك بدءاً لـP5. المسار الصحيح هو: إكمال P4، معالجة أخطاء Ruff/MyPy في النطاق المطلوب، إجراء التحقق البشري، اعتماد دليل الأدلة، ثم فتح قرار مستقل لكل بوابة سريرية. قبل ذلك تبقى هذه الخطة وثيقة تصميم وتنفيذ Staging فقط.

## قائمة تحقق قبل أي دمج كود خارجي

| الفحص | النتيجة المطلوبة |
|---|---|
| الترخيص | متوافق ومثبت في NOTICE وملف التبعيات |
| المصدر | مستودع رسمي، إصدار مثبت، وتاريخ صيانة معروف |
| الأمن | SBOM وفحص ثغرات ومراجعة أسرار وعدم تشغيل ملفات غير موثوقة |
| البيانات | لا بيانات حقيقية في الاختبارات، وتشفير ونطاق احتفاظ واضح |
| التكامل | CapabilityStatement وContract Tests ونسخة API مثبتة |
| التفويض | لا صلاحية تنتقل تلقائياً من النظام الخارجي إلى GULA |
| التدقيق | كل قراءة ورفض وإبطال وتعارض قابل للتتبع |
| الفشل | منع آمن، idempotency، retry محدود، وخطة رجوع |
| التشغيل | مراقبة وقياس وخطة دعم محلي وفصل عن المورد |
| الحوكمة | مراجعة بشرية وقرار رسمي قبل أي إنتاج سريري |

## القرار

أوصي بالمضي في **FHIR R4 + OpenHIE كنواة تكامل**، ثم بناء موصلات معزولة لـOpenELIS وDICOM، وتأجيل DHIS2 وOpenMRS إلى ما بعد تثبيت العقود والهوية. هذا يحقق نقل التكنولوجيا النافع من دون جعل GULA تابعاً لمنتج واحد أو منح جهة خارجية سلطة على المواطن أو الطبيب. لا توجد حاجة إلى إضافة Secret أو Connector خارجي لتنفيذ هذه الدراسة، ولم يتم تنفيذ إنتاج سريري أو رفع تطبيق أو تفعيل P5 ضمن هذه الخطوة.
