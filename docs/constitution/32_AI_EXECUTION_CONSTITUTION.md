# Constitution 32 — AI Execution Constitution

> Status: Ratified (PROGRAM-012 / PROGRAM-012A)
> Applies to: every AI model, every developer, every automation, every CI pipeline
> Enforcement: `scripts/enterprise_validation_engine.py` (hard gates), `scripts/constitution_enforcer.py`
> Companion documents: `docs/ai/AI_GOVERNANCE.md` (operating procedures), `CLAUDE.md` (operating manual)

## 32.1 Purpose

Every future modification to the GULA platform — by an AI model, a developer, or an
automated pipeline — must pass through a deterministic execution layer. No agent may
modify the repository outside this layer. This constitution defines the execution
protocol, the violation severity model, the automatic rejection rules, and the
automatic repair rules.

## 32.2 Non-Negotiable Execution Protocol

Every change must complete the following phases in order:

| # | Phase | Requirement | Gate |
|---|-------|-------------|------|
| 1 | Task Planning | Split work into atomic tasks; estimate risk, dependencies, affected modules, required tests, rollback impact | Reject plans with no rollback path |
| 2 | Impact Analysis | Identify changed files, APIs, tests, docs, DB objects, Android/Frontend surfaces | Record in commit message scope |
| 3 | Validation | `make validate` (fast scope) before commit; `make validate SCOPE=full` for release | Hard gates must pass |
| 4 | Regression Review | Compare metrics against `reports/validation/baseline.json` | Reject any regression |
| 5 | Self Review | Correctness, architecture, security, performance, naming, documentation, backward compatibility | Reject silent API breaks |
| 6 | Safe Commit | Conventional commit, atomic, with purpose, risk level, rollback instructions | Commit hooks enforced |
| 7 | Knowledge Update | Regenerate `docs/brain/PROJECT_BRAIN.md` (`make brain`) when structure/APIs/tests change | Brain freshness gate |
| 8 | Certification | Release-gate certification via `backend/app/certification/` and `scripts/certification_check.py` | Required for release |

## 32.3 Violation Severity Model

| Severity | Level | Definition | Consequence |
|----------|-------|------------|-------------|
| CRITICAL | 4 | Patient data loss risk, security vulnerability, destructive migration, secrets exposure, bypass of clinical safety | Change rejected; immediate rollback; incident report |
| HIGH | 3 | Breaking API compatibility, broken tests, failing hard gate, regression vs baseline, dead production code removal without proof | Change rejected; must be fixed before commit |
| MEDIUM | 2 | Missing tests for new feature, missing docs, missing ADR for architectural change, stale brain | Change blocked until documented |
| LOW | 1 | Cosmetic deviations (naming, formatting), optional improvements | Warning; advisory only |

## 32.4 Automatic Rejection Rules (RULES-AI-EXEC)

The following changes are automatically rejected — no human or AI may override without
an approved exception:

- **R1** Any change that fails a hard gate of the enterprise validation engine.
- **R2** Any change that introduces a regression against the stored baseline.
- **R3** Any commit that removes or weakens a clinical safety feature without a
  documented clinical review.
- **R4** Any change that deletes production code without a referenced proof of
  non-use (dead-code report, search results, test removal).
- **R5** Any change that modifies the database destructively without a
  backwards-compatible migration and a data-preservation review
  (`docs/constitution/31_DATA_PRESERVATION_CONSTITUTION.md`).
- **R6** Any dependency added without constitution-engine approval
  (Free/Open-Source/Self-Hosted First — `governance/` engines).
- **R7** Any commit that merges failing tests or CI (no fabricated green).
- **R8** Any change that modifies architecture without an ADR.
- **R9** Any commit message that omits purpose or scope.
- **R10** Any AI-generated code committed without passing the validation engine.

## 32.5 Automatic Repair Rules

Where repair is provably safe and reversible, the platform shall repair automatically:

- **P1** Formatting/lint violations auto-fixed by `ruff --fix` (safe fixes only).
- **P2** Stale Project Brain regenerated by `make brain`.
- **P3** Missing test stubs for new services auto-generated by
  `backend/app/engineering/testing/` generators, then human/AI must fill assertions.
- **P4** Failed CI rerun once automatically for known-flaky tooling; a second failure
  blocks the change.
- **P5** Broken imports or naming violations auto-repaired only when the repair is
  verifiable by static analysis (AST-based, e.g. `scripts/architecture_guardian.py`).

Repair is forbidden when: the change touches patient data, security boundaries,
migrations, or license-sensitive files — those always require human review.

## 32.6 Multi-Agent Consensus

- When multiple AI agents propose implementations, disagreements must be resolved
  before commit; conflicting implementations are never merged automatically.
- The selected implementation must be the one passing all hard gates with the lowest
  risk score; tie-break by architecture compliance and test coverage.
- Every rejected alternative must be recorded in the commit or ADR when its rejection
  is a deliberate architectural choice.

## 32.7 Safe Commit Engine

Every commit must carry: purpose, affected modules, risk level, rollback instructions,
validations passed, and (where applicable) linked ADR. The commit message format is
Conventional Commits: `type(scope): description`. Risk level must be stated in the
body when HIGH or CRITICAL.

## 32.8 Knowledge Synchronization

- `docs/brain/PROJECT_BRAIN.md` is the live knowledge index; it is stale when
  `scripts/project_brain.py --check` fails.
- Structural changes (new modules, endpoints, services, migrations, CI workflows)
  MUST regenerate the brain in the same change.
- No stale documentation: every changed behavior must update the owning document in
  the same commit (AGENTS.md, CLAUDE.md, ADRs, READMEs).

## 32.9 Continuous Health Scores

The following scores are tracked continuously by the validation engine and scorecard
(`scripts/repository_scorecard.py`): Architecture, Backend, Frontend, Security,
Testing, Performance, Documentation, Operations, Technical Debt, Repository Health.
A drop in any tracked score versus baseline is a regression (Constitution 32.4 R2).

## 32.10 Certification

Every release requires: architecture certification, security certification,
performance certification, integration certification, environment certification,
deployment certification, backend/frontend certification, and an overall readiness
score — produced by `backend/app/certification/` and the audit scripts under
`scripts/` (see `docs/ai/AI_GOVERNANCE.md` §4).

## 32.11 Determinism

AI sessions on this repository are deterministic when: (1) CLAUDE.md is read first,
(2) the Project Brain is fresh, (3) the validation engine gates the change,
(4) the baseline is current, (5) conventional commits with risk levels are used.
Deviations from this protocol must be recorded in the commit body.
