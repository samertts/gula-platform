# دليل تكامل مزودي الدفع — GULA Health Payments

**الحالة:** دليل تفعيل لاحق؛ لا يوجد مزود دفع متصل في هذا التسليم.
**المالك:** GULA Platform Team
**المؤلف:** Manus AI

> **القاعدة:** هذه النواة تسجل الفوترة والنية والقيود والاقتباسات؛ لا تحتفظ بالأموال ولا تنفذ صرفًا أو تحصيلًا إلكترونيًا أو تحويلًا مصرفيًا. لا يفعّل أي محول خارجي قبل استيفاء بوابات الاعتماد أدناه.

## 1. العقد الفني الموحد للمزوّد

يلتزم كل محول مزود بمعاملات ناتجة عن `Payment Intent` واحد، ومفاتيح عدم تكرار، ومرجع GULA ثابت، والتحقق المتبادل من المبلغ والعملة والمؤسسة. لا تنقل الواجهة الأمامية أسرارًا أو OTP أو PIN أو CVV، ولا تقرر حالة الدفع من رد المتصفح وحده.

| العملية | سلوك المحول | ضوابط إلزامية |
| --- | --- | --- |
| إنشاء عملية مزود | يستقبل `intent_id` ومبلغًا وعملة ورمز تاجر ويعيد مرجع مزود غير حساس | لا إعادة إنشاء عند إعادة المحاولة؛ يستخدم Idempotency-Key ومرجع GULA |
| Webhook | يقبل إشعارًا موقّعًا فقط ثم يسجله كحدث غير موثوق إلى أن يطابق الحالة | توقيع وتوقيت وanti-replay وتطابق المبلغ/العملة/المؤسسة والتحقق من المصدر |
| استعلام حالة | يسحب حالة العملية عند webhook متأخر أو مفقود أو نتيجة `UNKNOWN` | مصدر الحقيقة للمزود يكمل الدفتر ولا يستبدله |
| تسوية | يستورد ملف/واجهة تسوية منفصلين | `SUCCESS` لا تعني `SETTLED`؛ تفتح الفروق قضية تسوية |
| استرداد | ينشأ طلب مستقل ثم موافقة منفصلة ثم معالجة مزود | لا تعديل على الحركة الأصلية ولا اعتماد ذاتي |

## 2. حالات الفشل والتكرار

| الحالة | رد النظام للمستخدم | إجراء الخادم |
| --- | --- | --- |
| انقطع الاتصال بعد الإرسال | «جارٍ التحقق من حالة العملية؛ لا تعاود الدفع الآن.» | `UNKNOWN` أو `PENDING` ثم webhook + استعلام حالة + تسوية |
| webhook مكرر | لا يظهر خصم جديد أو نجاح ثانٍ | معالجة متكررة آمنة بالمرجع الفريد وقيد الحالة |
| webhook بترتيب متأخر | لا يُرجع الحالة إلى الوراء | آلة حالات تسمح بالانتقالات القانونية فقط |
| المبلغ أو العملة لا يتطابقان | لا يمنح الخدمة ولا ينشئ قيد نجاح | قضية تسوية ومراجعة بشرية |
| مزود غير متاح | لا يوجد failover آلي لعملية ربما نفذت جزئيًا | circuit breaker ثم استعلام الحالة قبل أي مسار بديل |

## 3. العملات والرسوم

تعامل الأسعار المنشورة من البنك المركزي العراقي بوصفها **مرجعًا قابلًا للتدقيق**، وليس ترخيصًا ضمنيًا لصرف العملة أو فرض رسم. تنشر صفحة البنك المركزي ملفات أسعار الدينار مقابل الدولار والعملات الرئيسية وأسعارًا تاريخية؛ صمم `RateProvider` لآلية استيراد مصرح بها بدل افتراض وجود API عامة.[1]

تحتفظ `FxRateSnapshot` بالمصدر وإصدار السعر والطابع الزمني، ولا تصدر النواة اقتباسًا إلا من لقطة تم التحقق منها وغير قديمة. تمثل العمولة الإدارية الافتراضية 2% سياسة `FxFeePolicy` قابلة للإصدار والاعتماد، وتظهر منفصلة عن سعر المرجع وعن أي رسوم مزود. اقتباس FX في هذا التسليم **للعرض المرجعي فقط**؛ لا يتحول إلى عملية صرف أو حوالة.

## 4. بوابات الاعتماد قبل تفعيل مزود

لا تنفذ الخطوة التالية إلا بعد توثيق مالكها ونتيجة مراجعتها.

| البوابة | دليل القبول | المالك |
| --- | --- | --- |
| الشريك والتنظيم | مزود مرخص، عقد موقع، وتأكيد نطاق المنتج/العملة/الرسوم | الشؤون القانونية والامتثال |
| مفاتيح وأسرار | HSM أو إدارة أسرار مركزية، تدوير، mTLS حيث يلزم، منع الأسرار من السجل | الأمن والهندسة |
| بيانات وإقامة | سياسة موثقة لمكان المعالجة والنسخ الاحتياطية، DPA وخطة خروج من المزود | الخصوصية والامتثال |
| الحماية | threat model، اختبار اختراق، WAF، حدود طلبات، تنبيهات SIEM | الأمن |
| التشغيل | sandbox، حالات ويب هوك مكرر/متأخر، استعلام حالة، ملفات تسوية، استعادة كارثة | SRE والمالية |
| المستهلك | إيصال واضح، رسوم مفصلة، مسار اعتراض ودعم وSLA وإتاحة الوصول | المنتج والدعم |
| الإصدار | feature flag وkill switch وcircuit breaker ومراقبة تدريجية | مالك المنصة |

## 5. النشر والترحيل

ينشئ الترحيلان التاليان الجداول الجديدة فقط ولا يربطان مزودًا:

```bash
cd backend
alembic upgrade head
```

ينفذ الإطلاق بوضع feature flags مغلق افتراضيًا لمسارات الدفع الإلكتروني والـFX على مستوى بيئة التشغيل. ويبدأ التحصيل النقدي في مؤسسة تجريبية مع مطابقة صندوق يومية وسجل فروق، ثم تراجع النتائج قبل التوسع.

## 6. حدود هذا التسليم

هذه العناصر **غير منفذة عمدًا**: محفظة GULA، رصيد قابل للتحويل، cash-in/cash-out، تحويل بين العملات، تحويلات دولية، KYC، AML/CFT، فحص قوائم العقوبات، webhooks مزود حية، بطاقات، QR، مصرف، استرداد مزود، أو تكامل حكومي. تمثل هذه منتجات وحوكمة مستقلة تتطلب موافقات وترخيصًا وشركاء واختبارات تشغيلية قبل التفعيل.

## 7. منسق المدفوعات متعدد المسارات

أضيفت طبقة `Payment Orchestration` كاختيار **استشاري فقط**. تسجل كل من الكيان المالي والمسار والمزود وقاعدة التوجيه وقرار الاختيار بإصدار واضح، لكنها لا تستدعي مزودًا ولا تنشئ خصمًا ولا تنفذ failover. يملك الكيان العراقي والمسار الدولي المستقبلي معرفات ودفاتر وتسويات مستقلة؛ فلا يسمح النظام بربط مزود أو قاعدة مسار بكيان مختلف عن مالك المسار.

| القرار | ما يفعله الإصدار الحالي | ما يبقى محظورًا |
| --- | --- | --- |
| `ADVISORY_SELECT` | يسجل المزود والمسار المرشحين مع الدرجة وأسباب القرار | لا يرسل API call ولا ينشئ عملية طرف ثالث |
| `MANUAL_REVIEW` | يسجل أن مستوى المخاطر يحتاج قرارًا بشريًا | لا يمرر العملية أو يحولها تلقائيًا |
| `NO_ELIGIBLE_ROUTE` | يسجل سبب غياب مسار صالح | لا يختار مزودًا احتياطيًا عشوائيًا ولا يعيد محاولة مزود حي |

يفصل النظام بين منشئ الكيان أو المسار أو المزود أو القاعدة وبين من يعتمدها للتوجيه الاستشاري. تبقى جميع المزودات في بيئة `sandbox` و`live_approved=false`، حتى بعد اعتمادها الاستشاري.
