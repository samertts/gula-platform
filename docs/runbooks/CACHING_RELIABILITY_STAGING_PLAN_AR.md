# خطة تجهيز Staging للكاش والموثوقية وOutbox

## النطاق والحالة الحالية

هذه الخطة مخصصة لاختبار طبقة التخزين المؤقت، عزل المنشآت، transactional Outbox، وتكامل التحصين على بيئة Staging منفصلة. الحالة الحالية هي **SAFE_STOP**: لم تُنفذ migrations `0026` إلى `0032`، ولم تُستخدم بيانات NID حقيقية، ولم يُفتح اتصال EHR حكومي فعلي.

| العنصر | الحالة الحالية | بوابة الانتقال |
|---|---|---|
| PostgreSQL Staging | مطلوب | نسخة معزولة ومشفرة مع snapshot قابل للاستعادة |
| Redis Staging | مطلوب | سياسة fail-closed واختبار انقطاع الخدمة |
| Migration `0032` | مُنشأ محلياً فقط | مراجعة schema ثم تنفيذ Staging بموافقة بشرية |
| Outbox `lab_id` | مضاف إلى النموذج | backfill/سياسة للأحداث القديمة قبل التفعيل |
| EHR/NID | غير متصل | Mock أو sandbox رسمي فقط |
| بيانات المرضى | ممنوعت في الاختبار | بيانات اصطناعية معلّمة بوضوح |

## ترتيب التنفيذ المقترح

أولاً، تُنشأ قاعدة PostgreSQL جديدة وRedis جديدان في مشروع Staging، مع حسابات ومفاتيح مختلفة تماماً عن الإنتاج. تُمنع الاتصالات الصادرة إلى نطاقات EHR/NID الحقيقية عبر firewall أو allow-list. تُسجل نسخة schema قبل الترحيل ويُختبر restore في حساب منفصل.

ثانياً، تُشغّل migrations في Staging فقط بعد فحص سلسلة Alembic (`0026`–`0032`) والتحقق من عدم وجود فرع migration متعارض. بعد إضافة `outbox_events.lab_id`، يجب اتخاذ قرار موثق بشأن الأحداث القديمة ذات القيمة NULL: إما ربطها من مصدر موثوق في Staging، أو إبقاؤها غير قابلة للعرض في مؤشرات tenant-scoped إلى أن تُراجع يدوياً. لا يجوز تخمين المنشأة من payload غير موثوق.

ثالثاً، تُحمّل بيانات اصطناعية متعددة المنشآت، ويُختبر أن مؤشرات Outbox والتقارير لا تعيد أي صف خارج `lab_id` الحالي. يجب اختبار replay لمعرف حدث من منشأة أخرى؛ النتيجة المتوقعة `404` وليس `403` أو كشف وجود الحدث.

رابعاً، تُختبر Redis في ثلاث حالات: خدمة متاحة، timeout، وخدمة متوقفة. في حال فشل Redis لا يجوز أن تتحول الاستجابة إلى كشف PII أو أن تتوقف العمليات الحرجة التي لا تعتمد على الكاش؛ أما البيانات التي تتطلب سياسة fail-closed فيجب أن تُرفض بوضوح. يجب التحقق من single-flight تحت حمل متزامن ومن انتهاء TTL والإبطال بعد replay أو تغيير حالة اللقاح.

خامساً، تُجرى اختبارات تحميل تدريجية على endpoints التقارير ومؤشرات Outbox باستخدام بيانات اصطناعية فقط. يبدأ الاختبار من 10 طلبات/ثانية ثم يرفع تدريجياً، مع قياس p50 وp95 وp99 ومعدل أخطاء قاعدة البيانات ومعدل cache hit/miss. لا تُقبل نتيجة دون حدود نجاح متفق عليها مسبقاً مع مالك النظام.

## قائمة قبول قبل أي تشغيل إنتاجي

| الاختبار | النتيجة المطلوبة |
|---|---|
| Migration up/down على نسخة Staging | نجاح دون فقد بيانات أو تغيير غير مقصود |
| إعادة تشغيل worker بعد انقطاع | لا فقد للأحداث؛ انتقال مضبوط بين الحالات |
| replay خارج tenant | عدم كشف الحدث وإرجاع `404` |
| cache key | لا يحتوي NID أو patient ID أو health number أو PII |
| cache invalidation | التقرير يعكس التغيير بعد الإبطال ضمن زمن SLA |
| Redis outage | سلوك fail-closed/تعافٍ موثق حسب نوع العملية |
| ضغط التقارير | p95 ضمن الهدف المعتمد ومعدل الخطأ مقبول |
| EHR mock | idempotency وack/retry/dead-letter تعمل دون اتصال حكومي |
| offline sync | لا فقد لسجل تطعيم، والتعارضات قابلة للتدقيق |

## بوابات الموافقة

لا تُنفذ migration على Staging أو تُنشأ بيانات اختبار خارجية إلا بعد موافقة مالك البيئة. ولا يُسمح بفتح موفر NID أو EHR الحقيقي قبل اعتماد عقد التكامل، الشهادات، allow-list، خطة rollback، واختبار أمني مرخّص على Staging. لا تُستخدم بيانات مواطنين حقيقية في load test أو في سجلات التطبيق.

## خطة rollback

قبل كل migration يُحفظ snapshot وتُختبر استعادته. عند فشل الترحيل، يتوقف النشر ويُحفظ log وschema diff، ثم تُستعاد نسخة Staging بدلاً من تنفيذ downgrade عشوائي على بيانات تحتوي أحداثاً جديدة. أي rollback في الإنتاج يحتاج قرار Go/No-Go منفصلاً ولا يدخل ضمن SAFE_STOP الحالي.
