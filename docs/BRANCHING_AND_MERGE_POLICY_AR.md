# سياسة الفروع والدمج الآمن لمنصة GULA

**الحالة:** سياسة تشغيلية ملزمة للمساهمات الجديدة.
**الهدف:** تقليل الفروع طويلة العمر، والحفاظ على السجل السريري والقدرة على التراجع، ومنع فقدان عمل غير مراجع.

> لا يُدمج تغيير سريري في `main` مباشرةً. ولا يُحذف فرع بعيد غير مدمج لمجرد قدمه أو كثرة الفروع؛ يُدمج أو يُغلق أو يُؤرشف أولاً بناءً على قرار موثق.

## 1. الفروع طويلة العمر المسموحة

| الفرع | الغرض | الحماية المطلوبة | مصدر الدمج المسموح |
|---|---|---|---|
| `main` | الإصدار الإنتاجي المصدق | مراجعة إلزامية، CI أخضر، منع force-push، منع الدمج المباشر | `staging` عبر PR معتمد فقط |
| `staging` | UAT والتحقق قبل الإنتاج | CI أخضر، ترحيلات ذات رأس واحد، توقيع UAT عند تغير المسارات السريرية | `develop` أو release مصدق عبر PR |
| `develop` | خط التكامل اليومي المراجع | CI أخضر، مراجعة واحدة على الأقل، بوابات عقود وسلامة | فروع عمل قصيرة عبر PR |

لا يُنشأ فرع رابع طويل العمر. تستخدم فروع قصيرة بالبادئات `feat/` أو `fix/` أو `chore/` أو `docs/` أو `hotfix/`، وتُحذف من البعيد تلقائياً بعد دمج PR. يجب أن يبدأ كل فرع قصير من `develop`، باستثناء `hotfix/` الذي يبدأ من `main` ويعاد دمجه إلى `develop` بعد النشر.

## 2. توحيد سلسلة السلامة السريرية الحالية

توجد سلسلة علاجية متتابعة وليست فروعاً متوازية مستقلة:

```text
fix/clinical-safety-p0
  -> fix/pharmacy-radiology-safety-p0
  -> fix/emergency-surgery-safety-p0
  -> fix/icu-lab-safety-p0
  -> release/clinical-safety-2026q3 (حزمة الجاهزية المراجعة)
```

يتحول الفرع الأخير إلى **فرع إصدار مؤقت واحد** باسم `release/clinical-safety-2026q3`. بعد نجاح بوابة الانحدار، يفتح PR واحد إلى `develop`. وبعد توقيع UAT، ينتقل PR من `develop` إلى `staging`، ثم من `staging` إلى `main`. بعد اكتمال ذلك، تحذف الفروع الخمسة من البعيد باعتبارها مدمجة، بينما تبقى الالتزامات محفوظة في تاريخ `main` وسجل PR.

## 3. خطة خفض الفروع البعيدة القائمة

لا تُحذف الفروع الحالية دفعة واحدة. تُجرى عملية خفض من ثلاث مراحل مع سجل قرار لكل فرع:

| التصنيف | القاعدة | الإجراء |
|---|---|---|
| مدمج في `main` أو `develop` | يمكن التحقق أن `git merge-base --is-ancestor <branch> <target>` ينجح | حذف الفرع البعيد بعد التأكد من عدم وجود PR مفتوح أو متطلب نشر. |
| له PR مفتوح | المراجعة أو CI ما زالا نشطين | يظل حتى قرار الدمج أو الإغلاق؛ لا ينشأ بديل له. |
| غير مدمج بلا PR | قد يحمل عملاً لا يظهر في الفرع الهدف | افتح issue أو PR مسودة يحدد المالك والقرار: دمج، إغلاق، أو أرشفة بعلامة `archive/<name>-<date>` قبل الحذف. |
| فرع اعتماديات أو توثيق صغير | لا يغير منطقاً سريرياً | دمج واحد فقط بعد CI، ثم حذف المصدر. |

الهدف بعد موجة التنظيف الأولى هو: **3 فروع طويلة العمر + فرع إصدار واحد مؤقت + ما لا يزيد عن 10 فروع عمل ذات PR مفتوح**. لا ينفذ حذف جماعي للفروع غير المدمجة من دون إثبات قابلية الاستعادة.

## 4. بوابات الدمج الإلزامية

كل PR يمس مساراً سريرياً أو ترحيلاً أو عقد عميل يمر بالترتيب التالي:

1. `ruff` للملفات المعدلة، وفحص تركيب Python.
2. بوابة الانحدار السريري الصريحة في CI.
3. اختبارات الخلفي والواجهة والعقود ذات الصلة.
4. `alembic heads` يعرض رأساً واحداً، و`alembic upgrade head` ينجح في قاعدة اختبار PostgreSQL.
5. فحص أن العميل يرسل `If-Match` و`Idempotency-Key` عندما يستدعي أمراً سريرياً محمياً.
6. مراجعة عدم وجود PHI في القياسات أو السجلات أو أحداث الرصد الخارجي.
7. UAT موثق للمجال السريري المتأثر قبل `staging`.

إذا تعارض الأداء مع التدقيق أو القفل أو منع التكرار، تفوز السلامة: يرفض الطلب أو يؤجل، ولا يُفتح مسار تجاوز.

## 5. إجراء التراجع

يبدأ التراجع بإيقاف المسار السريري المتأثر عبر إعداد أو حارس آمن، ثم تفعيل SOP بديل، ثم تحليل السجل غير القابل للتعديل. لا يُعاد نشر نسخة أقدم على قاعدة بيانات تحتوي كتابة بمخطط أحدث إلا بعد تقييم ترحيل أمامي متوافق. تظل مفاتيح عدم التكرار وسجل التدقيق فعالة أثناء الحادث.

## 6. الملكية والمراجعة

يتولى قائد هندسة المنصة صحة الفروع والبوابات، ويتولى مالك المجال السريري قبول UAT، ويتولى أمن المعلومات مراجعة الخصوصية والتنبيهات. تراجع هذه السياسة كل ثلاثة أشهر أو بعد أي حادث P0.
