# تنفيذ مسار المؤسسة الصحية في GULA

## النطاق

تم تنفيذ الطبقة الأولى الآمنة من مسار المؤسسة الصحية داخل `frontend-v3` فوق عقود الهوية ومساحات العمل والعضويات الموجودة في backend. المؤسسة ممثلة ككيان مستقل عن مالكها ومديرها وأطبائها وموظفيها؛ ولا يؤدي الدخول أو اختيار دور الواجهة إلى إنشاء مؤسسة أو عضوية أو صلاحية.

> **قاعدة المسار:** المؤسسة لا تملك المواطن، والمالك لا يصبح طبيباً، ومدير المؤسسة لا يحصل تلقائياً على صلاحيات مالية أو سريرية.

## ما تم تسليمه

| المجال | التنفيذ الفعلي |
|---|---|
| بوابة المؤسسة | تمت إضافة `/organization-workspace` كصفحة مؤسسية محكومة تحت ProtectedRoute وRoleGuard. |
| التنقل | أضيف رابط «بوابة المؤسسة الصحية» للأدوار المؤسسية المعروفة فقط. |
| Demo | يعرض مؤسسة اصطناعية وفروعاً وأقساماً وعضويات وقدرات، دون اتصال بالـAPI الحي ودون إنشاء أو حفظ. |
| اكتشاف المؤسسات في Live | يجمع معرفات المؤسسات من `GET /niam/workspaces` و`GET /niam/memberships/me` فقط. |
| الفروع | تُستخلص المرافق من المساحات المعادة ضمن المؤسسة، ولا تعرض الواجهة فرعاً كمؤسسة مستقلة. |
| الأقسام | تُعرض معرفات الأقسام المرتبطة بالسياق فقط؛ ولا تدعي الواجهة أن وجود القسم يعتمد خدمة أو ترخيصاً. |
| العضويات | تعرض العلاقة والنطاق والمنشأة والقسم والحالة دون `account_id` أو إنشاء هوية جديدة. |
| دورة الحياة | تعرض مراحل Draft وSubmitted وUnder Review وVerified وApproved وActive، مع تمييز الحالات التجريبية عن القرارات الخادمية. |
| الحوكمة | تعرض بوابات الترخيص ومراجعة الوصول والتدقيق كمتطلبات مستقلة، لا كحالات معتمدة تلقائياً. |
| العزل | لا تُستخدم بيانات Demo كـfallback عند فشل عقود Live؛ يظهر حجب صريح بدلاً من خلط السياقات. |

## العقود المستخدمة

في Live تعتمد الصفحة على `GET /niam/workspaces` و`GET /niam/memberships/me`. هذه العقود تعيد سياقاً محدوداً للمستخدم الحالي، ولا تمنح الصفحة حق استعراض كل المؤسسات أو كل الموظفين أو المرضى أو السجلات الطبية. لا توجد في هذه الموجة كتابات مؤسسية من الواجهة.

لم تُستخدم endpoints الإدارة الداخلية لإنشاء مؤسسة أو فرع أو قسم أو دعوة أو تعيين دور، لأن هذه العمليات تحتاج عقداً خادمياً متكاملاً مع صلاحيات مؤسسية، ونطاق Facility/Department، وإصدار/تعارض، وIdempotency، وتدقيق غير قابل للحذف.

## الحدود الأمنية

تظل بوابة المؤسسة طبقة عرض دفاعية. القرار النهائي بشأن العضوية والدور والصلاحية والسياق وحالة الترخيص والقدرة المؤسسية يجب أن يصدر من الخادم. اختيار مؤسسة في الواجهة يغير نطاق العرض فقط ولا يغير الصلاحيات.

لا تعرض الصفحة السجل الصحي الكامل لمجرد ارتباط المواطن بالمؤسسة، ولا تفتح المالية أو المخزون أو الأجهزة أو التأمين أو الطوارئ أو الإحالة أو الصحة العامة. كل Domain يحتاج عقداً منفصلاً يفرض الغرض والسياسة والعلاقة والموافقة عند الحاجة.

لم يتم ادعاء تكامل حكومي أو تحقق آلي من الترخيص. حالات المؤسسة والترخيص الظاهرة في Demo اصطناعية، أما Live فيقتصر على ما تعيده عقود الهوية الحالية. ولا تعتبر GULA نفسها Database Admin للمؤسسة أو الجهة الحكومية.

## ما لم يُنفذ عمداً

لم يتم تنفيذ طلب تسجيل مؤسسة أو رفع وثيقة ترخيص أو اعتماد أو تعليق أو إغلاق أو نقل ملكية. ولم يتم تنفيذ إدارة الفروع والأقسام أو الخدمات والقدرات أو الأجهزة والتكاملات أو المخزون أو المالية أو التأمين أو الجودة أو الشكاوى أو الحوادث أو مراجعات الوصول أو إلغاء صلاحيات موظف مغادر.

هذه الوظائف تحتاج أولاً إلى نماذج backend ومخططات OpenAPI واختبارات tenant isolation وRBAC سياقي وAudit وstate machine وversioning وbackup/restore rehearsal. لا يكفي أن يظهر زر في الواجهة لتصبح العملية آمنة.

## التحقق

أضيفت اختبارات الصفحة التي تثبت عزل Demo، وقراءة المساحات والعضويات الحية من الخادم، وعدم عرض `account_id`، والحجب الصريح عند فشل العقد. يجب تشغيل مجموعة frontend-v3 الكاملة وlint وفحوص الحوكمة والبناء قبل الدمج. نجاح الفحوص المحلية لا يثبت جاهزية الإنتاج أو نجاح فحوص GitHub البعيدة.

## الخطوات اللاحقة

الأولوية التالية هي backend-first: إضافة `/niam/me/organization-summary` أو عقد مكافئ يعيد أقل قدر من البيانات، ثم عقود ذاتية للفروع والأقسام والقدرات والترخيص والعضويات والدعوات ومراجعة الوصول. يجب أن يسبق كل واجهة كتابةٍ خادمٌ يفرض ownership وauthorization وversion/idempotency/audit.
