## 1. الملخص التنفيذي

أجريت عملية تدقيق أمني شامل واختبار اختراق حي على البنية التحتية، والواجهات الأمامية والخلفية، وتكاملات الجهات الخارجية (مثل Telegram)، وآليات العزل لبيئة العرض التجريبي (Demo Mode) لمنصة غولا الصحية الوطنية في العراق (**GULA**) [1] [2]. 

يُصنف النظام ضمن البنى الحرجة عالية الحساسية (Mission-Critical Clinical System)، حيث تخضع جميع العمليات لضوابط صارمة لحماية البيانات الطبية وسرية المرضى [3]. أظهرت نتائج الفحص أن البنية الأساسية للواجهة، وعزل جلسات العرض التجريبي، والتحقق من منع التسجيل الذاتي العام تعمل بفعالية تامة وتجتاز اختبارات الانحدار بنجاح (`167/167` اختبار أمني محلي مجتاز) [1]. ومع ذلك، تم رصد نقاط ضعف ومجالات تحسين حرجة تتطلب معالجة فورية لضمان الامتثال الكامل لمعايير حماية البيانات السريرية.

## 2. نطاق الفحص ومنهجية العمل

اعتمدت المنهجية على دمج أدوات الفحص الثاتي (SAST)، والفحص الديناميكي غير التدميري (DAST)، وتحليل البنية التحتية على سحابيتي Vercel وCloudflare، ومراجعة سياسات المصادقة وإدارة الجلسات والتكاملات [1] [2].

| محور الفحص | الأداة / التقنية المستخدمة | النطاق المغطى | الحالة / النتيجة |
| :--- | :--- | :--- | :--- |
| **البنية التحتية والشهادات** | فحص DNS، ترويسات الاستجابة، تحليل SSL/TLS عبر OpenSSL | `www.gula-platform.org` | شهادة Let's Encrypt صالحة، تفعيل HSTS، مع رصد خطأ 526 في مسار API الخلفي [1] [2]. |
| **الفحص الثابت (SAST)** | Bandit، فحص الأسرار المخصص، مراجعة الكود المصدري | ملفات المشروع `/backend` و `/frontend-v3` | نجاح فحص الحزم وغياب الثغرات المباشرة في التبعيات الإنتاجية؛ مع رصد مؤشرات أسرار تحتاج تدوير [1]. |
| **الفحص الديناميكي (DAST)** | اختبارات HTTP غير التدميرية، فحص الروابط ومسارات الصحة | النطاق الرسمي ومسارات الـ API | اجتياز صفحات العرض التجريبي وعزل الجلسات، مع وجود تحديات في تكوين التوجيه الخلفي للـ API [1] [2]. |
| **تكاملات الجهات الخارجية** | مراجعة أمن Telegram Webhooks وأوامر البوت | `backend/app/routes/telegram_webhook.py` | رصد غياب التحقق من Secret Token وتفويض الاستعلامات السريرية عبر البوت [2]. |

## 3. النتائج التفصيلية وتقييم المخاطر

### 3.1.نقاط القوة الأمنية المرصودة
* **إغلاق التسجيل الذاتي العام:** تم فرض قاعدة `PUBLIC_SELF_REGISTRATION_ENABLED=false` بصرامة على مستوى الإعدادات ومسارات التسجيل، بحيث يخضع إنشاء أي حساب جديد لإجراءات اعتماد وتحقق رسمية [1].
* **عزل بيئة العرض التجريبي (Demo Mode):** بيئة العرض معزولة تماماً وتعتمد على جلسات اصطناعية محلية بالكامل (`demo_viewer`) لا تتصل بقواعد البيانات الإنتاجية ولا تتيح أي عمليات سريرية حقيقية [1].
* **سلامة تبعيات الإنتاج:** أظهر فحص `npm audit` و `pip-audit` على حزم الإنتاج خلو التبعيات الحالية من الثغرات المعروفة ذات الخطورة العالية أو الحرجة في قوالب النشر [1].

### 3.2.الثغرات ومجالات التحسين المكتشفة

| معرّف الثغرة | التصنيف | الوصف التأثيلي | مستوى الخطورة | الإجراء التصحيحي المقترح |
| :--- | :--- | :--- | :--- | :--- |
| **SEC-01** | ترويسات الأمان المفقودة (Missing Security Headers) | غياب ترويسات `Content-Security-Policy` و `X-Frame-Options` على بعض مسارات الاستجابة الحية رغم تعريفها في ملفات التكوين [1] [2]. | **متوسط** | مراجعة middleware الترويسات في Vercel وتطبيقها بصرامة على جميع مسارات الاستجابة [2]. |
| **SEC-02** | أخطاء التوجيه والشهادات في الـ API | ظهور خطأ `526 Invalid SSL certificate` عند محاولة الوصول المباشر إلى نطاق الـ API الخلفي عبر Cloudflare [1] [2]. | **عالي** | تحديث إعدادات SSL/TLS في Cloudflare إلى وضع *Full (Strict)* والتأكد من توافق شهادة الخادم الخلفي [2]. |
| **SEC-03** | غياب التحقق من المصدر في Telegram Webhook | مسار `POST /telegram/webhook` يعالج الأوامر الواردة دون التحقق من ترويسة Secret Token الخاصة بـ Telegram أو توقيع الطلب [2]. | **عالي** | تفعيل التحقق الإلزامي من `X-Telegram-Bot-Api-Secret-Token` في مسار الـ Webhook [2]. |
| **SEC-04** | استعلامات البوت السريرية بلا تفويض (`chat_id`) | أوامر `/alerts` و `/stats` عبر بوت Telegram تستعلم عن تنبيهات `lab_id=1` دون مطابقة `chat_id` بمستخدم إداري مصادق عليه [2]. | **عالي** | ربط كل `chat_id` بمُعرّف مستخدم مُمكّن (Allowlist) وإلغاء الاستعلامات العامة غير المصرح بها [2]. |
| **SEC-05** | أسرار تجريبية ومفاتيح في ملفات التوثيق والاسكريبتات | رصد رموز مرجعية في ملفات الفحص والتوثيق (مثل سكريبت التحقق من البوت) [1]. | **منخفض** | تنظيف المستودع من أي مفاتيح أو رموز سابقة واعتماد متغيرات البيئة حصرياً عبر Secret Managers [1]. |

> > "إن الأنظمة الصحية الرقمية لا تتحمل أي تسامح مع الثغرات البرمجية أو غياب التحقق من الصلاحيات. يجب أن تُعامل كل نقطة تفاعل مع الواجهات والجهات الخارجية وفق مبدأ الثقة المعدومة (Zero Trust)."
> > — *دليل الهندسة الأمنية لمنصة GULA* [3]

## 4. توصيات المعالجة وخطة العمل

لضمان أعلى معايير الحماية والموثوقية قبل الاعتماد التشغيلي الكامل، تُوصى الإدارة الفنية بتنفيذ الخطوات التالية بشكل عاجل:

1. **معالجة تواصل الـ API والشهادات:** إعادة ضبط وضع التشفير بين Cloudflare والخادم الخلفي إلى *Full (Strict)* لضمان زوال خطأ 526 واستقرار الاتصالات المشفرة [1] [2].
2. **تأمين بوابة Telegram:** إضافة طبقة مصادقة تعتمد على `Secret Token` للطلبات القادمة من Telegram، وقصر الأوامر الإدارية السريرية على مسؤولي النظام المعتمدين فقط [2].
3. **فرض ترويسات الأمان:** التأكد من تفعيل ترويسات `CSP` و `HSTS` و `X-Content-Type-Options` على مستوى بوابة التوجيه الأمامية والخلفية بلا استثناء [1] [2].
4. **تدوير الأسرار:** تدوير أي مفاتيح أو رموز توكن قد ظهرت في سكريبتات الفحص القديمة أو أدوات التطوير [1].

## 5. الخاتمة

تُثبت نتائج التدقيق أن منصة GULA تتمتع ببنية أساسية صلبة وواجهة متطورة وآليات عزل ممتازة تمنع تسرب البيانات الإنتاجية في بيئة العرض التجريبي [1]. تنفيذ التوصيات المذكورة أعلاه سيكمل التحصين السيبراني للمنصة ويجعلها جاهزة بالكامل للاستخدام المؤسسي الواسع في القطاع الصحي العراقي [1] [3].

## 6. ملحق التحقق بعد المعالجة — 13 أغسطس 2026

### 6.1 تحديث الإصدار ونطاق التحقق

تمت مراجعة النتائج السابقة وإعادة اختبارها بعد نشر commit `774e334260326b8bec0dd61179c6cd206a7e5785` إلى خدمة `gula-backend` في Railway. سجل GitHub/Railway أكد حالة `Deployed to Railway` ثم عادت الخدمة إلى `Online`. هذا الملحق يحل محل أي ملاحظة سابقة تفيد بأن حماية Telegram لم تُطبق إنتاجياً.

### 6.2 تحصين Telegram الإنتاجي

تم إصلاح المسار الفعلي المستخدم في الإنتاج، وهو `POST /api/v1/telegram/webhook` في `backend/app/notifications/telegram_chat.py`. أصبح المسار يطبق، بالترتيب، تحققاً إلزامياً من `X-Telegram-Bot-Api-Secret-Token`، وallowlist للمحادثات عبر `TELEGRAM_ALLOWED_CHAT_IDS`، وتحققاً اختيارياً من `TELEGRAM_ADMIN_USER_ID`، مع رفض آمن للـ JSON غير الصالح ومعالجة عامة للأخطاء دون كشف تفاصيل داخلية. أضيفت اختبارات أمنية للمسار الفعلي، ونجحت اختبارات Telegram وSNDHS ذات الصلة، كما نجح CI الكامل للـ commit `774e3342`.

تم ضبط متغيرات الإنتاج في Railway عبر لوحة الخدمة المصادق عليها، دون حفظ القيم في Git أو الواجهة:

| المتغير | الحالة | الملاحظة |
| :--- | :--- | :--- |
| `TELEGRAM_WEBHOOK_SECRET_TOKEN` | مضبوط | Secret عشوائي قوي، وقيمته غير مدرجة في هذا التقرير |
| `TELEGRAM_ALLOWED_CHAT_IDS` | مضبوط | يتضمن Chat ID الذي قدمه مالك الحساب فقط |

### 6.3 أدلة الاختبار الحي

أُجريت اختبارات غير تدميرية على النطاق `https://api.gula-platform.org` بعد استقرار إعادة تشغيل Railway. أعاد `/health` الحالة `200` مع `system_ready=true`. أعاد JSON غير الصالح `400 BAD_REQUEST`. أعاد Secret Token غير الصحيح `403 FORBIDDEN`. وأعاد Secret صحيح مع Chat ID غير موجود في allowlist `403 FORBIDDEN` برسالة `Telegram chat is not authorized`. لم يُنفذ أمر Telegram مصرح به ولم تُرسل رسالة خارجية أثناء الاختبار.

> **النتيجة:** تم إغلاق SEC-03 وSEC-04 في المسار الفعلي للإنتاج، مع بقاء قاعدة تشغيلية إلزامية: يجب تدوير Secret Token فور الاشتباه في انكشافه، ويجب تحديث allowlist فقط عبر Secret Manager أو لوحة Railway المصادق عليها.

### 6.4 حالة العناصر المتبقية

لا ينبغي اعتبار هذا الملحق إقراراً بأن جميع عناصر التدقيق الأخرى مغلقة. ما زالت مراجعة ترويسات CSP على كل مسارات الواجهة، والتحقق المستمر من إعداد Cloudflare/Origin TLS، وتدقيق Dependabot/CodeQL، وتدوير أي أسرار تاريخية في GitHub Security، عناصر متابعة مستقلة. كما أن فحص الإنتاج لا يثبت الجاهزية السريرية أو الاعتماد الحكومي لنظام SNDHS؛ إذ يظل موصل STUB مرفوضاً في الإنتاج حتى تهيئة موصل LIVE مع اعتماد رسمي.
