# مواصفة تفويض الطبيب والأوامر السريرية قبل P5

**الحالة:** `P4_BLOCKED / NON_OPERATIONAL`  
**نوع الوثيقة:** سياسة حوكمة وعقد قبول مستقبلي؛ ليست واجهة API ولا تمنح صلاحية تشغيلية.  
**المبدأ:** لا يمنح اسم الحساب أو الاسم الظاهر أو نوع الجهة أو ادعاء المهنة أي صلاحية. يقرر الخادم التفويض لكل طلب، ولا يملك العميل إنشاء دور أو تفعيله أو تغيير نطاقه.

> أنا نظام ذكاء اصطناعي ولست مختصاً طبياً؛ تُعامل هذه الوثيقة كتحليل تصميمي مستنير لا كقرار علاجي أو تشخيص. يجب أن يراجعها مختص سريري مؤهل والجهات التنظيمية المخولة قبل الاعتماد أو التشغيل.

## 1. قرار الحوكمة

تمثل هذه المواصفة سياسة المنتج المطلوبة من مالك المنصة: لا يعد الحساب **طبيباً مخولاً في GULA** إلا عندما تثبت المنصة، بخطوتين مستقلتين، موافقة موثقة من مصدر وزارة الصحة ومصدر نقابة الأطباء، ثم يصدر الخادم تعييناً فعالاً محدود النطاق لدور إكلينيكي. لا تدعي الوثيقة وجود تكامل أو اعتراف رسمي أو واجهة تقنية مع أي جهة؛ وكل مصدر غير متكامل يبقى `READY_FOR_OFFICIAL_INTEGRATION` أو `PENDING_REVIEW`.

حتى تتحقق الموافقتان، يبقى الشخص في حالة حساب مواطن/فرد أو `PENDING_PROFESSIONAL_VERIFICATION`، بلا أوامر فحوص أو تصوير أو لقاحات أو وصفات، وبلا قدرة على تعيين نفسه طبيباً. لا تحول موافقة واحدة، أو وثيقة يرفعها المستخدم، أو اسم الوظيفة، أو تبعية جهة، أو اجتياز فحص واجهة إلى موافقة مهنية.

## 2. نموذج التحقق المهني الثنائي

| شرط خادمي | دليل مطلوب | نتيجة الإخفاق |
|---|---|---|
| تطابق الشخص | ربط مثبت بين الحساب و`Person` و`ProfessionalIdentity` | الرفض مع `PENDING_PROFESSIONAL_VERIFICATION` |
| مصدر وزارة الصحة | مرجع تحقق، حالة، طريقة، جهة تحقق، وقت إصدار/انتهاء، وأثر تدقيق | لا دور مهني ولا صلاحية |
| مصدر نقابة الأطباء | مرجع تحقق مستقل، حالة، طريقة، جهة تحقق، وقت إصدار/انتهاء، وأثر تدقيق | لا دور مهني ولا صلاحية |
| توافق الموافقتين | تطابق الشخص، المهنة، وحالة الصلاحية؛ تعارض الدليل يذهب لمراجعة بشرية | `PROFESSIONAL_VERIFICATION_CONFLICT` |
| تعيين العمل | عضوية أو تعيين خادمي فعال في مساحة عمل ومنظمة/منشأة مناسبة | الرفض خارج النطاق |
| سياسة الفعل | سياسة سماح صريحة للفعل والمورد، مع أولوية المنع | الرفض الافتراضي |

لا تستخدم المنصة موافقة أحد المصدرين نيابة عن الآخر. ولا يزيل انتهاء أحد الدليلين الصلاحيات بشكل صامت: يوقف الخادم الأفعال الجديدة فوراً، يحافظ على الأثر المدقق للأوامر السابقة، ويوجه الحالة إلى مراجعة الحوكمة.

## 3. طلب حساب المواطن بواسطة الطبيب

يمكن أن تكون الخدمة المستقبلية **طلب بدء حساب مواطن بواسطة طبيب مخول**، وليست «فتح حساب» أو «تفعيل حساب» تلقائياً. يبقى إنشاء الحساب، إثبات هوية الشخص، قبول الشروط، التحقق، والتنشيط ضمن دورة حياة حساب خادمية مستقلة. ولا يكسب الطبيب حق الاطلاع أو التحكم بحساب المواطن الناتج لمجرد تقديم الطلب.

| الفعل المستقبلي | من يطلبه | ما لا يسمح به |
|---|---|---|
| `citizen.account.request.initiate` | طبيب ذو تحقق ثنائي وتفويض صريح، بعد P4 | لا إنشاء حساب نشط، لا تجاوز تحقق المواطن، لا استبدال موافقته، لا منح عضوية أو دور |
| مراجعة الطلب | خدمة خادمية/موظف مخول وفق سياسة منفصلة | لا قرار من واجهة الطبيب أو Android |
| تفعيل حساب المواطن | دورة حساب خادمية مستقلة | لا تدخل من الطبيب أو اسم المنظمة |

هذه الوظيفة **غير مفعلة** لأن التسجيل الوطني/المواطنة خارج نطاق التنفيذ الحالي، ولأن P4 لم يغلق بعد.

## 4. محفظة صلاحيات الأوامر المقترحة

تمنح الصلاحيات لاحقاً لكل طبيب يحقق الشروط السابقة ولديه تعيين وسياسة موافقة مطابقة للسياق، لا لـ«أي طبيب» كصلاحية عالمية. لا تختار أي من هذه الأفعال جهة التنفيذ؛ يظل اختيار المختبر أو مركز التصوير أو منفذ الصرف للمواطن ضمن قائمة جهات مؤهلة، بعد أن يختارها هو، ما لم توجد حالة سريرية طارئة موثقة ومراجعة بسياسة منفصلة.

| مفتاح صلاحية مقترح | الغرض | محتوى الأمر الأدنى | حد العميل |
|---|---|---|---|
| `clinical.lab.order.create` | طلب فحوص مختبرية | قائمة فحوص من كتالوج معتمد، مرجع المريض، سبب/سياق سريري، توقيع الطبيب، صلاحية زمنية | لا يختار المختبر ولا يدخل/يعتمد نتيجة |
| `clinical.diagnostic_imaging.order.create` | طلب أشعة وسونار ورنين ومفراس وتصوير تشخيصي | نوع الفحص وكوده، مرجع المريض، معلومات سريرية لازمة، توقيع وصلاحية | لا يختار مركز التصوير ولا يفسر التقرير |
| `clinical.immunization.order.create` | أمر أو موافقة تلقيح | منتج/نوع لقاح من كتالوج معتمد، رقم الجرعة، الوقت المقترح، سبب، توقيع | لا يولد النظام الجرعة تلقائياً ولا يسجل الإعطاء |
| `clinical.medication.prescription.create` | وصف/موافقة علاج | دواء من كتالوج معتمد، جرعة، طريق، تكرار، مدة، تعليمات، توقيع | لا يصرف الدواء ولا يختار الصيدلية ولا يعتمد تعويضاً |

لا تتضمن هذه المفاتيح صلاحية تعديل النتائج، اعتماد نتائج المختبر، تحرير تقرير تصوير، إعطاء لقاح، صرف دواء، أو إسناد صلاحية لشخص آخر. تفصل هذه الأفعال في سياسات مستقلة وتحققها منشآت أو مهنيون مخولون.

## 5. بيانات الطلب وحرية اختيار المنفذ

يمثل الأمر مرجعاً للمريض لا نسخة حرة من الملف. يعرض الخادم الاسم والعمر والجنس من السجل القانوني في وقت الطلب. يحسب العمر من تاريخ الميلاد عند العرض ولا يحفظ كقيمة متقادمة. يقتصر الهاتف والعنوان على استخدام اتصال أو تنفيذ مبرر ومصرح به، ويحميان تشفيراً ونطاقاً؛ ولا يطلع عليهما إلا الطبيب المخول أو المنفذ الذي اختاره المواطن عندما تتطلب المهمة ذلك. لا تنقل هذه الحقول إلى كل منفذ محتمل قبل الاختيار.

تكون حالة المنفذ في كل أمر `PATIENT_SELECTION_REQUIRED` عند التوقيع. يعرض المواطن جهات تنفيذ متاحة ومؤهلة وفق الكتالوج والنطاق والسياسة، ويختار منفذاً واحداً. لا يستطيع الطبيب تثبيت منفذ أو استبدال اختيار المواطن، ولا يستطيع المنفذ الوصول إلى الأمر قبل اختياره والتحقق من نطاقه. لا يفسر هذا النص حرية الاختيار كضمان لتوفر خدمة أو سعر أو تغطية تأمينية.

## 6. دورة حياة غير قابلة للتجاوز

| الانتقال | الجهة الوحيدة المسموح لها | شرط خادمي |
|---|---|---|
| `DRAFT → SUBMITTED` | الطبيب المخول | تحقق مهني ثنائي، تعيين، سياسة، اكتمال البيانات، منع التكرار |
| `SUBMITTED → SIGNED` | الخادم بعد توقيع الطبيب | توقيع، ختم زمني، نسخة مورد، أثر تدقيق |
| `SIGNED → PATIENT_SELECTION_REQUIRED` | الخادم | لا منفذ معيّن ولا بيانات للجهات غير المختارة |
| `PATIENT_SELECTION_REQUIRED → PROVIDER_SELECTED` | المواطن/ممثل مخول | جلسة صالحة، سياسة اختيار، تسجيل اختيار مدقق |
| `PROVIDER_SELECTED → ACCEPTED/REJECTED` | المنفذ المختار المخول | نطاق منشأة وكتالوج وقدرة وسياسة |
| أي إلغاء أو استبدال | خادم وسياسة فعل صريحة | تدقيق، سبب، نسخة، ولا تعديل صامت بعد التوقيع |

تستبدل التعديلات بعد التوقيع بأمر خلفي ذي علاقة واضحة، مع حفظ النسخة الأصلية. تعيد العمليات المتكررة مفتاح نتيجة ثابتاً ولا تنتج أوامر مكررة، وترفض تعارض النسخة أو الحالة رفضاً واضحاً.

## 7. بوابة التفعيل والاختبارات

تبقى جميع الأفعال والحالات والمفاتيح المذكورة `PROPOSED_NOT_IMPLEMENTED / OFF`. لا تنفذ هذه الوثيقة مساراً أو قاعدة بيانات أو شاشة أو تكاملاً. يلزم قبل أي تفعيل: إغلاق P4-08 وP4-10 إلى P4-15 وP4-19 إلى P4-25 وP4-27، ومراجعة بشرية P4-31، ودمج وتحقق إنتاجي P4-32 [1].

وتشمل اختبارات القبول المستقبلية: رفض كل حساب لا يملك موافقتين حاضرتين، رفض نطاق منظمة أو منشأة مخالف، رفض العميل الذي يحاول إدخال دور أو حالة، منع إسناد منفذ قبل اختيار المواطن، منع عرض الهاتف والعنوان لمنفذ غير مختار، رفض تعديل أمر موقع، واختبارات التزامن والتدقيق والعودة. لا تستخدم بيانات مرضى حقيقية أو مولدة على واجهة إنتاجية للتحقق.
