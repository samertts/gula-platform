# تدقيق مصادر البيانات والكتابات في `frontend-v3`

**الحالة:** مكتمل للحصر الساكن، مع منع افتراضي للعمليات غير المعتمدة.  
**النطاق:** ملفات العرض وخطافات API وعميل REST المركزي في `frontend-v3`.  
**مصدر القرار الآلي:** [`frontend-v3/data-source-decisions.json`](../../frontend-v3/data-source-decisions.json).

## خلاصة القرار

لا يُعد وجود دالة Axios أو `useMutation` دليلًا على وجود قدرة تشغيلية معتمدة. لذلك ينتج `data-source-inventory.json` جردًا ثابتًا لكل ملف مصدر يستهلك كتالوج API أو React Query أو عميل API المباشر أو القراءة النطاقية أو حالة العرض التجريبية. ولكل سطح تصنيف واحد صريح: `contract-bound` أو `safe_bridge` أو `unbound` أو `demo-only`. وتُرفض بوابة الجودة أي نسخة من السجل لا تطابق إعادة التوليد من المصادر الحالية.

> لا تمنح الواجهة صلاحية ولا سياق منشأة ولا أثر تدقيقيًا للخادم. لذلك لا يمكن لترجمة طلب REST من واجهة العميل أو نجاح فحص `/authz/check` داخل المتصفح أن يحل محل الإلزام الخادمي.

| السطح | العقد المرجعي | القرار الحالي | سبب القرار |
|---|---|---|---|
| المرضى | `patients.read` | قراءة محكومة وممنوعة افتراضيًا | يعلن العقد والصلاحية وسياق المنشأة؛ وتبقى القراءة محجوبة حتى يثبت حارس الخادم. |
| الطلبات | `orders.read` | قراءة محكومة وممنوعة افتراضيًا | ينطبق عليها المبدأ نفسه؛ لا تعرض بيانات عند غياب فرض الصلاحية الخادمي. |
| السجل الصحي | `clinical.ehr.record.read` | جسر آمن | لا توجد قناة جلسة ونطاق وتشغيل frontend-v3 معتمدة بعد. |
| نتائج الفحوصات | `test-results.read` | جسر آمن | المسار كان يستدعي REST مباشرة؛ العقد وحده لا يثبت حارس السياق الخادمي. |
| العينات | — | جسر آمن | لا يوجد عقد قراءة مؤهل ومسجل لهذا السطح. |

## الكتابات

تضم طبقة `useApi.ts` تسع دوال طفرة مركزية، ستٌ منها طفرات سريرية أو مخبرية (`useCreatePatient` و`useUpdatePatient` و`useCreateOrder` و`useCancelOrder` و`useCreateResult` و`useCreateSample`). لم يثبت التدقيق أي استهلاك لها في بقية ملفات `src`، ومع ذلك لا تُعد آمنة: بقيت مُصنفة بوصفها تعريفات قديمة وغير موصولة وليست مسارات معتمدة.

وتظهر 12 طفرة موصولة بواجهات مرئية عبر أجهزة الحافة وإدارة المستشفيات وإدارة NIAM والإشعارات. سُجلت كل واحدة في `data-source-decisions.json` مع قرار المنع المقابل. يفرض `src/api/client.ts` الآن حاجزًا قبل الشبكة لجميع `POST` و`PUT` و`PATCH` و`DELETE`، ولا يستثني إلا مسارات ضيقة للمصادقة والتحقق وقرار القراءة. لا تدخل أي كتابة سريرية أو مخبرية أو إدارية أو ذات أثر خارجي ضمن الاستثناءات.

وبالمثل، يرفض الحاجز كل `GET` مباشر ما لم يكن من تهيئة الجلسة الضيقة (`/session` و`/setup/status` و`/greeting`). وبذلك لا تبقى قائمة API الواسعة قابلة لعرض مورد سريري أو مختبري أو عام غير مصنف لمجرد أن ملفًا قديمًا يستدعي Axios. صفحات المرضى والطلبات لا تمر بهذه القائمة؛ إذ تبقى قراءة النطاق الخاصة بها محجوبة داخل `workspaceScopedReads` حتى اعتماد بوابة خادمية تفرض السياق والصلاحية.

| فئة الكتابة | أمثلة الواجهات المرئية | القرار |
|---|---|---|
| كتابة سريرية ومخبرية | مريض، طلب، نتيجة، عينة | محجوبة؛ يلزم اعتماد مستقل لسياسة التعارض والأثر والتدقيق وidempotency. |
| أجهزة الحافة | حجر/إلغاء/إعادة تفعيل جهاز | محجوبة؛ يلزم عقد تفويض سلطة الأجهزة. |
| إدارة المؤسسات | إنشاء مستشفى أو قسم | محجوبة؛ يلزم عقد سلطة المؤسسة ونطاقها. |
| إدارة NIAM | سياسات/شهادات/اتحاد/حوكمة/ثقة/سير عمل | محجوبة؛ يلزم عقد إدارة NIAM وتدقيق أثر واضح. |
| الإشعارات | إرسال حالة طلب | محجوبة؛ يلزم اعتماد سياسة الأثر الخارجي والموافقة. |

## بوابة الجودة

يتحقق الأمر التالي من سجل القرارات، ومن الجرد صفحةً-بصفحة، ومن استمرار جسور النتائج والعينات والسجل الصحي، ومن وجود الحاجز المركزي، ومن بقاء صفحات المرضى والطلبات معلنة لعقدها وسياقها. كما يفشل إذا ادعى سطح تجريبي وجود بيانات تشغيلية:

```bash
cd frontend-v3
pnpm verify:data-sources
```

وعند تغيير مصدر بيانات، يجب تجديد السجل الملتزم به ثم فحصه:

```bash
pnpm generate:data-source-inventory
pnpm verify:data-sources
```

وأُدرج الأمر في `pnpm check` حتى لا يُعاد تفعيل مصدر قراءة أو كتابة دون تحديث قرار الحوكمة والضابط معًا.
