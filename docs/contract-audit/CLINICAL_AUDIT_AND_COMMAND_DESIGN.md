# تصميم السجل السريري والأوامر الحساسة

**الحالة:** تصميم مانع للتفعيل، 13 أغسطس 2026. لا يجيز هذا المستند أي كتابة سريرية.

## النطاق والقرار

تفرض عقود القراءة المؤهلة في المنصة بوابات نطاق وسياسات دقيقة، لكن أي أمر سريري يغير الحالة يحتاج دليلًا إضافيًا على أن الفعل مسند إلى هوية ونطاق محددين، وأن الأثر لا يمكن حذفه أو تغييره بصمت، وأن إعادة المحاولة أو التعارض لا تنتج تغييرًا مزدوجًا. لذلك تبقى جميع أوامر الملاحظات والمهام والقياسات والحالات **محجوبة** حتى يعتمد هذا التصميم وسياسة الأثر والتعارض الخاصة بكل أمر.

## تقييم السجل القائم

يوجد `IdentityAuditEntry` مع `entry_hash` و`previous_hash` وخدمة حساب سلسلة تجزئة. وهو مفيد لتدقيق الهوية، لكنه لا يكفي لسجل أوامر سريرية مستقل للأسباب التالية:

| جانب | السجل القائم | حدّه بالنسبة للأمر السريري |
|---|---|---|
| ربط المعاملة | تضاف السجلات عبر جلسة SQLAlchemy وتُنفّذ `flush` فقط. | لا يوجد عقد يلزم كل أمر سريري بإدخال الحدث في المعاملة نفسها قبل الالتزام. |
| مقاومة التعديل | التجزئة لا تغطي `changes` أو `extra_data` أو `context`، ولا يظهر منع قاعدة بيانات للحذف أو التحديث. | يمكن أن تتغير دلالة الحدث أو يُحذف بلا دليل لا يقبل الجدل. |
| التسلسل | يحصل الكاتب على آخر تجزئة بحسب `occurred_at`. | لا توجد سلسلة متسلسلة لكل منشأة مع قفل أو عداد يمنع سباق الكتّاب. |
| إعادة المحاولة | لا يوجد مفتاح idempotency أو إيصال أمر. | قد يعاد تنفيذ الأمر عند إعادة إرسال الشبكة أو انتهاء الرد. |

## مخطط التنفيذ المقترح بعد الاعتماد

| المكوّن | الضوابط الإلزامية |
|---|---|
| `clinical_audit_entries` | سجل إضافي فقط لكل منشأة، يحوي المستأجر والمؤسسة والمنشأة، نوع المورد ومعرفه، الفاعل والشخص والتعيين والجلسة، نوع الأمر، نتيجة القرار، معرف الارتباط، ووقت UTC. تغطي التجزئة المعيارية كل الحقول الدلالية بما فيها ملخص التغيير الآمن. |
| `clinical_audit_heads` | رأس سلسلة واحد لكل منشأة مع رقم تسلسل وتجزئة أخيرة. يحصل الكاتب على قفل صف في المعاملة نفسها حتى لا تتفرع السلسلة. |
| قيود قاعدة البيانات | منع `UPDATE` و`DELETE` على سجلات الأحداث ورؤوس السلسلة عبر صلاحيات نشر مقيدة أو محفزات تدقيق مناسبة للمحرك، مع اختبار يثبت الرفض. لا تحفظ بيانات صحية كاملة في التجزئة أو البيانات الوصفية. |
| `clinical_command_receipts` | مفتاح فريد `(tenant_id, organization_id, facility_id, command_type, idempotency_key)` مع تجزئة حمولة الطلب وحالة التنفيذ والاستجابة الموجزة. يعاد الرد السابق فقط عندما تتطابق تجزئة الحمولة. |
| معاملة الأمر | تحقق الهوية والتعيين والسياسة والنطاق وقاعدة انتقال الحالة ثم قفل المورد، وإنشاء إيصال، وتغيير الحالة، وإدخال حدث السجل، والتزام واحد. أي فشل يلغي كل الخطوات. |
| التعارض | تستخدم الموارد إصدارًا دلاليًا أو `If-Match` عندما يغير المستخدم حالة مقرؤة سابقًا. يكون تعارض الإصدار `409` ولا ينفذ أي تغيير أو حدث نجاح. |
| العمل دون اتصال | محظور افتراضيًا للأوامر السريرية. لا يسمح به إلا لأمر مسمى مع طابع وقت مصدر موثوق ومفتاح idempotency وسياسة تعارض واعتماد منفصل. |

## شروط اعتماد الأمر الواحد

لا ينتقل أمر من **ممنوع** إلى **مرشح للتنفيذ** إلا إذا وثقت ورقة قرار خاصة به العناصر التالية: أثره التشغيلي والسريري، المورد وحالة البداية والنهاية، السياسة الدقيقة، نطاق المنشأة، جهة الفاعل، مخطط الحدث، مفتاح إعادة المحاولة، أسلوب التعارض، سلوك الانقطاع، وخطة الاختبار السلبية. لا ينطبق اعتماد أمر على أمر آخر لمجرد تشابه المورد أو الدور.

> **قرار منع:** لا تنفذ ترحيلات أو واجهات أو طفرات tRPC للأوامر السريرية استنادًا إلى هذا التصميم وحده. يلزم اعتماد صريح للسياسة العامة ثم ورقة قرار مستقلة لكل أمر.
