# ADR-027: حدود التشغيل البيني المرجعية لـFHIR

**الحالة:** Proposed — يتطلب اعتماد Architecture Board والمالك السريري ومالك التكامل.
**التاريخ:** 2026-08-25
**النطاق:** توضيح معماري فقط؛ لا تغيير API أو migration أو بيانات أو قرار سريري في هذا ADR.

## السياق

يفرض الدستور الهندسي أن يكون تبادل البيانات السريرية عبر FHIR R4، بينما يمكن أن تُقرأ صياغة Platform Constitution على أنها تطلب `application/fhir+json` في كل endpoint. في RC1 توجد طبقات متداخلة: `app.fhir` كواجهة وقدرات ومراجع، و`app.national.fhir` كمحوّلات وتحقق ومصطلحات، و`routes/ehr_fhir.py` كبوابة `/fhir`، إضافةً إلى مخرجات FHIR أساسية في مسارات compliance ووظيفة بحث وطنية. هذا يخلق غموضاً في الخدمة المرجعية وفي المدى الذي ينطبق فيه content type. [1]

## القرار المقترح

> يفسر التفويض على أنه ينطبق على **التبادل السريري الخارجي أو بين الحدود النظامية**، لا على كل endpoint تشغيلي أو إداري أو صحي داخلي. يجب أن يستعمل تبادل مورد FHIR المعلن `application/fhir+json` وFHIR R4؛ ولا يغير ذلك محتوى أنواع الاستجابة الملائمة لواجهات غير FHIR.

| المجال | المالك المرجعي المقترح | القاعدة |
|---|---|---|
| واجهة التبادل السريري FHIR | `routes/ehr_fhir.py` تحت `/fhir` | نقطة دخول عامة واحدة لكل مورد أو عملية FHIR معلنة. |
| CapabilityStatement | `app.fhir._capabilities` | بيان واحد يعلن ما هو مدعوم فعلاً فقط. |
| محوّلات/تحقق/مصطلحات FHIR | `app.national.fhir` مع واجهة `app.fhir` | مكتبات داخلية؛ لا تنشئ public server موازياً. |
| مخرجات compliance FHIR الأساسية | `routes/compliance.py` | انتقالية؛ لا توسعها ولا تعلنها canonical exchange قبل خطة نقل واختبارات. |
| بحث وواجهات وطنية غير تبادلية | مساراتها القائمة | لا توسم FHIR بمجرد احتواء طلب أو نتيجة على بيانات صحية. |

## قيود السلامة

FHIR هو تمثيل وتبادل، وليس تفويضاً لقراءة شاملة أو كتابة حرة. يجب أن يبقى كل مورد مقيداً بالمصادقة والتفويض وعزل المؤسسة، وألا تكشف CapabilityStatement موردًا غير مدعوم. لا ينشئ endpoint FHIR نتيجة مختبر أو يحققها أو يطلقها متجاوزاً حارس الأمر، والتحكم بالنسخة، وعدم التكرار، والتدقيق، وآلة الحالات.

لا يعتمد هذا ADR على أن كل endpoint غير FHIR خاطئ، ولا يحول endpoint إداري إلى FHIR. ولا يسمح بالمزامنة الثنائية أو نسخ مصدر حقيقة للنتيجة أو العينة بين عدة routes.

## بدائل مرفوضة

| البديل | سبب الرفض |
|---|---|
| تحويل كل endpoint إلى FHIR content type فوراً | يكسر العقود التشغيلية ولا يضيف سلامة أو توافقاً حيث لا يوجد تبادل FHIR. |
| إنشاء FHIR server جديد مستقل | يضاعف مصدر القدرات والمحوّلات ومخاطر اختلاف tenant/audit. |
| ترك كل route يعرّف resource FHIR خاصاً به | يترك التناقض ويجعل الادعاءات غير قابلة للاختبار. |

## خطة اعتماد لاحقة

1. يعتمد الملاك هذا التفسير أو يصدرون بديلاً صريحاً.
2. ينشأ inventory لجميع public FHIR-like endpoints مع owner وresource/operation وauthorization وtenant filtering وحالة الانتقال.
3. تضاف اختبارات contract تمنع الإعلان عن مورد أو عملية غير مطبقة، وتثبت `application/fhir+json` للمسار `/fhir` فقط حيث ينطبق.
4. تخضع مخرجات compliance الانتقالية لخطة redirect/deprecation متوافقة ولا تزال متاحة حتى تنجح اختبارات المستهلكين.
5. تنفذ أية تغييرات لاحقة على فرع مستقل مع UAT تركيبية، ولا تعدل C5 أو manifest الإطلاق بقرار ذاتي.

## العواقب

يوفر القرار نقطة مرجعية قابلة للمراجعة ويمنع التوسع غير المنضبط في FHIR. لكنه لا يغلق C5 قبل الاعتماد والجرد والاختبارات والتنفيذ، ولا يزيل متطلبات CI أو staging أو Android أو mTLS أو UAT أو التوقيعات البشرية اللازمة لـGO.
