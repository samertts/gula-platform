# GULA IAM Account Foundation

**Status:** `IMPLEMENTED` for the narrow Phase 1 foundation slice; `UNVERIFIED` for production-wide rollout.

## Canonical model

GULA already contains a NIAM account model in `niam_accounts` and a separate identity model in `niam_identities`, linked through `Account.identity_id`. Phase 1 preserves that separation. `User` and `LabUser` remain legacy compatibility entities until an evidence-based mapping and rollback plan is completed.

The internal account ID is generated by the existing `IdentityBaseEntity` default. Email, phone and username are normalized before account creation, but they are not used as the immutable primary identity key. Existing database uniqueness constraints remain authoritative.

## Account lifecycle

The central lifecycle service defines legal transitions:

| Current state | Allowed next states |
|---|---|
| `pending_verification` | `active`, `deactivated` |
| `active` | `suspended`, `locked`, `disabled`, `deactivated` |
| `suspended` | `active`, `disabled` |
| `locked` | `active`, `disabled` |
| `disabled` | `deactivated` |
| `deactivated` | none |

Invalid transitions raise a hard error. No endpoint in this slice grants a user the ability to change their own security state; endpoint-level authenticated administrative authorization remains a required follow-up before exposing state-change operations broadly.

## Authentication relationship

The existing `AuthenticationService` remains the entry point. Successful login resolves an NIAM `Account`, and the access-token claims include the account UUID and identity ID. Accounts that are pending verification, suspended, disabled, deactivated or inactive are rejected with the same generic authentication failure behavior. Session creation continues to use the existing `UserSession` model and token rotation foundation.

The session creation path now relies on SQLAlchemy's internal ID default rather than passing a placeholder value. No plaintext token is added to logs or audit records by this slice.

## Verification provider architecture

`IdentityVerificationProvider` is a protocol for phone, email, official identity, OCR, NFC, professional registry and organization registry adapters. Unavailable external providers use an explicit `NotConnectedProvider` result with status `not_connected` and assurance `L0`; absence of a provider never becomes a successful verification.

The centralized assurance policy maps contact verification to `L1`, identity verification to `L2`, professional verification to `L3`, and organization verification to `L4`. `L5` is reserved for high-assurance policy and is not inferred by this slice.

## Security controls implemented in this slice

Account identifiers are normalized before creation. Passwords shorter than the existing minimum are rejected. Login uses a dummy hash for unknown identifiers and rejects non-active account states. Existing failed-attempt lockout behavior is preserved. The lifecycle state machine is deny-by-default and covered by unit tests.

## Deferred controls

Full OTP issuance and delivery, email/phone provider wiring, rate limiting, account-enumeration review across every endpoint, MFA/step-up, refresh-token reuse detection, HttpOnly cookie policy, administrative state-change authorization, migration backfill, frontend registration contract changes and mobile parity require separate tested slices. Official Iraqi identity, OCR, NFC and professional-registry integrations remain `NOT_CONNECTED` unless a real provider and integration test are supplied.

## Migration behavior

No destructive migration is included in this slice. Existing account, identity, user, lab-user, organization, facility, role and permission records are preserved. Any future backfill must first report duplicates, orphaned records, ambiguous identifiers and credential compatibility, then use an idempotent reversible mapping.

## Test evidence

The new Phase 1 unit suite covers legal activation, suspension, invalid reactivation, disabled-account protection and the explicit not-connected verification result. The suite passed with five tests. Python compilation of the modified identity services and models also passed.

## Known limitations

This document does not certify production readiness. The repository still contains multiple legacy authentication/authorization sources and the broad security requirements in IAM Phase 1 are not all closed by this narrow foundation slice. The next required work is to harden contact verification and session replay/reuse handling, add endpoint authorization tests, and validate the complete backend/frontend contract before any deployment decision.
