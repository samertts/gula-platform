## VERIFIED: an existing, evidenced GULA bootstrap pattern already solves this exact class of problem

Before proposing anything, the repository was searched for how GULA already
handles "how does the very first privileged account get created." It does,
for the legacy monolith:

- **`app/core/bootstrap/`** is a whole existing package: `config.py`
  (`BootstrapConfig.from_env()` — reads `ENABLE_BOOTSTRAP`,
  `ENABLE_NATIONAL_BOOTSTRAP`, `GULA_ADMIN_EMAIL`, `GULA_ADMIN_PASSWORD`/
  `_HASH`, and separate email configs for `ministry_admin`,
  `organization_admin`, `directorate_admin`, `lab_manager`, `auditor`,
  `security_officer`), `master_admin.py` (`ensure_master_admin()` /
  `_ensure_master_admin(db)`), `bootstrap.py` (orchestrator).
- **Idempotency**: `_ensure_master_admin` queries
  `LabUser.role == "master_admin"` first; if a row already exists, it
  returns early (optionally just linking a national-ID hash) — it **never**
  re-creates or duplicates. Keyed to "does a row for this specific role
  already exist," not "is the whole table empty" — this matters (see
  Q9/Q10 below).
- **Fail-safe skip, not fail-open**: if `GULA_ADMIN_PASSWORD` (or
  `_HASH`) is not configured, it logs an error and returns `None` —
  no account is created. Absence of configuration means absence of
  bootstrap, never a default/guessed credential.
- **Never exposed via HTTP.** It is called from
  `app/core/startup_guard.py`'s `run_startup_guard()`, in an explicit
  ordered list of **non-fatal** startup seeding steps:
  ```python
  for name, fn in [
      ("test types catalog", _run_seed_test_types),
      ("master admin", _run_ensure_master_admin),
      ("default subscriptions", _run_seed_default_subscriptions),
      ("national bootstrap", _run_national_bootstrap),
      ("audit log trigger", _run_ensure_audit_log_immutable),
  ]:
      try:
          await loop.run_in_executor(None, fn)
      except Exception as exc:
          logger.error("Seeding %s FAILED (non-fatal): %s", name, exc)
  ```
  Each step is independently try/excepted — one failing does not block
  application startup or any other step.
- **Deployment-controlled, not application-controlled.** The actual
  secret (`GULA_ADMIN_PASSWORD`) is generated by `scripts/server-setup.sh`
  at droplet provisioning time, written to `.env` (mode 600, owned by the
  deploy user), and printed to the operator's terminal **once** ("SAVE
  THESE CREDENTIALS — SHOWN ONLY ONCE"). Whoever controls the deployment
  process controls the bootstrap; there is no in-application privilege
  check involved at all, because the trust boundary is infrastructure
  access, not an API call.

**This is direct, load-bearing precedent** for "Prefer an explicit
deployment/provisioning boundary if repository evidence supports one" —
one does.

## BLOCKED (prerequisite, not the whole architecture): the sync/async engine gap

**VERIFIED, checked directly against the real (non-test) code, not
inferred from the earlier NR-044 citation alone**: `app/database.py`'s
actual `get_db()` — the same one `trust/routes.py` and every other NIAM
route imports (`from app.database import get_db`) — is a plain
**synchronous** generator (`def get_db(): db = SessionLocal(); yield db; ...`)
backed by `create_engine(...)` (sync). There is **no**
`create_async_engine` anywhere in `backend/` (grep, zero hits) and **no**
production-code `dependency_overrides` that would swap in a real async
session for NIAM routes specifically (grep, zero hits outside test
`conftest.py`, which exists precisely so tests never touch a real engine
at all).

Every NIAM route declares `db: AsyncSession = Depends(get_db)`. FastAPI
does not enforce that type hint at injection time, so this does not fail
immediately — but the moment any NIAM service actually does
`await db.execute(...)` against what is really a sync `Session`, it fails
(the exact `TypeError` NR-044 described). This is independently confirmed
here at the production-code level, not only in the test harness: **it
would reproduce against a real running deployment, not just in this test
suite.**

**Why this blocks the existing `startup_guard.py` hook specifically**: that
hook's entire non-fatal seeding list runs synchronous functions
(`_run_ensure_master_admin` etc.) via `loop.run_in_executor(None, fn)`,
each opening its own sync `SessionLocal()`. A Platform Authority bootstrap
step added to that exact list would need to call
`PlatformAuthorityService.grant(...)`, which is `async def` and requires
a real `AsyncSession` — one does not exist anywhere in this codebase to
give it. This is not a small wiring detail; it is the same
platform-wide, pre-existing gap that (per NR-044, and now re-confirmed
independently here) means **the entire NIAM async layer, including both
of Phase 6's two target routes, may not be reachable at all against a
real deployment today** — a fact that predates and is independent of this
session's authorization work, and is explicitly out of this phase's scope
to fix (no async engine is introduced by this document).

This is why Part E below states PRODUCTION DEPLOYMENT VERIFICATION
PENDING as a real, substantive caveat rather than a formality.

## PROPOSED bootstrap design (mirrors the verified pattern above)

Numbered per the directive.

### 1. WHO is allowed to create the first Platform Authority?

**PROPOSED**: whoever controls the deployment's environment configuration
and provisioning process — the same operator who already controls
`GULA_ADMIN_EMAIL`/`GULA_ADMIN_PASSWORD` via `scripts/server-setup.sh`.
Not an application role; an infrastructure-access boundary, exactly
mirroring the existing pattern.

### 2. HOW is that authority established before Platform Authority exists?

**PROPOSED**: a startup-time seed function (mirroring
`ensure_master_admin`), reading its target and capability from
environment configuration set before the process starts — never via a
runtime authorization check, because (per the whole point of bootstrap)
none can exist to check against yet.

### 3. HOW is bootstrap protected against arbitrary authenticated users?

**PROPOSED**: it is never reachable via any HTTP route (Section 7's own
constraint, already honored in Phase 10 — no route was added). An
authenticated NIAM actor, however privileged their organization role, has
no code path to it. The only "actor" is the deployment process itself.

### 4. Is bootstrap deployment-time / infrastructure-controlled / migration-controlled / manually approved / another mechanism?

**PROPOSED**: **deployment-time + infrastructure-controlled**, matching
`ensure_master_admin` exactly — not migration-controlled (Phase 9/10 both
already established migrations must never seed initial operators — Phase
9 §13 step 2, restated in the Phase 10 migration's own docstring), and not
a manually-approved in-app workflow (none exists to approve it, which is
the bootstrap problem itself).

### 5. How is the first operator identified?

**PROPOSED, with an open detail flagged as UNKNOWN rather than decided
here**: an environment variable identifying an **already-existing** NIAM
identity — e.g. `PLATFORM_AUTHORITY_BOOTSTRAP_IDENTITY_ID` (if the
operator already knows the `niam_identities.id`, from having registered
an account through the ordinary NIAM signup flow first) or
`PLATFORM_AUTHORITY_BOOTSTRAP_ACCOUNT_EMAIL` (resolved to
`Account.identity_id` at startup, mirroring how `GULA_ADMIN_EMAIL`
identifies the legacy admin). **UNKNOWN**: which of these two shapes is
better, and whether NIAM's account-creation flow is mature enough today
for an operator to reliably have a real account to point bootstrap at
before any admin UI exists — not resolved by this document, flagged as a
real open question rather than picked for convenience.

### 6. How is the bootstrap event audited?

**PROPOSED, backed by direct evidence this was anticipated**:
`app/identity/models/audit.py`'s `AuditAction` enum already declares
`bootstrap_started` and `bootstrap_completed` — defined, but (grep,
checked) **fired by nothing anywhere in this codebase today**. The
proposed bootstrap step would be the first real user of these two values,
via the same `CanonicalAuditService`/`AuditEventInput` this phase's
`PlatformAuthorityService.grant()` already uses — not a new audit
mechanism, and not bypassing the grant's own existing audit entry either
(bootstrap should still call the real `grant()` method, so both a
`bootstrap_started`/`bootstrap_completed` pair *and* the normal
`PLATFORM_AUTHORITY_GRANTED` entry `grant()` already emits would exist for
a bootstrap-issued grant — this is a feature, not double-logging: one
pair records "a bootstrap ran," the other records "a capability was
granted," which are different facts).

### 7. How is bootstrap disabled after initial provisioning?

**PROPOSED**: self-disabling by construction, mirroring
`_ensure_master_admin`'s exact idempotency shape — check whether an
assignment (active **or** historical/revoked) already exists for the
*specific* (identity, capability) pair the environment configuration
names, and skip if so. Not a separate "disable" step; the check itself is
permanent and re-evaluated (cheaply) on every restart.

### 8. Can bootstrap be repeated?

**PROPOSED**: not for a capability that has already been bootstrap-granted
once (regardless of subsequent revocation — mirrors §7). It *can*
harmlessly re-run on every application restart forever, the same way
`ensure_master_admin` does — each run is a no-op once its target state
exists.

### 9. What prevents privilege duplication?

**PROPOSED, three independent layers**: (a) the per-capability existence
check in §7; (b) `PlatformAuthorityService.grant()`'s own existing
idempotent-if-already-active behavior (built in Phase 10, unchanged here);
(c) the real, Postgres-verified partial unique index
(`uq_niam_platform_authority_active_capability`) — enforced at the
database level regardless of what the application layer does or fails to
check. Three layers, not one, deliberately — matching this session's own
established "defense in depth" discipline.

### 10. What happens if bootstrap partially fails?

**PROPOSED, and this is exactly why capability-scoped idempotency (§7,
matching `_ensure_master_admin`'s per-role check) matters more than a
naive "is the whole table empty" check**: if a bootstrap step grants
`platform.trust.manage` successfully but the process crashes before
reaching `platform.federation.manage`, a "table is empty" check would
never fire again (the table is no longer empty). A **per-(identity,
capability) existence check**, mirroring the verified precedent exactly,
self-heals on the next restart: `platform.trust.manage` is correctly
skipped (already granted), `platform.federation.manage` is correctly
retried (still missing). This is stated as the reason to model the check
this specific way, not left as an unstated assumption.

### 11. How is revocation performed later?

**PROPOSED**: no new mechanism — `PlatformAuthorityService.revoke()`
already exists (Phase 10) and works identically regardless of whether the
assignment being revoked came from bootstrap or a later (not-yet-built)
admin path. Whoever can run a one-off script with the same infrastructure
access bootstrap itself required can invoke it; this document does not
propose a route for it either (out of scope — Section 7 restated).

### 12. How is recovery handled if all Platform Authority assignments are revoked?

**PROPOSED, with a real gap flagged rather than hidden**: because §7's
idempotency check is scoped per-(identity, capability) and considers
historical/revoked rows as "already handled," a total lockout (every
assignment ever granted has since been revoked) would **not**
self-re-trigger bootstrap for the same identity/capability pair on
restart — bootstrap, as designed, is a true one-time-per-capability event,
not a standing recovery mechanism. **UNKNOWN / not resolved by this
document**: whether recovery from total lockout should be (a) a distinct,
differently-named recovery env var/procedure, deliberately separate from
ordinary bootstrap so it can't be casually left enabled, or (b) purely an
infrastructure-level action (direct, audited database access by whoever
already has it, exactly as privileged as bootstrap itself, with no
in-application code path at all). Both are legitimate; this document does
not choose, because neither is evidenced by an existing GULA pattern the
way ordinary bootstrap is (the legacy `master_admin` bootstrap has no
documented recovery-from-total-lockout story either, checked in this
pass — this is a gap in the existing precedent, not just in this
proposal).

## PART C — Bootstrap invariants (stated as requirements on any future implementation, not implemented here)

- Bootstrap cannot be invoked by ordinary authenticated users — enforced
  structurally by never exposing it via any route (unchanged from Phase
  10; restated as a permanent invariant, not a one-time choice).
- Bootstrap cannot grant organization RBAC — it only ever calls
  `PlatformAuthorityService.grant()`, which has no code path to
  `Membership`/`RoleAssignment` (Phase 10, unchanged).
- Bootstrap cannot create arbitrary capabilities — `grant()` already
  rejects anything outside the four `PlatformCapability` values
  (`UnknownPlatformCapability`, Phase 10, unchanged); a bootstrap step
  reusing `grant()` inherits this for free rather than needing its own
  check.
- Bootstrap can only establish the four approved capabilities — same
  basis.
- Bootstrap is auditable — §6.
- Bootstrap is idempotent — §7/§8/§10.
- Duplicate active assignments remain impossible — §9 (three layers,
  unchanged from Phase 10, not weakened by adding a bootstrap caller).
- Bootstrap has a defined completion state — "a
  `PlatformAuthorityAssignment` row exists for this (identity, capability)
  pair, active or historical" (§7).
- **Normal runtime authorization does not depend on bootstrap remaining
  enabled** — VERIFIED already true by construction:
  `require_platform_capability` (Phase 10) only ever queries
  `PlatformAuthorityAssignment` rows; it has no reference to bootstrap
  code, environment variables, or any "is bootstrap mode on" flag at all.
  Disabling/removing the bootstrap step after initial provisioning changes
  nothing about how ordinary requests are authorized.
- Revocation remains possible after bootstrap — §11.
- No client-supplied claim can bootstrap authority — the proposed
  mechanism reads only server environment configuration at process
  startup; no HTTP request body, header, or query parameter is ever
  consulted (there is no route to send one to).

prerequisite is not invented around; it is the same platform-wide,
pre-existing gap NR-044 already named, independently reproduced here
against real (non-test) code, and is out of this phase's scope to resolve.
