# نواة اشتراكات المؤسسات في GULA

**الحالة:** تصميم تنفيذ مرحلي آمن
**المالك:** GULA Platform Team
**المؤلف:** Manus AI

> **قرار معماري:** اشتراك المؤسسة التجاري، واشتراك الوصول التشغيلي الحالي (`LabSubscription`)، وفاتورة خدمة المريض ثلاثة مفاهيم منفصلة. لا يحل أي منها محل الآخر تلقائيًا، ولا يسمح لفاتورة اشتراك مؤسسة بأن تغيّر حالة تحصيل خدمة مريض أو تسوية شريك دفع.

## 1. النماذج المقترحة

| النموذج | المسؤولية | ضوابط الدقة |
| --- | --- | --- |
| `SubscriptionPlan` | إصدار تجاري غير قابل للتعديل ضمنيًا: عملة، سعر شهري/سنوي، فترة سماح وحدود استخدام وميزات | لا يتغير الإصدار بعد اعتماد الخطة؛ تنشأ خطة/إصدار جديد بدل تعديل عقد قائم |
| `PlatformSubscription` | عقد مؤسسة محدد: مختبر، خطة، مدة، تجديد، حالة | لا توجد أكثر من اشتراكات نشطة متداخلة للمختبر نفسه؛ لا ينفذ التجديد تلقائيًا في هذا الإصدار |
| `SubscriptionBillingCycle` | فاتورة اشتراك دورية مستقلة عن `PaymentInvoice` الخاصة بالمريض | قيد فريد لكل اشتراك وبداية فترة؛ التوليد idempotent ولا يستخدم float |
| `SubscriptionUsageEvent` | حدث استخدام غير قابل للتعديل بمفتاح عدم تكرار | يمنع التكرار ويحتفظ بالسبب والمرجع دون بيانات صحية حساسة |
| `SubscriptionUsageCounter` | عداد مجمع للحدود الدورية مع إصدار optimistic-lock | لا يتجاوز الحد بصمت؛ يعيد حالة مسموح/تحذير/مرفوض |
| `SubscriptionAuditEvent` | أثر تدقيق لحالة العقد والفوترة والحدود | append-only عبر ORM؛ لا تسجل أسرارًا أو بيانات طبية |

## 2. حالات العقد والفترة

```text
DRAFT → ACTIVE → PAST_DUE → SUSPENDED → CANCELLED
             │         └── Grace period ends
             └── renewal cycle: DRAFT → ISSUED → PAID | OVERDUE | VOID
```

يتطلب تفعيل خطة تجارية وموافقة استثناء أو تعليق اشتراك صلاحيات منفصلة. التجديد المتكرر يحسب فترة جديدة فقط عندما تستدعيه مهمة موثقة مستقبلًا؛ لا يوجد عامل خلفي مفعّل أو خصم تلقائي ضمن هذا التسليم.

## 3. سياسة الاستحقاق والاستخدام

تعمل الحدود وفق metric codes مثل `staff_users` و`branches` و`orders_per_day` و`ai_calls_per_day`. كل محاولة استخدام تتضمن `Idempotency-Key` أو مرجع عملية ثابتًا. يقرر المحرك ما إذا كان الحد يسمح بالفعل أو يحذر أو يرفض، ولا يغير `LabSubscription` القائم مباشرةً. يكون الربط التشغيلي لاحقًا عبر طبقة entitlement صريحة بعد اختبار كل مسار إنتاجي.

## 4. الفوترة والتحصيل

تولد الدورة فاتورة اشتراك مؤسسية منفصلة، مع مبلغ `Decimal` ثابت وعملة الخطة ونافذة استحقاق. لا تتحول إلى `PAID` لمجرد إنشاء نية دفع أو استلام طلب متصفح؛ تحتاج لاحقًا إلى حدث مزود موثق ومطابقة مبلغ/عملة/كيان وتسوية. في المرحلة الحالية يسجل النظام الفاتورة وحالتها فقط.

## 5. ما لا ينفذ هنا

لا تتضمن النواة بطاقات محفوظة أو خصمًا تلقائيًا أو مزود اشتراك حي أو webhook أو مطالبة تأمين أو تحصيل حكومي أو تحصيل دولي. تفعّل هذه الميزات لاحقًا باستخدام منسق الدفع الاستشاري بعد وجود عقد مزود ومراجعة امتثال وأمن وتسوية ناجحة.
