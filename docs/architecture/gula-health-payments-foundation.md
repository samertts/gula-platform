# تصميم GULA Health Payments Foundation

**الحالة:** تصميم وتنفيذ المرحلة التأسيسية P0
**النطاق:** من إنشاء الفاتورة حتى القيد المالي والتسوية الداخلية، دون إصدار محفظة أو تنفيذ تحويل مالي خارجي.
**المالك:** GULA Platform Team
**المؤلف:** Manus AI

> **مبدأ النطاق:** GULA في هذه المرحلة هي طبقة برمجية لإدارة دورة الفوترة والدفع والتدقيق في قطاع الصحة، وليست مزود خدمة دفع أو جهة حفظ أموال أو مصدّر محفظة. ولا يجوز تفعيل تكامل إنتاجي إلا مع شريك مرخّص ومراجعته قانونيًا وتعاقديًا.[1] [2]

## 1. الفصل المعماري

تفصل الوحدة بين **تسعير الرعاية الصحية** و**الاستحقاق/التغطية** و**الفاتورة** و**الدفع** و**التسوية**. لا يحق لمسار الدفع تغيير السعر أو التغطية، ولا تُنشئ أي واجهة `Transaction` مباشرة من طلب خدمة طبية. تبدأ الحركة دائمًا بفاتورة معتمدة، ثم `Payment Intent`، ثم محاولة دفع قابلة للتحقق، ثم قيد دفتر مستقل، وأخيرًا تسوية داخلية.

| المفهوم | مسؤوليته | ما لا يفعله |
| --- | --- | --- |
| Invoice | توثيق المبلغ المستحق وبنود الخدمة ومرجع المؤسسة | لا ينفذ دفعًا ولا يحتفظ برصيد نقدي |
| Payment Intent | طلب دفع محدد المبلغ والعملة والوجهة ومدة الصلاحية | لا يعني نجاح الدفع ولا يولد قيدًا تلقائيًا |
| Payment Attempt | توثيق طريقة الدفع ومحاولة المزوّد أو التحصيل النقدي | لا يصبح مدفوعًا عند عودة المتصفح |
| Ledger | تسجيل قيد مزدوج متوازن وغير قابل للحذف | لا يسمح بتعديل الرصيد يدويًا |
| Cash Shift | ربط عمليات النقد بالصندوق والمشغّل والوردية | لا يمنح صلاحية تعديل المبلغ المتوقع |
| Reconciliation | مقارنة السجل الداخلي مع بيانات الصندوق/المزوّد لاحقًا | لا يغيّر تاريخ المعاملة أو يزيل أثرها |

## 2. نموذج الحالة

```text
Invoice: DRAFT → ISSUED → PARTIALLY_PAID → PAID | VOID

Payment Intent: CREATED → PENDING → PROCESSING → SUCCEEDED | FAILED | EXPIRED | CANCELLED
                                                     ↓
                                                  SETTLED

Refund: REQUESTED → APPROVED → PROCESSING → SUCCEEDED | REJECTED | FAILED
```

نجاح محاولة الدفع منفصل عن التسوية؛ لذلك لا تنتقل النية إلى `SETTLED` في المرحلة التأسيسية إلا عبر عملية تسوية موثقة. وتتحقق الطبقة الخارجية مستقبلًا من توقيع الإشعار، والمرجع، والمبلغ، والعملة، والتاجر والطابع الزمني قبل تثبيت النجاح.

## 3. نموذج البيانات P0

| الجدول | الغرض | خاصية أمان أساسية |
| --- | --- | --- |
| `pay_invoices`, `pay_invoice_lines` | الفواتير وبنودها | المبلغ من البنود ولا يعدّل بعد الإصدار؛ الإلغاء لا يحذف السجل |
| `pay_payment_intents`, `pay_payment_attempts` | النية والمحاولات | مفتاح idempotency فريد ضمن المؤسسة، ومراجع مزود فريدة إن وجدت |
| `pay_ledger_accounts`, `pay_ledger_entries`, `pay_ledger_lines` | دفتر قيود مزدوج | قيد متوازن فقط؛ لا تحديث أو حذف؛ التصحيح بقيد عكسي |
| `pay_cash_shifts` | الصندوق والوردية | رصيد نهاية متوقع محسوب من القيود، والفارق يفتح حالة معالجة |
| `pay_refunds` | الاسترداد الكلي أو الجزئي | لا يتجاوز المبلغ الصافي المدفوع؛ يلزم السبب والموافق والمراجع |
| `pay_reconciliation_cases` | حالات عدم التطابق | حالات متطابقة/ناقصة/مكررة/اختلاف مبلغ/معلّقة مع سبب وإغلاق مدقق |
| `pay_audit_events` | سجل تدقيقي للتغيرات الحساسة | سجل إضافي غير قابل للحذف يضم الفاعل والمرجع والقرار والبيانات الآمنة |
| `pay_providers` | سجل مزوّدين مجرّدين | لا أسرار ولا بيانات بطاقات؛ الحالة الافتراضية `sandbox` |

## 4. واجهة مزودي الدفع

تعرّف النواة بروتوكولًا موحدًا باسم `PaymentProvider` يحوي عمليات إنشاء الدفع، التحقق، الاستعلام عن الحالة، الاسترداد، وجلب ملف التسوية. ويُضمَّن مزوّد تجريبي فقط في P0؛ لا توجد مفاتيح إنتاج ولا اتصال بشبكة مالية. تضيف P1 محولات مستقلة لمزودين مرخّصين بعد التحقق من القنوات الرسمية والعقود، لا داخل شاشات الخدمات الصحية.[2]

## 5. ضوابط إلزامية في التنفيذ

| الضابط | تطبيقه في P0 |
| --- | --- |
| عدم حفظ بيانات البطاقة الحساسة | لا حقل PAN أو CVV أو بيانات بطاقة في النماذج أو الواجهات |
| Idempotency | قبول مفتاح فريد عند إنشاء نية الدفع وإرجاع النية الأصلية عند إعادة الطلب المتطابق |
| الثبات المحاسبي | دفتر قيود متوازن ومغلق؛ الاسترداد/العكس فقط بدل الحذف أو تعديل الرصيد |
| عزل المؤسسة | جميع عمليات القراءة والتغيير مقيدة بمعرّف المؤسسة للمستخدم؛ الأدوار الوطنية فقط تستطيع الاستعلام العام عند الحاجة |
| Least privilege | نطاقات صلاحيات منفصلة لعرض، إنشاء، تحصيل نقدي، استرداد، وتسوية المدفوعات |
| موافقة الاسترداد | لا استرداد بلا سبب ومرجع، مع قابلية فصل الموافقة عن المعالجة |
| سجلات تدقيق | تسجل الإجراءات المالية الحساسة مع الفاعل ومرجع الكيان دون معلومات صحية حساسة |
| عدم الثقة بعودة العميل | لا توجد واجهة تغيّر الحالة إلى نجاح استنادًا إلى redirect أو حقل عميل فقط |

## 6. ما هو مؤجل بوضوح

تؤجل المحفظة، التحويل من شخص إلى شخص، تعبئة أو سحب رصيد، معالجة البطاقات، KYC/AML التشغيلي، ملف PCI DSS، التسوية المصرفية الفعلية، webhooks إنتاجية، وحساب الرسوم التعاقدية إلى مراحل لاحقة. لا يُقرأ التأجيل كإعفاء من المتطلبات التنظيمية؛ بل يمنع واجهة P0 من ادعاء أداء وظيفة مالية منظَّمة قبل الجاهزية.

## 7. خطة التطور

| المرحلة | الناتج | شرط البوابة |
| --- | --- | --- |
| P0 | فواتير، نوايا، نقد، دفتر، استرداد، صندوق، تسوية داخلية، تدقيق، مزوّد تجريبي | اختبارات الوحدة والتكامل والمراجعة الأمنية |
| P1 | محولات لمصارف/PSP/محافظ/QR، إشعارات موقعة، حالة التسوية | شريك مرخص، عقد، مفاتيح بيئة اختبار، مراجعة أمنية وقانونية |
| P2 | تقارير مالية، رسوم، إعفاءات، تغطية، مدفوعات مركبة وجزئية ونطاق مؤسسي أوسع | اعتماد قواعد العمل والحوكمة المالية |
| P3 | أي محفظة أو رصيد قابل للتحويل | ترخيص وتنظيم وشراكات وشهادات واختبارات تشغيلية مستقلة |

## 8. امتداد العملات الأجنبية والاقتباسات

تُضاف طبقة `Currency & FX Engine` كامتداد مستقل للنواة، لا كتحويل مالي. وهي تقوم بتخزين سعر مرجعي رسمي، وإصدار اقتباس محدد المدة، وحساب رسوم معلنة، ثم إرجاع إجمالي قابل للتدقيق. لا تنفذ أي صرف أو حوالة خارجية أو تحويل بين أرصدة؛ تلك قدرات مستقبلية مشروطة بمزود مرخص وسياسة امتثال فعالة.[3]

| الكيان | وظيفته | قيد أمان وحوكمة |
| --- | --- | --- |
| Currency Registry | تعريف ISO 4217 ووحدات الجزء العشري وسياسة التقريب | لا يقبل النظام عملة أو دقة غير معرفة مركزيًا |
| FX Rate Snapshot | لقطة لسعر منشور، المصدر، الإصدار، التوقيت، وحالة التحقق | لا تعديل على اللقطة المستخدمة في اقتباس مؤكد |
| FX Fee Policy | سياسة رسوم حسب العملة والخدمة والمزود وفترة السريان | نسبة 2% قيمة افتراضية قابلة للتهيئة، وليست سعرًا رسميًا |
| FX Quote | المبلغ الأصلي وسعر المرجع والرسوم والإجمالي وتاريخ الانتهاء | `REQUOTE_REQUIRED` عند انتهاء الصلاحية أو قدم المصدر |
| FX Audit | علاقة ثابتة بين الفاتورة/النية واللقطة والاقتباس | تعرض التفاصيل للمواطن دون إخفاء الرسوم أو ادعاء أنها سعر رسمي |

### تدفق الاقتباس

```text
Official-rate import → validation → immutable rate snapshot → quote
       → fee-policy evaluation → central rounding → user confirmation
       → Payment Intent reference
```

تستخدم كل الحسابات `Decimal` وتطبق قاعدة التقريب من الخادم فقط. وبذلك لا يختلف إجمالي الويب عن التطبيق المحمول أو نقطة البيع. يظل IQD عملة التشغيل الافتراضية في P0؛ أما الاقتباسات بعملات أخرى فهي مسجلة ومقفلة زمنيًا، ولا تسمح بإنشاء التزام أو دفع حقيقي حتى يجيز المزوّد والسياسة ذلك.

## 9. الفصل الوظيفي وحالات المخاطر

| القدرة | منفذة الآن | محجوزة لمرحلة لاحقة |
| --- | --- | --- |
| منع التكرار | مفتاح عدم التكرار، مرجع صندوق فريد، حالات عملية مقيدة | معالجة تزامن المزوّد وشبكة الدفع الحية |
| فصل المهام | مقدم طلب الاسترداد لا يوافق طلبه، وصلاحيات منفصلة | عتبات اعتماد مزدوجة وسياسة تعيين ديناميكية |
| المخاطر | سجل تدقيق، قيود على الانتقال، عزل المؤسسة، سجل حالات التسوية | قواعد velocity/device/IP، مراقبة AML/CFT، قوائم العقوبات |
| تسوية الدفع | تسوية الصندوق وحالة فرق قابلة للمراجعة | ملفات تسوية المزوّد والبنك والتطابق الآلي |
| إشعارات المزوّد | نموذج واجهة مخصص فقط | webhook موقّع + استعلام حالة + جدولة إعادة المحاولة |
| النزاعات وحماية المستهلك | بيانات التدقيق والمرجع موجودة | مركز شكاوى وSLA وسير عمل الاعتراض/chargeback |

> **قاعدة تشغيلية:** لا يغيّر أي webhook مستقبلي الحالة إلى نجاح ببيانات العميل. يجب أن يفحص محول المزوّد التوقيع والمرجع والمبلغ والعملة والتاجر والطابع الزمني، ثم يطبق عملية متكررة آمنة ويترك أثرًا تدقيقيًا.

## 10. بوابات التفعيل قبل الإنتاج

لن تُفعل خصائص العملات الأجنبية، أو محولات البطاقات/QR/المحافظ، أو KYC/AML، أو أي محفظة GULA بناءً على وجود الجداول والواجهات فقط. يلزم، قبل ذلك، شريك مرخص وعقد مراجع، سياسة إقامة بيانات ونسخ احتياطي، إدارة مفاتيح آمنة، مراجعة نموذج التهديد، اختبارات اختراق، مراقبة تشغيلية، واختبارات فشل الكهرباء والشبكة والتسوية.
