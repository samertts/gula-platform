# سياق وردية الطبيب والوصول السريري المقيّد

## الغرض

يضيف هذا التغيير طبقة مستقلة بين المصادقة والتفويض السريري. تسجيل الدخول يثبت هوية المستخدم فقط، أما الوصول السريري الموسّع فلا يُمنح إلا بعد وجود مهمة سريرية ووردية فعّالة مرتبطة بالمستخدم والمؤسسة والمنشأة والموقع والدور والغرض.

> **Authentication ≠ Duty ≠ Clinical Authorization**

التصميم **Fail-Closed**: عند غياب Duty أو انتهاء سياقه أو وجود تعارض في السياقات أو عدم تطابق النطاق، يكون القرار `DENY` ولا تُستخدم قيم العميل كمصدر نهائي للصلاحية.

## المكونات المنفذة

| المكوّن | الوظيفة |
|---|---|
| `DoctorDuty` | المهمة المجدولة، هوية الطبيب، المؤسسة، المنشأة، القسم، الجناح، الدور، الغرض، أوقات الوردية والحالة. |
| `DutyContext` | سياق تشغيل جديد لكل وردية بدأها الخادم، مع وقت انتهاء وإصدار تفويض مستقل. |
| `ShiftContext` | وقت الوردية المصدّق من الخادم والمنطقة الزمنية وحالة البدء والانتهاء. |
| `ClinicalAccessContext` | نطاق الوصول الفعلي للموارد والمرضى، مع صلاحية زمنية وإصدار يمكن إبطاله. |
| `DutyHandover` | نقل المرضى والمهام بين مهمتين متوافقتين في المؤسسة والمنشأة والموقع. |
| `DutyAuditEvent` | سجل قرارات البدء والوصول والتدقيق والتسليم وBreak-Glass دون أسرار. |
| `DutyBreakGlass` | وصول طوارئ موقت، بسبب إلزامي، مريض محدد، نطاق محدد، وانتهاء تلقائي. |
| `DutyLifecycleRegistry` | إبطال مفاتيح cache opaque واستدعاء إيقاف Speech والتنبيهات عند انتهاء السياق. |

## قواعد التفويض

يُعاد تقييم التفويض على الخادم عند كل طلب سريري، وليس عند فتح الشاشة فقط. يتطلب القرار الإيجابي تطابق المستخدم، حالة الطبيب المهنية، المؤسسة، المنشأة، القسم، الجناح، الدور، الغرض، حالة Duty، وقت الخادم، ونطاق المريض. لا يكفي أن يكون الطبيب موجوداً في المستشفى للوصول إلى جميع المرضى.

الأولوية التشغيلية لنطاق المريض هي المريض المعيّن، ثم نطاق الجناح أو القسم، ثم المنشأة، ثم نطاق الطوارئ عند وجود مهمة مناسبة. لا يسمح التنفيذ الحالي بخلط سياقين نشطين؛ وجود أكثر من سياق فعال للمستخدم يؤدي إلى `CONCURRENT_ACTIVE_DUTIES` ورفض القرار بدلاً من دمج الصلاحيات.

## انتهاء الوردية والإبطال

عند الإنهاء أو السحب أو الانتهاء الزمني، يُغلق `DutyContext`، ويُعطّل `ClinicalAccessContext`، وتُزاد نسخة التفويض، ويُحدّث سجل الوردية، ويُبطل cache المسجل للسياق، وتُستدعى callbacks الخاصة بإيقاف Speech والتنبيهات السريرية. لا تعتمد العملية على Logout. يوجد أيضاً `expire_due_contexts()` لتشغيل sweep خادمي دوري.

## Break-Glass

لا يُفتح Break-Glass إلا مع `emergency=true` ومريض محدد وسبب غير فارغ. الحد الأقصى للمدة 60 دقيقة. بعد إنشاء الجلسة، يسمح التقييم فقط بالوصول إلى المريض المحدد أثناء الجلسة الفعالة، مع التدقيق والمدة المنتهية؛ ولا تتحول الجلسة إلى صلاحية دائمة.

## API

| المسار | الوظيفة |
|---|---|
| `POST /doctor-duty/{duty_id}/start` | بدء Duty معيّن من الخادم. |
| `POST /doctor-duty/{context_id}/end` | إنهاء السياق وإبطال الوصول الموسّع. |
| `POST /doctor-duty/authorize` | تقييم طلب سريري عند التنفيذ. |
| `POST /doctor-duty/break-glass` | فتح وصول طوارئ موقت بسبب إلزامي. |
| `POST /doctor-duty/{duty_id}/handover` | بدء تسليم المرضى والمهام. |
| `POST /doctor-duty/handover/{handover_id}/confirm` | تأكيد التسليم وإنهاء وصول الطبيب الخارج. |

تعيد المسارات بيانات السياق التشغيلي الضرورية فقط، ولا تعرض الرقم الوطني الخام أو حمولة سريرية كاملة.

## الترحيل والاختبارات

أضيفت migration `20260818_0033` وهي متوافقة مع توليد SQL offline في PostgreSQL. الـdowngrade غير المتصل يولد SQL، بينما يمنع التنفيذ online destructive rollback وفق سياسة الاحتفاظ بالبيانات.

تشمل الاختبارات الحالية عدم وجود Duty، انتهاء Duty، اختلاف المنشأة والقسم والجناح، المريض غير المعيّن، التعدد المؤسسي، رفض mutation بعد الانتهاء، وإبطال cache والقنوات عند revocation. اختبارات الاتصال الفعلي بـPostgreSQL وRedis، واختبارات الأجهزة والواجهة وSpeech الحقيقي، واختبار تكامل NID، يجب تنفيذها في Staging محمي قبل أي تفعيل إنتاجي.

## حالة القبول الحالية

| المجال | الحالة الحالية |
|---|---|
| Duty Authorization | PASS — اختبارات وحدات وقرار server-side fail-closed. |
| Shift Expiration | PASS جزئياً — lifecycle وsweep منفذان؛ يحتاجان جدولة Staging فعلية. |
| Reactivation | PASS تصميمياً — كل Start ينشئ context جديداً؛ يحتاج اختبار تكامل قاعدة البيانات. |
| Patient Scope | PASS جزئياً — scope للمريض والموقع منفذ؛ يلزم ربط كل clinical mutation فعلياً بالخدمة. |
| Handover | PASS جزئياً — workflow منفذ؛ يلزم تحقق تكامل المهام واللوحة السريرية. |
| Cache Invalidation | PASS — registry opaque keys وcallbacks منفذة؛ يجب تسجيل جميع cache producers. |
| Audit | PASS جزئياً — أحداث Duty والوصول وBreak-Glass موجودة؛ يلزم مراجعة retention وimmutability في Staging. |
| Offline Security | BLOCKED — يتطلب ربط dataset المشفر بسياسة Duty وsync/conflict الموجودة واختبار جهاز فعلي. |
| Emergency Access | PASS جزئياً — جلسة موقتة وسبب وتدقيق منفذة؛ يلزم مراجعة مستقلة للسياسة التشغيلية. |
| Cross-tenant Isolation | PASS جزئياً — فحص المؤسسة والمنشأة في الخدمة؛ يلزم اختبارات PostgreSQL RLS/tenant middleware. |
| Clinical Mutation Authorization | PASS جزئياً — الأوامر السريرية وملاحظات السجل مربوطة بـDuty guard؛ تبقى مسارات سريرية أخرى بحاجة إلى حصر وربط في Staging. |

## الإغلاق المحلي المضاف

أضيف Guard مشترك في `app.security.clinical_duty_guard`، وتم تطبيقه على عمليات إنشاء وإلغاء وإكمال الأوامر السريرية، وعلى إنشاء SOAP وProgress وNursing وConsultation وOperation وEmergency notes. يتطلب كل mutation ترويسة `X-Duty-Context-ID`، ويتحقق الخادم من ملكية السياق وحالته ووقت انتهائه ونطاق المريض قبل أي كتابة. المعرّفات الصحية المؤقتة غير القابلة للتحقق رقمياً تُرفض بدلاً من تخطي scope.

لم تُطبق السياسة على مسارات إدارة المصطلحات أو المعرفة العامة لأنها ليست عمليات patient-record mutation؛ أما بقية المسارات السريرية غير المفحوصة فتظل ضمن قائمة Staging حتى تُربط بعقد patient/facility واضح دون تخمين.

## قيود السلامة

لم تُنفذ migration على قاعدة إنتاج، ولم تُمنح صلاحيات حقيقية تلقائياً، ولم يبدأ P5، ولم يحدث deployment أو merge. الحالة الصحيحة بعد هذه المرحلة هي `DOCTOR_DUTY_PARTIAL` إلى حين إكمال تكامل جميع مسارات clinical mutation وoffline والاختبارات الخارجية.
