# برنامج GULA للمنصة الصحية الوطنية

**الحالة:** خارطة تنفيذ مرجعية محدثة
**المالك:** GULA Platform Team
**المؤلف:** Manus AI

> **قرار النطاق:** الرؤية الكاملة تمثل برنامجًا وطنيًا متعدد السنوات، وليست دفعة تطوير واحدة. يظل التنفيذ الحالي مركزًا على الأسس الموجودة بالفعل، وعلى نواة الدفع والفوترة والعملات بوصفها خدمة مستقلة قابلة لإعادة الاستخدام؛ ولا يتحول وجود نموذج أو واجهة إلى خدمة مالية أو حكومية مفعلة.

## 1. مبادئ لا تتغير

تُنظَّم المنصة حول هوية واحدة، ومؤسسة ومساحة عمل وسياق وصول، ثم خدمات صحية، فالفوترة والاستحقاق، ثم الدفع والتسوية والتدقيق. لا يرتبط أي تطبيق أو واجهة مباشرة بمزود دفع أو سجل مالي أو هوية حكومية؛ تتكامل جميعها من خلال واجهات خدمة موثقة ومحكومة بالصلاحيات.

| المبدأ | تطبيقه المعماري | نتيجة إلزامية |
| --- | --- | --- |
| حساب GULA واحد | هوية أساسية وWorkspaces متعددة | لا حسابات مكررة للشخص نفسه بحسب الدور |
| RBAC + ABAC + سياق | المؤسسة، المورد، الغرض، الوقت، والطوارئ تكمل الدور | الدور وحده لا يمنح قراءة كل البيانات |
| عزل المجال | الهوية، الصحة، الفوترة، الدفع، FX، والتدقيق وحدات مستقلة | لا منطق محفظة في واجهة المواطن أو مسار خدمة MRI |
| Failure-first | حالات `PENDING` و`UNKNOWN` والتكرار والارتداد والمعالجة اللاحقة | لا فقد صامت للبيانات ولا وصف "فشل" قبل تحقق موثوق |
| سجل مصدر الحقيقة | قيود مزدوجة غير قابلة للحذف وسجل تدقيق | الرصيد إسقاط للقيود وليس قيمة تُعدّل يدويًا |
| مزود محايد | محولات معزولة لمزودي الحكومة والدفع | لا ارتباط بنيوي بمزود واحد ولا أسرار في الواجهة |
| الخصوصية افتراضيًا | تقليل البيانات، إخفاء الحقول، مبرر الوصول، سجل المواطن | لا تسريب تشخيص أو نتيجة ضمن إيصال أو لوحة مالية |

## 2. تصنيف المتطلبات حسب الأولوية

| الشريحة | النطاق | الحالة في هذا التسليم |
| --- | --- | --- |
| A — أساس تشغيلي | هوية، مؤسسات، Workspaces، تفويض، تدقيق، API versioning، correlation IDs، feature flags، kill switches | تُراجع مع المكونات الموجودة؛ تُوثق متطلبات الدمج الناقصة |
| B — نطاقات الرعاية | المواطن، المختبر، المستشفى، الصيدلية، الأشعة، المواعيد، الطوابير، النتائج | موجودة كمجالات منفصلة في المستودع؛ لا يعاد بناؤها ضمن هذا التغيير |
| C — تجربة موحّدة | تعدد اللغات، RTL/LTR، إمكانية الوصول، بحث مراعي للصلاحيات، Offline + Sync | خارطة UX/العمل غير المتصل موثقة؛ كل تطبيق ينفذها تدريجيًا |
| D — النواة المالية | التسعير، الاستحقاق، الفوترة، النقد، النية، القيود، الاسترداد، التسوية، التدقيق | **تنفيذ P0 داخل الخلفية** |
| E — المدفوعات الخارجية | محولات PSP/مصارف/QR/محافظ، webhooks موقعة، استعلام الحالة، failover | عقود ومحاذير فقط؛ لا مزود إنتاجي ولا أسرار |
| F — العملات وFX | سجل العملات، لقطات السعر، الاقتباسات، الرسوم، الدفاتر متعددة العملات | **تنفيذ وضع غير إنتاجي**؛ لا صرف ولا حوالة خارجية |
| G — الحوكمة المالية | KYC، AML/CFT، مكافحة الاحتيال، الاعتراضات، حماية المستهلك، الإقامة المحلية للبيانات | تصاميم وواجهات تمدد فقط؛ تتطلب برامج امتثال وتشغيل مستقلة |
| H — التوسع الوطني | البيانات الإحصائية، المحافظات، HA، DR، تحليلات غير كاشفة | خطة مرحلة لاحقة بعد تجارب تشغيلية وقياس موثوق |

## 3. خارطة مراحل مع بوابات قرار

| المرحلة | الناتج القابل للقياس | بوابة الخروج |
| --- | --- | --- |
| 0 — Reality Audit | جرد المكونات، المخاطر، التكرار، وملكية البيانات | توثيق مصدر الحقيقة لكل مجال |
| 1 — Architecture & Zero Drift | عقود APIs، مخطط نطاقات، حدود ملكية البيانات، migrations | لا واجهة تعتمد مسارًا داخليًا غير موثق |
| 2 — Identity & Authorization | Workspace context، RBAC/ABAC، MFA، sessions، audit | اختبارات عزل المؤسسة والصلاحيات الحساسة |
| 3–6 — Health Experience | أساس المجالات الصحية وتجربة المواطن وWorkspaces وOffline | pilot محدود دون بيانات مالية خارجية |
| 7 — Financial & Billing | Invoice، cash shift، payment intent، ledger، refunds، reconciliation | اختبارات تكرار/انقطاع/تسوية وتدقيق |
| 8 — Payment Orchestration | adapters، webhook verification، status polling، provider registry | شريك مرخص وبيئة اختبار ومراجعة أمنية وقانونية |
| 9 — Multi-Currency & FX | snapshots، quotes، policies، rounding، ledgers by currency | سياسة عملة ورسوم مصادق عليها ومصدر أسعار رسمي موثق |
| 10–12 — Compliance & Resilience | ضوابط أمن، موبايل/سطح مكتب، chaos/DR، مراقبة | اختبارات استعادة ومراجعة اختراق وRPO/RTO متفق عليهما |
| 13–15 — Pilot to National | pilot، توسع محافظة، إنتاج وطني | قياس نجاح، حوكمة، تمويل، وعمليات 24/7 |

## 4. قواعد الأمان التشغيلية

> **قاعدة الدفع:** نجاح الدفع لا يساوي نجاح التسوية.
> **قاعدة FX:** السعر المرجعي الموثق + رسوم مفصّلة + اقتباس ثابت + تاريخ + تدقيق.
> **قاعدة المحفظة:** لا محفظة أو رصيد قابل للتحويل قبل الترخيص؛ الدفتر هو مصدر الحقيقة عند وجوده.
> **قاعدة الحالة المجهولة:** عند فقد التحقق لا تعلن الفشل ولا تعاود الخصم؛ تسجّل `UNKNOWN` وتُستكمل بالتحقق والتسوية.

| عنصر مرن | السلوك المقرر |
| --- | --- |
| Kill switch | تعطيل مزود أو قدرة بميزة مهيأة دون إيقاف المنصة |
| Circuit breaker | إيقاف إرسال الطلبات مؤقتًا إلى مسار فاشل وتسجيل سبب واضح |
| Dead-letter & replay | عدم فقد الحدث الفاشل، مع إعادة تشغيل متكررة آمنة |
| Correlation ID | ربط الواجهة، API، الحدث، السجل، والمزوّد الخارجي دون كشف بيانات حساسة |
| Configuration as data | سياسات الرسوم والحدود والصلاحيات صالحة للإصدار والتدقيق؛ لا أرقام عمل داخل الكود |
| Human override | حالة استثنائية مضبوطة بصلاحية ومبرر وموافقة وتدقيق، لا تعديل صامت |

## 5. ما لا يفعله هذا التسليم

لا ينشئ محفظة GULA، ولا يحفظ أموالًا، ولا يقدّم سعر صرف، ولا يرسل حوالة، ولا ينجز KYC/AML/CFT، ولا يتصل بمزود دفع أو بنك أو جهة حكومية. هذه الوظائف تتطلب تراخيص أو شركاء أو ضوابط تشغيل وأمن واختبارات إنتاجية منفصلة.

## 6. مراجع التصميم التنظيمية

يعتمد توجيه الدفع والعملات في النواة على توثيق البنك المركزي العراقي للإطار القانوني للدفع، والمؤسسات المعتمدة للتحصيل، وأسعار الصرف المنشورة؛ انظر [ملاحظات البحث التنظيمي](../payments-regulatory-research.md).
