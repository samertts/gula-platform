# نموذج سجل المواطن ومساحات العمل المهنية في GULA

## الغرض والقرار المعماري

يعرض GULA للمستخدم **واجهة موحدة لفهم هويته ومساحاته المصرح بها**، لكنه لا ينشئ مخزناً موحداً يجمع كل ما يتعلق بالمواطن في سجل واحد. هذا الفصل مقصود لحماية الخصوصية وتقليل نطاق الوصول ومنع انتقال الصلاحيات بين السياقات. لذلك فإن عبارة «سجل المواطن» في تجربة المستخدم تعني **ملخصاً موجهاً للغرض**، لا نسخة كاملة من السجل الوطني أو السجل الصحي أو ملفات المؤسسات.

> **قاعدة حاكمة:** الواجهة تعرض ما أعاده الخادم في العقد المصرح به، ولا تنشئ هوية وطنية أو تحققاً مهنياً أو عضوية أو تفويضاً من حالة محلية أو من قيمة role في المتصفح.

صفحة الملخص الجديدة هي `/my-record`. أما `/citizen` فتبقى مساحة المواطن الصحية المنفصلة، وتظل قراءاتها محصورة في مسارات `GET /citizen-platform/me/*` المعتمدة وعلاقة `CitizenRelationship` النشطة والمحددة النطاق. ولا يعني امتلاك مساحة مهنية أن صاحبها يستطيع قراءة السجل الصحي لمواطن آخر.

## طبقات النموذج

يفصل النموذج بين الكيانات التالية. قد ترتبط ببعضها عبر معرفات داخلية، لكنها لا تُدمج في بطاقة أو صلاحية واحدة لمجرد أن الشخص نفسه يظهر في أكثر من سياق.

| الطبقة | ما تمثله | مصدر الحقيقة | ما تعرضه `/my-record` | ما لا تمنحه تلقائياً |
|---|---|---|---|---|
| **Account / Identity** | الحساب الإنساني والجلسة الأساسية | جلسة GULA وعقد المصادقة | ملخص الاسم والبريد وحالة التحقق العامة | لا تمنح ملكية بيانات وطنية أو صحية |
| **VerificationRecord** | دليل تحقق، ومنه دليل مهني | خدمة الهوية والتحقق الخادمية | مؤشرات سياقية غير حساسة عند إعادتها ضمن العقد | لا ينشئ دوراً مهنياً بمجرد الاستيراد |
| **CitizenRelationship** | علاقة صريحة بين الحساب وسجل المواطن أو المريض مع نطاق وصلاحية وحالة | خدمة علاقات الهوية | لا تعرض تفاصيل صحية خاماً | لا تفترض أن كل حساب يملك كل سجلات المواطنين |
| **Citizen workspace** | مساحة شخصية للمواطن | خدمة NIAM بعد أهلية الحساب والعلاقة | نوع المساحة وحالتها وكونها شخصية | لا توسع الوصول إلى سجل مواطن آخر |
| **Professional workspace** | سياق مهني مؤهل، مثل الطبيب أو الصيدلي أو المختبر | تحقق مهني صالح ثم workspace وmembership | نوع المهني والوصف الوظيفي الآمن والعضوية العامة | لا يسمح بقراءة صحة مواطن دون علاقة أو سياق سريري مفوض |
| **Membership / Role** | عضوية داخل مؤسسة أو منشأة أو قسم وصلاحياتها | NIAM وتفويض الخادم | وصف المساحة وحالتها فقط | لا يستبدل التحقق المهني ولا يتجاوز النطاق المؤسسي |
| **Health record** | بيانات المواعيد والأدوية والنتائج والملخص الصحي | مسارات المواطن الصحية أو السياق السريري المصرح | لا تُنسخ إلى `/my-record` | لا تُعرض من خلال بطاقة الهوية العامة |

## تجربة المستخدم المنفذة

توجد صفحة `MyRecordPage` داخل shell المصادق في `frontend-v3`. وهي محمية بسياسة دور مركزية تسمح فقط بالأدوار المعروفة في عقد الواجهة الحالية، ولا تضيف صلاحية تشغيلية أو سريرية جديدة. عند الجلسة الحية تستدعي الصفحة `apiClient.listWorkspaces()` الذي يقرأ `GET /niam/workspaces`، ثم تعرض فقط الحقول الآمنة التي أعادها الخادم، مثل نوع المساحة والحالة والعضوية المهنية العامة.

تبديل السياق لا يتم بحالة React محلية. زر التبديل يستدعي `apiClient.switchWorkspace(workspaceId)`، أي `POST /niam/workspaces/{id}/switch`، ثم ينتقل إلى dashboard بعد نجاح الخادم. في حال الرفض أو انتهاء العضوية تعرض الصفحة رسالة فشل ولا تنشئ fallback محلياً ولا تغيّر role أو صلاحية في المتصفح.

| الحالة | السلوك المقصود |
|---|---|
| جلسة حية وقائمة مساحات ناجحة | عرض المساحات التي أعادها الخادم فقط |
| جلسة حية بلا مساحات | عرض حالة فارغة آمنة؛ لا إنشاء مساحة مهنية من الواجهة |
| خطأ من الخادم | عرض خطأ وإتاحة إعادة المحاولة؛ لا بيانات بديلة مختلقة |
| مساحة مهنية متحقق منها | عرضها فقط إذا أعاد الخادم `professional_type` ضمن workspace مؤهل |
| وضع Demo | عرض بطاقة اصطناعية للقراءة فقط؛ لا استدعاء `/niam/workspaces` ولا بيانات مؤسسة حقيقية |
| تبديل سياق مرفوض | إبقاء السياق الحالي وإظهار سبب عام دون كشف تفاصيل أمنية |

## الحدود بين السجل العام والسجل الصحي

السجل العام في `/my-record` هو **سجل حساب وسياقات وصول**. وهو لا يكرر البيانات التي تقدمها `CitizenWorkspacePage` في `/citizen`. تبقى بيانات المواعيد والأدوية والنتائج والملخص الصحي في المسارات الصحية الخاصة بالمواطن، حيث يتحقق الخادم من `CitizenRelationship` النشطة ونطاقها. لا يجوز إضافة قراءة صحية إلى `/my-record` لمجرد رغبة UX في جمع كل شيء.

كما أن `/citizen` ليس مدخلاً عاماً لمهنيي الصحة. إذا كان الطبيب أو الصيدلي يملك حساباً شخصياً للمواطن، فيجب أن يكون ذلك سياق مواطن مستقلاً ومؤهلاً خادمياً؛ أما workspace المهني فلا يتحول تلقائياً إلى citizen workspace ولا يفتح سجل مريض.

> **شرط الوصول الصحي:** امتلاك الحساب أو workspace مهني أو role في الواجهة لا يكفي. يلزم سياق خادمي صحيح وعلاقة أو تفويض سريري محدد النطاق، مع تدقيق لكل عملية حساسة.

## منع الإنشاء أو الترقية التلقائية

لا تنشئ بيانات النقابة أو الوزارة حساباً أو role أو workspace مهنياً بصورة آلية. يمكن استقبال سجلات خارجية في طبقة العزل الموصوفة في [توثيق الاستقبال الخارجي](security/external-ingestion-dmz-staging-ar.md)، لكن نتيجة المطابقة لا تصبح تفويضاً بذاتها. يجب أن تمر الحالات الملتبسة أو المتعارضة بالمراجعة البشرية، وأن ينتج عن التحقق الخادمي `VerificationRecord` صالح وغير منتهٍ قبل إتاحة workspace مهني.

يظل إنشاء العضوية المهنية وتعيين الصلاحيات عملية منفصلة، مرتبطة بالمؤسسة والنطاق والمدة والحالة والإصدار. ويجب أن تفشل العملية مغلقاً عند غياب الدليل أو تضارب المعرفات الصلبة، مع تسجيل محاولة الرفض في سجل التدقيق. لا يمكن لـ frontend تعديل هذه الشروط أو اختصارها.

| قرار | النتيجة |
|---|---|
| اسم المستخدم أو role المحلي يقول «doctor» | لا ينشئ إثباتاً مهنياً ولا عضوية |
| سجل خارجي يطابق بإشارة ضعيفة | يبقى للمراجعة، ولا يحدث auto-match |
| تعارض في national ID أو license | حالة conflict/review، ولا ترقية تلقائية |
| `VerificationRecord` مهني موثق ونشط وغير منتهٍ | يصبح إنشاء workspace المهني ممكناً وفق سياسة الخادم |
| workspace مهني موجود بلا علاقة مواطن | لا يفتح بيانات المواطن الصحية |

## ما تم تسليمه في هذا التغيير

تمت إضافة صفحة الملخص، وربطها بالمسار المحمي والـ lazy loading وprefetch، وإضافتها إلى التنقل المركزي وسطح الهاتف مع الإبقاء على `/citizen` منفصلاً. أضيفت اختبارات تثبت أن وضع Demo اصطناعي ولا يطلب المساحات الحية، وأن الحالة الحية تعرض فقط المساحات المعادة من الخادم، وأن التبديل يمر عبر عميل API، وأن صفحة السجل لا تعرض معرفات وطنية أو صحية خاماً. كما أضيف فحص axe آلي للـ live shell.

| الملف أو العقد | الحالة |
|---|---|
| `frontend-v3/src/pages/my-record/MyRecordPage.tsx` | منفذ: ملخص الهوية والمساحات دون سجل شامل |
| `frontend-v3/src/pages/my-record/MyRecordPage.test.tsx` | منفذ: Demo/live/switch/accessibility |
| `frontend-v3/src/routes/index.tsx` | منفذ: route محمي عبر `RoleGuard` |
| `frontend-v3/src/permissions/routePolicies.ts` | منفذ: سياسة `/my-record` مركزية |
| `frontend-v3/src/permissions/index.ts` | منفذ: رابط التنقل المركزي |
| `frontend-v3/src/components/navigation/MobileBottomNav.tsx` | منفذ: اختصار محمول لا يخفي `/citizen` الصحي |
| `frontend-v3/src/routes/prefetch.ts` | منفذ: تحميل كود فقط دون API |
| `backend/app/identity/*` و`/niam/workspaces` | موجود مسبقاً: مصدر الأهلية الخادمي |

## ما يحتاج إلى backend أو قرار حوكمة لاحقاً

لا يتضمن هذا التغيير endpoint جديداً لتجميع السجل ولا يطبق استيراداً حقيقياً لبيانات الدولة. إذا تقرر مستقبلاً عرض ملخص تحقق أو حالة علاقة داخل صفحة السجل، فيجب أولاً تعريف OpenAPI ومالك البيانات وحقول الحد الأدنى وسياسة الاحتفاظ وسجل التدقيق واختبارات tenant isolation. الخيار الآمن هو عقد ملخص محدود يعيد معرفات داخلية وحالات تحقق ووصف مساحات، من دون national ID أو رقم ترخيص خام أو بيانات سريرية.

كذلك لا تزال جاهزية PostgreSQL واسع النطاق، rehearsals للنسخ الاحتياطي والاستعادة، إعداد DMZ الفعلي، الموافقات القانونية والتنظيمية، وربط الجهات الخارجية مسؤوليات مستقلة. الوثائق الموجودة تصف التصميم والمتطلبات ولا تعني أن تلك البنية شُغلت في الإنتاج أو أن المنصة حصلت على اعتماد قانوني عراقي.

## معايير القبول الأمنية

يُقبل هذا السطح عندما يبقى backend هو مصدر القرار النهائي، وتكون كل قراءة صحية أو عملية تبديل سياق ضمن عقد ومجال واضحين، ولا يستطيع Demo الوصول إلى live data، ولا تنشئ الواجهة دوراً أو عضوية، ولا تكشف الصفحة معرفات حساسة. يجب إعادة تشغيل typecheck والاختبارات والبناء وفحص الفروقات قبل كل commit، كما يجب إبقاء التغيير على branch وPR منفصلين إلى أن تكتمل المراجعة.
