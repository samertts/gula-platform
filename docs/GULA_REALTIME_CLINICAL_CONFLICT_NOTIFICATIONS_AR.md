# تصميم الإشعارات الفورية للتعارضات السريرية في GULA

## 1. الهدف

تهدف هذه الآلية إلى تنبيه الطبيب أو المسؤول السريري بوجود تعارض قد يؤثر في سلامة المريض، مع ضمان أن الإشعار ليس مجرد رسالة عابرة، بل **مهمة قابلة للتتبع والإقرار والتصعيد**.

لا يجب أن يحمل الإشعار تفاصيل سريرية حساسة كاملة، ولا أن يمنح صلاحية حل التعارض. وظيفته هي توجيه الشخص المخول إلى سجل آمن داخل GULA، حيث تُطبق الصلاحيات والتحقق من النسخة وآلة الحالات.

> الإشعار لا يعتمد القرار السريري ولا يحل التعارض؛ هو يفتح مسار التدخل ويثبت أن النظام حاول إيصال التنبيه.

## 2. متى يُنشأ الإشعار؟

ينشأ الإشعار بعد حفظ التعارض ومعرّف التدقيق داخل معاملة ناجحة، وليس قبلها. إذا فشلت معاملة التعارض، لا يجوز إرسال تنبيه يوحي بوجود تعارض غير محفوظ.

```text
تعارض نسخة/حالة
      ↓
حفظ conflict + audit داخل ACID transaction
      ↓
نشر ClinicalConflictCreated event عبر Outbox
      ↓
تقييم الخطورة والمستلمين
      ↓
إرسال الإشعار عبر القنوات المناسبة
      ↓
تسجيل delivered / failed / acknowledged
```

يُستخدم Outbox حتى لا يؤدي تعطل WebSocket أو خدمة الإشعارات إلى فقدان الحدث السريري.

## 3. تصنيف الخطورة

| المستوى | أمثلة | المستلم الأول | زمن الإقرار المستهدف | التصعيد |
|---|---|---|---:|---|
| `P0_CRITICAL` | تعارض في حالة حرجة، خفض أولوية طوارئ، تعارض جرعة دوائية أو نتيجة حرجة | الطبيب المناوب وفريق الطوارئ | 60 ثانية | تصعيد تلقائي إلى قائد النوبة ثم غرفة القيادة |
| `P1_URGENT` | تعارض قبول أو نقل أو سرير لمريض غير مستقر، اختلاف فرز عاجل | الطبيب المسؤول أو منسق القسم | 5 دقائق | تصعيد بعد انتهاء المهلة |
| `P2_HIGH` | تعارض في خطة علاج أو ملاحظة سريرية مؤثرة دون علامة حرجة | الفريق المعالج | 30 دقيقة | تذكير ثم مدير القسم |
| `P3_ROUTINE` | تعارض إداري أو تحديث غير سريري | مسؤول السجل أو الإدارة | يوم عمل | قائمة عمل فقط |

لا تُستنتج الخطورة من نص حر أو من الجهاز. تُحسب من قواعد معتمدة تعتمد على نوع المورد، حالة Patient Flow، أولوية المريض، نوع العملية، وصلاحية المستخدم.

## 4. قواعد المستلمين

يجب تحديد المستلمين من الخادم عبر **RBAC + سياق المؤسسة + المناوبة الحالية + علاقة المستخدم بالمريض**. لا يرسل العميل قائمة مستلمين موثوقة.

| القاعدة | التطبيق |
|---|---|
| نطاق المؤسسة | لا يصل التنبيه إلا إلى مستخدمين في `hospital_id` و`lab_id` المناسبين. |
| الدور | لا يكفي كون المستخدم طبيبًا؛ يجب أن يملك صلاحية حل نوع التعارض. |
| المناوبة | يفضل المستلم المناوب حاليًا بدل إرسال جميع الأطباء. |
| علاقة الرعاية | يضاف الطبيب أو الفريق المكلف بالمريض عند وجود علاقة موثقة. |
| التغطية | يضاف البديل عند غياب المستلم أو عدم إقراره. |
| تقليل البيانات | يحتوي الإشعار على رقم تعارض ومؤشر عام، وليس تشخيصًا أو تفاصيل كاملة. |
| منع التضارب | لا يُرسل التنبيه إلى مستخدم لا يحق له رؤية السجل حتى لو كان ضمن المؤسسة. |

## 5. قنوات الإشعار

لا تعتمد الحالات الحرجة على قناة واحدة:

| القناة | الاستخدام | ملاحظات |
|---|---|---|
| WebSocket | إشعار فوري داخل تطبيق GULA | يحتاج اتصالًا حيًا وheartbeat وإعادة اتصال. |
| Server-Sent Events | بديل بسيط لبث الإشعارات من الخادم للمتصفح | مناسب للإشعارات أحادية الاتجاه. |
| In-app task | قائمة مهام غير مقروءة | مصدر الحقيقة المستمر حتى بعد إغلاق الصفحة. |
| Push Notification | تنبيه جهاز مُدار | يجب ألا يحتوي بيانات سريرية كاملة. |
| صوت/مرئي داخل القسم | P0 عند وجود محطة عمل مفتوحة | يحتاج سياسة محلية لمنع الإزعاج والتكرار. |
| SMS أو اتصال خارجي | آخر بديل وفق سياسة حكومية | لا يرسل تفاصيل صحية؛ يرسل طلب دخول آمن أو رقم مهمة. |

بالنسبة إلى GULA، الترتيب المقترح هو **Outbox + Broker داخلي + WebSocket/SSE + In-app task**، مع Push للجهاز المُدار للحالات P0 إذا سمحت سياسة المؤسسة.

```json
{
  "event_id": "evt_01J...",
  "event_type": "clinical.conflict.created",
  "aggregate_type": "SyncConflict",
  "aggregate_id": "conf_01J...",
  "operation_id": "op_01J...",
  "hospital_id": 7,
  "lab_id": 12,
  "severity": "P0_CRITICAL",
  "resource_type": "Encounter",
  "resource_id": "enc_01J...",
  "patient_reference": "pat_ref_opaque_01J...",
  "reason_code": "STALE_CRITICAL_TRIAGE",
```

لا يضع الحدث اسم المريض أو التشخيص أو قيم النتائج في قناة البث. يفتح المستخدم صفحة محمية بعد التحقق من الجلسة والصلاحية.

## 7. مسارات API

### 7.1 فتح قناة الإشعارات

```http
GET /api/v1/notifications/stream
Cookie: access_token=...
X-Device-ID: ER-TABLET-02
Accept: text/event-stream
```

أو عبر WebSocket:

```text
wss://api.gula-platform.org/api/v1/notifications/ws
```

يجب أن يرسل الخادم heartbeat دوريًا، وأن يعيد العميل الاتصال بتأخير تدريجي. عند إعادة الاتصال يرسل العميل `last_event_id` لاسترجاع الأحداث الفائتة من قائمة المهام، لا من الذاكرة المؤقتة للقناة فقط.

### 7.2 قراءة قائمة التنبيهات والمهام

```http
GET /api/v1/notifications?status=unread&severity=P0_CRITICAL&limit=50
```

الاستجابة:

```json
{
  "items": [
    {
      "notification_id": "ntf_01J...",
      "event_id": "evt_01J...",
      "severity": "P0_CRITICAL",
      "title": "تعارض سريري يتطلب تدخلاً عاجلاً",
      "message": "يوجد تعارض في أولوية حالة طوارئ.",
      "conflict_id": "conf_01J...",
      "resource_type": "Encounter",
      "resource_id": "enc_01J...",
      "requires_ack": true,
      "status": "delivered",
      "created_at": "2026-08-17T14:32:02Z",
      "expires_at": "2026-08-17T15:32:02Z"
    }
  ],
  "unread_count": 3,
  "critical_unacknowledged_count": 1
}
```

### 7.3 الإقرار بالاستلام

الإقرار بالاستلام لا يعني حل التعارض:

```http
POST /api/v1/notifications/{notification_id}:acknowledge
Idempotency-Key: ack_01J...
```

```json
{
  "acknowledged_at": "2026-08-17T14:32:18Z",
  "ack_channel": "web",
  "note": "بدأت مراجعة التعارض"
}
```

الاستجابة:

```json
{
  "notification_id": "ntf_01J...",
  "status": "acknowledged",
  "acknowledged_by": 42,
  "acknowledged_at": "2026-08-17T14:32:18Z",
  "conflict_status": "pending_review"
}
```

### 7.4 بدء معالجة التعارض

```http
POST /api/v1/clinical-conflicts/{conflict_id}:claim
If-Match: "conflict-conf_01J-v2"
```

```json
{
  "claim_reason": "ON_CALL_CLINICIAN_REVIEW"
}
```

الغرض من claim هو تقليل عمل عدة أشخاص على التعارض نفسه. لكنه لا يمنع مسؤولًا أعلى من التدخل عند التصعيد، ولا يستبدل `expected_entity_version` عند الحل.

### 7.5 حل التعارض

```http
POST /api/v1/clinical-conflicts/{conflict_id}:resolve
If-Match: "conflict-conf_01J-v2"
Content-Type: application/json
```

```json
{
  "decision": "accept_server",
  "reason_code": "LATEST_CLINICAL_ASSESSMENT",
  "reason_note": "تمت مراجعة سجل الطبيب المناوب واعتماد التقييم الأحدث.",
  "expected_entity_version": 8
}
```

إذا تغير التعارض أو السجل منذ فتحه، يعاد `412 Precondition Failed` ولا ينفذ القرار القديم.

### 7.6 التصعيد اليدوي

```http
POST /api/v1/notifications/{notification_id}:escalate
```

```json
{
  "reason_code": "NO_ACK_WITHIN_TARGET",
  "target_role": "senior_on_call",
  "note": "لم يصل إقرار خلال المهلة"
}
```

التصعيد لا يكرر التنبيه عشوائيًا؛ ينشئ مستوى إشعار جديدًا وسجلًا واضحًا للمستلم والسبب.

### 7.7 استرجاع الأحداث الفائتة

```http
GET /api/v1/notifications/replay?after_event_id=evt_01J...&limit=100
```

يُستخدم بعد انقطاع WebSocket أو إغلاق التطبيق. ويعيد فقط أحداث نطاق المستخدم التي لم تنتهِ مدة الاحتفاظ بها.

## 8. منع الإغراق والتكرار

يُمنع إرسال عشرات التنبيهات لنفس التعارض إذا حدثت إعادة محاولة أو تغيرت حقول غير جوهرية. يستخدم النظام:

```text
dedupe_key = conflict_id + severity + current_entity_version
```

إذا تغيرت الخطورة أو النسخة، يُسمح بإشعار جديد. أما heartbeat أو إعادة التسليم فلا تنشئ إشعارًا جديدًا.

يجب تطبيق حدود مثل:

| الحالة | السياسة |
|---|---|
| P0 غير مُقر | إعادة تنبيه داخل GULA كل 30–60 ثانية حسب السياسة، مع تصعيد بعد دقيقة. |
| P1 غير مُقر | تذكير كل 5 دقائق ثم تصعيد إلى منسق القسم. |
| P2 | تذكير داخل قائمة المهام دون صوت متكرر. |
| P3 | لا بث فوري؛ قائمة عمل أو ملخص دوري. |
| نفس التعارض للمستلمين أنفسهم | تجميعه في إشعار واحد. |
| عدة تعارضات للمريض نفسه | تجميع مع إبقاء كل `conflict_id` قابلًا للتتبع. |

## 9. نموذج الإقرار والتصعيد

```text
created
  ↓
delivered
  ↓
acknowledged ───────→ under_review ─→ resolved
  ↓                         │
no_ack                      └──────→ rejected/reopened
  ↓
escalated
  ↓
secondary_acknowledged
  ↓
incident_review (if still unresolved)
```

الإقرار له ثلاثة مستويات منفصلة:

| المستوى | المعنى |
|---|---|
| `delivered` | حاول النظام تسليم الإشعار إلى قناة أو قائمة المهام. |
| `acknowledged` | أكد المستخدم أنه رأى الإشعار. |
| `resolved` | اتخذ مستخدم مخول قرارًا على التعارض نفسه. |

لا يجوز اعتبار `acknowledged` حلًا سريريًا.

## 10. العمل أثناء انقطاع الشبكة

إذا كان الطبيب Offline، لا يمكن ضمان وصول WebSocket. لذلك تكون **قائمة المهام الخادمية هي مصدر الحقيقة**، وتحتفظ الواجهة المحلية بآخر إشعارات موقعة ومرخصة حتى انتهاء صلاحيتها.

في الوضع المتدهور:

- يعرض التطبيق حالة «قد توجد إشعارات غير متزامنة».
- لا يعلن أن الإشعار وصل إلى الطبيب إذا لم يرسل الجهاز إقرارًا خادميًا.
- عند عودة الاتصال، يسترجع الأحداث بعد `last_event_id`.
- لا يسمح Offline بحل تعارض سريري نهائي.
- يمكن تسجيل «اطلعت محليًا» كإشارة غير معتمدة، ثم يؤكدها الخادم عند الاتصال.
- إذا كان التعارض P0 ولا توجد قناة اتصال، تُفعّل سياسة التشغيل البديلة مثل النداء الداخلي أو الهاتف المؤسسي.

## 11. الأمن والخصوصية

تطبق قناة الإشعارات المصادقة والتفويض في كل اتصال، ولا تعتمد على فتح WebSocket قديم. ويجب:

1. عزل القناة حسب `lab_id` و`hospital_id` وrole وcare team.
2. عدم وضع اسم المريض أو التشخيص أو نتيجة المختبر داخل عنوان Push أو SMS.
3. استخدام معرف تعارض opaque وفتح التفاصيل عبر API محمي.
4. تسجيل كل تسليم وإقرار وتصعيد وفشل.
5. إبطال القناة عند انتهاء الجلسة أو تغيير الدور أو إلغاء الجهاز.
6. تشفير الاتصال وتقييد Push للأجهزة المُدارة.
7. عدم استخدام Redis Pub/Sub وحده كمصدر دائم؛ يجب حفظ الحدث في Outbox وقائمة المهام.

## 12. شاشة الطبيب

يظهر للطبيب شريط ثابت:

```text
[حرج 1] [عاجل 2] [مهام غير مقروءة 5]
```

وتظهر بطاقة P0 بالشكل التالي:

```text
تعارض سريري حرج
حالة طوارئ · يحتاج تدخلًا خلال 60 ثانية
المؤسسة: قسم الطوارئ
رقم التعارض: CONF-184

[فتح المراجعة الآمنة] [إقرار الاستلام]
```

بعد فتح المراجعة لا تظهر إلا البيانات المسموح بها، مع مقارنة النسخة المحلية والخادمية، وأزرار «حل التعارض» وفق صلاحية المستخدم. لا يظهر زر حل لمستخدم يملك حق القراءة فقط.

## 13. مراقبة النظام

تقاس المؤشرات التالية:

| المؤشر | الغرض |
|---|---|
| `notification_delivery_latency` | الزمن من حفظ التعارض إلى التسليم. |
| `ack_latency` | الزمن من التسليم إلى الإقرار. |
| `critical_unacknowledged_age` | عمر أقدم تنبيه حرج دون إقرار. |
| `escalation_rate` | نسبة التنبيهات التي احتاجت تصعيدًا. |
| `duplicate_notification_rate` | كشف خلل إزالة التكرار. |
| `replay_gap_count` | الأحداث التي استعادها الجهاز بعد الانقطاع. |
| `channel_failure_rate` | فشل WebSocket أو Push أو SSE. |
| `conflict_resolution_age` | زمن بقاء التعارض حتى الحل. |

ينبغي إنشاء تنبيه تشغيلي إذا ارتفع `critical_unacknowledged_age` أو تعطلت قناة الإشعارات، لأن فشل نظام الإشعارات نفسه قد يمثل خطرًا سريريًا.

## 14. القرار المعماري المقترح

يُبنى المسار بهذه الطبقات:

```text
Clinical Conflict Transaction
        ↓
Transactional Outbox
        ↓
Notification Dispatcher / Broker
        ↓
WebSocket + SSE + In-app Task + Managed Push
        ↓
Delivery / Acknowledgement / Escalation Store
        ↓
Audit and Observability
```

يجب أن يكون كل مسار قابلًا لإعادة المحاولة، وأن تكون عملية الإرسال idempotent، وألا يؤدي فشل قناة واحدة إلى إسقاط المهمة من قائمة العمل. أما حل التعارض فيبقى داخل خدمة التعارض السريرية وبفحص نسخة جديد.

## الخلاصة

التصميم الآمن ليس «إرسال WebSocket إلى الطبيب» فقط. المطلوب هو **تعارض محفوظ أولًا، ثم Outbox، ثم تنبيه مصنف، ثم إقرار، ثم تصعيد، ثم حل مخول مع نسخة وتدقيق**. وتكون قائمة المهام المستمرة هي الضمان عند إغلاق التطبيق أو انقطاع الشبكة، بينما تستخدم WebSocket أو SSE لتقليل زمن الوصول، ولا تُرسل التفاصيل السريرية الحساسة في Push أو SMS.
