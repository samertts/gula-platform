# تنفيذ مسار الطبيب في GULA

## النطاق

تم تنفيذ الطبقة الأولى الآمنة من مسار الطبيب داخل `frontend-v3` فوق عقود الهوية ومساحات العمل وبوابة القراءة السريرية الموجودة في backend. الهدف هو تقديم تجربة طبيب قابلة للاستخدام في العرض التجريبي، وقابلة للاتصال بالبيئة الحية دون أن تجعل الواجهة مصدراً للصلاحية أو تنشئ حساباً مهنياً أو تعرض بيانات خارج نطاق الخادم.

> **قاعدة المسار:** تسجيل الدخول يثبت هوية الحساب، أما المهنة والعضوية والدور والسياق والصلاحيات فتظل قراراً خادمياً مستقلاً.

## ما تم تسليمه

| المجال | التنفيذ الفعلي |
|---|---|
| مركز الطبيب | أصبح `/dashboard` يعرض لوحة متخصصة عندما يكون الدور المعروض `doctor`. |
| Demo | عرض اصطناعي معزول للمرضى والطلبات والجدول والمهام، دون اتصال بالـAPI الحي. |
| مساحات العمل | في Live تُقرأ المساحات من `GET /niam/workspaces`، وتُعرض فقط المساحات المهنية من نوع `physician`. |
| تبديل السياق | يتم فقط عبر `POST /niam/workspaces/{workspace_id}/switch`؛ اختيار الزر لا ينشئ دوراً أو صلاحية. |
| قراءة المرضى | تستخدم الواجهة `GET /api/v1/clinical/patients` من خلال `workspaceScopedReads` فقط. |
| قراءة الطلبات | تستخدم الواجهة `GET /api/v1/clinical/orders` من خلال `workspaceScopedReads` فقط، ولا تعرض نتائج الطلب داخل DTO الطلب. |
| الفشل الآمن | رفض السياق أو توقف rollout أو غياب إثبات المؤسسة يعرض رسالة حجب واضحة ولا يستخدم legacy fallback. |
| تقليل الإفصاح | لا تعرض الواجهة `phone` أو `national_id` أو `national_id_hash` أو `lab_id` أو payload نتائج خام. |
| علي رضا | ظهر كمرشد داخل السياق؛ لا يُمنح وصولاً مستقلاً ولا يوقّع أو يكتب أو يعتمد قراراً سريرياً. |
| المسار السريري | Appointment وEncounter والنتائج والوصفات والإحالات والمتابعة تظهر بحالات `يتطلب عقداً خادمياً` أو `تجريبي فقط` عند عدم وجود عقد قابل للتنفيذ. |
| Demo القديم | أزيل إنشاء المريض المحلي من تبويب التسجيل، وأصبح تبويباً توضيحياً للقراءة فقط دون حفظ بيانات. |

## سلسلة الثقة في Live

لا تعتبر لوحة الطبيب الحساب أو الدور المحلي دليلاً كافياً. القراءة الحية لا تبدأ قبل اختيار مساحة مهنية أعادها الخادم، ثم تمر عبر clinical gateway الذي يثبت سياق المؤسسة والمنشأة والعضوية وربط الحساب بالمصدر السريري والتفويض. إذا فشل أي جزء من السلسلة، تُحجب القراءة.

الواجهة تعرض الحد الأدنى من DTOs التي يسمح بها العقد الحالي: معرف عرضي، اسم عرض، بيانات ديموغرافية محدودة للمريض، وحالة الطلب وعدد الفحوصات دون تضمين نتائج أو معرفات tenant حساسة. الحماية الموجودة في المتصفح دفاعية فقط، والـbackend هو المرجع النهائي.

## ما لم يُنفذ عمداً

لم يتم إنشاء عقد كتابة سريري أو واجهة تحفظ Clinical Note أو Encounter أو Prescription أو Referral أو Result. هذه العمليات تحتاج إلى state machine، وRBAC سياقي، وعلاقة رعاية، وموافقة أو أساس قانوني، ونسخة/`If-Match`، و`Idempotency-Key`، وتدقيق غير قابل للحذف.

كذلك لم يتم تنفيذ التحقق الحكومي أو OCR أو NFC أو biometric/liveness أو provisioning لهوية وطنية. لم تُعرض تلك القدرات كأنها تحقق فعلي. ولم يتم توصيل الأجهزة أو الجلسات أو Break-Glass أو سجل الوصول أو التفويض إلى واجهات self-service غير موجودة في العقد الحالي.

## الاختبارات

أضيفت اختبارات `DoctorWorkspacePanel.test.tsx` التي تثبت أن Demo لا يستدعي مساحة عمل أو clinical gateway، وأن Live لا يقرأ قبل تفعيل سياق مهني عبر endpoint الخادم، وأن رفض بوابة القراءة يؤدي إلى حجب آمن دون fallback legacy. تم تشغيل الاختبار المستهدف بنجاح بثلاثة اختبارات.

ينبغي قبل الدمج النهائي تشغيل مجموعة frontend-v3 كاملة، ثم `typecheck` و`lint` و`build` وفحوص الحوكمة والعقود والعزل. نجاح الاختبارات المحلية لا يثبت جاهزية الإنتاج ولا نجاح فحوص GitHub البعيدة.

## الخطوات اللاحقة المطلوبة

الخطوة التالية backend-first هي إضافة عقود ذاتية محدودة للمواعيد والجلسات والأجهزة وسجل الوصول والمهام، ثم اختبارها بعزل المؤسسة، والصفحات، والتدقيق، وانتهاء الصلاحية. بعد ذلك فقط يمكن استبدال الحالات المحجوبة في الواجهة بقراءات خادمية.

أما الكتابة السريرية فتحتاج مسارات مستقلة ومراجعة سلامة قبل تفعيلها. لا ينبغي فتح زر حفظ أو توقيع أو اعتماد لمجرد اكتمال الواجهة، لأن ذلك سيحوّل الواجهة إلى مصدر صلاحية غير آمن.
