### 2.2 Preference reuse

The GULS preference API reuses the existing `accessibility_profiles` table rather than adding a user-language table:

- `backend/app/models/user_preferences.py` defines `accessibility_profiles` with `user_id`, `lab_id`, a JSON `preferences` column, a `version` column, and a unique constraint on `user_id`.
- `backend/app/localization/preferences.py` writes `language`, `fallback_language`, and `auto_download` into that same JSON through `preference_store.save()` at lines 235–245. The production store is backed by `AccessibilityProfile`; the in-memory store is a test/restricted fallback.
- `backend/app/routes/user_preferences.py` keeps the legacy accessibility response model with `extra="ignore"`, so added GULS keys do not break existing clients. The effective language remains English until the requested pack reaches `READY`.
- Health preferences remain separate (`health_preferences`, encrypted payload, consent-bound) and are not consulted by GULS language selection.
- The H1 correction rejects a preferred language unless it is active, publishable, has an assigned locale, and has both linguistic and overall approval `approved`; blocked `fa` is rejected with `409 LANGUAGE_NOT_ACTIVE` as recorded in `P00_INDEPENDENT_REVIEW.md`.

No production database, production key, or PHI was accessed during this review.

### 2.3 Residual database/state risks

- **M4 (MEDIUM, residual):** GULS and legacy accessibility share `preferences["language"]`; the in-memory store has no `ETag`/`If-Match` optimistic concurrency. Multi-writer deployments need concurrency control before production.
- **M5 (MEDIUM, residual):** download sessions and pack lifecycle state are process-local. A multi-replica deployment requires shared persistent state.
- **M6 (MEDIUM, residual):** local pack state is not cryptographically signed. The default pack root was moved away from `/tmp` to a service-account-home path, but OS-level protection and state integrity remain deployment responsibilities.
- These are documented residual risks, not silently fixed defects.

## 3. Security findings

### 3.1 Corrections retained from the P00 pass

The following corrections were verified in the isolated branch and are not duplicated here:

- **C1 CRITICAL:** clinical catalogs are derived from archive contents; declared/actual mismatch is rejected and the clinical gate applies to real files.
- **H1 HIGH:** preferred-language endpoint enforces registry activity, publishability, locale, and approvals.
- **H2 HIGH:** `stable_http_detail()` and explicit-code pass-through preserve stable GULS codes such as `DOWNLOAD_BLOCKED_BY_DATA_SAVER` in production HTTP responses; fixed English messages are not overwritten by Arabic detail.
- **H3 HIGH:** synthetic packs are refused at production/staging startup, require `GULS_SYNTHETIC_SIGNER_KEY_ID`, and are signer-key bound; the default root is safer.
- **H4 HIGH:** clinical governance validates `ApprovalRecord` role separation for translator, linguistic reviewer, and clinical reviewer.
- **M1/M2/M3/M7/M8/M9:** `ROLLBACK_REQUIRED -> NOT_INSTALLED` retry, `MAX_PACK_MEMBERS = 256`, contiguous-prefix download coverage with `COMPLETE`/`DOWNLOADING` transport states, archive-driven clinical/quota checks, signed-field validation, and explicit expired-token handling.

Existing controls confirmed by P00 remain intact: Ed25519 fail-closed verification, no private key in the repository, path traversal/absolute path/symlink/executable rejection, byte limits, file-set/hash consistency, atomic install with previous-version preservation, downgrade rejection, English fallback without raw-key leakage, short-lived constant-time download tokens, data-saver/roaming checks, and user/lab preference isolation.

### 3.2 Web offline security position

The new `frontend-v3/src/guls/offline/` module mirrors the backend safety model locally: Ed25519 signature verification through Web Crypto, SHA-256 per-file and content hashes, manifest/schema validation, archive-derived catalog detection, rejection of clinical catalogs in dynamic packs, safe path and suffix checks, member/size limits, and fail-closed stable error codes. Pack bytes are kept out of Workbox caches and stored in IndexedDB only after verification.

No private key, token, password, or production signer material is added by the Web change. The security residual from P02 is that the module has no production call sites yet and its Cache Storage helpers are not registered with service-worker activation; this prevents an end-user installation path and untested cache migration, rather than introducing a new bypass.

## 5. Dependency and audit notes

- **No new runtime dependency:** the Web offline runtime uses native IndexedDB, Web Crypto, `DecompressionStream`, `Cache Storage`, and `fetch`. `frontend-v3/package.json` and any lockfile are unchanged. `vite-plugin-pwa` already existed as a dev dependency; its new Workbox rule is configuration, not a new component.
- **Constitution alignment for this change:** native browser APIs were preferred over a commercial/offline SDK; there is no paid dependency, no vendor-specific coupling, and no new proprietary service. No external dependency was introduced without documented justification.
- **Python Dependency Audit (`backend/requirements-lock.txt`)** is one of the failing PR checks and also fails on baseline. GULS-021 did not change dependency manifests, so this is a pre-existing red gate, not a new audit regression. CI `Dependency Review` checks report `pass`.
- **Ruff Format** fails as described in section 4; the conflicting Python 3.14 syntax would break 3.11/3.12 runtime compatibility, so the file was not reformatted to satisfy the tool.
- **Native toolchain:** `for tool in java gradle swift xcodebuild flutter dotnet; do ... done` exited 0 with `java=/usr/bin/java` and `gradle=NOT_FOUND`, `swift=NOT_FOUND`, `xcodebuild=NOT_FOUND`, `flutter=NOT_FOUND`, `dotnet=NOT_FOUND`. Android/iOS/Flutter desktop builds were therefore not run locally.
