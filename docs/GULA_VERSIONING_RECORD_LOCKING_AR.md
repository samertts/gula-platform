# Versioning وRecord Locking في GULA

## الملخص التنفيذي

يجب ألا تعتمد المستشفيات على قفل واجهة المستخدم وحده، ولا على قاعدة `آخر تعديل يفوز`. النموذج الآمن هو الجمع بين:

1. **Optimistic Versioning** لكل سجل سريري، وهو الحاجز الإلزامي الذي يمنع الكتابة فوق نسخة أحدث.
2. **قفل تطبيقي قصير الأجل** لتحسين تجربة المستخدم وإظهار أن سجلًا ما قيد التحرير، لكنه لا يحل محل فحص النسخة.
3. **Pessimistic Database Lock** داخل معاملة قصيرة جدًا للموارد المتنافس عليها، مثل السرير أو وحدة الدم أو مخزون دوائي، وليس طوال مدة فتح شاشة المريض.
4. **سجل إصدارات وتدقيق append-only** يحفظ قبل التعديل وبعده ومن نفذ العملية ولماذا.

> القفل يمنع أو يقلل التعديل المتزامن، أما `version` فهو الضمان النهائي ضد الكتابة فوق بيانات تغيّرت.

## 1. اختيار السياسة حسب نوع السجل

| نوع المورد | السياسة الافتراضية | سبب الاختيار |
|---|---|---|
| ملف المريض وEncounter | Optimistic + سجل أحداث | عدة فرق تحتاج القراءة، ولا يجب احتجاز الملف طويلًا. |
| الفرز والأولوية والحالة | Optimistic إلزامي + آلة حالات | كل انتقال يحتاج نسخة وصلاحية وتدقيقًا. |
| المواعيد | Optimistic، وقفل قصير عند الحجز | منع الحجز المزدوج وتعارض الوقت. |
| الأسرة | Pessimistic داخل معاملة قصيرة + قيود فريدة | لا يجوز تعيين سرير واحد لمريضين. |
| غرفة العمليات | Pessimistic/lease قصير | المورد محدود وحساس زمنيًا. |
| وحدة الدم أو جرعة دوائية | Pessimistic داخل معاملة الاستهلاك | منع صرف الوحدة أو المخزون مرتين. |
| النتائج المخبرية | Optimistic + حالات اعتماد | لا يسمح بتعديل نتيجة معتمدة؛ التصحيح يكون كنسخة أو إضافة مصححة. |
| الملاحظات السريرية | Append-only أو Versioned Draft | لا تُمسح الملاحظة الأصلية؛ التصحيح يضيف نسخة أو ملحقًا. |
| لوحة الطوارئ | Optimistic + أحداث append-only | السرعة مهمة، لكن لا يجوز فقدان تغيير الأولوية أو الفرز. |

## 2. نموذج النسخ الإلزامي

كل سجل قابل للتعديل يحتاج إلى الحقول التالية:

```text
version              INTEGER NOT NULL DEFAULT 1
updated_at           TIMESTAMP WITH TIME ZONE NOT NULL
updated_by           INTEGER NOT NULL
last_operation_id    VARCHAR(64) NULL
last_request_id      VARCHAR(64) NULL
record_state         VARCHAR(30) NOT NULL
```

ويُضاف إلى كل طلب تعديل:

```json
{
  "expected_version": 7,
  "operation_id": "op_01J...",
  "reason_code": "TRIAGE_REASSESSMENT",
  "reason_note": "إعادة تقييم سريري"
}
```

ويجب أن يدعم HTTP أيضًا:

```http
If-Match: "encounter-enc_01J-v7"
Idempotency-Key: idem_01J...
X-GULA-Operation-ID: op_01J...
```

لا يقبل الخادم تعديلًا حساسًا إذا غابت `expected_version` أو `If-Match`. وفي العمليات غير السريرية منخفضة الخطورة يمكن السماح بقراءة أحدث نسخة ثم التعديل، لكن يجب أن تكون هذه استثناءات موثقة في سياسة المورد.

## 3. التنفيذ الصحيح للـ Optimistic Locking

لا يكفي قراءة السجل ثم تغيير `version` داخل كائن SQLAlchemy؛ فهذا قد يسمح لطلبين بقراءة النسخة نفسها ثم الكتابة فوق بعضهما. يجب أن يكون فحص النسخة وتحديثها عملية ذرية على مستوى قاعدة البيانات:

```sql
UPDATE national_encounters
SET
    flow_state = :target_state,
    status = :status,
    version = version + 1,
    updated_by = :user_id,
    updated_at = CURRENT_TIMESTAMP,
    last_operation_id = :operation_id
WHERE id = :encounter_id
  AND lab_id = :lab_id
  AND version = :expected_version
  AND is_deleted = FALSE;
```

ثم يفحص التطبيق عدد الصفوف المتأثرة:

```text
1 row  → نجاح، ثم كتابة سجل التدقيق داخل نفس المعاملة
0 rows → تعارض نسخة أو سجل غير موجود أو خارج النطاق
```

إذا كانت النتيجة صفرًا، يجب إعادة `409 Conflict` أو `412 Precondition Failed`، وإنشاء سجل تعارض عند كون العملية سريرية. لا يجوز إعادة المحاولة تلقائيًا بتحديث النسخة إلى القيمة الأحدث؛ يجب إعادة قراءة السجل أو بدء مسار مراجعة.

## 4. القفل التطبيقي Record Lock

القفل التطبيقي مفيد لمنع شخصين من تحرير النموذج نفسه في الوقت ذاته، لكنه ليس بديلًا عن النسخة. يُنفذ كـ**lease** قصير الأجل لا كقفل دائم.

### جدول `record_locks`

| الحقل | الوصف |
|---|---|
| `id` | معرف القفل. |
| `resource_type` | Encounter، Appointment، Bed، Result. |
| `resource_id` | معرف المورد. |
| `lab_id`, `hospital_id` | نطاق المؤسسة. |
| `owner_user_id` | المستخدم الذي حصل على القفل. |
| `owner_device_id` | الجهاز. |
| `lock_token_hash` | بصمة رمز القفل، لا يخزن الرمز خامًا. |
| `acquired_at` | وقت الحصول. |
| `expires_at` | وقت الانتهاء الإجباري. |
| `last_heartbeat_at` | آخر تجديد. |
| `released_at` | وقت التحرير. |
| `status` | active، released، expired، revoked. |

### خصائص القفل

| الخاصية | السياسة المقترحة |
|---|---|
| مدة أولية | 2–5 دقائق حسب نوع الشاشة. |
| التجديد | heartbeat كل 30–60 ثانية. |
| الحد الأقصى | لا تمديد بلا نهاية؛ يحتاج المستخدم إعادة الحصول على القفل. |
| انتهاء الجلسة | ينتهي القفل عند انتهاء الجلسة أو فقدان الاعتماد. |
| الانقطاع | لا يُعتبر القفل المحلي قفلًا خادميًا بعد انقطاع الاتصال. |
| التداخل | قفل واحد فعال للمورد نفسه داخل النطاق. |
| التحرير | تحرير صريح أو انتهاء تلقائي. |
| التعطيل | مسؤول مخول يستطيع revoke مع سبب وتدقيق. |

لا ينبغي إبقاء معاملة قاعدة البيانات مفتوحة طوال فترة تحرير المستخدم. القفل التطبيقي هو إشارة تشغيلية، بينما المعاملة الفعلية يجب أن تكون قصيرة عند الحفظ.

## 5. القفل التشاؤمي لموارد محدودة

يستخدم `SELECT ... FOR UPDATE` داخل معاملة قصيرة عندما يكون المورد غير قابل للحجز المزدوج.

### مثال تعيين سرير

```sql
BEGIN;

SELECT id, status, version
FROM beds
WHERE id = :bed_id
  AND hospital_id = :hospital_id
FOR UPDATE NOWAIT;

-- تحقق من أن السرير متاح وأن المريض لا يملك تعيينًا فعالًا آخر

INSERT INTO bed_assignments (...);
UPDATE beds
SET status = 'occupied', version = version + 1
WHERE id = :bed_id;

INSERT INTO audit_events (...);
COMMIT;
```

إذا كان السرير مقفولًا من معاملة أخرى، يعاد `409 BED_RESOURCE_BUSY` أو `423 Locked` مع `Retry-After` قصير. لا ينبغي استخدام `SKIP LOCKED` في عملية التعيين نفسها إذا كان تجاوزه قد يؤدي إلى إخفاء مورد مطلوب؛ يمكن استخدامه فقط لبناء قوائم تشغيلية غير حاسمة.

## 6. مسارات API المقترحة

### قراءة سجل مع النسخة

```http
GET /api/v1/encounters/{encounter_id}
```

الاستجابة:

```http
ETag: "encounter-enc_01J-v7"
```

```json
{
  "id": "enc_01J...",
  "flow_state": "triaged",
  "priority": "urgent",
  "version": 7,
  "updated_at": "2026-08-17T14:29:04Z",
  "editable": true,
  "lock": {
    "status": "available"
  }
}
```

### الحصول على قفل تحريري

```http
POST /api/v1/records/Encounter/{encounter_id}/lock
Cookie: access_token=...
X-Device-ID: ER-TABLET-02
```

الاستجابة:

```json
{
  "resource_type": "Encounter",
  "resource_id": "enc_01J...",
  "lock_token": "lt_01J...",
  "expires_at": "2026-08-17T14:35:00Z",
  "server_version": 7
}
```

### تجديد القفل

```http
POST /api/v1/records/Encounter/{encounter_id}/lock:heartbeat
Authorization: ...
X-Lock-Token: lt_01J...
```

إذا كان القفل منتهيًا، يعاد `423 Locked` أو `409 LOCK_EXPIRED` ولا يُجدد تلقائيًا دون تحقق من المستخدم.

### تحرير القفل

```http
DELETE /api/v1/records/Encounter/{encounter_id}/lock
X-Lock-Token: lt_01J...
```

### حفظ تعديل بنسخة متوقعة

```http
PATCH /api/v1/encounters/{encounter_id}
If-Match: "encounter-enc_01J-v7"
Idempotency-Key: idem_01J...
X-GULA-Operation-ID: op_01J...
Content-Type: application/json
```

```json
{
  "flow_state": "in_progress",
  "priority": "stat",
  "expected_version": 7,
  "reason_code": "CLINICAL_REASSESSMENT",
  "reason_note": "تمت إعادة معاينة المريض بواسطة الطبيب المناوب"
}
```

النجاح:

```json
{
  "id": "enc_01J...",
  "version": 8,
  "flow_state": "in_progress",
  "updated_by": 42,
  "audit_event_id": "audit_01J..."
}
```

### التعارض

```json
{
  "error": {
    "code": "STALE_VERSION",
    "message_ar": "تغير السجل منذ فتحه؛ لم يُطبق التعديل.",
    "resource_type": "Encounter",
```

### قراءة تاريخ الإصدارات

```http

```

لا تعرض هذه العملية كل البيانات الحساسة لكل مستخدم؛ تخضع للصلاحيات وتقليل البيانات.

### حل تعارض

```http
POST /api/v1/conflicts/{conflict_id}:resolve
If-Match: "conflict-conf_01J-v3"
```

```json

  "decision": "accept_server",
  "reason_code": "LATEST_CLINICAL_ASSESSMENT",
  "reason_note": "اعتماد تقييم الطبيب المناوب",
  "expected_entity_version": 8
}
```

حل التعارض لا يحذف الاقتراح المحلي؛ بل يغير حالة التعارض ويضيف قرارًا جديدًا إلى سجل الأحداث.

## 7. حالات HTTP القياسية

| الكود | الحالة |
|---:|---|
| `409 Conflict` | تعارض نسخة أو عملية أعمال أو تكرار غير متطابق. |
| `412 Precondition Failed` | قيمة `If-Match` قديمة. |
| `423 Locked` | المورد محجوز بقفل تطبيقي فعال. |
| `428 Precondition Required` | غياب شرط النسخة في عملية حساسة. |
| `422 Unprocessable Entity` | انتقال سريري غير مسموح أو بيانات غير صالحة. |
| `403 Forbidden` | المستخدم لا يملك صلاحية التعديل أو الحل. |
| `404 Not Found` | المورد غير موجود ضمن نطاق المؤسسة؛ لا يكشف الخادم وجوده خارج النطاق. |
| `503 Service Unavailable` | لا يمكن ضمان الحفظ؛ في Offline Mode تعاد العملية إلى الطابور المحلي. |

## 8. استراتيجية منع التعارض في الواجهة

عند فتح السجل، تحفظ الواجهة `version` و`ETag`. وعند وجود قفل فعال تعرض اسم الدور أو «محرر آخر» دون كشف بيانات غير لازمة. إذا تغيرت النسخة أثناء التحرير، تعرض الواجهة:

> تغير السجل من مستخدم آخر. لم يتم حفظ تعديلاتك. اختر عرض الفروقات أو حفظها كمسودة للمراجعة.

ولا تعرض زرًا باسم «استبدال نسخة الخادم» للمستخدم العادي. الخيارات تكون:

| الخيار | الاستخدام |
|---|---|
| إعادة التحميل | تجاهل المسودة المحلية بعد تأكيد المستخدم. |
| حفظ كمسودة | إنشاء اقتراح منفصل لا يغير مصدر الحقيقة. |
| عرض الفروقات | مقارنة القيم والتوقيتات والمستخدمين. |
| طلب مراجعة | فتح تعارض لمسؤول مخول. |

## 9. ما لا ينبغي قفله

لا ينبغي قفل كامل ملف المريض أو كامل القسم لفترة طويلة؛ فهذا يسبب اختناقًا في الطوارئ. كما لا ينبغي قفل السجل اعتمادًا على فتح الصفحة فقط، لأن الأجهزة قد تتعطل أو يترك المستخدم الشاشة مفتوحة.

القفل مخصص لتقليل التداخل، وليس لمنع العمل الطبي. الحاجز الحقيقي هو التحديث الذري المشروط بالنسخة، وسجل الأحداث، وآلة الحالات.

## 10. ملاحظات مهمة على GULA الحالية

تحتوي GULA على `OptimisticLockMixin.version`، كما أن `Encounter` يرفع النسخة داخل `transition_flow_state`. لكن التنفيذ الآمن في الإنتاج يحتاج تحسينين مهمين:

1. تحويل تحديثات النسخة إلى `UPDATE ... WHERE version = expected_version` أو استخدام آلية SQLAlchemy versioning بحيث يكون الفحص والتحديث ذريين، بدل الاعتماد على قراءة الكائن ثم رفع `version` في الذاكرة.
2. تمرير `lab_id` إلى كل قراءة داخل خدمة الانتقال؛ فلا يكفي أن تتحقق route من النطاق ثم تستدعي خدمة تبحث عن `encounter_id` وحده.

ويجب تطبيق نفس السياسة على `Appointment` و`BedAssignment` والنتائج والأدوية، مع قفل تشاؤمي قصير فقط للموارد التي لا تقبل الحجز المزدوج.

## 11. قواعد خاصة بالطوارئ والعمل Offline

في وضع Offline لا يمكن اعتبار قفل الواجهة المحلي قفلًا خادميًا. لذلك:

- تُسجل العملية محليًا كاقتراح مع `base_version` عند آخر مزامنة.
- عند عودة الاتصال يعاد فحص النسخة والصلاحية وآلة الحالة.
- إذا تغير السجل، تُنشأ حالة تعارض بدل الكتابة فوقه.
- عمليات الوصول والفرز الحرجة تُحفظ كأحداث مستقلة، ولا تُدمج مع آخر تعديل عشوائيًا.
- لا يسمح Offline بحل التعارض أو اعتماد نتيجة أو تعديل هوية وطنية نهائية.
- إذا انتهت صلاحية الجلسة أو الجهاز، تمنع العمليات الحساسة وتبقى المسودات مشفرة للمراجعة.

## 12. اختبارات القبول

| الاختبار | النتيجة الإلزامية |
|---|---|
| موظفان يحفظان النسخة نفسها | نجاح واحد، ورفض واحد بـ`409/412`، دون فقدان. |
| قفل منتهي | رفض الحفظ أو طلب قفل جديد. |
| جهازان يعيّنان السرير نفسه | معاملة واحدة فقط تنجح. |
| انتقال غير مسموح | `422` وتسجيل محاولة مخالفة. |
| إعادة إرسال الطلب نفسه | نفس النتيجة دون أثر جانبي مكرر. |
| حل التعارض بعد تغير السجل | رفض الحل القديم بـ`412`. |
| انقطاع الشبكة أثناء الحفظ | مسودة محلية مشفرة أو فشل واضح، لا نجاح وهمي. |
| مستخدم خارج المؤسسة | رفض وعدم كشف وجود السجل. |
| تعطل الجهاز صاحب القفل | انتهاء القفل تلقائيًا واستعادة التشغيل دون تدخل قاعدة البيانات. |
| تاريخ الإصدارات | كل نسخة قابلة للتتبع قبل/بعد ومن نفذها ولماذا. |

## التوصية النهائية

اعتمد GULA سياسة **Optimistic Versioning كحاجز إلزامي لكل تعديل**، وأضف **Record Lease Lock قصيرًا للواجهة** لتحسين التنسيق، واستخدم **Pessimistic Row Lock داخل معاملة قصيرة** للسرير والدم والدواء والمخزون. لا تستخدم قفلًا طويلًا على ملف المريض، ولا تستخدم `last-write-wins` في أي قرار سريري.

بهذا النموذج تحافظ المؤسسة على السرعة في الطوارئ، وتمنع الكتابة فوق البيانات، وتبقى كل عملية قابلة للمراجعة حتى عند العمل المتزامن أو Offline.
