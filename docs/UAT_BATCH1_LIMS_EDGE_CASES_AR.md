# حزمة تنفيذ UAT للدفعة الأولى: LIMS وحارس الأوامر السريرية

**الإصدار المرشح:** PR #242 / `release/clinical-safety-2026q3`
**نوع البيانات:** تركيبية فقط؛ يمنع إدخال أي PHI أو بيانات إنتاجية.
**هدف القبول:** إثبات أن مسار المختبر يرفض الأوامر الناقصة أو المتضاربة أو غير المصرح بها، وأن كل أمر قانوني يملك أثرًا واحدًا وسجل تدقيق قابلًا للتتبع.

> لا يبدأ التنفيذ البشري في staging قبل نجاح الفحوص المحلية، وتأكيد رأس Alembic واحد، وتوثيق بيئة الاختبار. لا يحوّل نجاح اختبار وحدة تلقائياً إلى قبول سريري؛ يجب تنفيذ حالات UAT بالأدوار المفصولة أدناه.

## 1. البيئة والأدوار

| العنصر | القيمة المطلوبة |
|---|---|
| المؤسستان | `LAB-A-UAT` و`LAB-B-UAT` مع عزل كامل للبيانات |
| المريض/العينة | معرفات تركيبية فقط، مثل `UAT-PATIENT-001` و`UAT-SPECIMEN-001` |
| الأدوار | فني إدخال، أخصائي اعتماد مخول، طبيب/مستلم نتيجة، مهندس منصة، مراقب UAT |
| فصل الواجبات | لا يعتمد منشئ النتيجة النتيجة ذاتها عندما تتطلب السياسة اعتماداً مستقلاً |
| النقل | اتصال TLS ببيئة staging فقط؛ لا تسجيل لحمولات سريرية في أدوات الدردشة أو التذاكر |
| المراقبة | `GET /metrics/prom` برمز اختبار محمي؛ لا PHI في labels أو Sentry |
| أدلة القبول | رقم إيصال الأمر، رقم التدقيق الداخلي، حالة المورد وإصداره، نتيجة HTTP، ولقطة مؤشر مجردة |

## 2. قاعدة التنفيذ الموحدة

لكل حالة، ينفذ المراقب التسلسل التالي: يسجل نسخة المورد الحالية، يضع قيمة `If-Match` مطابقة، ينشئ `Idempotency-Key` عشوائياً واحداً، ينفذ الطلب، ثم يتحقق من حالة المورد وإصداره وإيصال الأمر وسجل التدقيق. في الحالات التي تتطلب إعادة إرسال أو سباقاً، لا يُنشأ مفتاح جديد إلا إذا كان الهدف اختبار أمر جديد مستقل.

| الحقل في سجل UAT | ما يسجل |
|---|---|
| Case ID | معرف الحالة أدناه |
| Actor / Tenant | دور الاختبار وLAB-A أو LAB-B، من دون اسم حقيقي |
| Resource version | القيمة قبل وبعد العملية |
| Command evidence | معرف الإيصال ورقم التدقيق فقط؛ لا المفتاح نفسه |
| Expected / actual | حالة HTTP، انتقال الحالة، وعدد الآثار الجانبية |
| Decision | Pass / Fail / Blocked مع اسم المراجع وتوقيته |

## 3. حالات الحافة ذات الأولوية القصوى

### A. حارس الأوامر: الرؤوس، التكرار، والتزامن

| المعرف | حالة الحافة | طريقة التنفيذ | القبول الإلزامي |
|---|---|---|---|
| B1-G01 | غياب `If-Match` | أرسل اعتماد/إطلاق نتيجة صحيحة وظيفياً بلا رأس النسخة | `428` أو الرفض المتعاقد عليه؛ لا تعديل ولا إيصال مكتمل. |
| B1-G02 | `If-Match` غير صالح | اختبر فراغاً، نصاً غير رقم، قيمة سالبة، وقيمة متعددة | رفض آمن لا يُحوّل القيمة ولا ينفذ الأثر. |
| B1-G03 | نسخة قديمة | افتح النتيجة في جلستين؛ حدّثها في الأولى ثم نفّذ الثانية بالنسخة القديمة | تضارب `409`، ولا overwrite صامت ولا increment إضافي. |
| B1-G04 | مفتاح عدم تكرار غائب/فارغ | أرسل الطلب من دون الرأس ثم بمسافات فقط | رفض قبل الأثر الجانبي، ويظهر سبب مجرد في المراقبة. |
| B1-G05 | إعادة إرسال ناجحة | أعد **الطلب نفسه** بعد نجاحه بالمفتاح نفسه | إيصال واحد وحالة مورد واحدة وسجل تدقيق واحد للأثر. |
| B1-G06 | إعادة إرسال متزامنة | أرسل الطلب نفسه مرتين في الوقت نفسه من جلستين | فائز واحد فقط؛ لا اعتماد أو إطلاق أو إشعار مزدوج. |
| B1-G07 | مفتاح مكرر بحمولة مختلفة | أرسل مفتاحاً مستخدماً لعملية أو مورد آخر أو جسم مختلف | رفض واضح؛ لا يسمح بتحويل المفتاح إلى عملية أخرى. |
| B1-G08 | تعطل التسجيل/التدقيق | في بيئة اختبار محكومة، حاكِ فشل حفظ إيصال الأمر أو سجل التدقيق | يفشل الأمر مغلقاً؛ لا تبقى نتيجة/حالة متغيرة بلا دليل تدقيق. |
| B1-G09 | إعادة المحاولة بعد مهلة عميل | اقطع اتصال العميل بعد الإرسال أو حاكِ timeout ثم أعده بالمفتاح نفسه | لا أثر ثانٍ؛ يمكن للمشغل إثبات النتيجة من الإيصال والسجل. |

### B. دورة العينة والنتيجة: الانتقالات غير القانونية

| المعرف | حالة الحافة | طريقة التنفيذ | القبول الإلزامي |
|---|---|---|---|
| B1-L01 | إدخال نتيجة لعينة غير متحققة | أنشئ طلباً وعينة مستلمة غير verified ثم حاول إدخال/اعتماد النتيجة | رفض؛ تبقى حالة العينة والنتيجة دون تغيير. |
| B1-L02 | تجاوز حالة العينة | حاول انتقالاً يقفز مرحلة من الدورة المعتمدة أو يعيد العينة إلى حالة سابقة | رفض آلة الحالات وتدقيق محاولة الرفض. |
| B1-L03 | عينة ملغاة أو مرفوضة | حاول إدخال/اعتماد/إطلاق نتيجة مرتبطة بعينة ملغاة أو مرفوضة | رفض في كل نقطة؛ لا يسمح بمسار استثناء صامت. |
| B1-L04 | نتيجة غير معتمدة | حاول إطلاق نتيجة مسودة أو pending أو بلا توقيع الاعتماد المطلوب | رفض؛ لا يصبح `released` إلا بعد التسلسل القانوني. |
| B1-L05 | اعتماد بصلاحية غير كافية | نفذ الاعتماد بحساب فني غير مخول ثم بحساب الاعتماد المصرح | الأول يرفض والثاني فقط يمكنه الانتقال القانوني. |
| B1-L06 | توقيع مفقود أو خاطئ | أرسل اعتماداً بلا توقيع أو بمعرّف توقيع لا يطابق الحساب أو النتيجة | رفض؛ لا تحفظ حالة اعتماد جزئية. |
| B1-L07 | تعدد النتائج للطلب | حرر نتيجة واحدة وأبق أخرى pending ثم حاول اعتماد/إصدار التقرير أو الطلب النهائي حيث ينطبق | يمنع الإغلاق النهائي ما دام التسلسل الناقص قائماً. |
| B1-L08 | قيمة/وحدة غير متوقعة | جرّب قيمة فارغة أو غير قابلة للتحويل أو وحدة مخالفة لتعريف الاختبار في بيانات UAT | يرفض التحقق أو يطلب تصحيحاً واضحاً؛ لا تُخزن قيمة ملتبسة. |
| B1-L09 | زمن خارج الترتيب | أدخل طابعاً زمنياً يسبق التحقق أو يأتي بعد الإطلاق عند توفر الحقل في المسار | يرفض أو يرفع حالة مراجعة حسب العقد؛ لا يختفي التناقض. |

| المعرف | حالة الحافة | طريقة التنفيذ | القبول الإلزامي |

| B1-C01 | نتيجة حرجة قبل الإطلاق | علّم نتيجة حرجة ثم حاول الإقرار أو الإبلاغ قبل أن تصبح قابلة للإطلاق | لا إقرار نهائي أو تواصل سريري كاذب قبل الحالة القانونية. |
| B1-C02 | مستلم غير مخول | حاول إقرار نتيجة حرجة بحساب لا يطابق المستلم أو دوره | رفض ولا تغيير لحالة الإقرار. |
| B1-C03 | إقرار مكرر | أقر النتيجة ثم أعد الإقرار بالمفتاح نفسه وبمفتاح جديد | الأثر الأول فقط؛ الثاني لا ينشئ تسجيلاً أو وقتاً جديداً. |
| B1-C04 | مستلم غير متاح | حاكِ عدم توفر المستلم المعين وفق سيناريو UAT | لا يعتبر الإبلاغ مكتملاً دون دليل تسليم أو مسار تصعيد معتمد. |
| B1-C05 | تزامن إقرارين | نفذ إقرارين من مستلمين في الوقت نفسه | إقرار موثوق واحد؛ الثاني يرفض أو يعيد الحالة النهائية من دون أثر جديد. |
| B1-C06 | إخطار/تدقيق فاشل | حاكِ فشل قناة الإبلاغ أو سجل التدقيق | لا تظهر النتيجة على أنها أُغلقت أو أُقرت؛ يتصاعد الحادث وفق SOP. |

### D. العزل والخصوصية والتخزين المؤقت

| المعرف | حالة الحافة | طريقة التنفيذ | القبول الإلزامي |
|---|---|---|---|
| B1-P01 | تخمين معرف بين مؤسستين | من LAB-B استخدم UUID/ID صحيحاً لمورد LAB-A في قراءة وتعديل واعتماد وإطلاق | `404` أو رفض مخول من دون إظهار الاسم أو الحالة أو وجود المورد. |
| B1-P02 | إعادة استخدام مفتاح عبر مؤسسة | استخدم مفتاح عدم تكرار نفسه في LAB-A ثم LAB-B | لا تعارض عبر المؤسسات ولا كشف متبادل؛ لكل مؤسسة نطاقها. |
| B1-P03 | رابط تاريخ عام | اطلب تاريخاً بمعلومة اتصال تركيبية | المسار معطل افتراضياً ولا يعرض قائمة أو تفاصيل. |
| B1-P04 | رؤوس التخزين المؤقت | افحص طلب نتيجة مصرحاً به عبر أدوات المطور أو proxy اختبار | رؤوس منع التخزين موجودة؛ لا يسمح cache مشترك بمشاركة النتيجة. |
| B1-P05 | تسرب القياسات | نفذ عملية UAT ثم راجع `/metrics/prom` وسجل Sentry الاختباري | لا اسم/معرف مريض أو مستخدم أو قيمة نتيجة أو مفتاح أمر في المقاييس أو الحدث. |

## 4. معايير الإيقاف والقبول

يتوقف UAT فوراً عند أي نجاح لانتقال ممنوع، أو أثر جانبي مكرر، أو فشل كتابة تدقيق، أو وصول عابر للمؤسسات، أو ظهور PHI في المراقبة. يصنف ذلك P0 ولا يعاد التنفيذ على نحو يمحو الأدلة. يفتح قائد UAT حادثاً، ويحتفظ بسجل التدقيق والـSHA ورقم الحالة، ويطبق SOP البديل.

لا تقبل الدفعة الأولى إلا إذا نجحت كل حالات P0/P1 أعلاه، ولم يظهر فشل تدقيق أو أثر مكرر أو وصول عابر للمؤسسات، وكانت بوابة الانحدار ورأس Alembic وحالة الجاهزية ناجحة. تكون عيوب التدريب أو النصوص فقط P2 ولا تصبح مقبولة إلا بقرار موثق وموعد إصلاح.
