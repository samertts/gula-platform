# خطة تنفيذ P0: ربط الأجهزة وإغلاق الإدخال السريري المباشر

**الحالة الحالية:** `NO-GO` لأي ربط حي لجهاز طبي.  
**نطاق الخطة:** نتائج محللات المختبر الواردة فقط؛ يبقى DICOM/الأشعة في وضع المحاكاة ولا يدخل في هذه الدفعة.  
**قاعدة لا تقبل التفاوض:** لا يستطيع جهاز أو بوابة جهاز إنشاء نتيجة سريرية معتمدة، أو تغيير العينة إلى `analyzed`، أو إغلاق طلب، أو إطلاق نتيجة.

> الهدف ليس جعل نقطة النهاية الحالية تعمل مع جهاز حقيقي بسرعة، بل استبدالها بمسار موثوق وآمن: هوية جهاز قوية، تسليم غير مكرر، حجر سريري، ثم اعتماد بشري قابل للتدقيق.

## 1. سبب الخطة ونقطة البداية

مسار `/device/results` الحالي ينشئ `LabResult` ويغيّر حالة العينة والطلب مباشرة بعد طلب يعتمد على مستخدم بشري، بينما `device_id` اختياري ولا توجد حماية موحدة من إعادة الإرسال أو تطابق لرسالة الجهاز. كما أن موصلات ASTM/HL7 وسجل الأجهزة وطابور الأجهزة الحاليين مصممون للمحاكاة أو التحليل، وليسوا مسار نقل طبي حي.

| الأصل القائم            | ما يستفاد منه                                | القيد الذي يعالج في P0                                                              |
| ----------------------- | -------------------------------------------- | ----------------------------------------------------------------------------------- |
| `lab_device_gateway.py` | نموذج HMAC ووقت وnonce وقائمة سماح           | غير موصول بمسار الكتابة، والقبول فيه ليس مغلقاً عند غياب المفتاح أو تعطل مخزن nonce |
| `devices/outbox.py`     | عزل المؤسسة، عدم التكرار، retry وdead-letter | محاكاة فقط ولا يضمن إدخال رسالة من جهاز حقيقي                                       |
| محللات ASTM/HL7         | بداية تطبيع للرسالة                          | لا يوجد framing إنتاجي أو هوية جهاز أو idempotency أو حجر سريري                     |
| `/device/results`       | ربط barcode ونتائج                           | كتابة سريرية وتغيير حالة مباشران يجب إلغاؤهما من مسار الجهاز                        |

## 2. خيارات الإطلاق

| النهج                                    | النتيجة                                                                                        | الكلفة/الإعداد                                                 | القرار                                  |
| ---------------------------------------- | ---------------------------------------------------------------------------------------------- | -------------------------------------------------------------- | --------------------------------------- |
| **إطلاق المرحلة الأولى بلا إدخال حي**    | تبقى الأجهزة في المحاكاة وتستعمل المنشأة الإجراء الوسيط المعتمد لديها لإدخال النتائج ومراجعتها | لا يحتاج بوابة أجهزة جديدة؛ أقل تعقيداً                        | **المسار الأخف والموصى به لـGO الحالي** |
| **تجربة ربط مضبوطة لاحقاً**              | محلل واحد في منشأة واحدة يرسل قياسات إلى حجر فقط عبر بوابة محلية موثوقة                        | يحتاج خادماً/بوابة في المنشأة، شهادات، تنسيق شبكة ومورد الجهاز | يبدأ فقط بعد اكتمال الدفعات أدناه       |
| **ربط جهاز مباشرة بواجهة الويب الحالية** | يسمح بكتابة نتائج وتغيير الحالات من طلب API                                                    | إعداد سريع ظاهرياً لكنه غير آمن سريرياً                        | **مرفوض**                               |

البوابة المحلية المقترحة تعمل قرب الجهاز داخل شبكة المنشأة المنعزلة، وتفتح اتصالاً خارجياً مشفراً فقط إلى المنصة. لا تُكشف أجهزة ASTM/MLLP أو serial أو DICOM مباشرة للإنترنت ولا يُشغّل هذا النوع من الاتصال المستمر من تطبيق الويب الأساسي.

## 3. تعريف النجاح غير القابل للتجاوز

ينجح P0 فقط إذا حققت المنصة الشروط الآتية معاً:

1. تكون الكتابة السريرية من الجهاز **معطلة افتراضياً** في كل بيئة، ولا تفعّل إلا بمفتاح ميزة عالمي ومفتاح منشأة ومفتاح جهاز بعد التوقيعات.
2. تثبت هوية كل بوابة أو جهاز بشهادة عميل `mTLS` أو اعتماد مكافئ تديره الجهة، وتربط بالمؤسسة والجهاز وحالة الاعتماد.
3. تحفظ كل رسالة واردة كرسالة inbox معاملاتية ذات معرف وبصمة وحالة، وتبقى إعادة الرسالة نفسها غير مؤثرة؛ أما المعرف نفسه بحمولة مختلفة فيسجل حادث أمن ويرفض.
4. تتحول نتيجة الجهاز إلى **قياس محجور** فقط. لا يسمح لمسار الجهاز بإصدار `LabResult` نهائي أو تغيير حالة طلب/عينة أو اعتماد/إطلاق نتيجة.
5. يتطلب نقل القياس المحجور إلى النتيجة الرسمية حارس الأوامر: دور مخول، `If-Match`، `Idempotency-Key`، تدقيق قبل/بعد، والتحقق من آلة الحالات.
6. يفشل الإدخال مغلقاً إذا غابت الهوية أو الشهادة أو التوقيع أو nonce أو الوقت أو مخزن منع التكرار أو مطابقة العينة/الاختبار/الوحدة.

## 4. الدفعات التنفيذية المتتابعة

### الدفعة A — الاحتواء والإيقاف الآمن

**الفرع المقترح:** `fix/device-p0-containment`

يضاف مفتاح ميزة مركزي باسم مثل `device_clinical_ingestion` بقيمة افتراضية `false` في جميع البيئات. عندما يكون مغلقاً، تعيد `/device/results` خطأ `503` مجرداً قبل قراءة `barcode` أو أي نتائج. حتى عند الفتح في بيئة اختبار، يمنع المسار الحالي من إنشاء `LabResult` أو تغيير `sample.status` أو `order.status`؛ يستبدل مؤقتاً بقبول إلى حجر فقط بعد اكتمال الدفعات التالية.

| التغيير             | قاعدة القبول                                                                           |
| ------------------- | -------------------------------------------------------------------------------------- |
| حظر الكتابة الحالية | طلب مصادق عليه أو غير مصادق عليه إلى المسار لا يخلق نتيجة ولا يغير حالة ولا يطبع token |
| ضبط الإنتاج         | بيئة الإنتاج لا تقبل قيمة تفعيل يدوية غير موثقة في سجل الإطلاق                         |
| تدقيق الرفض         | يسجل سبب مجرد ومعرف جهاز/مؤسسة متاحان، من دون barcode أو PHI في السجل                  |
| اختبار رجوعي        | المسارات البشرية الشرعية للنتائج لا تتغير سلوكياً                                      |

### الدفعة B — هوية الجهاز والرسالة المعاملاتية

**الفرع المقترح:** `fix/device-p0-identity-inbox`

تنشأ ترحيلات Alembic مستقلة وتراجع ضد الرأس المعتمد قبل الدمج. لا يعاد استعمال جداول المحاكاة بوصفها مصدر ثقة إنتاجي.

| الكيان                   | الحقول الدنيا                                                                                                               | الضوابط                                                                                                  |
| ------------------------ | --------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| `device_identities`      | `id`, `lab_id`, `device_uid`, vendor/model/serial, `certificate_fingerprint`, protocol, status, approved/revoked timestamps | فريد لكل `(lab_id, device_uid)`، وشهادة فريدة، وحالات `pending/active/suspended/revoked/retired`         |
| `device_inbox_messages`  | `id`, `lab_id`, `device_id`, `message_id`, nonce, occurred_at, payload_digest, protocol, status, received_at                | فريد لكل `(lab_id, device_id, message_id)` ولكل nonce ضمن نافذة السياسة؛ payload مشفر أو مرجع تخزين محمي |
| `device_security_events` | المؤسسة والجهاز ونوع الحادث والسبب المجرد والتوقيت وcorrelation id                                                          | append-only؛ لا payload سريري خام في الأحداث أو metrics                                                  |

ينشأ `DeviceIngressService` بوصفه **نقطة الدخول الوحيدة**. لا تثق الخدمة برأس HTTP يحمل شهادة من العميل؛ تتحقق طبقة ingress موثوقة من `mTLS` ثم تمرر هوية موثقة داخل سياق خادم محمي. للحالات التي يرسل فيها المحلل عبر بوابة محلية فقط، توقع البوابة المغلف كاملاً بـHMAC وتستخدم مفتاحاً مرجعياً من مدير الأسرار، وليس ملف إعداد أو قاعدة بيانات تطبيقية.

يجعل التحقق من timestamp وnonce والتوقيع وقائمة السماح إلزامياً. يتحول فقد Redis أو أي مخزن منع التكرار إلى `503` أو `409` آمنين، لا إلى قبول متدهور. يبقى Redis تسريعاً فقط؛ مصدر الحسم هو قيد قاعدة البيانات المعاملاتي.

### الدفعة C — التطبيع والحجر السريري

**الفرع المقترح:** `fix/device-p0-quarantine-workflow`

تفصل هذه الدفعة النقل عن القرار السريري. يضاف كيان قياس وارد مثل `instrument_measurements` وحالاته:

```text
received -> parsed -> matched -> quarantined -> pending_review
                                      |                 |
                                   rejected          accepted_by_authorized_user
                                                            |
                                                     clinical_result_draft
```

لا يوجد انتقال من `received` أو `quarantined` إلى `completed/released`. لا يقبل الانتقال إلى `clinical_result_draft` إلا أمراً بشرياً موثقاً يطابق العينة المتحققة، الاختبار المطلوب، وحدة صالحة، ملف جهاز مفعل، وإصدار المورد الحالي.

| نقطة الفحص                             | الرفض الإلزامي                                              |
| -------------------------------------- | ----------------------------------------------------------- |
| عينة غير موجودة أو ليست `verified`     | حجر/رفض؛ لا نتيجة ولا تغيير حالة                            |
| جهاز من مؤسسة أخرى أو جهاز موقوف       | `404/403` مجرد؛ حادث أمني                                   |
| رمز اختبار أو وحدة خارج ملف الجهاز     | حجر استثناء؛ لا تحويل صامت                                  |
| قيمة غير رقمية أو خارج حد ملف الاختبار | حجر؛ لا تطبيع قسري                                          |
| نتيجة مكررة أو رسالة قديمة             | نفس النتيجة السابقة فقط إن تطابق digest؛ خلاف ذلك رفض وحادث |
| فشل التدقيق أو الحفظ                   | rollback كامل؛ لا يبقى قياس مقبول بلا أثر                   |

تستدعي واجهة المراجعة البشرية `ClinicalCommandGuard` أو المكافئ المعتمد، وتطلب `If-Match` و`Idempotency-Key`. يظل اعتماد النتيجة وإطلاقها ضمن صلاحيات منفصلة عن مشغل الجهاز أو مشرف البوابة.

### الدفعة D — التشغيل، المراقبة، والقتل الآمن

**الفرع المقترح:** `test/device-p0-pilot-gates`

تنفذ البوابة المحلية على مضيف منشأة خاضع لإدارة تقنية المعلومات. تقبل فقط منافذ وبروتوكولات ومصادر IP المسموح بها داخل VLAN الأجهزة، وتمنع الاتصالات الواردة من الإنترنت. ترسل مخرجات آمنة إلى المنصة عبر `mTLS`، مع قائمة شهادات قابلة للإلغاء وhealth check لا يحتوي PHI.

يلزم مفتاح إيقاف عالمي، وآخر لكل منشأة، وآخر لكل جهاز. ينقل الإيقاف كل الرسائل الجديدة إلى `rejected` أو يوقف الوكيل قبل أي كتابة؛ لا يتلف الرسائل الموجودة في inbox أو سجلات التدقيق. تنبه المراقبة عن شهادة قريبة الانتهاء، رسائل مرفوضة، replay، inbox متراكم، dead-letter، فجوة heartbeat، وفشل مطابقة العينة.

## 5. مصفوفة الاختبار والقبول

| المجال            | اختبارات آلية إلزامية                                           | قبول UAT إلزامي                                                    |
| ----------------- | --------------------------------------------------------------- | ------------------------------------------------------------------ |
| الإيقاف الافتراضي | endpoint محظور، ولا كتابة عند إغلاق المفتاح                     | يثبت قائد UAT عدم ظهور أي نتيجة/تغيير حالة بعد محاولة جهاز اصطناعي |
| الهوية            | شهادة غائبة/منتهية/ملغاة/من جهاز آخر ترفض                       | تفعيل جهاز واحد فقط ثم إلغاؤه والتحقق من الرفض الفوري              |
| التوقيع وreplay   | توقيع خاطئ، وقت قديم، nonce مكرر، message ID مكرر بحمولة مختلفة | يكرر المشغل رسالة صحيحة ويفحص عدم تكوين قياس ثانٍ                  |
| العزل             | نفس device UID أو barcode من مؤسسة أخرى لا يكشف وجوده           | تجرب مؤسستان تركيبـيتان حالة التخمين والتكرار                      |
| المعاملات         | فشل inbox أو audit أو المطابقة يعمل rollback                    | تعطيل خدمة اختبارية ثم إثبات عدم وجود حالة سريرية جزئية            |
| الحجر             | رسالة سليمة تنتهي `quarantined` ولا تنشئ `LabResult`            | يوافق مستخدم مخول فقط على قياس مطابق ويثبت أثر التدقيق             |
| التزامن           | إرسالان متوازيان لنفس المغلف يتركان سجلاً واحداً                | يقارن المراقب عدد inbox/measurement/audit قبل وبعد                 |
| التعافي           | انقطاع البوابة، retry، dead-letter، مفتاح الإيقاف               | لا تفقد رسالة ولا تنفذ مرتين بعد العودة                            |

تفشل الدفعة فور نجاح إدخال غير موثق، أو قبول بلا هوية قوية، أو إنشاء نتيجة نهائية من مسار الجهاز، أو تغيير حالة عينة/طلب بلا أمر بشري، أو إعادة أثر جانبي، أو تسرب PHI في السجل أو المراقبة.

## 6. أدلة كل دفعة وقرار التفعيل

لا تدمج أي دفعة تلقائياً. لكل فرع: فحص Ruff وMyPy للنطاق المتغير، اختبارات وحدات وتكامل مستهدفة، اختبار انحدار خلفي مناسب، وفحص Alembic head واحد. تحفظ تقارير CI وروابطها ورقم الـSHA في سجل GO.

لا يفعّل الربط الحي بعد دمج الشفرة فقط. يلزم قبل التجربة المحدودة: اعتماد أمن المعلومات لتصميم الشبكة والشهادات، موافقة مختبرية على ملف الجهاز وخريطة الاختبارات/الوحدات، توقيع قائد السلامة السريرية على مسار الحجر، ونتيجة UAT ناجحة باستخدام بيانات تركيبية. يبدأ التشغيل بجهاز واحد ومنشأة واحدة، قراءة إلى حجر فقط، مع مراقبة مكثفة ومفتاح قتل مختبر.

## 7. ما لا يدخل في هذه الدفعة

لا تشمل P0 بناء DICOM/PACS حي، أو التحكم العلاجي في مضخات/أجهزة ICU، أو تفعيل auto-release، أو إدخال بيانات إنتاجية، أو تخزين شهادات ومفاتيح في Git. تلك نطاقات لاحقة مستقلة وتتطلب مراجعة مخاطر ومورد الجهاز واختبارات تخصصية إضافية.
