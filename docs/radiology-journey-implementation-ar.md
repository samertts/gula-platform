# تنفيذ مسار الأشعة والتصوير الطبي في GULA

## الملخص

أضيفت بوابة آمنة لمسار الأشعة والتصوير الطبي داخل `frontend-v3` تحت المسار `/radiology-operations`. صُممت الصفحة لتفصل بين طلب التصوير، الموعد، الدراسة، التقرير، الصورة، وقائمة العمل، بدلاً من اعتبار الصورة أو التقرير مصدراً وحيداً للحقيقة. يبقى backend هو المرجع النهائي للهوية والتفويض والحالات والتوقيع والإصدار والتدقيق.

## ما تم تنفيذه

تقدم الصفحة وضع Demo اصطناعياً ومعزولاً يعرض دورة الطلب والتحقق والوصول والدراسة والتقرير وقوائم فني الأشعة واختصاصي الأشعة. يستطيع الزائر التنقل بين الطلبات والمواعيد والدراسات والتقارير الاصطناعية، لكن لا يوجد إنشاء طلب أو check-in أو تغيير حالة أو توقيع أو إشعار حرج أو عارض صور حقيقي أو رابط PACS.

في Live تقرأ الصفحة مساحات العمل من `GET /niam/workspaces`، وتقبل فقط مساحة غير شخصية مرتبطة بمنشأة وحالتها فعالة أو موثقة أو معتمدة. بعد تفعيل السياق بواسطة `POST /niam/workspaces/{workspace_id}/switch`، تُقرأ metadata محدودة من العقود التالية:

| المجال | العقد | حدود العرض |
|---|---|---|
| الطلبات | `GET /radiology/orders` | modality وbody part وpriority وstatus ودلالة محدودة؛ لا يظهر Patient ID الخام |
| المواعيد | `GET /radiology/appointments` | التاريخ والوقت والغرفة والحالة؛ لا يوجد check-in أو تعديل |
| الدراسات | `GET /radiology/exams` | accession وmodality وbody part وعدّادات الصور والسلاسل |
| قائمة اختصاصي الأشعة | `GET /radiology/radiologist-worklist` | metadata الدراسة فقط |
| قائمة فني الأشعة | `GET /radiology/technologist-worklist` | metadata الدراسة فقط |
| التقارير | غير موصولة في هذه الموجة | تبقى gated حتى عقد report lifecycle وتوقيع آمن |
| الصور وDICOM/PACS | غير موصولة في هذه الموجة | لا روابط عامة ولا تنزيل أو طباعة |

## فصل الصور عن قاعدة GULA

تحتفظ GULA ببيانات الدراسة والعلاقة والـmetadata، بينما تحتاج صور DICOM إلى PACS أو VNA أو تخزين كائنات محكوماً. لا تُضمّن الصفحة صوراً داخل bundle ولا تضع URL عاماً إلى ملف DICOM. أي عارض مستقبلي يجب أن يستخدم authorized retrieval ورابطاً قصير العمر، ويطبق صلاحية سريرية وسجلاً لفتح الصورة والتنزيل والطباعة.

## الحراسة والعزل

أضيفت سياسة دفاعية لمسار `/radiology-operations` تشمل الأدوار الموجودة فعلياً: الإدارة، الطبيب، الموظف، الفني، و`demo_viewer`. هذه الحراسة ليست بديلاً عن authorization الخادمي. لا تنشئ المؤسسة صفة اختصاصي أشعة، ولا تمنح الصفحة وصولاً إلى صورة أو تقرير بمجرد وجود مستخدم أو طلب؛ يجب أن يثبت الخادم Professional Identity وMembership وFacility Context والعلاقة السريرية المناسبة.

## الحالات والوظائف المحجوبة

تبقى دورة الطلب والحجز والوصول والتحقق من الهوية والسلامة الخاصة بـMRI والصبغة وإنشاء الدراسة واستلام DICOM وتقييم الجودة والتوزيع والتفسير والتقرير والتوقيع والإصدار والاكتشاف الحرج والمشاركة وإعادة القراءة والاستيراد الخارجي والتخزين والأرشفة كلها بحاجة إلى عقود خادمية مستقلة أو لم تُفتح من الواجهة الحالية.

أي كتابة مستقبلية تحتاج state machine صريحة، منع الانتقال غير الصالح، `If-Match` أو version، `Idempotency-Key`، علاقة مريض وسياق سريري، صلاحية مهنية، تدقيقاً غير قابل للحذف، وفصلاً بين التقرير الأصلي والإضافة والتصحيح والرأي الثاني. لا يعتمد النظام على Patient Name، ولا يستخدم Last Write Wins لحل تعارضات الهوية أو التقرير أو الدراسة.

الاكتشافات الحرجة لا تُعامل كتنبيه مرئي فقط؛ يلزم تسلسل Sent ثم Delivered ثم Acknowledged ثم Escalated عند الحاجة، مع تحديد الفريق السريري المسؤول وسجل التدقيق. كما لا يحول الذكاء الاصطناعي أو التعرف على الصور اقتراحاً إلى تشخيص أو تقرير نهائي دون مراجعة بشرية.

## اختبارات حاجز API

تمت إضافة سماح ضيق لقراءات الطلبات والمواعيد والفحوص وقوائم العمل. بقيت قراءات التقارير والصور غير المصنفة محجوبة، كما بقيت كل كتابات الأشعة محجوبة في حاجز الواجهة. أضيفت اختبارات تثبت عزل Demo، وعدم القراءة قبل تفعيل سياق المنشأة، وعدم تسريب `patient_id`، وحجب عارض DICOM والتقارير والتوقيع والاكتشافات الحرجة.

## الحدود التشغيلية

هذه الموجة لا تثبت تكاملاً مع جهاز CT أو MRI أو PACS أو VNA أو DICOM Gateway أو RIS خارجي، ولا تثبت ترخيص Tele-Radiology أو اعتماد تقرير أو إرسال إشعار حرج أو مشاركة دراسة مع طبيب آخر. كما لا تعني جاهزية الإنتاج أو اكتمال متطلبات الخصوصية والاحتفاظ والتعافي من الكوارث؛ تلك تحتاج بنية تشغيلية وموافقات أمنية وقانونية واختبارات PostgreSQL وPACS فعلية ببيانات اصطناعية.
