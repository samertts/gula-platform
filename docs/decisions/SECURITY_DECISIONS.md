## AD-SEC-001: JWT Token Strategy

| Field | Value |
|-------|-------|
| **Decision ID** | AD-SEC-001 |
| **Problem** | The GULA Platform needs an authentication mechanism that supports access + refresh tokens, revocation, fine-grained permission versioning, and is secure for healthcare data. The token strategy must work across the monolith and future microservices, support mobile clients (long-lived sessions), and integrate with the existing FastAPI/Starlette middleware ecosystem. |
| **Context** | Users authenticate via `POST /login` (username/email + password). The platform issues an access token (short-lived, default 15-60 min) and a refresh token (long-lived, default 30 days). Access tokens carry `user_id`, `lab_id`, `role`, `perm_ver`, `jti`, and `type` (access vs. refresh). Token signing uses `SECRET_KEY` from environment (hard-fail if missing or weak). The JWT library is `python-jose` (python-jose). Token blacklisting uses Redis via `blacklist:jti:{jti}` key. Permission versioning (`perm_ver`) invalidates all tokens for a user when their roles/permissions change. |
| **Alternatives Considered** | (1) HS256 (symmetric) — single secret for signing and verification. (2) RS256 (asymmetric) — private key signs, public key verifies, enabling third-party verification. (3) OAuth2 opaque tokens — token introspection endpoint, no JWT. (4) Session cookies — server-side session store, cookie-based auth. |
| **Chosen Solution** | **HS256 symmetric JWT tokens** with the following design: (a) Access token: `{"type":"access", "jti": uuid4, "user_id", "lab_id", "role", "perm_ver", "exp", "iat"}`, short TTL (configurable via `JWT_EXPIRE_MINUTES`). (b) Refresh token: `{"type":"refresh", "jti": uuid4, "user_id", "exp", "iat"}`, long TTL (configurable via `REFRESH_TOKEN_EXPIRE_DAYS`), signed with a separate `REFRESH_TOKEN_SECRET`. (c) Blacklisting: `blacklist:jti:{jti}` in Redis for logout and token revocation. (d) Permission versioning: `perm_ver` in the token payload is checked against the user's current `perm_version` (stored in Redis and DB); if mismatched, the token is rejected and the user must re-authenticate. (e) Timing-safe login: dummy hash prevents user enumeration. Shared auth library (`shared/auth`) provides canonical `create_access_token`, `create_refresh_token`, `decode_access_token`, `hash_password`, `verify_password`. |
| **Rejected Solutions** | RS256 rejected because: asymmetric keys add key management complexity (key rotation, distribution), third-party verification is not needed (only the GULA backend verifies tokens), and HS256 is simpler for a single-service deployment. OAuth2 opaque tokens rejected because: every API call requires a token introspection request to the authorization server (latency + load), JWT is self-contained (no introspection needed), and mobile clients work better with self-contained tokens. Session cookies rejected because: server-side session storage doesn't scale horizontally without a shared session store (Redis would be required for every request), mobile apps require token-based auth (Bearer header), and cookie auth is vulnerable to CSRF. |
| **Trade-offs** | *Positive:* Self-contained tokens (no DB/Redis lookup for every request). Permission versioning provides instant revocation without blacklisting individual tokens. Separate refresh token secret limits blast radius (refresh token compromise doesn't leak signing key). Timing-safe login prevents user enumeration. Shared library ensures consistency across monolith and future microservices. *Negative:* JWT size (~1KB) adds overhead to every request. Token revocation requires Redis (blacklist check on every request). Permission versioning forces re-login when roles change. HS256 means any service that knows `SECRET_KEY` can forge tokens (mitigation: keep `SECRET_KEY` secret, never share across trust boundaries). |
| **Evidence** | Implemented in `backend/app/security/auth.py` using `shared/auth`. `build_token_payload()` constructs the JWT payload with `user_id`, `lab_id`, `role`, `perm_ver`. `blacklist_token()` and `is_token_blacklisted()` manage revocation via Redis. `_DUMMY_HASH` pre-computed bcrypt hash used for timing-safe login. `config.py` enforces: `SECRET_KEY` must be set and not weak (`_is_weak_secret`), `JWT_ALGORITHM` defaults to HS256, `JWT_EXPIRE_MINUTES` defaults to 60, `REFRESH_TOKEN_EXPIRE_DAYS` defaults to 30, `REFRESH_TOKEN_SECRET` must be set and distinct from `SECRET_KEY`. |
| **Approval** | Engineering Lead (2026-01-01) |
| **Implementation Date** | 2026-01-01 |
| **Review Date** | 2026-07-01 |
| **Impact** | All authenticated endpoints use the `get_current_user` dependency which decodes the JWT and verifies `perm_ver`. The `perm_ver` check in `dependencies.py` compares the token's `perm_ver` against the value in `user:perm_ver:{user_id}` Redis key (set by `bump_perm_version()` in `session.py`). Logout calls `blacklist_token(jti, ttl)`. Refresh tokens are stored server-side (session DB) and rotated on use. |
| **Risk** | *High.* JWT compromise is catastrophic (attacker can impersonate any user). Mitigations: (a) `SECRET_KEY` and `REFRESH_TOKEN_SECRET` are strong random values (generated by `make secrets-gen`), (b) weak-secret detection in `config.py` prevents deployment with default/weak keys, (c) access tokens are short-lived (configurable, default 60 min), (d) refresh tokens are rotated on use (old refresh token is invalidated), (e) `perm_ver` provides instant revocation, (f) all JWT operations go through `shared/auth` (tested, audited). |
| **Rollback Strategy** | Rollback to a different token strategy: (1) deploy new auth endpoints that issue the new token format, (2) support both old and new tokens during transition (dual validation in `get_current_user`), (3) after all clients have rotated to new tokens, disable old token validation. This is a weeks-long transition, not a quick rollback. |
| **Future Re-evaluation Criteria** | Re-evaluate when: (a) the platform supports OAuth2 third-party clients that need token introspection, (b) RS256 or ES256 becomes necessary for multi-service trust boundaries, (c) a JWT library vulnerability requires a migration to a different library (e.g., python-jose to PyJWT), (d) the Iraqi Ministry of Health mandates a specific authentication standard (e.g., SAML assertions for national health data access). |

## AD-SEC-002: Multi-Factor Authentication

| Field | Value |
|-------|-------|
| **Decision ID** | AD-SEC-002 |
| **Problem** | Medical laboratory accounts with access to patient data require stronger authentication than passwords alone. The platform must support multiple MFA methods to accommodate different lab environments and user preferences, including healthcare professionals who may not have smartphones, government officials with specific authentication requirements, and lab technicians who need fast, frequent access. |
| **Context** | The MFA module (`backend/app/security/mfa_service.py`) supports three methods: TOTP (authenticator app, primary method), SMS (phone-based verification code, fallback), and WebAuthn (biometric/passkey, advanced). MFA setup is per-user with device management. Backup codes are generated during setup for account recovery. MFA sessions have a 10-minute TTL (`MFA_SESSION_TTL_MINUTES = 10`). The `MFADevice` and `MFASession` models store device info and pending MFA state. |
| **Alternatives Considered** | (1) TOTP only — simplest, no phone number needed, works with any authenticator app. (2) SMS only — universal reach, but SMS is insecure (SIM swap, SS7 attacks). (3) WebAuthn only — most secure, but requires platform/browser support. (4) **TOTP + SMS + WebAuthn (chosen)** — supports all user scenarios. |
| **Chosen Solution** | **Three-method MFA** (TOTP primary, SMS fallback, WebAuthn advanced): (a) TOTP — `generate_totp_secret()`, `generate_totp_uri()` for QR code setup, `verify_totp()` for validation. Primary method for most users. (b) SMS — OTP via SMS (fallback for users without smartphones). Uses Twilio/similar provider abstracted via `shared/auth/mfa`. (c) WebAuthn — `generate_registration_options_for_user()`, `verify_registration()`, `generate_authentication_options_for_user()`, `verify_authentication()`. For high-security roles (admin, ministry). (d) Backup codes — generated on MFA setup, hashed with bcrypt, stored in `MFADevice.backup_codes` as JSON array, verified via `verify_backup_code()` / `hash_backup_codes()`. (e) MFA sessions — `MFASession` tracks pending MFA verification and expires after 10 minutes. Users with `high_security` deployment mode have 2FA required. |
| **Rejected Solutions** | TOTP-only rejected because: some lab staff may not have smartphones (SMS fallback needed). SMS-only rejected because: SMS is vulnerable to SIM swap and SS7 attacks, unreliable in some Iraqi regions, and costs per message. WebAuthn-only rejected because: not all platforms support WebAuthn (older browsers, Windows 7), biometric hardware is not universal, and it complicates the setup flow for non-technical users. |
| **Trade-offs** | *Positive:* Multiple methods accommodate all user scenarios. Backup codes provide account recovery without support tickets. MFA sessions (10-min TTL) allow a grace period after login before MFA is required again. `high_security` deployment mode enforces 2FA automatically. WebAuthn provides phishing-resistant authentication for high-security roles. *Negative:* Three methods to maintain and test. SMS costs scale with user count. WebAuthn requires HTTPS (already in place) and browser support. MFA adds friction to the login flow (especially for lab technicians logging in frequently). SMS delivery reliability in Iraq is not guaranteed. |
| **Evidence** | Implemented in `backend/app/security/mfa_service.py` using `shared/auth/mfa` and `shared/auth/webauthn`. `MFADevice` model stores TOTP secrets, WebAuthn credentials, SMS phone numbers, and backup codes. `MFASession` model tracks pending MFA. Feature flags and deployment mode override (`high_security` → `2FA required`) are in `feature_flags.py`. |
| **Approval** | Engineering Lead (2026-01-01) |
| **Implementation Date** | 2026-01-01 |
| **Review Date** | 2026-07-01 |
| **Impact** | MFA setup is per-user via `POST /auth/mfa/setup`. TOTP is available to all users. SMS is available as a fallback. WebAuthn is available for high-security roles. `high_security` deployment mode enforces 2FA for all users via feature flags override. MFA bypass is not possible for users in `high_security` mode. Backup codes are one-time-use and regenerated on new device setup. |
| **Risk** | *Medium.* Risks: (a) user locked out due to lost phone + lost backup codes — mitigated by admin account recovery (audit-logged), (b) SMS delivery failures — mitigated by TOTP as primary method, (c) WebAuthn credential loss (platform credential manager reset) — mitigated by backup codes and fallback to TOTP, (d) MFA session hijacking — mitigated by 10-min TTL and IP binding. |
| **Rollback Strategy** | Disable MFA: set feature flag to disable MFA enforcement, allow existing MFA sessions to expire, and remove MFA setup endpoints. This should only be done in emergencies (e.g., MFA service outage). |
| **Future Re-evaluation Criteria** | Re-evaluate when: (a) a new MFA method becomes standard (e.g., FIDO2 passkeys, WhatsApp OTP), (b) the number of SMS OTP messages exceeds cost budget, (c) a security incident reveals a weakness in one of the three methods, (d) the Iraqi government mandates a specific MFA standard for health data access. |

## AD-SEC-003: RBAC + ABAC Hybrid Authorization

| Field | Value |
|-------|-------|
| **Decision ID** | AD-SEC-003 |
| **Problem** | The GULA Platform serves multiple user roles (lab technician, lab manager, doctor, province admin, ministry admin, master admin) across multiple laboratories. Authorization must be role-based (who can do what) AND attribute-based (what data they can access). A single role hierarchy is insufficient because even within the same role, access depends on lab membership, province, and deployment mode. |
| **Context** | Role hierarchy (9 roles × 13 permissions): `master_admin` (level 100), `ministry_admin` (90), `province_admin` (80), `hospital_admin` (70), `lab_manager` (60), `doctor` (50), `lab_technician` (40), `nurse` (30), `viewer` (20). Permissions: `manage_system`, `manage_roles`, `manage_users`, `manage_labs`, `view_all_data`, `manage_patients`, `manage_orders`, `manage_results`, `manage_samples`, `view_results`, `view_patients`, `manage_billing`, `manage_reports`. |
| **Alternatives Considered** | (1) RBAC only — pure role-based with no attribute checks. (2) ABAC only — fine-grained attribute policies for everything. (3) **RBAC + ABAC hybrid (chosen)** — role defines base permissions, attributes refine access. |
| **Chosen Solution** | **RBAC + ABAC hybrid** in `backend/app/security/rbac.py` and `backend/app/security/abac.py`:

**RBAC layer:** Role hierarchy with permission sets. `ROLE_LEVELS` defines hierarchy (integer levels). `ROLE_PERMISSIONS` defines permission sets per role. `has_permission(role, permission)` checks a role's permission. `can_manage_role(actor_role, target_role)` ensures hierarchical management. `require_role(*allowed_roles)` is a FastAPI dependency guard. `can_manage_user(actor, target_user)` adds province-level scoping for `province_admin`.

**ABAC layer:** `ABACRule` with `AttributeCondition` — evaluates conditions against a context dict. Condition operators: `equals`, `not_equals`, `in`, `not_in`, `greater_than`, `less_than`, `contains`, `matches`. Rules can be combined with `effect` (ALLOW/DENY), `priority`, and `conditions`. This supports fine-grained policies like: "a doctor can view results only for their own patients" or "a lab technician can edit results only before validation."

**Hybrid enforcement:** `require_own_lab()` — platform roles bypass, non-platform roles must match `lab_id`. `require_feature_for_lab()` — checks per-tenant feature flag. `assert_lab_within_limit()` — enforces subscription tier limits. |
| **Rejected Solutions** | RBAC-only rejected because: a `lab_technician` in Lab A should not access Lab B's data (requires ABAC `lab_id` check), `province_admin` should only manage users in their province (requires ABAC `province` check), and deployment mode overrides (e.g., `high_security` requires `audit_chain` and `2FA`) are attribute-driven. ABAC-only rejected because: defining every permission as a set of attribute conditions is verbose and error-prone, role hierarchy provides a clear mental model that ABAC policies lack, and most authorisation decisions are role-based (RBAC covers 80% of cases). |
| **Trade-offs** | *Positive:* RBAC provides clear, predictable authorisation for common cases. ABAC handles edge cases (lab isolation, province scoping, deployment mode overrides) without bloating the role hierarchy. The hybrid approach is simpler than pure ABAC and more flexible than pure RBAC. Both layers use the shared library (`shared/rbac`), enabling consistency across monolith and future microservices. *Negative:* Two systems to understand and maintain. Debugging authorization failures requires checking both RBAC and ABAC rules. ABAC rules are in code (not configuration), requiring deployment for changes. The hybrid approach can lead to confusion about which layer applies to a given decision. |
| **Evidence** | Implemented in `backend/app/security/rbac.py` (re-exports from `shared/rbac`) and `backend/app/security/abac.py`. Role hierarchy has 9 roles with 13 permissions. `require_own_lab()` is called in every route handler that accesses tenant data. `require_feature_for_lab()` gates per-tenant features. `assert_lab_within_limit()` enforces subscription tier limits. ABAC rules support 8 condition operators. |
| **Approval** | Engineering Lead (2026-01-01) |
| **Implementation Date** | 2026-01-01 |
| **Review Date** | 2026-07-01 |
| **Impact** | Every authenticated route uses `require_role()` and/or `require_own_lab()`. Platform roles (`master_admin`, `ministry_admin`, `province_admin`) bypass `require_own_lab()` for legitimate cross-lab operations (ministry reporting, analytics). Per-tenant feature flags are enforced via `require_feature_for_lab()`. Subscription tier limits are enforced via `assert_lab_within_limit()`. ABAC rules are available for fine-grained policies but are not yet used extensively (current coverage is RBAC-heavy). |
| **Risk** | *Medium.* Risks: (a) a missing `require_own_lab()` call in a new route leaks data across labs — mitigated by code review checklist requiring `lab_id` verification on every data-accessing route, (b) ABAC rule misconfiguration allows unintended access — mitigated by ABAC rules being in code (reviewed in PR), (c) `require_role()` used without `require_own_lab()` for a tenant-scoped route — mitigated by automated integration tests that assert cross-lab isolation. |
| **Rollback Strategy** | RBAC changes are additive (new roles/permissions) — rollback by removing the new role/permission and redeploying. ABAC changes are also additive — rollback by reverting the rule and redeploying. Neither change type breaks existing functionality in the reverse direction. |
| **Future Re-evaluation Criteria** | Re-evaluate when: (a) the number of ABAC rules exceeds 50 (managing rules in code becomes unwieldy), (b) the team needs externalized authorization (OPA, Casbin) for audit/compliance reasons, (c) ABAC rules need to be modifiable without deployment (runtime policy updates), (d) the platform expands to support external third-party access with different authorization models. |

## AD-SEC-004: National ID Encryption at Rest

| Field | Value |
|-------|-------|
| **Decision ID** | AD-SEC-004 |
| **Problem** | The Iraqi National ID (الرقم الوطني) is personally identifiable information (PII) that must be protected at rest. The SNDHS integration requires storing `national_id` and `sndhs_health_id` for each patient. These fields must be encrypted in the database, decrypted only when needed, and never exposed in logs, error messages, or API responses without explicit consent. |
| **Context** | `patients.national_id` and `patients.sndhs_health_id` are stored in the `patients` table. The encryption key is `ENCRYPTION_KEY` from environment (hard-fail if missing, with ephemeral dev fallback). The encryption implementation uses Fernet (symmetric authenticated encryption) via `shared/security`. The `encrypt()` and `decrypt()` functions are in `backend/app/security/encryption.py`. Decryption is performed only when needed (e.g., SNDHS sync, patient card generation, identity verification). API responses that include these fields are explicitly controlled — never in list views, only in detail views with appropriate permissions. |
| **Alternatives Considered** | (1) Plaintext storage — no encryption, store `national_id` as a plain varchar column. (2) Hash-only — store a hash of `national_id` for matching, but can't recover the original for SNDHS sync. (3) **Fernet symmetric encryption (chosen)** — AES-128-CBC with HMAC authentication via Fernet, key from environment. (4) PostgreSQL `pgcrypto` — native DB-level encryption using `pgp_sym_encrypt`/`pgp_sym_decrypt`. (5) Hashicorp Vault — external encryption service. |
| **Chosen Solution** | **Fernet symmetric encryption** using `shared/security`: (a) Encryption: `encrypt_value(data, key)` — returns a base64-encoded Fernet token. (b) Decryption: `decrypt_value(data, key)` — returns the original plaintext. (c) Key: `ENCRYPTION_KEY` from environment, loaded in `backend/app/security/encryption.py`. (d) Indexing: `national_id` has an index on the encrypted value (exact match only — no LIKE queries, as required by security invariants). (e) Dual-read: code gracefully handles `None` for pre-backfill rows (SNDHS Phase 1). All access to decrypted values is audited via `log_action()` in `audit_service.py`. |
| **Rejected Solutions** | Plaintext storage rejected because: a DB breach would expose all national IDs, non-compliant with Iraqi data protection law, and violates the security invariant "never store plaintext national IDs" (documented in `CLAUDE.md`). Hash-only rejected because: SNDHS sync requires the original `national_id` for government APIs, patient card generation embeds it, and identity verification needs to display it. PostgreSQL `pgcrypto` rejected because: it ties encryption to the database (can't query with application-level encryption), key management is different from app-level (PG uses `SET session`), and it's less portable across DB providers. Hashicorp Vault rejected because: it adds infrastructure complexity (Vault cluster + agent), network latency for every encrypt/decrypt operation, and operational overhead that is disproportionate for a single-server deployment. |
| **Trade-offs** | *Positive:* AES-128-CBC with HMAC authentication (Fernet) provides confidentiality + integrity. Application-level encryption works across any DB provider. Key management is simple (`ENCRYPTION_KEY` env var). Shared library ensures consistency across monolith and future microservices. Dual-read pattern ensures backward compatibility. *Negative:* Encrypted field can't be used for partial-match (`LIKE`) queries (by design — phone lookups must use exact match). Key rotation requires re-encrypting all stored values. Decryption adds ~1ms per operation. If `ENCRYPTION_KEY` is lost, all encrypted data is unrecoverable. Development falls back to an ephemeral key (data encrypted with dev key can't be decrypted in production). |
| **Evidence** | Implemented in `backend/app/security/encryption.py` using `shared/security`. `ENCRYPTION_KEY` is required in production (hard fail with `sys.exit(1)`). Dev fallback generates an ephemeral Fernet key with a warning log. The SNDHS Phase 1 migrations add the encrypted columns with `_has_column()` guards. `config.py` enforces `_is_weak_secret()` check on `ENCRYPTION_KEY`. |
| **Approval** | Engineering Lead, Compliance Officer (2026-01-01) |
| **Implementation Date** | 2026-01-01 (encryption), 2026-07-08 (SNDHS national_id fields) |
| **Review Date** | 2026-07-01 |
| **Impact** | `patients.national_id` is encrypted at rest in the `patients` table. `patients.sndhs_health_id` is also encrypted. Access to decrypted values is controlled via `require_role()` and requires an explicit audit log entry. API responses that include these fields are explicitly controlled — never in list views. `phone` lookups must use exact match (no LIKE). The security invariant "never store plaintext national IDs" is documented in `CLAUDE.md` and enforced by code review. |
| **Risk** | *High.* Risks: (a) `ENCRYPTION_KEY` loss — all encrypted data is permanently unrecoverable (mitigated by storing a backup key in secure offline storage), (b) key rotation — all existing encrypted values must be re-encrypted with the new key (mitigated by planning key rotation as a periodic maintenance task), (c) decryption in logs — code review must ensure encrypted values are never logged (mitigated by `_is_weak_secret` only checking the key value itself, not the encrypted output), (d) timing side-channel — decryption timing could leak information (mitigated by Fernet being constant-time). |
| **Rollback Strategy** | Rollback to plaintext: not possible without re-encryption or a full DB dump and restore. If the encryption feature has a critical bug: disable the encryption layer (store plaintext temporarily), fix the bug, and re-encrypt all affected values. This should only be done in a code-red emergency. |
| **Future Re-evaluation Criteria** | Re-evaluate when: (a) a new encryption standard is mandated by Iraqi law, (b) Fernet is deprecated or found to have a vulnerability, (c) the team needs field-level encryption with different keys per lab (each lab has its own `ENCRYPTION_KEY`), (d) the platform needs to support client-side encryption (zero-knowledge architecture), (e) key rotation becomes operationally burdensome and the team needs automatic key rotation (e.g., via Vault or AWS KMS). |

## AD-SEC-005: Audit Log Hash Chain Integrity

| Field | Value |
|-------|-------|
| **Decision ID** | AD-SEC-005 |
| **Problem** | Medical laboratory operations must be fully auditable — every action that creates, modifies, or deletes patient data must be recorded in an immutable audit trail. The audit log must be tamper-evident: if an attacker gains database access and modifies past audit entries, the integrity violation must be detectable. |
| **Context** | `AuditLog` model stores all audited actions. The hash chain ensures tamper evidence: each audit entry includes `previous_hash` (SHA-256 of the previous entry) and its own `hash` (SHA-256 of `previous_hash + action + entity_type + entity_id + user_id + timestamp + details`). Breaking the chain requires recomputing all subsequent hashes. The audit log module is in `backend/app/audit/` with `log_action()` in `backend/app/services/audit_service.py`. |
| **Alternatives Considered** | (1) Plain audit log — no hashing, just a table of actions with timestamps. (2) Append-only DB — database-level trigger prevents UPDATE/DELETE on audit log table. (3) **Hash chain (chosen)** — cryptographic linking of audit entries. (4) External audit service — separate write-only audit store (e.g., AWS CloudTrail). |
| **Chosen Solution** | **Hash chain audit log** with the following design: (a) Each `AuditLog` entry has fields: `id`, `action`, `entity_type`, `entity_id`, `user_id`, `lab_id`, `details` (JSON), `ip_address`, `user_agent`, `previous_hash`, `hash`, `created_at`. (b) Hash computation: `SHA-256(previous_hash || action || entity_type || entity_id || user_id || lab_id || details || created_at)`. (c) Chain verification: starting from the first entry (genesis hash `0000...`), verify each entry's hash matches the recomputed value and that its `previous_hash` matches the previous entry's `hash`. (d) Integrity check: a background job periodically verifies the chain and alerts on any break. (e) SNDHS v2 audit enhancement adds `sndhs_correlation_id` to relevant entries for government audit compliance. |
| **Rejected Solutions** | Plain audit log rejected because: no tamper evidence, an attacker with DB access can silently modify or delete audit entries, non-compliant with healthcare audit requirements (HIPAA-like Iraqi regulations). Append-only DB rejected because: database-level triggers can be bypassed with superuser access, DB triggers are not portable across PostgreSQL versions, and they provide no tamper evidence (an attacker can UPDATE rows if they have the right permissions). External audit service rejected because: adds network dependency, data leaves our infrastructure (sovereignty concern), operational complexity (yet another service), and cost at scale. |
| **Trade-offs** | *Positive:* Tamper-evident — any modification to past entries is detectable by chain verification. Hash computation is fast (SHA-256). No external dependencies. Works offline (no network required for logging). DB-level constraints prevent NULL hashes. Chain verification can be automated. *Negative:* Storage grows with each audit entry (but storage is cheap — audit logs are text data). Chain verification becomes slower as the log grows (O(n) scan). DB migration to add a new field requires recomputing hashes for all subsequent entries. Hash collisions are theoretically possible (SHA-256 collision resistance makes this negligible). |
| **Evidence** | Implemented in `backend/app/audit/` with `log_action()` in `audit_service.py`. The `AuditLog` model includes hash fields. The SNDHS Phase 1 migration `20260505_0005_sndhs_phase1_audit_logs_v2.py` enhances the audit log with SNDHS correlation fields. Chain verification is available as a background job but not yet automated. All mutations write to the audit log (security invariant: "All mutations MUST write to the audit log"). |
| **Approval** | Engineering Lead (2026-01-01) |
| **Implementation Date** | 2026-01-01 |
| **Review Date** | 2026-07-01 |
| **Impact** | Every audited action creates an `AuditLog` entry with a hash chain link. The `log_action()` function computes `previous_hash` from the last entry and computes the current `hash`. Chain verification is available via admin endpoint or background job. SNDHS Phase 1 adds enhanced audit fields. The immutable policy ensures no existing migration is modified (hash chain integrity is preserved). |
| **Risk** | *Low.* The primary risk is hash chain break due to a bug (e.g., race condition creating two entries with the same `previous_hash`). Mitigated by DB-level unique constraint on `previous_hash` (implicitly) and serial execution of `log_action()`. Another risk: chain verification is not yet automated — a broken chain could go undetected. Mitigation: automate chain verification as a background job in the next sprint. |
| **Rollback Strategy** | Hash chain is forward-only. If the chain breaks due to a bug: fix the bug, recompute hashes from the break point forward, and deploy a migration to repair the chain. This requires a maintenance window and is a rare event. |
| **Future Re-evaluation Criteria** | Re-evaluate when: (a) the audit log exceeds 100M entries (chain verification becomes too slow), (b) the team needs distributed audit logging (multiple services writing to the same chain), (c) a more efficient tamper-evident structure is needed (e.g., Merkle tree), (d) the Iraqi government mandates a specific audit format (e.g., SNDHS v2 audit schema), (e) the hash function (SHA-256) needs to be upgraded due to cryptographic advances. |

## AD-SEC-006: Rate Limiting Strategy

| Field | Value |
|-------|-------|
| **Decision ID** | AD-SEC-006 |
| **Problem** | The GULA Platform must protect against DoS attacks, brute-force login attempts, API abuse, and accidental traffic spikes. Rate limiting must be per-user (authenticated) and per-IP (unauthenticated), use a sliding window for accuracy, and differentiate between clinical write endpoints (exempt from shedding) and other endpoints. |
| **Context** | Rate limiter (`backend/app/security/rate_limit.py`) uses Redis via `cache` singleton for shared state across uvicorn workers. Falls back to in-memory store in development (single-process). Algorithm: fixed-window per (key, time-bucket) pair, with standardised response headers (`X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset`, `Retry-After`). | **Chosen Solution** | **Fixed-window rate limiting** with Redis shared state: (a) Key: `rate_limit:{key}:{window_bucket}`. (b) Window: configurable per endpoint (default 60 seconds). (c) Max requests: configurable per endpoint (default 100/min for general endpoints, 10/min for login). (d) Headers: standardised `X-RateLimit-*` on every response. (e) Clinical write exemption: `/results`, `/orders`, `/samples`, `/critical-alerts` are exempt from shedding (patient-safety operations must never be rate-limited). (f) IP extraction: priority order with anti-spoofing via private IP detection. |
| **Rejected Solutions** | Token bucket rejected because: implementation is more complex, requires tracking both tokens and time, and the fixed-window approach is sufficient for current use cases. Sliding window log rejected because: storing a timestamp for every request is memory-intensive, especially in Redis (O(n) per key). Leaky bucket rejected because: constant processing rate doesn't match our traffic pattern (bursts of lab results after instrument runs). |
| **Trade-offs** | *Positive:* Redis-backed rate limiting is shared across all workers (true global limit). Fixed-window is simple, efficient (O(1) per check), and well-understood. Clinical write exemption ensures patient safety operations are never shed. Headers provide clear feedback to clients and developers. Private IP detection prevents header spoofing. *Negative:* Fixed-window has a burst allowance at window boundaries (all requests can be exhausted at the start of the window). Redis is a single point of failure for rate limiting (but falls back to in-memory if Redis is down). Login rate limiting at 10/min may be too restrictive for some users (mitigated by configurable windows). |
| **Evidence** | Implemented in `backend/app/security/rate_limit.py`. Used for login endpoints (10 requests/min), API endpoints (100 requests/min), registration (3 requests/hour), and password reset (3 requests/hour). Clinical write paths are exempt. The `RateLimiter` class supports direct use in tests and background tasks (no `Request` object needed). Redis fallback: if Redis is down, rate limiting degrades to in-memory (single-process limits only). |
| **Approval** | Engineering Lead (2026-01-01) |
| **Implementation Date** | 2026-01-01 |
| **Review Date** | 2026-07-01 |
| **Impact** | All API routes have rate limiting applied via middleware or per-route decorator. Login endpoints are most strictly limited (10 req/min). | **Risk** | *Low.* The hybrid approach is well-established. Risks: (a) refresh token DB table grows unbounded (mitigated by periodic cleanup of expired tokens), (b) `perm_ver` race condition (user's permissions change during a batch of requests) — mitigated by checking on every request, (c) Redis outage prevents `perm_ver` check (mitigated by in-memory fallback for `perm_ver` lookup). |
| **Rollback Strategy** | Switch to pure JWT (no server-side refresh tokens): issue longer-lived access tokens, remove refresh token storage, remove session listing/revocation endpoints. This loses revocation capability but simplifies the system. |
| **Future Re-evaluation Criteria** | Re-evaluate when: (a) the number of concurrent sessions exceeds 100,000 (refresh token DB cleanup needs optimisation), (b) the team needs token exchange or token impersonation (admin acting as a user for debugging), (c) a more sophisticated session management pattern is needed (e.g., session policies, device fingerprinting, location-based session validation), (d) the platform moves to a stateless architecture where server-side session storage is not available. |

## AD-SEC-012: API Key Strategy for Service Accounts

| Field | Value |
|-------|-------|
| **Decision ID** | AD-SEC-012 |
| **Problem** | Non-human actors (device bridge, edge agent, third-party integrations, monitoring tools, batch scripts) need to authenticate with the GULA API without interactive login. API keys must be scoped to specific permissions, revocable, and distinguishable from human user sessions for audit purposes. |
| **Context** | `backend/app/security/service_accounts.py` manages API keys for service accounts. Each key is: `service_account:{prefix}:{hashed_key}` where `prefix` is the first 8 characters of the raw key (for identification). The raw key is a random 256-bit value (`secrets.token_urlsafe(32)`). Keys are stored as bcrypt hashes in the `service_accounts` table (never plaintext). Key scope defines which endpoints and operations the key can access. Audit logging tracks all key usage. |
| **Alternatives Considered** | (1) JWT issued to service accounts — same as user auth, service account gets a long-lived JWT. (2) Basic auth — username:password for each service account. (3) **API key in Authorization header (chosen)** — `Authorization: Bearer gula_{key}` for consistency with user auth. |
| **Chosen Solution** | **Bearer token API keys** with the following design: (a) Key format: `gula_{random_256bit_value}` — prefix "gula_" identifies GULA keys, the rest is a `secrets.token_urlsafe(32)` random value. (b) Storage: bcrypt hash of the key (never plaintext). (c) Identification: first 8 chars of the raw key are stored as a prefix for log identification. (d) Scope: each key has a permission scope (e.g., `device_bridge:write`, `metrics:read`, `webhook:deliver`). (e) Revocation: keys can be revoked (status = inactive), which stops working immediately. (f) Rotation: keys have an optional expiry date; `make secrets-gen` generates new keys. (g) Audit: all key usage is logged with `user_agent="service_account:{prefix}"`. |
| **Rejected Solutions** | JWT for service accounts rejected because: long-lived JWTs are harder to revoke (can't blacklist individual service tokens without Redis), JWT expiry requires key rotation planning (confusing for operators), and JWTs are larger than API keys. Basic auth rejected because: username:password in every request is less secure (password is the key, not a bearer token), and mixing basic auth with Bearer auth in the same Authorization header parsing complicates middleware. |
| **Trade-offs** | *Positive:* API keys are consistent with user auth (both use `Authorization: Bearer <token>`). Bcrypt hashing protects keys at rest (DB breach doesn't expose keys). Prefix-based identification makes logs readable. Scope limits blast radius per key. Revocation is immediate. *Negative:* Key rotation requires coordination with the service owner (the new key must be deployed before the old key expires). Bcrypt hashing adds ~10ms per verification (acceptable for service-to-service auth at low volume). No built-in key usage dashboard (would need to build one). |
| **Evidence** | Implemented in `backend/app/security/service_accounts.py`. Used by: device bridge (`services/device_bridge/app/integration/gula_client.py`), edge agent (`edge_agent/`), monitoring tools (`metrics */prom`), and webhook delivery. Key prefix format: `gula_{8-char-ident}_{random}`. Scope currently used: `device_bridge:write` for instrument result ingestion. |
| **Approval** | Engineering Lead (2026-01-01) |
| **Implementation Date** | 2026-01-01 |
| **Review Date** | 2026-07-01 |
| **Impact** | Service accounts authenticate via `Authorization: Bearer gula_{key}`. The `get_current_user` dependency in `dependencies.py` differentiates between user JWTs and API keys. API keys are managed via the admin API (`POST /admin/service-accounts`). Audit logs show `service_account:{prefix}` as the user_agent for key-based requests. |
| **Risk** | *Medium.* API key risks: (a) key leakage (accidentally committed, printed in logs) — mitigated by bcrypt storage (leaked keys can't be reversed to plaintext, but can be used immediately), (b) key not rotated — mitigated by optional expiry dates, (c) scope too broad — mitigated by minimum-scope principle during key creation, (d) key in URL/query string — mitigated by requiring Authorization header (reject query string keys). |
| **Rollback Strategy** | Revoke all API keys via admin API → rotate all service credentials to new keys or switch to JWT-based service auth. The latter requires deploying the new auth method and updating all service clients. |
| **Future Re-evaluation Criteria** | Re-evaluate when: (a) the number of service accounts exceeds 100 (key management needs a dashboard), (b) API keys need to support fine-grained resource-level scoping (not just endpoint-level), (c) the team needs automatic key rotation (keys that auto-rotate on a schedule), (d) a security audit recommends replacing API keys with mTLS or OAuth2 client credentials. |

## AD-SEC-013: Metrics Endpoint Protection

| Field | Value |
|-------|-------|
| **Decision ID** | AD-SEC-013 |
| **Problem** | The GULA Platform exposes a Prometheus metrics endpoint (`/metrics/prom`) that provides detailed performance data (CPU, memory, request rate, latency, error rate, DB pool status). | **Context** | Metrics configuration: `config/prometheus/` contains scrape config and alerting rules. The metrics endpoint requires `Bearer METRICS_BEARER_TOKEN` in production (`ENV=production`). | **Alternatives Considered** | (1) No auth — metrics publicly accessible. (2) Internal-only network — metrics only accessible from within the Docker network (Prometheus container can reach, external can't). (3) **Bearer token auth (chosen)** — simple, standard, compatible with Prometheus' `bearer_token` config. (4) mTLS — mutual TLS for metrics scraping. |
| **Chosen Solution** | **Bearer token authentication** for the `/metrics/prom` endpoint: (a) Token: `METRICS_BEARER_TOKEN` from environment, strong random value. (c) Prometheus config: `bearer_token_file` in `config/prometheus/` contains the token. (d) `make metrics-token`: generates `METRICS_BEARER_TOKEN` and writes it to `config/prometheus/metrics_token` for Prometheus. (e) Security invariant: must require Bearer token in production (documented in `CLAUDE.md`, enforced by code review). |
| **Rejected Solutions** | No auth rejected because: metrics leak information about system behaviour, usage patterns, and potential vulnerabilities (could aid an attacker in targeting the system). Internal-only network rejected because: it works in Docker Compose (Prometheus is on the same network), but breaks in Kubernetes (Prometheus may be on a different network) and doesn't protect against container breakout. mTLS rejected because: it adds certificate management complexity, Prometheus mTLS configuration varies across versions, and a simple bearer token is sufficient for this use case. |
| **Trade-offs** | *Positive:* Simple, standard bearer token auth. Compatible with Prometheus' built-in `bearer_token` config. Token is manageable via `make metrics-token`. Defence-in-depth: metrics also has network-level protection (Docker internal network). *Negative:* Token must be shared with Prometheus (stored in a file). Token rotation requires updating both the env var and the Prometheus config file. If token is leaked, an attacker can scrape metrics (no IP whitelisting). |
| **Evidence** | Implemented as middleware in `backend/app/routes/metrics.py`. The `METRICS_BEARER_TOKEN` env var is loaded in `config.py`. Prometheus config at `config/prometheus/` uses `bearer_token_file`. `make metrics-token` script generates and writes the token. The security invariant is documented in `CLAUDE.md` and enforced by the production startup guard. |
| **Approval** | Engineering Lead (2026-01-01) |
| **Implementation Date** | 2026-01-01 |
| **Review Date** | 2026-07-01 |
| **Impact** | `/metrics/prom` requires `Authorization: Bearer <token>` in production. Prometheus is configured with the token. Development environments may bypass auth for debugging. The token is generated by `make secrets-gen` or `make metrics-token`. Metrics endpoint exposes: request rate, latency histograms, error count, DB pool status, memory usage, and garbage collection stats. |
| **Risk** | *Low.* The bearer token pattern is simple and well-understood. Risks: (a) token leaked in Prometheus config file — mitigated by file permissions and `.gitignore` for the token file, (b) token rotation forgotten — mitigated by periodic token rotation in operational runbooks, (c) development environment without auth accidentally exposed to internet — mitigated by firewall rules (Docker internal network only). |

| **Future Re-evaluation Criteria** | Re-evaluate when: (a) the platform adds more metrics endpoints that need different access policies, (b) the monitoring stack switches to OpenTelemetry collector (which may handle auth differently), (c) a more sophisticated auth mechanism (mTLS, OAuth2 client credentials) becomes necessary for compliance reasons, (d) Prometheus is replaced with a different monitoring system that has different auth capabilities. |

## AD-SEC-015: Kill Switch Architecture

| Field | Value |
|-------|-------|
| **Decision ID** | AD-SEC-015 |
| **Problem** | The GULA Platform has autonomous systems (auto-repair engine, self-audit auto-fix, AI autonomous decisions, scaling operations) that can modify system behaviour without human intervention. In an emergency (e.g., AI starts making incorrect suggestions, auto-repair causes a loop, security incident), administrators must be able to immediately stop all autonomous actions without taking the entire platform offline. |
| **Context** | The kill switch (`backend/app/core/kill_switch.py`) is a central emergency stop for all autonomous system actions. When ACTIVE: auto-repair actions are blocked, self-audit auto-fix is blocked, scaling operations are blocked, and all AI autonomous decisions are blocked. Normal API traffic and reads continue unaffected — this is NOT a system shutdown, only autonomous AI/repair actions stop. Activation methods: (1) Environment variable `KILL_SWITCH=true` + container restart, (2) API endpoint `POST /admin/kill-switch/activate` (instant, admin only), (3) Redis key `gula:kill_switch` (instant, propagates to all instances). Deactivation mirrors activation. |
| **Alternatives Considered** | (1) No kill switch — rely on manual intervention for each autonomous subsystem. (2) System-wide shutdown — stop the entire backend to stop autonomous actions. (3) **Granular kill switch (chosen)** — stops autonomous actions while keeping API traffic flowing. |
| **Chosen Solution** | **Three-activation-method kill switch:** (a) In-memory flag: set via API (`POST /admin/kill-switch/activate`), fastest activation (no restart, no Redis dependency). Tracks `_activated_at` and `_activated_reason` for audit. (b) Redis key (`gula:kill_switch`): auto-expires after 24 hours (`ex=86400`). Instant propagation to all backend instances (workers poll Redis). (c) Environment variable (`KILL_SWITCH=true`): requires container restart but works even if Redis is down. Check order: in-memory → Redis → env var (first active wins). (d) `status()`: returns whether active, reason, activation time, and env var override status. (e) Integration: `is_kill_switch_active()` is called by auto-repair engine (`auto_repair.py` via `_guard_repair()`), self-audit agent, decision guard (`decision_guard.py`), and AI sandbox. |
| **Rejected Solutions** | No kill switch rejected because: an AI malfunction or auto-repair loop could cause cascading issues that require immediate intervention — waiting for a code deploy is too slow. System-wide shutdown rejected because: it stops all API traffic (result entry, patient registration, report printing), which would halt laboratory operations — unnecessary since only autonomous actions need stopping. |
| **Trade-offs** | *Positive:* Granular — stops only autonomous actions. Three activation methods provide redundancy (env var works without API or Redis, API works without restart or Redis, Redis works without restart or env var). Auto-expire (24h) prevents zombie activation. Audit tracking (reason, time) for compliance. *Negative:* Redis key auto-expires after 24 hours — if a kill switch is needed for longer, it must be renewed (by design — prevents forgotten kill switches from blocking autonomous actions indefinitely). API endpoint is admin-only (requires `GULA_ADMIN_TOKEN`). The kill switch has no effect on manual operations (clinical workflows continue). |
| **Evidence** | Implemented in `backend/app/core/kill_switch.py`. `is_kill_switch_active()` checks three sources in order. `activate()` and `deactivate()` with optional Redis propagation. `status()` for admin dashboard. Auto-repair engine calls `_guard_repair()` which checks `is_kill_switch_active()`. AI approval workflow (`ai/approval.py`) checks kill switch before executing approved AI actions. `make kill-switch-on` / `make kill-switch-off` commands for DigitalOcean-level traffic block. |
| **Approval** | Engineering Lead (2026-01-01) |
| **Implementation Date** | 2026-01-01 |
| **Review Date** | 2026-07-01 |
| **Impact** | `is_kill_switch_active()` is the single function that gates all autonomous actions. Auto-repair engine: blocks repair actions when active. Self-audit auto-fix: blocks fixes. AI sandbox: blocks AI execution. Scaling operations: blocked. Normal API traffic (result entry, patient registration, reporting) continues unaffected. The `make kill-switch-on` command configures DigitalOcean-level traffic block in addition to the application-level kill switch. |
| **Risk** | *Low.* The kill switch is simple and well-tested. Risks: (a) kill switch activated accidentally — mitigated by admin-only API and confirmation step, (b) kill switch forgotten in active state — mitigated by 24-hour Redis auto-expire and monitoring alert for prolonged activation, (c) all three activation methods fail simultaneously — mitigated by their independence (env var works if API and Redis are down, in-memory works if Redis and env var are not set). |
| **Rollback Strategy** | Deactivate via any of the three methods: API (`POST /admin/kill-switch/deactivate`), Redis (`DEL gula:kill_switch`), or env var (set `KILL_SWITCH=false` and restart). If all three fail, restart the backend without `KILL_SWITCH=true` (env var override is the most persistent). |
| **Future Re-evaluation Criteria** | Re-evaluate when: (a) a new autonomous subsystem is added that should be gated by the kill switch, (b) the kill switch needs more granular controls (stop AI but allow auto-repair, or vice versa), (c) the kill switch needs to integrate with external monitoring systems (PagerDuty, OpsGenie) for automatic activation on critical alerts, (d) the platform adds autonomous financial operations that need their own kill switch. |
