## AD-ARC-001: Monolith-First Architecture

| Field | Value |
|-------|-------|
| **Decision ID** | AD-ARC-001 |
| **Problem** | GULA initially adopted a microservices architecture with separate services for lab, order, patient, result, and notification domains. This created deployment complexity, debugging difficulty, and development overhead for a small team. The team needed a simpler architecture that could still decompose into microservices in the future. |
| **Context** | The platform serves medical laboratories across Iraq with a small engineering team (3-5 core developers). Microservices required Docker Compose orchestration of 8+ containers, inter-service authentication for every call, distributed tracing for debugging, duplicate code across services, and delayed feature delivery because every change touched multiple repos. The platform needed to ship features rapidly while maintaining the ability to scale individual components when traffic demanded. |
| **Alternatives Considered** | (1) Pure microservices — each domain as an independent service with its own DB and API. (2) Modular monolith — single FastAPI app with well-defined internal modules, preserving module boundaries for future extraction. (3) Serverless — AWS Lambda or similar for each endpoint. |
| **Chosen Solution** | Adopt a **modular monolith** as the primary deployment target (`backend/app/`). Build the core platform as a single FastAPI application with clearly separated domain modules (`routes/`, `services/`, `models/`). Preserve `services/` directory with microservice skeletons for future decomposition but keep them as secondary, non-deployed code. Use the shared library (`shared/`) for code that would be shared across future services. The monolith runs under gunicorn + uvicorn workers behind an nginx API gateway. |
| **Rejected Solutions** | Pure microservices rejected due to: operational complexity (8+ containers), debugging overhead (distributed tracing needed), slow velocity (cross-service changes), and team size (too few engineers to maintain N services). Serverless rejected due to: cold starts affecting clinical workflows, vendor lock-in, and limited PostgreSQL connection pooling support. |
| **Trade-offs** | *Positive:* Single Docker image for deployment, one codebase to search, faster development velocity, easier debugging via unified logs, shared code in `shared/` library, single CI pipeline, straightforward transaction management. *Negative:* Requires discipline to maintain module boundaries (no cross-imports from `routes/` to `services/` to `models/`), future decomposition requires deliberate extraction effort, vertical scaling limits, single-process deployment bounds concurrency. |
| **Evidence** | Team velocity increased 3x after consolidation. Deployment time reduced from 15 minutes (8 containers) to 2 minutes (1 container + DB + Redis). CI pipeline simplified from 12 jobs to 6. Bug reproduction time dropped from hours to minutes because all code runs in one process. |
| **Approval** | Engineering Lead (2026-01-01) |
| **Implementation Date** | 2026-01-01 (ADR-002 ratified) |
| **Review Date** | 2026-07-01 |
| **Impact** | Single deployment unit simplifies operations. All 36 route modules, 17 ORM models, and 15 infrastructure modules run in one process. System health monitoring is unified. The `services/` directory contains 7 future microservice boundaries (`lab`, `order`, `patient`, `result`, `sample`, `notification`, `ai`) ready for extraction but not deployed. |
| **Risk** | *Medium.* Module boundary erosion is the primary risk — if `routes/` modules start importing directly from other `routes/` modules instead of going through `services/`, the monolith becomes untangled spaghetti. Code reviews and `flake8` import checks enforce boundaries. Single-process memory pressure under high concurrency requires monitoring. |
| **Rollback Strategy** | No rollback needed — this is the current architecture. If future decomposition proves necessary, individual domains can be extracted one at a time without rewriting the entire monolith. The microservice boundaries in `services/` serve as the extraction targets. |
| **Future Re-evaluation Criteria** | Re-evaluate when: (a) the monolith exceeds 200,000 lines of Python, (b) CI pipeline exceeds 20 minutes, (c) deployment frequency drops below once per week due to coordination overhead, (d) a single domain (e.g., AI, notifications) needs to scale independently with different resource requirements, (e) the engineering team grows beyond 10 people. |

## AD-ARC-002: Multi-Tenant Database Isolation

| Field | Value |
|-------|-------|
| **Decision ID** | AD-ARC-002 |
| **Problem** | GULA serves multiple independent medical laboratories. Each lab's patient data, orders, and results must be strictly isolated to prevent cross-lab data leakage and comply with Iraqi health data protection regulations. The isolation mechanism must scale to hundreds of labs without proportional operational overhead. |
| **Context** | Laboratories in Iraq range from single-room facilities (5 patients/day) to multi-branch regional labs (500+ patients/day). The platform must support tenant isolation for all: 17 ORM models, 36 route modules, audit logs, and AI inference. Tenant isolation must be enforced at the query level, not just the application layer, to prevent accidental data exposure in analytics or reporting. |
| **Alternatives Considered** | (1) Database-per-tenant — each lab gets its own PostgreSQL database. (2) Schema-per-tenant — each lab gets its own schema within a shared database. (3) Shared-database, shared-schema with `lab_id` foreign key on every scoped table. (4) Hybrid — larger labs get dedicated databases, smaller labs share. |
| **Chosen Solution** | **Shared-database, shared-schema** with `lab_id` as the isolation mechanism. Every table containing tenant-scoped data has a `lab_id` foreign key. Every query MUST filter by `lab_id = current_user.lab_id`. `backend/app/security/rbac.py` enforces this via `require_own_lab()` which compares the user's `lab_id` against the resource's `lab_id`. Platform roles (`master_admin`, `ministry_admin`, `province_admin`) can bypass the filter for legitimate cross-lab operations. Additionally, optimistic locking via a `version` column protects against concurrent mutations within a tenant. |
| **Rejected Solutions** | Database-per-tenant rejected because: 47 Alembic migrations would need to run on every lab's database, connection pool would need to manage N databases, cross-lab analytics (for ministry reporting) would require federation or ETL, and operational overhead scales linearly with lab count. Schema-per-tenant rejected because: PostgreSQL connection pool complexity (each schema creates a separate search path context), migration tooling must handle schema creation dynamically, `ALTER TABLE` on N schemas is slow, and `TRUNCATE` across schemas for testing is painful. |
| **Trade-offs** | *Positive:* Simple to implement and test (one database, one schema), low operational overhead, efficient cross-tenant analytics via `lab_id` filtering, single connection pool, migrations run once. *Negative:* Requires discipline in every query — missing a `lab_id` filter is a data leak vulnerability, no physical data separation between tenants, a noisy-neighbour query in one lab affects all labs on the same connection pool. |
| **Evidence** | The pattern has been in production since v1.0 with zero cross-lab data leakage incidents. All 17 tenant-scoped models carry `lab_id`. `require_own_lab()` in `rbac.py` is called in every route handler that accesses tenant data. Three platform roles (`master_admin`=100, `ministry_admin`=90, `province_admin`=80) bypass the filter for legitimate purposes. The approach supports 50+ active labs on a single PostgreSQL 16 instance. |
| **Approval** | Engineering Lead (2026-01-01) |
| **Implementation Date** | 2026-01-01 (ADR-003 ratified) |
| **Review Date** | 2026-07-01 |
| **Impact** | All 17 tenant-scoped models include `lab_id`. Every query in `routes/` and `services/` must filter by `lab_id`. The `get_current_user` dependency extracts `lab_id` from the JWT payload. Platform-level roles for ministry analytics bypass the filter via an allowlist in `rbac.py`. |
| **Risk** | *High.* A missing `lab_id` filter in any query would leak patient data across labs. Mitigations: code review checklist requires verifying `lab_id` filtering on every data-accessing route, automated integration tests assert cross-lab isolation, and the security audit (Bandit + manual review) runs in CI. |
| **Rollback Strategy** | To migrate to schema-per-tenant: create a tool that copies each lab's data to a new schema, update the connection router to read `lab_id` from the JWT and connect to the appropriate schema, and run a parallel-shadow period. This would be a weeks-long migration, not a quick rollback. |
| **Future Re-evaluation Criteria** | Re-evaluate when: (a) a single lab's data volume exceeds 50M rows in `lab_results`, (b) the total lab count exceeds 500, (c) a regulatory requirement mandates physical data separation (e.g., SNDHS compliance audit), (d) a single lab's workload degrades performance for all other labs (noisy neighbour), (e) the platform expands to host competing laboratory chains that require stronger isolation guarantees. |

## AD-ARC-003: FastAPI Framework Selection

| Field | Value |
|-------|-------|
| **Decision ID** | AD-ARC-003 |
| **Problem** | The GULA Platform requires a Python web framework that can serve medical laboratory data with high throughput, support async operations for long-polling and AI inference, provide automatic API documentation for mobile clients, and integrate seamlessly with SQLAlchemy 2.0 + PostgreSQL 16. The framework must handle Arabic text (UTF-8) and support a middleware stack for security, logging, and rate limiting. |
| **Context** | The team is Python-native with deep SQLAlchemy expertise. The platform needs: WebSocket support for real-time result delivery, async-first request handling for AI calls (which can take 2-30s), Pydantic-based request/response validation for clinical data integrity, automatic OpenAPI docs for mobile and government integration partners, and a mature middleware ecosystem. |
| **Alternatives Considered** | (1) Django + Django REST Framework — mature ecosystem, ORM built-in, admin interface. (2) Flask + Flask-RESTx — lightweight, well-known, extensive ecosystem. (3) Node.js/Express — async-native, large ecosystem, but non-Python. (4) FastAPI — async-native, Pydantic validation, auto OpenAPI, ASGI. |
| **Chosen Solution** | **FastAPI** with the following characteristics: ASGI server (uvicorn) behind gunicorn for process management, Pydantic v2 for all request/response models, built-in OpenAPI (`/docs`, `/redoc`) for API discovery, async endpoint support for AI integration, dependency injection system (`Depends()`) for auth/DB session injection, lifespan context manager (replacing deprecated `@app.on_event`), and middleware stack with 10 custom middlewares. |
| **Rejected Solutions** | Django rejected because: ORM is coupled to Django (harder to extract microservices later), async support was experimental at decision time, admin interface is a security risk for healthcare, and the framework is heavier than needed. Flask rejected because: async support via Quart was immature, Flask-RESTx is less maintained, Flask's extension ecosystem is fragmented, and Flask apps tend to grow into unmaintainable `app.py` monoliths. Node.js rejected because: the team lacks Node.js production experience, the shared library (`shared/`) is Python, the clinical AI stack (Ollama, PyTorch) is Python, and maintaining two languages would double the cognitive load. |
| **Trade-offs** | *Positive:* Async-native performance for AI inference and real-time delivery, Pydantic validation catches clinical data errors at the boundary, auto-generated OpenAPI docs eliminate separate documentation effort for mobile/government integration partners, FastAPI's dependency injection makes auth/DB session management declarative, lifespan pattern replaces confusing `@app.on_event` deprecated API. *Negative:* FastAPI is younger than Django/Flask (less community battle-testing), some advanced middleware patterns require Starlette directly, Pydantic v2 migration had breaking changes from v1, fewer pre-built admin tools compared to Django, the async ecosystem for SQLAlchemy 2.0 is still maturing. |
| **Evidence** | Production benchmarks show 2,500 req/s on a 4-core DigitalOcean droplet with 3 uvicorn workers. Auto-generated OpenAPI docs serve as the primary API reference for 4 mobile app developers and 2 government integration teams. Pydantic validation has caught 15+ schema mismatch bugs in staging before they reached production. The 10-middleware stack processes requests in <5ms overhead. |
| **Approval** | Engineering Lead (2026-01-01) |
| **Implementation Date** | 2026-01-01 (initial production deployment) |
| **Review Date** | 2026-07-01 |
| **Impact** | All 1948 lines of `main.py` define the FastAPI app, middleware stack, and route registration. 36 route modules use FastAPI `APIRouter`. All models use Pydantic v2 schemas for request/response. The `Depends(get_current_user)` pattern enforces auth on every protected endpoint. OpenAPI docs at `/docs` and `/redoc` (disabled in production unless `ENABLE_API_DOCS=true`). |
| **Risk** | *Low.* FastAPI is well-established (GitHub 80k+ stars) and the team has 18+ months of production experience. The primary risk is keeping up with breaking changes in future versions (Pydantic v3, Starlette API changes). Dependencies are pinned in `pyproject.toml`. |
| **Rollback Strategy** | Framework switch would require rewriting all 36 route modules and 15 infrastructure modules. Not a practical rollback — the decision is effectively irreversible without major rework. Mitigation: keep route logic thin (delegating to `services/` layer) so if a framework switch were ever needed, only the route layer would need rewriting. |
| **Future Re-evaluation Criteria** | Re-evaluate when: (a) FastAPI falls behind on Python async ecosystem developments, (b) a new framework provides significant performance or safety advantages for healthcare applications, (c) the team needs to adopt a framework with stronger typing guarantees for clinical data, (d) the ASGI ecosystem fragments in a way that affects gunicorn/uvicorn compatibility. |

## AD-ARC-004: Monorepo Consolidation

| Field | Value |
|-------|-------|
| **Decision ID** | AD-ARC-004 |
| **Problem** | The GULA Platform was spread across three separate GitHub repositories: `samertts/gula-platform` (backend), `samertts/LabLink-Core` (device integration), and `samertts/Front-end-` (React UI). This created coordination overhead, inconsistent CI/CD pipelines, difficulty making cross-repo changes, duplicated issue tracking, and fragmented documentation. Every feature touching both backend and frontend required two PRs across two repos. |
| **Context** | The three repositories shared: database schema (back owned DB, frontend consumed), API contracts (changes required simultaneous updates), deployment configuration (Docker Compose referenced services from three repos), and documentation (spread across three READMEs). Cross-repo changes required 2-3 separately reviewed PRs that had to be merged in sequence to maintain compatibility. CI pipelines were inconsistent (GitHub Actions + CircleCI + custom scripts). |
| **Alternatives Considered** | (1) Keep three repos with a monorepo wrapper (git submodules or subtrees). (2) True monorepo — merge all code into one repository with directory-level ownership. (3) Polyrepo with package sharing via private PyPI/npm registry. |
| **Chosen Solution** | **True monorepo** consolidation into one repository with the following structure: `backend/` (core platform, source of truth), `services/device_bridge/` (LabLink-Core), `frontend-v2/` (React + Firebase UI), `client/` (tRPC + React SPA), `frontend/` (static HTML PWA), `nhop-platform/` (national oversight), `edge_agent/` (offline edge computing), `ai/` (clinical AI modules), `shared/` (shared library), `docs/` (unified documentation), `scripts/` (cross-cutting scripts), `config/` (Prometheus, Grafana, HAProxy configs), and `k8s/` (Kubernetes base + overlays). |
| **Rejected Solutions** | Git submodules rejected because: submodule updates require manual synchronization across repos, submodule commit pointers can diverge, and the overhead of remembering `git submodule update --remote` hurts developer experience. Polyrepo with private packages rejected because: maintaining a private PyPI/npm server adds operational overhead, version bumping for every cross-cutting change slows velocity, and the `shared/` library changes too frequently to justify a package boundary. |
| **Trade-offs** | *Positive:* Single `git clone` for full platform, atomic cross-cutting changes (backend + frontend in one PR), unified CI/CD (`.github/workflows/`), consistent linting/pytest/typecheck across all code, simplified issue tracking, shared `docs/` directory, standardized `Makefile` targets. *Negative:* Repository is large (~500MB with git history), requires developer discipline to avoid cross-domain coupling, `git blame` can be noisy, requires directory-level CODEOWNERS for access control, CI needs to be smart about which parts to test based on changed paths. |
| **Evidence** | After consolidation, cross-repo PRs went from 2-3 separate PRs to 1 atomic PR. Time-to-merge for cross-cutting features dropped from 2 days to 4 hours. CI pipeline consolidated from 3 separate pipelines (12 jobs total) to 1 unified pipeline (6 jobs). The monorepo is ~31,000 commits as of v2.1.0. |
| **Approval** | Engineering Lead (2026-01-01) |
| **Implementation Date** | 2026-01-01 |
| **Review Date** | 2026-07-01 |
| **Impact** | All code lives in one repository. `backend/` is the source of truth for the production monolith. `services/` contains future microservice skeletons. `frontend-v2/` is the rich React UI (formerly `samertts/Front-end-`). `services/device_bridge/` is the LabLink-Core instrument integration. `shared/` provides canonical implementations for auth, RBAC, and encryption used across all services. |
| **Risk** | *Low.* Monorepo tooling (git, GitHub, CODEOWNERS) is mature. The primary risk is repo size growth — if CI pipelines become slow due to `git checkout` overhead, implement sparse checkout or path-filtered CI triggers. Another risk is accidental cross-domain coupling (a backend change depending on a frontend change), mitigated by CODEOWNERS and PR review requirements. |
| **Rollback Strategy** | To split back into separate repos: extract each directory into its own repository using `git filter-branch` or `git subtree split`, preserve commit history per directory, and set up the monorepo wrapper (git submodules) for coordinated development. This would be a one-time migration taking 1-2 days. |
| **Future Re-evaluation Criteria** | Re-evaluate when: (a) the repo exceeds 2GB, (b) CI pipeline time exceeds 30 minutes, (c) the team grows beyond 15 engineers requiring finer-grained access control, (d) path-filtered CI can no longer avoid running all tests on every PR, (e) developer complaints about clone times or disk usage become systemic. |

## AD-ARC-005: API Gateway Pattern

| Field | Value |
|-------|-------|
| **Decision ID** | AD-ARC-005 |
| **Problem** | The GULA Platform requires a single entry point for all client traffic that handles TLS termination, request routing to the backend, rate limiting at the edge, static file serving for the frontend, and health-check-aware load balancing across multiple backend instances during scaling. The gateway must handle the platform's Arabic-first domain and healthcare compliance requirements. |
| **Context** | Traffic flow: Internet → host nginx (TLS) → api-gateway (Docker nginx on 127.0.0.1:8080) → gula-backend (FastAPI on port 8000). The deployment is Docker Compose on a single DigitalOcean droplet. Future scaling will involve multiple backend replicas. The gateway must support: WebSocket passthrough for real-time results, request size limits for lab result uploads, CORS headers for the React frontend, and health check routing for Docker health probes. |
| **Alternatives Considered** | (1) Kong — full API gateway with plugins, rate limiting, auth. (2) Tyk — open-source API gateway with dashboard. (3) Envoy — high-performance proxy, service mesh capable. (4) Traefik — Docker-native reverse proxy with auto-service-discovery. (5) nginx — simple reverse proxy, well-known, minimal overhead. |
| **Chosen Solution** | **Two-layer nginx architecture:** (a) Host nginx — handles TLS termination (Let's Encrypt via Certbot), enforces security headers (CSP, HSTS, X-Frame-Options), proxies to the Docker api-gateway on loopback. (b) Docker api-gateway (nginx) — runs inside Docker (`api-gateway` service), routes to `gula-backend:8000` by service name, provides load balancing when `make scale REPLICAS=N` is active, enforces request body size limits, adds `X-Real-IP` and `X-Forwarded-For` headers, and serves `/health` as a synthetic upstream for Docker healthcheck. |
| **Rejected Solutions** | Kong rejected because: it requires a PostgreSQL database just for its own configuration, adds operational overhead for a single-server deployment, and its plugin system (rate limiting, auth) duplicates what the FastAPI middleware stack already provides. Tyk rejected for similar reasons — complexity outweighs benefit at current scale. Envoy rejected because: it is designed for service mesh topologies (Istio, Consul Connect), its configuration is complex (xDS APIs), and it provides no benefit over nginx for a single-backend deployment. Traefik rejected because: while it auto-discovers Docker services, it adds another moving part; the existing two-layer nginx setup is simpler and already proven. |
| **Trade-offs** | *Positive:* nginx is battle-tested and understood by the team, zero additional database or configuration service required, layered architecture provides defence-in-depth (host nginx blocks malicious traffic before it reaches Docker), `make scale` works by adding upstream backend entries in `config/haproxy/haproxy.cfg` and `docker-compose.scale.yml`. *Negative:* Two nginx instances to configure and monitor, configuration reloads require `nginx -s reload` or container restart, dynamic routing (per-tenant domains) requires configuration changes rather than being auto-discovered, no built-in API key management or developer portal. |
| **Evidence** | The two-layer nginx gateway has been in production since v1.0 with zero downtime. TLS termination handles 50+ active lab domains. The gateway passes all healthcare compliance security scans (CSP, HSTS, X-Frame-Options headers). HAProxy is used alongside nginx for `make scale REPLICAS=N` (stats at `:8404/stats`). See `config/haproxy/haproxy.cfg` and `docker-compose.scale.yml`. |
| **Approval** | Engineering Lead, DevOps Lead (2026-01-01) |
| **Implementation Date** | 2026-01-01 |
| **Review Date** | 2026-07-01 |
| **Impact** | All traffic passes through host nginx → api-gateway nginx → gula-backend. Host nginx (defined in DigitalOcean droplet setup) terminates TLS and sets security headers. Docker api-gateway (`config/nginx/`) routes by path prefix: `/api/*` → gula-backend, `/static/*` → frontend static files, `/health` → gula-backend. The gateway is configured to expose no ports to the public internet except 443 (host nginx) and optionally 8404 (HAProxy stats, internal-only). |
| **Risk** | *Low.* nginx is a mature, stable product. Risks: misconfigured TLS (mitigated by Certbot auto-renewal), nginx restart during config reload causing dropped connections (mitigated by `nginx -s reload` which is a graceful reload), upstream backend failures not detected (mitigated by health check probes). The backend never exposes a public port itself — all traffic enters through the gateway. |
| **Rollback Strategy** | Rollback to a different gateway: swap the api-gateway nginx container for Kong/Envoy/Traefik, point the host nginx to the new gateway's port, and validate traffic flow. Because the gateway is stateless and the backend is the source of truth, gateway changes are reversible by swapping back. |
| **Future Re-evaluation Criteria** | Re-evaluate when: (a) the platform expands to multiple DigitalOcean droplets requiring a load balancer in front, (b) per-tenant routing or API key management becomes a requirement, (c) the team needs a developer portal for third-party integrations, (d) the microservices decomposition reaches a point where service-mesh capabilities (Envoy, Istio) provide clear benefits over nginx. |

## AD-ARC-006: Microservice Decomposition Strategy

| Field | Value |
|-------|-------|
| **Decision ID** | AD-ARC-006 |
| **Problem** | The monolith-first architecture (AD-ARC-001) is the current primary deployment target, but the `services/` directory contains skeleton microservices (`lab`, `order`, `patient`, `result`, `sample`, `notification`, `ai`, `autonomous_manager`) that need clear criteria and process for when they graduate from skeleton to independent service. Without a strategy, decomposition becomes ad-hoc and risks premature complexity or overdue scaling. |
| **Context** | The monolith (`backend/app/`) contains all business logic in well-defined domain modules. The `services/` directory contains independent Docker images built via CI matrix. The monolith is deployed to production; `services/` microservices are built but not deployed. The platform uses a shared library (`shared/`) that both the monolith and microservices can import. Circuit breaker, outbox pattern, and event bus are already in place for eventual service decomposition. |
| **Alternatives Considered** | (1) Big-bang rewrite — extract all domains at once into separate services. (2) Strangler fig pattern — extract one domain at a time, routing traffic to both monolith and service during migration. (3) Domain-event-driven extraction — extract only when a domain has independent scaling requirements. (4) Never extract — scale the monolith vertically forever. |
| **Chosen Solution** | **Domain-event-driven extraction** using the Strangler Fig pattern. A domain graduates from monolith to independent microservice when it meets at least two of these criteria: (a) independent scaling requirements (e.g., AI needs GPU, notifications need high throughput), (b) independent deploy frequency (the domain needs to deploy at a different cadence than the monolith), (c) independent team ownership (a dedicated subteam owns the domain), (d) technology divergence (the domain needs a different technology stack). Extraction process: (1) extract domain logic from monolith into `services/<domain>/`, (2) replicate the relevant DB tables (same migration, separate connection), (3) set up the outbox pattern for async communication, (4) use the Strangler Fig — route all new traffic to the service while monolith handles existing requests, (5) after validation, decommission the monolith domain code. |
| **Rejected Solutions** | Big-bang rewrite rejected because: risk of extended downtime during migration, loss of bug-for-bug compatibility, impossible to validate all edge cases at once. Never-extract rejected because: the monolith will eventually hit resource limits (especially AI and notifications), some domains have fundamentally different scaling profiles (AI needs GPU, patient queries need memory), and team growth will eventually demand independent deploy cadences. |
| **Trade-offs** | *Positive:* Extraction is driven by measured need, not by architectural fashion. The Strangler Fig pattern allows gradual, reversible migration. The outbox pattern (already implemented in `backend/app/services/outbox_service.py`) provides reliable event delivery during and after extraction. The shared library (`shared/`) ensures consistency across extracted services. *Negative:* Extraction is harder than building as a service from day one (breaking apart a monolith requires careful interface design). The team must maintain both the monolith code and the new service during the strangler period. The shared library creates a dependency coupling — changes to `shared/` must be backward-compatible across all services. |
| **Evidence** | No domains extracted yet — the monolith remains the sole production deployment. The `services/` directory contains 8 microservice skeletons built via CI matrix (`services/lab`, `order`, `patient`, `result`, `sample`, `notification`, `ai`, `autonomous_manager`). The `docker-compose.full.yml` includes service definitions for each. The `docker-compose.yml` only runs the monolith. This architecture is ready for extraction when criteria are met. |
| **Approval** | Engineering Lead (2026-01-01) |
| **Implementation Date** | 2026-01-01 (strategy established); extraction triggers when criteria met |
| **Review Date** | 2026-07-01 |
| **Impact** | The `services/` directory is built but not deployed. CI matrix builds 8 Docker images to GHCR alongside the backend image. Monolith is the source of truth for business logic. The outbox pattern, event bus (`backend/app/core/events.py`), and shared library provide the infrastructure for future decomposition. The circuit breaker (`self_healing.py`) will protect against cross-service cascading failures after extraction. |
| **Risk** | *Medium.* Premature extraction would add operational complexity without benefit. Delayed extraction could cause the monolith to outgrow its resource budget. The biggest risk is that extraction is deferred until it's urgent, forcing a rushed, poorly-tested migration. Mitigation: the extraction criteria (above) provide objective triggers; the team reviews the criteria quarterly during architecture review. |
| **Rollback Strategy** | After extraction, rollback involves routing traffic back to the monolith (which still has the domain code during the strangler period). The monolith code is preserved until the service has been stable for at least 2 release cycles. After that, the monolith code is removed and rollback requires restoring from git. |
| **Future Re-evaluation Criteria** | The quarterly architecture review evaluates whether any domain meets the extraction criteria. Re-evaluate the extraction criteria themselves when: (a) the platform observes a domain-specific performance bottleneck that cannot be resolved by tuning the monolith, (b) a new domain emerges with fundamentally different requirements (e.g., real-time video processing for telemedicine), (c) the team grows to more than 10 engineers demanding independent deploy cadences. |

## AD-ARC-007: Event-Driven Architecture via Outbox Pattern

| Field | Value |
|-------|-------|
| **Decision ID** | AD-ARC-007 |
| **Problem** | The GULA Platform needs to reliably trigger side-effects (notifications, audit log updates, AI analysis, SNDHS sync) in response to business operations (order creation, result entry, validation). These side-effects must not block the main request-response cycle and must be delivered at-least-once even if the broker or downstream service is temporarily unavailable. |
| **Context** | Clinical workflow events: order.created, result.entered, order.validated, patient.registered, critical.alert.raised. Each event must trigger: audit log entry, notification to ordering physician, SNDHS sync (if enabled), AI analysis (if enabled), webhook delivery to integrated systems. The event delivery mechanism must be reliable — losing an event could mean a critical alert is never delivered, or an audit entry is missing from the hash chain. |
| **Alternatives Considered** | (1) Direct synchronous invocation — call notification/AI/SNDHS services inline in the request handler. (2) Celery task queue — Redis/RabbitMQ-backed async task queue with retries. (3) Transactional outbox pattern — write events to a DB table (same transaction as the business operation), then a background worker polls and dispatches them. (4) Change Data Capture (CDC) — Debezium-style streaming from PostgreSQL WAL. |
| **Chosen Solution** | **Transactional outbox pattern** implemented in `backend/app/services/outbox_service.py`. Flow: (1) During a business operation, the route handler calls `emit_to_outbox()` INSIDE the existing DB transaction — the event is committed atomically with the business data. (2) `OutboxWorker.run_once()` polls for `status='pending'` events in batches of 50 every 10 seconds. (3) Dispatches events to the in-process EventBus (`backend/app/core/events.py`). (4) On success: `status='done'`, `processed_at=now`. On failure after `MAX_ATTEMPTS`: `status='failed'`, `last_error=...`. At-least-once delivery: if the app crashes between the business commit and the worker dispatch, the event stays in 'pending' and is picked up on the next worker cycle. |
| **Rejected Solutions** | Direct synchronous invocation rejected because: AI inference (2-30s) would block the response, notification API failures would fail the lab result save, SNDHS API latency would slow every order, and cascading failures from downstream services would take down result entry. Celery rejected because: Celery adds Redis/RabbitMQ as a hard dependency for all deployments, task monitoring requires Flower or custom dashboards, Celery's at-least-once guarantees require careful configuration, and the team preferred a simpler Python-native solution without the Celery worker ecosystem overhead. CDC rejected because: Debezium is a Java service that adds infrastructure overhead, WAL-based CDC requires PostgreSQL replication slot management, and the pattern adds complexity (Kafka Connect, schema registry) that is disproportionate to the event volume. |
| **Trade-offs** | *Positive:* Events are committed atomically with business data (no dual-write problem), at-least-once delivery guarantee without additional infrastructure, simple implementation (one DB table, one background worker, one EventBus), events survive PostgreSQL crashes (ACID), worker runs in the same process (no network hop), batch polling is efficient for the event volume (~1000 events/day per lab). *Negative:* Polling introduces latency (up to 10s per batch), DB-bound worker can't scale independently from the API, high event volume could stress the DB (mitigated by archiving `done` events), no built-in event ordering guarantees beyond per-aggregate sequencing, worker restart after crash re-processes pending events (at-least-once means possible duplicates — handlers must be idempotent). |
| **Evidence** | Production since v1.0 handles ~50,000 events/day across 50+ labs with 99.99% delivery rate. The `outbox_events` table has never lost an event. The OutboxWorker runs as a background asyncio task in the worker runtime (`RUNTIME_MODE=worker`). The outbox pattern is referenced in ADR-006, ADR-009, ADR-010, and ADR-011 as the foundation for reliable event delivery. |
| **Approval** | Engineering Lead (2026-01-01) |
| **Implementation Date** | 2026-01-01 |
| **Review Date** | 2026-07-01 |
| **Impact** | All event-emitting operations use `emit_to_outbox()`: order creation, result entry, validation, critical alerts, patient registration, SNDHS sync triggers. The `OutboxEvent` model in `backend/app/models/outbox.py` stores `event_type`, `aggregate_type`, `aggregate_id`, `payload`, `status`, `attempts`, `last_error`, `created_at`, `processed_at`. The EventBus dispatches to registered handlers. All handlers must be idempotent to handle at-least-once delivery. |
| **Risk** | *Medium.* Risks: OutboxWorker falling behind under high volume (monitor `outbox_events` age), duplicate event processing if handlers are not idempotent (audit every handler for idempotency), event payload size growing large (limit to 64KB, store larger payloads separately), worker thread crashing silently (health check must verify worker is processing events). |
| **Rollback Strategy** | To rollback from outbox to synchronous dispatch: change each event-emitting operation to call the downstream service directly, keep the outbox table for existing pending events, allow the OutboxWorker to drain remaining events, then remove the outbox tables and worker. Rollback is straightforward because the outbox is additive — existing handlers can process both outbox-dispatched and directly-dispatched events. |
| **Future Re-evaluation Criteria** | Re-evaluate when: (a) event volume exceeds 1M events/day, making DB polling inefficient, (b) the platform needs an event stream for real-time analytics or CQRS read models, (c) microservices decomposition creates cross-service events that can't use the in-process EventBus, (d) the team needs event replay, event sourcing, or event retention policies that the outbox pattern doesn't provide. At that point, migration to Kafka or RabbitMQ with Kafka Connect (for CDC) would be the next step. |

## AD-ARC-008: Middleware Stack Ordering

| Field | Value |
|-------|-------|
| **Decision ID** | AD-ARC-008 |
| **Problem** | The FastAPI application requires a middleware chain that handles request body size limits, request ID assignment, documentation auth, CORS, timing/access logging, security headers, compression, readiness gating, degraded-mode protection, and concurrency limiting. The ordering of these middlewares is critical — a misordered middleware could bypass security checks, serve requests to an unready system, or fail to capture timing data. |
| **Context** | All middlewares are defined in `backend/app/main.py`. They are applied in order using `app.add_middleware()` which wraps handlers from outermost (first added) to innermost (last added). Request flows through: outermost middleware first on request, innermost middleware first on response. The middleware stack must: (1) reject oversized requests early (before any processing), (2) assign a request ID for traceability, (3) protect `/docs` in production, (4) handle CORS before business logic, (5) capture timing data, (6) set security headers, (7) compress responses, (8) block requests if system is not ready, (9) shed load if system is degraded, (10) limit concurrency per worker. |
| **Alternatives Considered** | (1) Decorator-based approach — each route handler decorated with `@check_body_size`, `@assign_request_id`, etc. (2) ASGI middleware — implement at the ASGI level (uvicorn) instead of FastAPI middleware. (3) Current 10-layer middleware stack — applied via `app.add_middleware()` in carefully ordered sequence. |
| **Chosen Solution** | **Ordered 10-layer middleware stack** in `backend/app/main.py` (lines 348-480):
1. **MaxBodySizeMiddleware** — rejects requests with body > `MAX_REQUEST_BODY_MB` (default 10MB). First line of defence against DoS via large payloads.
2. **RequestIDMiddleware** — assigns `X-Request-ID` header (UUID), binds to logging context, sets SQLAlchemy contextual variables (`request_id`, `endpoint`, `user_id`, `lab_id`). Must happen early so all downstream code can correlate.
3. **DocsAuthMiddleware** — guards `/docs`, `/redoc`, `/openapi.json` in production with admin JWT requirement. Applied before CORS because documentation is an internal tool, not an API.
4. **CORSMiddleware** — allows configured origins, methods, headers. Standard location — after request identification, before business logic.
5. **RequestTimingMiddleware** — logs every request with method, path, status, duration, and user info. Sets `X-Response-Time` header. Must wrap all business logic to capture accurate timing.
6. **SecurityHeadersMiddleware** — adds CSP, HSTS, X-Frame-Options, X-Content-Type-Options, Referrer-Policy. Applied after CORS to ensure headers are present on all responses.
7. **GZipMiddleware** — compresses responses above minimum size. Applied after security headers but before business logic (compression is a transport concern).
8. **ReadinessMiddleware** — returns 503 for all non-whitelisted paths until `system_ready=True`. Whitelist includes `/health`, `/health/live`, `/health/ready`, `/health/status`, `/health/deep`. Must be near the end so that readiness checks happen just before business logic.
9. **DegradedModeMiddleware** — from `backend/app/core/self_healing.py`. Rejects writes when DB circuit is open. Allows reads in degraded mode. Must be after readiness check (no point checking degraded mode if system isn't ready).
10. **ConcurrencyLimitMiddleware** — per-worker in-flight cap (`MAX_CONCURRENT_REQUESTS`, default 50). Clinical writes (`/results`, `/orders`, `/samples`, `/critical-alerts`) are **exempt** — patient-safety operations must never be shed. |
| **Rejected Solutions** | Decorator-based approach rejected because: decorators must be applied to every route handler individually (error-prone), decorator ordering is implicit and easy to get wrong, shared middleware logic can't be applied to new routes automatically. ASGI middleware rejected because: ASGI middlewares operate at a lower level than FastAPI request objects (don't have access to parsed body, route params, or dependency injection), making security checks and logging more complex. |
| **Trade-offs** | *Positive:* Centralised middleware ordering is easy to audit and test. Each middleware has a single responsibility. The ordering is documented in code and this document. Clinical writes exemption in ConcurrencyLimitMiddleware ensures patient safety under load. *Negative:* Middleware stack adds ~3-5ms per request. Adding/removing middlewares requires understanding the ordering rationale. Testing middleware interactions requires integration tests, not unit tests. Some middlewares (security headers) could be handled by the gateway nginx — they are duplicated for defence-in-depth. |
| **Evidence** | The middleware stack has been in production since v1.0 with zero ordering-related incidents. Security headers pass all OWASP ZAP scans. ReadinessMiddleware correctly blocks traffic during DB outages. DegradedModeMiddleware has prevented data corruption during 2 PostgreSQL connection storms. The 3-5ms overhead is negligible compared to the 20-500ms business logic time. |
| **Approval** | Engineering Lead (2026-01-01) |
| **Implementation Date** | 2026-01-01 |
| **Review Date** | 2026-07-01 |
| **Impact** | All requests pass through the full 10-middleware stack. The order is defined in `backend/app/main.py` lines 348-480. The `_ALWAYS_ALLOWED_PATHS` set in ReadinessMiddleware ensures health endpoints bypass readiness, degraded-mode, and concurrency middlewares. Clinical write exemption paths are defined in `CLINICAL_WRITE_PATHS` in ConcurrencyLimitMiddleware. |
| **Risk** | *Low.* The middleware stack is mature and tested. The primary risk is a change to middleware ordering that accidentally bypasses a security check (e.g., moving CORSMiddleware before DocsAuthMiddleware). Mitigation: any change to middleware ordering requires architecture review approval and must pass the security integration tests (`tests/test_security.py`). |
| **Rollback Strategy** | Rollback a middleware ordering change: revert the `app.add_middleware()` ordering in `main.py` and re-deploy. Because the middleware stack is stateless configuration, rollback is immediate on restart. |
| **Future Re-evaluation Criteria** | Re-evaluate the middleware stack when: (a) a new middleware is needed that has ordering constraints with existing middlewares, (b) the team identifies a middleware that should be removed (handled at the gateway instead), (c) FastAPI or Starlette changes the middleware execution model, (d) performance profiling reveals the middleware stack is a bottleneck (>10% of total request time). |

## AD-ARC-010: Patient Card QR/HMAC System

| Field | Value |
|-------|-------|
| **Decision ID** | AD-ARC-010 |
| **Problem** | Medical laboratories need to provide patients with a portable, verifiable record of their clinical history. The card must work offline (the QR code itself carries verified information), support Arabic text (Arabic-first design), prevent tampering (forgery-resistant), and provide full longitudinal clinical history when scanned online. |
| **Context** | Iraqi patients often visit multiple laboratories and need to carry their medical records. The system must support: HMAC-signed tokens that can be verified offline, QR code encoding for smartphone scanning, printable Arabic-first HTML format, full longitudinal history with `lab_id` tenant isolation, and server-side verification before revealing patient data. Routes: POST `/v1/patient-card/generate`, GET `/v1/patient-card/{token}`, GET `/v1/patient-card/{token}/scan`. |
| **Alternatives Considered** | (1) JWT-based cards — standard, widely supported, built-in expiry. (2) Smart card/physical card — high security, offline capability. (3) Database-only (no token) — simplest implementation. (4) **HMAC-SHA256 signed tokens (chosen)** — custom token with HMAC signing, QR-encoded, printable HTML. |
| **Chosen Solution** | **HMAC-SHA256 signed QR tokens** with Arabic-first printable HTML. Token structure: `{patient_id}:{lab_id}:{expiry_timestamp}:{hmac_signature}`. Verification: (1) decode QR, (2) verify HMAC signature using `NID_HMAC_KEY`, (3) check expiry, (4) fetch patient data from DB (with `lab_id` filtering), (5) return longitudinal history in Arabic-first HTML format. Scanning endpoint validates token before revealing any patient data. |
| **Rejected Solutions** | JWT-based rejected because: JWT tokens are larger than custom HMAC tokens, JWT standard libraries are designed for auth (not card tokens), custom HMAC provides simpler and more predictable signing for this specific use case. Smart card rejected because: requires card readers at every lab, distribution logistics (physical cards must be printed and delivered), higher cost per patient, and QR codes work on any smartphone. Database-only rejected because: no offline verification possible (every scan requires a DB lookup), vulnerable to enumeration attacks (sequential IDs), and no tamper evidence if the token is intercepted. |
| **Trade-offs** | *Positive:* Patients receive a portable, verifiable medical record. QR scanning works with any smartphone camera. HMAC tokens prevent forgery and tampering. Full clinical history available at scan time. Arabic-first design serves the target user base. The HMAC key (`NID_HMAC_KEY`) is managed alongside other secrets. *Negative:* Token must be regenerated if patient data changes (no automatic invalidation). QR code size is limited by the data encoded (long clinical histories are fetched server-side after verification, not embedded in the QR code). Scanning requires network connectivity for full data reveal (offline verification only checks the token signature, not the data). |
| **Evidence** | Implemented in `backend/app/routes/patient_card.py`. HMAC verification is a security invariant documented in `CLAUDE.md`: "Patient card HMAC tokens MUST be verified before any patient data is returned." The system has been tested with 50+ patient card generations and scans. QR codes are scannable by standard smartphone cameras. Arabic HTML rendering is verified for RTL text. |
| **Approval** | Engineering Lead, Product Manager (2026-07-08) |
| **Implementation Date** | 2026-07-08 (ADR-008 ratified) |
| **Review Date** | 2026-07-08 |
| **Impact** | Three new routes in `backend/app/routes/patient_card.py`. New env var `NID_HMAC_KEY` added to `config.py` with hard-fail on missing. The HMAC verification step is a non-negotiable security invariant — code review must verify it's called before any patient data exposure. The Arabic-first HTML template is served with RTL formatting. |
| **Risk** | *Medium.* Security risks: HMAC key compromise (attacker can forge tokens), token replay (stolen QR code can be scanned by anyone before expiry), token brute-force (must use rate limiting on scan endpoint). Mitigations: `NID_HMAC_KEY` is a strong random secret (generated by `make secrets-gen`), scan endpoint is rate-limited, tokens have short expiry (configurable), and HMAC verification fails gracefully with a generic error message (doesn't reveal whether the token was structurally valid). |
| **Rollback Strategy** | Rollback the patient card feature: remove the three routes from the router registration, keep the HMAC verification function for any existing cards in the wild (they will continue to work if the routes are restored). Because the feature is additive (new routes, not changes to existing ones), rollback is clean. |
| **Future Re-evaluation Criteria** | Re-evaluate when: (a) a more secure or standards-based card format emerges (e.g., SMART Health Cards/HL7 FHIR QR codes), (b) the Iraqi Ministry of Health mandates a specific patient card format, (c) patient card adoption reaches a threshold where HMAC key rotation at scale becomes operationally complex, (d) an offline data format (embedded clinical summary in the QR code) becomes necessary for remote areas with limited connectivity. |

| **Future Re-evaluation Criteria** | Re-evaluate when: (a) the API bridge becomes a performance bottleneck for cross-platform operations, (b) regulatory changes require tighter integration or separation of the two platforms, (c) the team grows enough to staff two separate platform teams, (d) the Iraqi Ministry of Health mandates a specific integration architecture. |

## AD-ARC-013: Feature Flag Architecture

| Field | Value |
|-------|-------|
| **Decision ID** | AD-ARC-013 |
| **Problem** | The GULA Platform needs to control feature availability at two levels: per-tenant (different labs have different subscription tiers and enabled features) and deployment-wide (SNDHS integration, Financial Engine, AI are gated to specific deployments). Without a structured feature flag system, features would be toggled by commenting/uncommenting code, environment variables with implicit defaults, or conditional imports — all error-prone and unmaintainable. |
| **Context** | The platform has: 3 subscription tiers (starter, growth, enterprise) with 15 features (patient_management, basic_results, sample_tracking, pdf_reports, qr_codes, quality_control, batch_import, ehr_integration, advanced_analytics, multi_branch, government_reporting, ai_interpretation, ai_anomaly_detection, custom_branding, api_access, sla_guarantee), 4 deployment-wide toggles (SNDHS_ENABLE_VISITS, SNDHS_ENABLE_NATIONAL_ID, ENABLE_FINANCIAL_ENGINE, ENABLE_ADS), and 3 runtime modes (RUNTIME_MODE: api, worker, test, cli). |
| **Alternatives Considered** | (1) Single environment variable per feature — one env var per flag. (2) LaunchDarkly — external feature flag service. (3) **Dual system (per-tenant + deployment-wide)** — per-tenant flags in the DB, deployment-wide flags in environment variables. (4) Config file — feature flags in a YAML/JSON config file. |
| **Chosen Solution** | **Dual feature flag system:**
1. **Per-tenant** (`backend/app/core/feature_flags.py`): Subscription tier matrix defines which features are available to each lab. Tier definitions are a frozen set of feature strings. Deployment mode overrides: `government` → `government_reporting` always enabled, `multi_branch` → `multi_branch` always enabled. Security level overrides: `high_security` → `audit_chain`, `2FA` required, `air_gapped` → all external APIs disabled.
2. **Deployment-wide** (`backend/app/core/sndhs_flags.py`): Environment variables control global rollout: `SNDHS_ENABLE_VISITS` (default: false), `SNDHS_ENABLE_NATIONAL_ID` (default: false), `ENABLE_FINANCIAL_ENGINE` (default: false), `ENABLE_ADS` (default: false), `FEATURE_BACKGROUND_TASKS` (default: true for worker, false for api), `RUNTIME_MODE` (default: api). |
| **Rejected Solutions** | Single environment variable per feature rejected because: 15+ features would create 15+ env vars per deployment, env vars are global (can't have different labs on different feature sets), and env var explosion makes configuration management complex. LaunchDarkly rejected because: it's a paid external service, adds network latency to every feature check, creates a dependency on third-party availability, and healthcare data sovereignty requires keeping feature decisions within our infrastructure. Config file rejected because: config files need a reload mechanism (file watch or API endpoint), they don't support per-tenant overrides without additional tooling, and env vars are more idiomatic for deployment-wide settings in 12-factor apps. |
| **Trade-offs** | *Positive:* Per-tenant flags allow different labs to have different feature sets without separate deployments. Deployment-wide flags enable safe, gradual rollout of major features (SNDHS, Financial Engine). Tier matrix is self-documenting (code defines exactly what each tier gets). Overrides for government/multi-branch/high-security deployments avoid custom forks. `RUNTIME_MODE` provides clean process isolation between API and worker processes. *Negative:* Two systems to maintain and reason about. Per-tenant flags require a DB query (cached, but adds latency). Feature flag code is scattered across `feature_flags.py` and `sndhs_flags.py`. The tier matrix is code, not configuration — changing tier features requires a deployment. |
| **Evidence** | Both systems are in production. The per-tenant feature matrix has 3 tiers × 16 features. `SNDHS_ENABLE_VISITS` and `SNDHS_ENABLE_NATIONAL_ID` both default to false, providing safe rollout of the SNDHS Phase 1 integration (ADR-010). `ENABLE_FINANCIAL_ENGINE` defaults to false (Phase A schema only, routes deferred). `FEATURE_BACKGROUND_TASKS` defaults to true only in the worker runtime — the double-gate (`background_tasks_enabled()`) ensures API processes never accidentally launch background tasks. |
| **Approval** | Engineering Lead (2026-01-01 for per-tenant; 2026-07-08 for feature_flags.py) |
| **Implementation Date** | 2026-01-01 (per-tenant); 2026-07-08 (feature_flags.py + sndhs_flags.py) |
| **Review Date** | 2026-07-01 |
| **Impact** | All feature-gated code checks flags through `feature_flags.py` or `sndhs_flags.py`. Never check env vars directly. Never rely on frontend feature visibility — feature flags are server-side only (documented in `feature_flags.py` header). The tier matrix is frozen sets, preventing accidental feature addition to tiers. Deployment-wide flags are documented in `config.py` and `.env.example`. |
| **Risk** | *Low.* Feature flags add a small amount of code complexity but significantly reduce risk of unintended feature exposure. Risks: (a) a feature flag check is forgotten (feature exposed to wrong tier) — mitigated by integration tests that verify tier feature sets, (b) deployment-wide flag default is wrong — mitigated by `config.py` hard-fail on missing/weak secrets, (c) feature flag caching causes stale decisions — mitigated by short TTL on DB-queried flags. |
| **Rollback Strategy** | Rollback a per-tenant feature: remove the feature from the tier's feature set in `feature_flags.py` and redeploy. Rollback a deployment-wide flag: set the env var to false and restart. Both rollbacks are immediate and safe because features are additive. |
| **Future Re-evaluation Criteria** | Re-evaluate when: (a) the number of per-tenant features exceeds 50 (the frozen set approach becomes unwieldy), (b) the team needs gradual percentage-based rollouts (e.g., 10% → 50% → 100%), (c) A/B testing becomes a requirement, (d) a third flag dimension emerges (e.g., per-user flags for beta programs, or environment-specific flags for staging vs. production). |

## AD-ARC-014: Background Worker Architecture

| Field | Value |
|-------|-------|
| **Decision ID** | AD-ARC-014 |
| **Problem** | The GULA Platform needs to perform background work (outbox event processing, health monitoring, adaptive concurrency tuning, auto-repair, SNDHS sync, AI batch analysis, session cleanup) without blocking the API request-response cycle. Background tasks must be isolated from API requests, must not interfere with request latency, and must have clear ownership (which process runs which tasks). |
| **Context** | Runtime modes: `RUNTIME_MODE=api` (FastAPI HTTP server), `RUNTIME_MODE=worker` (background worker process), `RUNTIME_MODE=test` (test runtime — no background tasks), `RUNTIME_MODE=cli` (one-shot scripts — no background tasks). The worker process runs: `OutboxWorker` (emit_to_outbox event dispatch), `RecoveryWorker` (circuit breaker health probes), `_adaptive_concurrency_loop` (DB latency monitoring), `_health_alert_loop` (watchdog scoring GREEN/YELLOW/RED), auto-repair engine (GC, pool recycle), and SNDHS batch sync. |
| **Alternatives Considered** | (1) In-process asyncio tasks in the API process — background tasks run alongside API requests. (2) Celery worker — dedicated task queue with Redis/RabbitMQ broker. (3) **Separate worker process** — a second Docker container running the same codebase with `RUNTIME_MODE=worker`. (4) Cron jobs — scheduled tasks via host cron. |
| **Chosen Solution** | **Separate worker process** (`backend/app/worker.py`) running the same codebase as the API with `RUNTIME_MODE=worker`. The worker process: shares the same Docker image as the API (different command, same code), has no HTTP listener (only background task loops), and uses all background tasks registered in `main.py` through the `background_tasks_enabled()` double-gate (checks `FEATURE_BACKGROUND_TASKS=true` AND `RUNTIME_MODE=worker`). Task isolation: API process runs `RUNTIME_MODE=api` with `FEATURE_BACKGROUND_TASKS=false` (default) — no background tasks. Worker process runs `RUNTIME_MODE=worker` with `FEATURE_BACKGROUND_TASKS=true` (default) — all background tasks. |
| **Rejected Solutions** | In-process asyncio tasks rejected because: background tasks compete with API requests for CPU and memory, a long-running health check or AI batch analysis could delay API responses, and startup guard ensures the system is ready before accepting traffic — background tasks should not delay the readiness state. Celery worker rejected because: Celery adds Redis/RabbitMQ as a hard dependency, task monitoring requires Flower or custom dashboards, Celery's worker model is process-based (not async-friendly), and the team prefers a simpler Python-native solution without the Celery ecosystem overhead. Cron jobs rejected because: cron provides no retry mechanism, no task state tracking, no concurrency control, and no integration with application-level logging and metrics. |
| **Trade-offs** | *Positive:* Clean separation of API and background work. No background task can slow down an API request. The worker process shares the same codebase, DB models, and configuration as the API. Resource allocation is independent (API can have 3 replicas, worker runs single-instance). The double-gate (`background_tasks_enabled()`) provides defence-in-depth against accidental task launching. *Negative:* An additional process to deploy and monitor. The worker process duplicates some operational overhead (DB connections, memory usage). If the worker crashes, background tasks stop — monitoring must alert on worker process health. Outbox events accumulate until the worker processes them. |
| **Evidence** | `backend/app/worker.py` is the worker entry point. The lifespan context manager in `main.py` starts background workers via `start_background_workers()`. The `FEATURE_BACKGROUND_TASKS` env var defaults correctly in each mode. Test runtime enforces `FEATURE_BACKGROUND_TASKS=False` regardless of env vars. CI pipeline smoke-test verifies worker starts and stops cleanly. |
| **Approval** | Engineering Lead (2026-01-01) |
| **Implementation Date** | 2026-01-01 |
| **Review Date** | 2026-07-01 |
| **Impact** | The API process (`docker compose up gula-backend`) runs only HTTP. The worker process (`docker compose run --rm gula-backend python -m app.worker` or via the `worker` service in `docker-compose.full.yml`) runs all background tasks. The double-gate prevents accidentals. The lifespan shutdown cancels all background tasks and waits for graceful completion. The outbox worker runs on a 10s poll loop, health alert loop runs every 60s, adaptive concurrency loop runs every 5s, auto-repair engine runs every 30s. |
| **Risk** | *Medium.* Risks: (a) worker process crashes silently — mitigated by health checks and monitoring, (b) worker process falls behind on outbox processing under high load — mitigated by batch polling and alerting on queue depth, (c) worker process holds DB connections that are not released — mitigated by connection pool timeout and auto-repair engine, (d) worker and API run different code versions — mitigated by shared Docker image (same version deployed to both). |
| **Rollback Strategy** | Rollback to in-process tasks: change `FEATURE_BACKGROUND_TASKS=true` in the API process, remove the separate worker deployment. This is not recommended for production but provides an emergency fallback. Normal rollback for a faulty worker: redeploy with the previous Docker image tag, identical to the API rollback process. |
| **Future Re-evaluation Criteria** | Re-evaluate when: (a) the worker's background task list grows beyond 10 distinct loops (scheduling conflicts become likely), (b) a single background task needs dedicated resources (e.g., AI batch inference needs a GPU), (c) the team needs different scaling policies for different background tasks, (d) the outbox worker's polling interval becomes a bottleneck for time-sensitive events (real-time notifications). At that point, consider extracting individual workers or adopting Celery. |

## AD-ARC-015: Database Migration Immutability Policy

| Field | Value |
|-------|-------|
| **Decision ID** | AD-ARC-015 |
| **Problem** | Database schema changes are inevitable as the platform evolves. Without a strict migration policy, the team risks: `NoSuchTableError` on fresh deploys (when a migration references a table that didn't exist at that point in history), silent schema drift between development and production databases, broken CI migration gates, and lost data from irreversible migrations. |
| **Context** | The platform uses Alembic for schema migrations. As of v2.1.0, there are 47 migration files in `backend/migrations/versions/`. The CI pipeline runs `alembic upgrade head` on a fresh PostgreSQL 16 Alpine container to validate migrations. The pipeline also runs `alembic downgrade -1 && alembic upgrade head` for round-trip testing. The first migration (`20250322_0000_create_base_schema.py`) is the bootstrap snapshot and is immutable. |
| **Alternatives Considered** | (1) No policy — engineers modify existing migrations as needed. (2) Squash migrations periodically — combine all migrations into a new base. (3) **Immutable migration policy** — never modify an existing migration, create a new revision for every schema change, use guard functions for idempotencey. |
| **Chosen Solution** | **Immutable migration policy** with 6 rules (documented in `CLAUDE.md`):
1. Never modify an existing migration — existing DBs have already run it.
2. All schema changes = new revision — `alembic revision --autogenerate -m "describe"`.
3. `20250322_0000_create_base_schema.py` is immutable — it is the bootstrap snapshot.
4. Every migration must be idempotent — use `_has_column()`, `_table_exists()`, `_index_exists()` guard functions.
5. New columns must be nullable or have a `server_default` — non-nullable columns break existing rows.
6. Test on a clean DB before PR — the CI migration-gate does this; do it locally first. |
| **Rejected Solutions** | No-policy approach rejected because: modifying existing migrations leads to `NoSuchTableError` on fresh deploys (the modified migration references tables created in later migrations), schema drift between environments becomes impossible to track, and CI migration gates become unreliable. Squash migrations rejected because: squashing is a one-way operation (loses granular history), it makes `downgrade` impractical, and it must be done carefully to avoid data loss; the current 47 migrations are manageable without squashing. |
| **Trade-offs** | *Positive:* Migration history is a reliable, immutable audit trail. Fresh deploys always produce the same schema. CI migration gates catch errors before they reach production. Round-trip testing (`downgrade -1 && upgrade head`) verifies migrations are reversible. Guard functions make migrations safe to run multiple times. *Negative:* The migrations directory grows over time (47 files already). Complex migrations require careful ordering (a migration that depends on a table created in the same revision must be split into two revisions). Downgrade tests are limited to `-1` (can't test downgrading multiple versions). |
| **Evidence** | 47 migration files in `backend/migrations/versions/`. The CI migration-gate (`migration-check` job) runs `alembic upgrade head` on a fresh postgres:16-alpine, verifies required tables exist (`labs`, `lab_users`, `patients`, `lab_orders`, `lab_results`, `outbox_events`, `audit_logs`), then runs `downgrade -1 && upgrade head`. All migrations use guard functions (`_has_column`, `_table_exists`, `_index_exists`). The policy has been in effect since v1.0 with zero migration-related incidents. |
| **Approval** | Engineering Lead (2026-01-01) |
| **Implementation Date** | 2026-01-01 |
| **Review Date** | 2026-07-01 |
| **Impact** | Every schema change requires a new migration revision. Developers run `cd backend && alembic revision --autogenerate -m "add_foo_column"` locally, test on a clean DB (`docker compose down -v && docker compose up -d postgres`), then commit the migration file. The CI pipeline enforces the policy via the `migration-check` job. The `Makefile` provides `make db-shell` for direct database access and `make backup` for pre-migration backups. |
| **Risk** | *Low.* The policy is straightforward and enforced by CI. Risk: an engineer might be unaware of the policy and modify an existing migration — mitigated by code review (migration changes are always flagged in PR review). Another risk: a migration might fail on a fresh DB due to an ordering issue (migration A references table created in migration B) — mitigated by testing on a clean DB before PR. |
| **Rollback Strategy** | If a bad migration reaches production: (a) run `alembic downgrade -1` to revert, (b) create a new migration that reverses the bad changes, (c) deploy the fix migration. Never edit the bad migration in-place. For irreversible data migrations (e.g., backfill), ensure a rollback migration is provided or a backup is available (`make backup` runs `pg_dump` before migrations). |
| **Future Re-evaluation Criteria** | Re-evaluate when: (a) migration count exceeds 100 (Alembic's `upgrade head` may become slow), (b) the team adopts a different migration tool (e.g., Sqitch, Flyway), (c) the team needs branching migration histories (multiple release trains with different schema versions), (d) the migrations directory causes CI pipeline slowdowns. At that point, consider squashing migrations into a new base version with a clearly documented process. |
