## AD-CLN-001: Arabic-First Medical Terminology Strategy

| Field | Value |
|-------|-------|
| **Decision ID** | AD-CLN-001 |
| **Problem** | The GULA Platform serves Iraqi medical laboratories where the primary language is Arabic. Lab test names, results, patient data, clinical interpretations, and user interface must all be in Arabic. However, the underlying medical standards (LOINC, SNOMED), instrument output protocols (ASTM, HL7), and many drug/test names are in English. The platform must bridge Arabic clinical workflows with English-centric medical data exchange standards. |
| **Context** | Arabic is the primary language: `PLATFORM_NAME_AR = "منصة غولا الصحية"`, all user-facing labels and messages have Arabic (`message_ar`) and English (`message`) variants, and error responses include Arabic text. Medical terminology mapping must connect: local Arabic test names (as used by Iraqi labs) to standard LOINC codes (for interoperability), instrument output (English/ASCII) to Arabic display names, and clinical interpretation output in Arabic. Lab technicians enter data in Arabic (patient names, test results), but instruments output in English. |
| **Alternatives Considered** | (1) English-only with Arabic UI translation — store all data in English, translate UI to Arabic. (2) Arabic-only with English fallback — store all data in Arabic, fallback to English where Arabic is unavailable. (3) **Bilingual canonical storage with Arabic-first display (chosen)** — store both Arabic and English names where possible, display Arabic first, English second. |
| **Chosen Solution** | **Bilingual terminology system with Arabic-first display:** (a) Test catalog: each test type has both an Arabic name (`name_ar`) and an English name (`name_en`). Arabic is used in all user-facing displays. (b) Instrument input: incoming ASTM/HL7 results contain English codes — these are mapped through a lookup table to the local test catalog entry (which has Arabic display names). (c) Patient data: names are stored in Arabic (UTF-8), with optional English transliteration for interoperability. (d) Clinical notes: Arabic is the primary language; interpretations are generated in Arabic by the Ali Reza Engine (AD-AI-006). (e) LOINC mapping: each test in the catalog can optionally link to a LOINC code for interoperability with external systems. (f) ICU collation: PostgreSQL 16 with ICU locale `ar_IQ.UTF-8` for proper Arabic sorting and full-text search. |
| **Rejected Solutions** | English-only rejected because: lab staff read Arabic, patient records must be in Arabic for legal purposes, and the Iraqi Ministry of Health requires Arabic documentation. Arabic-only rejected because: instrument protocols (ASTM/HL7) are English-centric, some medical terms have no standard Arabic equivalent, and international interoperability requires English test names. |
| **Trade-offs** | *Positive:* Arabic-first user experience for Iraqi lab staff. Bilingual catalog supports both local and international use. LOINC mapping enables EHR integration (AD-ARC-008/FHIR). ICU collation provides proper Arabic sorting. *Negative:* Dual-language fields increase storage and maintenance. Terminology mapping requires manual curation for local test names. Some medical terms may not have widely accepted Arabic equivalents. Arabic full-text search with ICU tokenizer may miss dialectal variations. |
| **Evidence** | `PLATFORM_NAME_AR = "منصة غولا الصحية"` in `config.py`. Error messages include Arabic variants (`detail_ar`). Test types in `backend/app/models/test_type.py` include both `name_ar` and `name_en`. The test catalog at setup time seeds Arabic test names. LOINC mapping is optional per test. |
| **Approval** | Engineering Lead, Product Manager (2026-01-01) |
| **Implementation Date** | 2026-01-01 |
| **Review Date** | 2026-07-01 |
| **Impact** | All user-facing text is Arabic-first with English fallback. Test names in the catalog are bilingual. Incoming instrument results map to Arabic display names. LOINC codes enable interoperability. Arabic full-text search uses ICU locale. |
| **Risk** | *Low.* Bilingual terminology is well-established in the codebase. Risks: (a) terminology mapping for new lab tests is missed (test appears in English) — mitigated by requiring Arabic name for all new test types, (b) LOINC mapping is incomplete (some tests lack LOINC codes) — mitigated by optional LOINC field (it's a best-effort mapping), (c) Arabic full-text search misses results due to morphology — mitigated by using PostgreSQL ICU tokenizer which handles Arabic better than the default parser. |
| **Rollback Strategy** | Switch to English-first: change the display logic to use `name_en` first, `name_ar` second. This is a setting in configuration, not a code change. |
| **Future Re-evaluation Criteria** | Re-evaluate when: (a) the Iraqi Ministry of Health mandates a specific Arabic medical terminology standard, (b) SNOMED CT Arabic edition becomes available and should replace or augment LOINC mapping, (c) dialectal Arabic support becomes necessary (Kurdish, Turkmen minority languages), (d) Arabic NLP for clinical text reaches sufficient maturity to automate terminology mapping. |

## AD-CLN-002: Lab Test Catalog Standardization

| Field | Value |
|-------|-------|
| **Decision ID** | AD-CLN-002 |
| **Problem** | Each laboratory has its own test catalog with local names, units, reference ranges, and test codes. For cross-lab interoperability (population health, patient history across labs), the platform needs to normalize these into a standard catalog. Tests must be linkable to LOINC codes for EHR integration, and must carry proper metadata (sample type, unit, reference range by demographics, turnaround time). |
| **Context** | The test catalog is defined in `TestType` model with fields: `name_ar`, `name_en`, `loinc_code`, `sample_type`, `unit`, `reference_range` (default), `turnaround_time`, `is_active`, `test_category`. The device bridge normalizes instrument-specific result codes to the catalog. Reference ranges in `ReferenceRangeDef` can be overridden per lab and per demographic (age, gender, pregnancy status). The catalog is seeded with common Iraqi lab tests during setup (`seed_critical_data` in startup guard). |
| **Alternatives Considered** | (1) No standard catalog — each lab manages its own test list independently. (2) Mandatory LOINC — every test MUST have a LOINC code. (3) **Standard catalog with optional LOINC mapping (chosen)** — shared catalog of common tests, labs can extend, LOINC is optional. |
| **Chosen Solution** | **Shared test catalog with per-lab extensions and optional LOINC mapping:** (a) Base catalog: seeded at setup with 200+ common Iraqi lab tests (CBC, chemistry, serology, microbiology, hormones, urinalysis, coagulation). (b) LOINC mapping: each base test can be linked to a LOINC code (optional — many local tests don't have exact LOINC equivalents). (c) Per-lab extensions: labs can add custom tests not in the base catalog, with locally defined reference ranges. (d) Reference ranges: `ReferenceRangeDef` supports age/gender/pregnancy-specific ranges. Labs can override default ranges. (e) Sample types: `SpecimenCatalog` defines acceptable sample types per test (blood, serum, plasma, urine, CSF, etc.). (f) Panels: `Panel` and `PanelTest` define test panels (e.g., "Basic Metabolic Panel" contains Na, K, Cl, CO2, BUN, Creatinine, Glucose). |
| **Rejected Solutions** | No standard catalog rejected because: cross-lab interoperability would require manual mapping for every patient transfer, population health analysis would be impossible with incompatible test names, and LOINC mapping would need to be done per-lab (duplicated effort). Mandatory LOINC rejected because: many local Iraqi tests have no LOINC equivalent, LOINC codes are updated quarterly (would require constant maintenance), and some labs run research/experimental tests that have no LOINC code. |
| **Trade-offs** | *Positive:* Shared catalog enables cross-lab patient history (same test, same name). LOINC mapping is done once per test type (not per lab). Reference range by demographics improves diagnostic accuracy. Panel support simplifies test ordering. *Negative:* Catalog maintenance effort (adding new tests, updating LOINC mappings). Labs that join with custom test catalogs need mapping effort. LOINC mapping may be inaccurate for some local tests (approximate mapping). |
| **Evidence** | `TestType` model in `backend/app/models/test_type.py`. `ReferenceRangeDef` for demographic-specific ranges. `SpecimenCatalog` for sample types. `Panel` and `PanelTest` for test panels. Base catalog seeded during `seed_critical_data()` in startup guard. |
| **Approval** | Engineering Lead, Product Manager, Medical Advisor (2026-01-01) |
| **Implementation Date** | 2026-01-01 |
| **Review Date** | 2026-07-01 |
| **Impact** | 200+ common tests in the base catalog (seeded at setup). Labs can add custom tests. LOINC mapping is optional. Reference ranges support age/gender/pregnancy-specific values. Panels simplify order entry. Device bridge maps instrument codes to the catalog. |
| **Risk** | *Low.* The test catalog is stable and well-defined. Risks: (a) LOINC mapping is incorrect for some tests (two different local tests mapped to the same LOINC code) — mitigated by review process for LOINC mappings, (b) lab-specific reference ranges are not set (lab uses default ranges which may be inappropriate) — mitigated by reference range setup during lab onboarding, (c) base catalog misses common Iraqi tests — mitigated by extending the catalog based on lab usage patterns. |
| **Rollback Strategy** | Catalog changes are additive (new tests, new LOINC mappings) — rollback by reverting the change. Removing a test from the base catalog requires checking that no lab is using it. |
| **Future Re-evaluation Criteria** | Re-evaluate when: (a) the catalog exceeds 1000 tests (management becomes unwieldy), (b) LOINC quarterly releases require systematic updates, (c) the Iraqi Ministry of Health mandates a specific national test catalog, (d) SNOMED CT integration adds another terminology mapping layer. |

## AD-CLN-003: Critical Value Alert Protocol

| Field | Value |
|-------|-------|
| **Decision ID** | AD-CLN-003 |
| **Problem** | Lab results that fall outside critical thresholds (panic values) require immediate clinical attention. The platform must detect critical values, alert the ordering physician or lab manager, and track acknowledgment. Different labs have different critical thresholds for the same tests. The alert protocol must comply with Iraqi Ministry of Health requirements for critical value notification. |
| **Context** | Critical value thresholds are defined per test per lab in `ReferenceRangeDef` with `critical_low` and `critical_high` fields (in addition to `normal_low` and `normal_high`). When a result is entered with a value outside the critical range: an alert is generated, notification is sent to the ordering physician (via SMS, email, or in-app notification), the lab manager is notified if the physician doesn't acknowledge within a configurable timeout, and the alert is tracked in the audit log. Critical alerts are exempt from rate limiting and concurrency shedding (AD-ARC-008, AD-SEC-006). |
| **Alternatives Considered** | (1) No critical alert — result is entered normally, no special notification. (2) Lab technician manually calls the physician — no automated alerting. (3) **Automated critical alert with escalation (chosen)** — system detects critical values, sends alerts, tracks acknowledgment, escalates if unacknowledged. |
| **Chosen Solution** | **Automated critical alert protocol:** (a) Thresholds: `critical_low` and `critical_high` per test per lab in `ReferenceRangeDef` (overrideable at lab level). (b) Detection: when result is entered/saved, the system checks if the value exceeds critical thresholds. (c) Alert generation: creates a `CriticalAlert` record with result details, timestamp, and assigned responder (ordering physician). (d) Notification: sends alert via available channels (SMS primary, email secondary, in-app notification). (e) Acknowledgment: physician must acknowledge within configurable timeout (default: 30 minutes). (f) Escalation: if not acknowledged within timeout, lab manager is notified. If still unacknowledged after second timeout (default: 60 minutes), the notification escalates to the lab director. (g) Audit: all critical alerts, notifications, acknowledgments, and escalations are logged in the audit log (hash chain). (h) Exemption: critical alert endpoints are exempt from rate limiting and concurrency shedding (patient safety operations must never be shed). |
| **Rejected Solutions** | No critical alert rejected because: non-compliant with Iraqi Ministry of Health requirements and patient safety standards. Manual phone call rejected because: error-prone (forgotten calls, wrong number), no audit trail, and no escalation if the physician is unavailable. |
| **Trade-offs** | *Positive:* Automated detection ensures no critical result goes unnoticed. Escalation chain ensures clinician acknowledgment. SMS notification works even when the physician is not at their computer. Audit trail for compliance. Exempt from shedding (always delivered). *Negative:* SMS delivery depends on mobile network reliability. Escalation pressure may annoy physicians (false positives from incorrect critical thresholds). Three-tier escalation (physician → lab manager → lab director) may be overkill for some lab types. |
| **Evidence** | Critical alert system implemented in `backend/app/routes/critical_alerts.py`. `ReferenceRangeDef` has `critical_low`/`critical_high` fields. Alert creation, notification, acknowledgment, and escalation are implemented. Exempt from rate limiting and concurrency shedding (documented in `CLAUDE.md` as security invariant: "Clinical writes (`/critical-alerts`) are exempt"). |
| **Approval** | Engineering Lead, Product Manager, Medical Advisor (2026-01-01) |
| **Implementation Date** | 2026-01-01 |
| **Review Date** | 2026-07-01 |
| **Impact** | Critical results are automatically detected and escalated. Physicians must acknowledge within 30 minutes (configurable). Escalation to lab manager after 30 min, lab director after 60 min. All actions are audited. Critical alert delivery is exempt from shedding. |
| **Risk** | *Low.* The protocol is well-defined. Risks: (a) incorrect critical thresholds (too many false positives) — mitigated by lab-configurable thresholds, (b) SMS delivery failure — mitigated by fallback to email and in-app notification, (c) physician on leave or unavailable — mitigated by escalation chain (lab manager responds), (d) false sense of security (system detects critical but no one acts) — mitigated by escalation + audit trail. |
| **Rollback Strategy** | Disable automated critical alerts: revert to manual physician notification. This removes the escalation and audit features but ensures no false alert pressure on clinicians. |
| **Future Re-evaluation Criteria** | Re-evaluate when: (a) the Iraqi Ministry of Health issues new critical value reporting requirements, (b) the false-positive rate from incorrect thresholds exceeds 5% of alerts, (c) the platform needs to support more sophisticated alert routing (on-call schedules, group notification), (d) SMS delivery reliability in Iraq becomes a systemic issue (need alternative channel like WhatsApp). |

## AD-CLN-004: Clinical Interpretation Engine Design

| Field | Value |
|-------|-------|
| **Decision ID** | AD-CLN-004 |
| **Problem** | Lab results need clinical context — a result outside the reference range may indicate a specific condition, but interpreting results requires medical knowledge. The platform must provide automated clinical interpretations (suggestions, not diagnoses) that help clinicians understand results faster, while clearly distinguishing AI-generated suggestions from verified clinical diagnoses. |
| **Context** | The clinical interpretation engine is part of the Ali Reza Engine (AD-AI-006). It operates within the AI guardrails framework: interpretations are `SUGGESTION`-type operations that require human approval before being added to the patient record. The engine considers: current result values vs. reference ranges, delta from previous results (rate of change), trends over time (multiple results), pattern matching (combinations of abnormalities suggesting specific conditions), and patient demographics (age, gender, pregnancy). |
| **Alternatives Considered** | (1) No interpretation — raw results with reference ranges only. (2) Static interpretation — hardcoded rules (e.g., "High glucose → consider diabetes"). (3) **AI-powered interpretation (chosen)** — LLM-based interpretation with clinical context, filterable by confidence threshold. |
| **Chosen Solution** | **AI-powered clinical interpretation with rules-based fallback:** (a) AI interpretation: the Ali Reza Engine (LLM-based) generates Arabic-language clinical interpretations considering the full clinical context (current results, trends, demographics). Output is a `SUGGESTION` that requires human approval. (b) Rules-based fallback: if the AI engine is unavailable (network, model load), a simpler rules-based engine generates basic interpretations (e.g., "Sodium is low — consider SIADH, diuretic use, or adrenal insufficiency"). (c) Disclaimer: all AI-generated interpretations carry a disclaimer: "هذا تفسير تلقائي وليس تشخيصاً طبياً. يجب مراجعة الطبيب المختص." ("This is an automated interpretation, not a medical diagnosis. Must be reviewed by a specialist.") (d) Approval: interpretations must be approved by a clinician before being added to the patient's permanent record. (e) Confidence: each interpretation includes a confidence score (0.0-1.0). Low-confidence suggestions are flagged more prominently for human review. |
| **Rejected Solutions** | No interpretation rejected because: clinicians benefit from automated suggestions (faster result review, fewer missed patterns). Static interpretation rejected because: hardcoded rules are brittle, don't handle complex multi-result patterns, and can't adapt to new medical knowledge without code changes. |
| **Trade-offs** | *Positive:* Clinicians get automated interpretation suggestions that speed up result review. AI can detect patterns that rules-based systems miss (multi-result correlations, subtle trends). Rules-based fallback ensures availability even when AI is down. *Negative:* AI interpretations can be wrong (hallucinated) — mitigated by always requiring human approval. Liability concerns (clinician may rely on AI instead of forming their own judgment) — mitigated by clear disclaimers and approval requirement. LLM latency (2-10s) adds delay to result review workflow. |
| **Evidence** | Interpretation engine under development as part of the Ali Reza Engine (`backend/app/ai/`). Rules-based fallback in `backend/app/clinical/`. Disclaimers are appended to all AI-generated interpretations. Confidence scores are displayed alongside suggestions. Human approval is required before any interpretation is added to the patient record. |
| **Approval** | Engineering Lead, AI Team Lead, Medical Advisor (2026-07-08) |
| **Implementation Date** | 2026-07-08 (development started) |
| **Review Date** | 2026-07-08 |
| **Impact** | Clinicians receive AI-powered interpretation suggestions for lab results. Suggestions require human approval before being added to the permanent record. Rules-based fallback ensures availability. Clear disclaimers accompany all AI output. |
| **Risk** | *Medium.* Risks: (a) AI interprets incorrectly (misleading suggestion) — mitigated by human approval requirement and confidence scoring, (b) over-reliance on AI — mitigated by mandatory human approval and disclaimers, (c) liability for incorrect AI suggestions — mitigated by clear disclaimers and audit trail, (d) interpretation latency slows down result review — mitigated by async interpretation generation (results appear immediately, interpretations appear when ready). |
| **Rollback Strategy** | Disable AI interpretation: fallback to rules-based only. If rules-based is also problematic, disable interpretation entirely (raw results with reference ranges only). |
| **Future Re-evaluation Criteria** | Re-evaluate when: (a) AI interpretation accuracy reaches a threshold where auto-approval for high-confidence suggestions is clinically appropriate, (b) the Iraqi Ministry of Health issues guidance on clinical AI interpretation, (c) liability frameworks for clinical AI are established in Iraqi law, (d) the engine needs to support multi-language interpretations (Arabic, Kurdish, English). |

## AD-CLN-005: Order State Machine

| Field | Value |
|-------|-------|
| **Decision ID** | AD-CLN-005 |
| **Problem** | Lab orders have a lifecycle: created (pending), results entered (completed), validated (locked), or cancelled. The state machine must enforce valid transitions, prevent modifications to validated orders, and provide clear error messages when an invalid transition is attempted. The state machine must be enforced at the service layer (not just the API layer) to prevent bypass via other code paths. |
| **Context** | The order state machine is defined in `backend/app/domain/order_state.py`. States: `pending` (initial, awaiting results), `completed` (all results entered), `validated` (locked, terminal), `cancelled` (terminal). Valid transitions: `pending → completed`, `pending → cancelled`, `completed → validated`, `completed → cancelled`. Invalid transitions (blocked): `validated → anything` (terminal), `cancelled → anything` (terminal), `pending → validated` (must have results first). Enforcement: `can_transition()`, `enforce_transition()` (raises HTTP 409), `assert_not_locked()` (raises HTTP 423), `assert_not_cancelled()` (raises HTTP 409). |
| **Alternatives Considered** | (1) No state machine — orders are updated freely, no transition validation. (2) State machine in API layer only — enforced by route handlers, not by service functions. (3) **State machine in domain layer (chosen)** — enforced in `domain/order_state.py`, called by both routes and services. |
| **Chosen Solution** | **Domain-layer state machine** with enforcement at the service layer: (a) States: `pending`, `completed`, `validated`, `cancelled`. (b) Transitions: defined in `_TRANSITIONS` dict. (c) Enforcement functions: `can_transition()` — returns boolean, `enforce_transition()` — raises HTTP 409 with allowed transitions in the error message, `assert_not_locked()` — raises HTTP 423 if `locked_at` is not None (order is immutable after validation), `assert_not_cancelled()` — raises HTTP 409. (d) Error responses: Arabic + English (`detail` and `detail_ar`). (e) Validation enforcement: `locked_at` timestamp set when transitioning to `validated`. After `locked_at` is set, no mutations to the order's results or samples are allowed. |
| **Rejected Solutions** | No state machine rejected because: data integrity would be compromised — orders could be validated without results, results could be modified after validation, cancelled orders could be reactivated. API-layer only rejected because: service-layer functions could be called from multiple code paths (background tasks, admin scripts) and bypass API-level validation. |
| **Trade-offs** | *Positive:* Clear, testable state transitions. Consistent enforcement regardless of code path. HTTP 409 for invalid transitions (semantically correct — the request conflicts with the resource state). HTTP 423 for locked orders (semantically correct — the resource is locked). Arabic error messages. *Negative:* State machine is simple (4 states, 4 transitions) — may need expansion for complex workflows. HTTP error codes require client-side handling (409, 423 are less common than 400). |
| **Evidence** | `backend/app/domain/order_state.py` defines the canonical state machine. Used by `routes/results.py` and `services/` layer. `_TRANSITIONS` dict is the single source of truth. HTTP 409 for invalid transitions, HTTP 423 for locked orders. Arabic error messages provided. |
| **Approval** | Engineering Lead, Product Manager (2026-01-01) |
| **Implementation Date** | 2026-01-01 |
| **Review Date** | 2026-07-01 |
| **Impact** | All order mutation endpoints enforce the state machine. Validated orders are immutable (`locked_at` prevents mutations). Cancelled orders cannot be modified. Invalid transitions return clear error messages in Arabic and English. |
| **Risk** | *Low.* The state machine is simple and well-tested. Risks: (a) future workflow requires more states (e.g., `pending_review`, `partial_results`, `amended`) — the current 4-state machine would need expansion (mitigated by the state machine being a single dict that is easy to extend), (b) race condition: two concurrent requests try to validate the same order — mitigated by optimistic locking (`version` column), (c) `locked_at` not set for some validation paths — mitigated by asserting `locked_at is not None` in `assert_not_locked()`. |
| **Rollback Strategy** | State machine changes are additive (new states, new transitions) — rollback by reverting the change. The simple state machine makes rollback straightforward. |
| **Future Re-evaluation Criteria** | Re-evaluate when: (a) new order workflows require additional states (e.g., `partially_completed`, `amended`), (b) the Iraqi Ministry of Health mandates specific order lifecycle states, (c) the state machine needs to support automated state transitions (e.g., auto-validate after all results are entered and no anomaly detected), (d) the platform needs to support multi-step validation workflows (e.g., technician enters results, supervisor validates, doctor approves). |

## AD-CLN-006: Result Versioning & Optimistic Locking

| Field | Value |
|-------|-------|
| **Decision ID** | AD-CLN-006 |
| **Problem** | Lab results can be corrected or amended after initial entry (pending results can be corrected, validated results are immutable but may need to be amended with full audit trail). The platform must: prevent concurrent overwrites (two technicians editing the same result simultaneously), maintain a full history of result changes, and clearly distinguish initial results from corrected/amended results. |
| **Context** | Optimistic locking: `LabResult` model has a `version` column (integer, starts at 1). Every mutation checks `version` against the value read at fetch time — if they don't match, the mutation is rejected (409 Conflict). Result versioning: each change to a result creates a new version (old value is preserved in a `result_versions` table or similar). Amendment: validated results cannot be modified (state machine enforces this), but a new "amended result" can be created (linked to the original, with explicit `is_amendment` flag, reason for amendment, and amended_by user). Audit: every result change is audited (audit log hash chain). |
| **Alternatives Considered** | (1) No locking — last-write-wins, concurrent edits overwrite each other silently. (2) Pessimistic locking — lock the row during editing (SELECT FOR UPDATE). (3) **Optimistic locking + versioning (chosen)** — version column checked on write, full history preserved via result versions. |
| **Chosen Solution** | **Optimistic locking with full result version history:** (a) `LabResult.version` column: incremented on each mutation. Checked via `WHERE version = :expected_version`. If the row was modified by another transaction, the update affects 0 rows → the operation is rejected (409 Conflict). (b) Result version history: each mutation saves the previous version's values to a `result_versions` table, preserving the full change history. (c) Amendment: validated results can be amended by creating a new `LabResult` record linked to the original via `amends_result_id`. The amendment carries `reason` and `amended_by` fields. (d) Audit: every write to `LabResult` (create, update, amend) is logged in the audit log (hash chain). (e) Tenant isolation: `lab_id` filtering is enforced on every result query. |
| **Rejected Solutions** | No locking rejected because: concurrent edits can silently overwrite patient data — a technician's correction could be overwritten by another technician's simultaneous edit, losing the correction. Pessimistic locking rejected because: it requires long-running transactions (bad for web applications), can cause deadlocks, and adds complexity (transaction management across multiple operations). |
| **Trade-offs** | *Positive:* Optimistic locking prevents concurrent overwrites without blocking reads. Full result version history provides a complete audit trail. Amendment support for validated results (with explicit flags and reasons). *Negative:* 409 Conflict errors require client-side retry logic (the client must re-fetch, reapply changes, and retry). Version history grows the database (result_versions table). A client holding a stale version can't write until they refresh. |
| **Evidence** | `LabResult.version` column defined in `backend/app/models/result.py`. Optimistic locking check in `routes/results.py` via SQLAlchemy's `version_id_col`. Result version history in `result_versions` table. Amendment support via `amends_result_id` foreign key. Audit logging for every write. |
| **Approval** | Engineering Lead (2026-01-01) |
| **Implementation Date** | 2026-01-01 |
| **Review Date** | 2026-07-01 |
| **Impact** | Every LabResult has a `version` column. Concurrent edits are rejected with 409 Conflict (client must retry). Result changes are versioned (full history preserved). Validated results can be amended (with reason and audit trail). All mutations are audited. |
| **Risk** | *Low.* Optimistic locking is a standard pattern. Risks: (a) client doesn't handle 409 correctly (user sees an error instead of being prompted to retry) — mitigated by client-side retry logic and user-friendly error messages, (b) version history grows unbounded — mitigated by retention policy for old versions (configurable retention period), (c) amendment of validated result bypasses immutability constraint — mitigated by explicit `is_amendment` flag and audit trail (amendment is tracked separately from original). |
| **Rollback Strategy** | Disable optimistic locking: remove the version check (not recommended — concurrent overwrites would be possible again). Version history can be queried regardless of locking status. |
| **Future Re-evaluation Criteria** | Re-evaluate when: (a) version history exceeds 100M rows (performance impact on queries), (b) concurrent edit conflicts exceed 1% of writes (indicates the locking strategy needs tuning or migration to a different pattern), (c) the platform needs to support distributed result entry (offline edge agent creating results that conflict on sync), (d) the Iraqi Ministry of Health mandates specific amendment tracking requirements. |

## AD-CLN-007: Device Bridge Result Normalization

| Field | Value |
|-------|-------|
| **Decision ID** | AD-CLN-007 |
| **Problem** | Medical laboratory instruments from different vendors (Sysmex, Roche, Mindray) output results in different formats, units, and reference ranges. The same test (e.g., Hemoglobin) may be reported as "HGB" with units "g/dL" on one instrument and "Hb" with units "g/L" on another. The device bridge must normalize these into the platform's standard test catalog before ingestion. |
| **Context** | The device bridge (`services/device_bridge/`) handles ASTM E1381/1382 and HL7 v2.x protocol communication with instruments. It normalizes instrument-specific output into a standard internal schema before forwarding to the GULA backend via `gula_client.py`. Normalization includes: test code mapping (instrument code → GULA test catalog ID), unit conversion (instrument unit → GULA standard unit), reference range adjustment (instrument range → lab-specific range), and flag interpretation (instrument flags → GULA critical/normal flags). |
| **Alternatives Considered** | (1) Raw pass-through — forward instrument output as-is, no normalization. (2) Backend-only normalization — instrument sends raw data, backend normalizes. (3) **Device bridge normalization (chosen)** — normalization happens in the device bridge before forwarding. |
| **Chosen Solution** | **Device bridge normalization with device profiles:** (a) Device profiles: configuration files per instrument model that define: instrument-specific test codes → GULA test catalog ID mapping, unit conversion formulas, flag mapping (H/L/LL → critical/high/low/normal), and reference range override defaults. (b) Normalization flow: instrument sends ASTM/HL7 message → device bridge parses the message → device profile maps codes and converts values → standard schema is forwarded to GULA backend. (c) GULA backend receives already-normalized results (just validates and stores). (d) Supported instruments: Sysmex (haematology), Roche (clinical chemistry), Mindray (diagnostics), and generic ASTM/HL7 devices. |
| **Rejected Solutions** | Raw pass-through rejected because: the backend would receive incompatible test codes, units, and formats — each lab would need manual mapping for every instrument. Backend-only normalization rejected because: the monolith would need to handle real-time device protocols and normalization logic simultaneously, and adding a new instrument would require a backend deployment (device profiles in the bridge can be updated independently). |
| **Trade-offs** | *Positive:* Clean separation of concerns — device bridge handles protocol-specific normalization, backend handles business logic. Device profiles are configuration (not code) — new instruments can be added without backend changes. Standard schema simplifies backend processing. *Negative:* Device bridge is an additional service to deploy and monitor. Device profiles must be maintained for each instrument model. ## AD-CLN-009: Negative Result Filtering Architecture

| Field | Value |
|-------|-------|
| **Decision ID** | AD-CLN-009 |
| **Problem** | Lab results that are within normal range ("negative" or "normal" results) constitute the vast majority of results. For clinical decision support, population health analysis, and AI training, filtering out negative results is essential — they create noise, skew statistical models, and make it harder to find clinically interesting patterns. The platform needs a structured way to handle negative results in analytics without losing the data (it must be kept for the patient record). |
| **Context** | A result is "negative" (within normal range) when its value falls between `normal_low` and `normal_high` in the `ReferenceRangeDef` for the test, patient demographics, and lab. Negative results are stored normally in `LabResult` (never deleted). They are included in patient history (full longitudinal record). They are filtered in specific contexts: clinical interpretation (AI focuses on abnormal results), anomaly detection (only flags significant changes, not normal fluctuations), population health (aggregate statistics include all results, but negative results are weighted differently), and alerting (critical alerts only fire for critical values). |
| **Alternatives Considered** | (1) Store all results, query all — no filtering logic, all queries return all results. (2) Store all results, filter at query time — negative results are filtered by the application layer. (3) **Store all results, filter with database indexes (chosen)** — negative results are indexed for efficient filtering without application-layer logic. |
| **Chosen Solution** | **Database-level negative result filtering with partial indexes:** (a) Negative detection: a result is flagged as `is_negative` at write time based on reference range comparison. This is a computed boolean column on `LabResult`. (b) Partial index: `CREATE INDEX idx_lab_results_positive_only ON lab_results (lab_id, test_type_id) WHERE is_negative = FALSE` — efficient queries for non-negative results. (c) Analytics: population health queries use WHERE filters to include/exclude negative results as appropriate. (d) AI: interpretation engine receives the complete result set but weights abnormal results higher. (e) Patient record: full history includes all results (negative and positive) — no filtering at the patient record level. |
| **Rejected Solutions** | No filtering (query all) rejected because: a typical lab runs 70-80% normal results — querying and processing all results for every clinical interpretation would be wasteful and slow. Application-layer filtering rejected because: it requires loading all results into memory (inefficient for large datasets) and complex query logic across multiple code paths. |
| **Trade-offs** | *Positive:* Efficient queries for non-negative results (partial index on `is_negative = FALSE`). `is_negative` is computed at write time (no runtime cost on read). Full patient history is preserved (no data loss). Analytics can choose to include or exclude negative results. *Negative:* `is_negative` must be updated if reference ranges change (a result that was negative could become positive with new ranges). Storage overhead for the computed column and partial index. Negative results are still stored and take disk space. |
| **Evidence** | `LabResult.is_negative` computed column. Partial indexes for non-negative results. Reference range comparison logic in `routes/results.py` (at result entry). Analytics queries (`routes/stats.py`) use WHERE filters. AI interpretation receives full result set with negative/positive weighting. |
| **Approval** | Engineering Lead (2026-01-01) |
| **Implementation Date** | 2026-01-01 |
| **Review Date** | 2026-07-01 |
| **Impact** | `is_negative` is computed at result write time. Partial indexes optimize queries for non-negative results. Analytics and AI can filter efficiently. Full patient history is preserved (no data loss even for negative results). |
| **Risk** | *Low.* Negative filtering is straightforward. Risks: (a) reference range change makes existing `is_negative` values stale — mitigated by background job that recomputes `is_negative` for affected results when reference ranges change, (b) `is_negative` is incorrectly computed due to a bug — mitigated by automated tests for the computation logic, (c) developer forgets to use the partial index (queries all results) — mitigated by query performance monitoring and EXPLAIN ANALYZE in PR review. |
| **Rollback Strategy** | Remove the `is_negative` column and partial index: all queries revert to scanning the full results table (slower but correct). |
| **Future Re-evaluation Criteria** | Re-evaluate when: (a) the negative/positive classification needs to be more granular (e.g., `is_borderline`, `is_critical`), (b) reference range changes require systematic recomputation of `is_negative` for all historical results, (c) the partial index becomes less efficient as the proportion of non-negative results grows. |

## AD-CLN-012: Patient Identity Matching (MPI) Strategy

| Field | Value |
|-------|-------|
| **Decision ID** | AD-CLN-012 |
| **Problem** | Patients may be registered multiple times across different laboratories or even within the same lab (different branches, different visits with incomplete identifiers). Duplicate patient records can lead to fragmented medical histories, repeated tests, and incorrect clinical decisions. The platform needs a Master Patient Index (MPI) that detects and resolves duplicate patient records while maintaining tenant isolation. |
| **Context** | The MPI module is in `backend/app/services/mpi/`. Matching criteria: full name (Arabic, with fuzzy matching for spelling variations), national ID (exact match, encrypted, SNDHS Phase 1), date of birth (exact match), phone number (exact match only — security invariant: "Phone lookups MUST use exact match"), mother's name (Iraqi convention uses mother's name as a patient identifier), and lab ID (tenancy boundary — only match within the same lab or across labs with patient consent). Matching algorithm: deterministic (exact matches on national ID or phone) + probabilistic (fuzzy name + DOB + mother's name scoring). |
| **Alternatives Considered** | (1) No MPI — each patient registration is separate, no duplicate detection. (2) Deterministic MPI only — exact matches only (national ID or phone), no fuzzy matching. (3) **Deterministic + probabilistic MPI (chosen)** — exact matches for high-confidence matching, fuzzy scoring for potential duplicates. |
| **Chosen Solution** | **Hybrid deterministic + probabilistic MPI:** (a) Deterministic matching: exact match on national ID (`patients.national_id`, encrypted, exact comparison) OR exact match on phone number (security invariant: phone lookups use exact match — never LIKE). These matches are high-confidence and can be auto-merged (or suggested for merge with audit trail). (b) Probabilistic matching: scoring algorithm based on name similarity (edit distance for Arabic names with known spelling variations), DOB match, mother's name match. Scores above a configurable threshold are flagged as potential duplicates for manual review. Scores above a higher threshold may be auto-merged. (c) Tenant isolation: matching is within-lab by default. Cross-lab matching requires patient consent (or is limited to `master_admin`/`ministry_admin` roles for SNDHS purposes). (d) Merge workflow: detected duplicates are reviewed by a user with appropriate permissions. The merge preserves both records (primary + alias) with a link. Merged patient history combines all records. (e) SNDHS integration: national ID matching is the primary deterministic method for the SNDHS identity. |
| **Rejected Solutions** | No MPI rejected because: duplicate patient records would proliferate, creating fragmented medical histories and potential for repeated unnecessary tests. Deterministic MPI only rejected because: not all patients have a national ID (children, refugees), phone numbers change, and name variations (spelling, married vs. maiden name) would miss true matches. |
| **Trade-offs** | *Positive:* Deterministic matching catches high-confidence duplicates (same national ID). Probabilistic matching catches spelling variations and demographic matches. Merge workflow preserves all records (audit trail). Tenant isolation prevents cross-lab matching without consent. *Negative:* Probabilistic matching can produce false positives (suggesting a merge for different patients with similar demographics). False negatives (failing to detect a true duplicate) lead to fragmented records. Arabic name fuzzy matching is challenging (complex morphology, common honorifics, tribal names). Merge is a one-way operation (unmerge is complex and rarely needed). |
| **Evidence** | MPI module at `backend/app/services/mpi/`. Test module at `backend/tests/test_mpi_matcher.py`. Deterministic matching on national ID and phone. Probabilistic matching with configurable thresholds. Merge workflow with audit trail. SNDHS national ID matching integration (Phase 1). |
| **Approval** | Engineering Lead, Product Manager, Medical Advisor (2026-01-01) |
| **Implementation Date** | 2026-01-01 |
| **Review Date** | 2026-07-01 |
| **Impact** | Patient registrations are checked against the MPI for potential duplicates. Deterministic matches (national ID, phone) are auto-flagged for merge. Probabilistic matches (name + DOB + mother's name) are flagged for manual review. Merged patients have linked records. SNDHS national ID provides a government-verified identity anchor. |
| **Risk** | *Medium.* MPI risks: (a) false positive merge (different patients merged incorrectly) — mitigated by requiring human review for probabilistic matches, (b) false negative (true duplicate not detected) — mitigated by periodic batch matching jobs that find missed matches, (c) Arabic name matching is error-prone — mitigated by continuous improvement of name matching from reviewed false positives/negatives, (d) merge is complex to undo — mitigated by preserving both records as primary/alias (primary can be changed). |
| **Rollback Strategy** | Disable MPI matching: skip MPI check during patient registration. Existing merged records remain (they have link entries). New duplicates will not be detected. |
| **Future Re-evaluation Criteria** | Re-evaluate when: (a) the MPI accuracy metrics (precision, recall) fall below acceptable thresholds, (b) SNDHS national ID adoption reaches critical mass (most patients have national IDs — deterministic matching becomes the primary method), (c) the platform needs to support cross-lab patient matching at scale (for the SNDHS national patient index), (d) a better Arabic name matching algorithm becomes available (ML-based matching), (e) the merge workflow needs to support automatic unmerge (if a merge was incorrect). |
