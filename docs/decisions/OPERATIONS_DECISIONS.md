## AD-OPS-001: Docker Compose MVP vs Full Stack Decision

| Field | Value |
|-------|-------|
| **Decision ID** | AD-OPS-001 |
| **Problem** | The GULA Platform requires container orchestration for development, testing, and production deployments. The team needed to decide between a minimal viable platform (PostgreSQL + Redis + backend) for rapid development and a full observability/monitoring stack (Prometheus, Grafana, Loki, Tempo, HAProxy, RabbitMQ) for production. The choice affects development velocity, production operations, and resource utilization. |
| **Context** | Two Docker Compose configurations: `docker-compose.yml` (MVP: postgres, redis, backend, api-gateway) for development and minimal production. `docker-compose.full.yml` (adds Prometheus, Grafana, Loki, Tempo, HAProxy, RabbitMQ) for production observability and scaling. The MVP is the primary deployment target (fits on a single DigitalOcean droplet). The full stack is opt-in (use `docker compose -f docker-compose.full.yml`). |
| **Alternatives Considered** | (1) Full stack always — deploy everything all the time. (2) MVP by default, full stack optional (chosen) — deploy core services, add observability/HA when needed. (3) Kubernetes — full container orchestration from day one. |
| **Chosen Solution** | **Two-tier Docker Compose: MVP (default) + Full (opt-in):** (a) `docker-compose.yml` — postgres:16-alpine, redis:7-alpine, gula-backend (FastAPI + gunicorn), api-gateway (nginx). This is the default for `make up`. (b) `docker-compose.full.yml` — extends MVP with Prometheus (metrics collection), Grafana (dashboards), Loki (log aggregation), Tempo (distributed tracing), HAProxy (load balancing for `make scale`), RabbitMQ (message broker for future microservices). (c) Development: `make up` starts the MVP (fast, minimal resource usage). (d) Production: `make up` deploys the MVP initially, full stack is added incrementally as needed. (e) Scaling: `make scale REPLICAS=N` uses `docker-compose.scale.yml` to add backend replicas behind HAProxy. |
| **Rejected Solutions** | Full stack always rejected because: it doubles resource usage (memory, CPU) on the development machine and the DigitalOcean droplet, most developers don't need Grafana dashboards or distributed tracing for daily work, and it slows `docker compose up` significantly (more containers to build and start). Kubernetes rejected because: overkill for a single-server deployment, significant operational overhead (cluster management, ingress controllers, persistent volumes), and the team lacks Kubernetes production experience. |
| **Trade-offs** | *Positive:* MVP starts in <30 seconds (vs. 2+ minutes for full stack). Lower resource usage (MVP ~2GB RAM vs. full ~4GB). Developers only run what they need. Observability stack is available on demand (`-f docker-compose.full.yml`). Incremental production hardening — start with MVP, add full stack components as operational needs arise. *Negative:* Two Docker Compose files to maintain (drift risk — a change in one may not be reflected in the other). Full stack requires reading the docs to know it exists (new team members may not discover it). Migration from MVP to full stack requires a config change and restart. |
| **Evidence** | `docker-compose.yml` is the default configuration. `make up` launches MVP. `docker-compose.full.yml` is available for full stack. `make monitoring` starts the opt-in observability profile. The CI pipeline (`make ci`) tests the MVP configuration (syntax-gate + lint + docker build). |
| **Approval** | Engineering Lead, DevOps Lead (2026-01-01) |
| **Implementation Date** | 2026-01-01 |
| **Review Date** | 2026-07-01 |
| **Impact** | Development uses MVP (fast, minimal). Production starts with MVP and adds full stack components as needed. `make up` / `make down` / `make restart` operate on the MVP config. Full stack is `docker-compose.full.yml` or `make monitoring`. |
| **Risk** | *Low.* Two-config approach is well-established. Risks: (a) config drift between `docker-compose.yml` and `docker-compose.full.yml` — mitigated by periodic reviews and a CI check that validates both configs, (b) developer unaware of full stack — mitigated by `make help` listing all available configs, (c) production deploys without essential observability — mitigated by `make health-deep` providing basic diagnostics even without the full stack. |
| **Rollback Strategy** | Switch between MVP and full stack by changing the Docker Compose file argument. No data migration is needed (shared volumes). |
| **Future Re-evaluation Criteria** | Re-evaluate when: (a) the platform grows beyond a single DigitalOcean droplet (need Kubernetes or Docker Swarm), (b) the MVP resource limits are exceeded and the full stack becomes mandatory for all deployments, (c) the team standardizes on a single deployment configuration (unified docker-compose.yml with optional profiles), (d) a PaaS (Render, Railway, Supabase) replaces Docker Compose for some components. |

## AD-OPS-002: Database Connection Pool Sizing

| Field | Value |
|-------|-------|
| **Decision ID** | AD-OPS-002 |
| **Problem** | The GULA Platform uses SQLAlchemy connection pooling for PostgreSQL access. The pool must be sized to support concurrent API requests without exhausting PostgreSQL's `max_connections` (default 100). Pool size must consider: number of uvicorn workers (`WEB_CONCURRENCY`), pool size per worker (`DB_POOL_SIZE`), and overflow connections (`DB_MAX_OVERFLOW`). The formula must be rechecked whenever any of these knobs change. |
| **Context** | Default values: `WEB_CONCURRENCY=3` (3 uvicorn workers), `DB_POOL_SIZE=6` (connections per worker), `DB_MAX_OVERFLOW=12` (temporary connections beyond pool size). Connection budget: `3 × (6 + 12) = 54`. This fits within PostgreSQL's default `max_connections=100` with 46 connections reserved for admin, monitoring, and other services. The formula is documented in `CLAUDE.md` as a hard requirement. |
| **Alternatives Considered** | (1) Single connection per worker — pool size = 1, no overflow. (2) Large pool — pool size = 20 per worker (test max_connections budget). (3) **Conservative pool with overflow buffer (chosen)** — moderate pool size (6) + overflow (12) for burst traffic. |
| **Chosen Solution** | **Conservative pool sizing with overflow for bursts:** (a) Formula: `WEB_CONCURRENCY × (DB_POOL_SIZE + DB_MAX_OVERFLOW) < postgres.max_connections`. (b) Default: 3 × (6 + 12) = 54 ≤ 100 (PostgreSQL default). (c) Pool parameters: `pool_size=6`, `max_overflow=12`, `pool_timeout=30` (seconds to wait for a connection), `pool_recycle=3600` (recycle connections after 1 hour to prevent stale connections), `pool_pre_ping=True` (check connection liveness before each use). (d) Monitoring: pool status exposed via `/health/deep` and `/metrics/prom`. (e) Auto-repair: if pool exhaustion is detected, the auto-repair engine drains and reconnects the pool. |
| **Rejected Solutions** | Single connection rejected because: a slow query blocks all other requests in that worker (no concurrent DB access). Large pool rejected because: 20 connections × 3 workers = 60 (without overflow), leaving only 40 connections for admin/monitoring — overflow would exceed 100. |
| **Trade-offs** | *Positive:* Conservative sizing stays within PostgreSQL limits. Overflow handles burst traffic without connection errors. Pre-ping prevents stale connection errors. Auto-repair handles pool exhaustion. *Negative:* 6 connections per worker means 6 concurrent DB operations per worker (3 workers = 18 simultaneous operations). If all 6 connections are busy, the 7th request waits (pool_timeout=30s). Overflow (12) adds temporary connections but they are not recycled (could exhaust if overflow persists). |
| **Evidence** | Implemented in `backend/app/database.py`. Pool parameters: `pool_size=6`, `max_overflow=12`, `pool_timeout=30`, `pool_recycle=3600`, `pool_pre_ping=True`. Pool status available via `/health/deep` (pool size, overflow, checked-in, checked-out, etc.). Auto-repair engine (`auto_repair.py`) monitors pool health and triggers drain+reconnect on exhaustion. |
| **Approval** | Engineering Lead, Platform Architect (2026-01-01) |
| **Implementation Date** | 2026-01-01 |
| **Review Date** | 2026-07-01 |
| **Impact** | 54 connections budgeted out of 100. 46 reserved for admin, monitoring, and other services. If `WEB_CONCURRENCY`, `DB_POOL_SIZE`, or `DB_MAX_OVERFLOW` changes, the budget must be rechecked. Pool monitoring via `/health/deep`. Auto-repair handles exhaustion. |
| **Risk** | *Low.* The formula is simple and well-documented. Risks: (a) silent configuration change (someone increases `WEB_CONCURRENCY` without adjusting pool size) — mitigated by startup guard that validates the budget formula, (b) PostgreSQL `max_connections` is changed outside of our control (managed DB service change) — mitigated by monitoring and alerting on connection pool usage, (c) connection leak exhausts the pool — mitigated by `pool_pre_ping` (detects stale connections), `pool_recycle` (reclaims leaked connections), and auto-repair engine. |
| **Rollback Strategy** | Reduce pool size: lower `DB_POOL_SIZE` and/or `DB_MAX_OVERFLOW` to reduce connection usage. This reduces concurrent DB throughput but prevents connection exhaustion. |
| **Future Re-evaluation Criteria** | Re-evaluate when: (a) `WEB_CONCURRENCY` is changed (must recompute budget), (b) PostgreSQL `max_connections` is changed (managed DB upgrade or configuration change), (c) connection pool exhaustion events occur despite current sizing, (d) the platform adds more services that consume PostgreSQL connections (worker process, edge agent sync). |

## AD-OPS-003: DigitalOcean Droplet Deployment Strategy

| Field | Value |
|-------|-------|
| **Decision ID** | AD-OPS-003 |
| **Problem** | The GULA Platform needed a production infrastructure provider for Iraqi medical laboratories. Requirements: in-region hosting (data sovereignty — patient data must stay in Iraq or nearby), predictable pricing (no surprise cloud bills), acceptable latency for Iraqi users, and sufficient capacity for a PostgreSQL 16 + Redis 7 + FastAPI stack. |
| **Context** | Deployment target: DigitalOcean droplet in the Frankfurt region (closest to Iraq with good connectivity). Configuration: single droplet running Docker Compose with all services. Host nginx handles TLS termination (Let's Encrypt via Certbot). Backend runs in Docker under api-gateway nginx. Scripts: `scripts/repair-droplet.sh` (destructive repair), `scripts/diagnose-droplet.sh` (read-only diagnostics), `scripts/deploy.sh` (deployment). |
| **Alternatives Considered** | (1) AWS EC2 — mature, many services, but expensive and complex. (2) On-premise server — full control, but procurement delay, maintenance burden, no disaster recovery. (3) **DigitalOcean (chosen)** — simple, predictable pricing, good performance for the price, data center in Frankfurt (regional compliance). (4) Render/Railway — PaaS with managed PostgreSQL, but less control over infrastructure. |
| **Chosen Solution** | **DigitalOcean single-droplet deployment:** (a) Droplet: 4 vCPU, 8GB RAM, 200GB SSD (sufficient for MVP + moderate traffic). (b) Region: Frankfurt (FRA1) — closest DigitalOcean region to Iraq with acceptable latency (~80ms from Baghdad). (c) OS: Ubuntu 22.04 LTS. (d) Docker Compose: all services run on a single droplet (MVP: postgres, redis, backend, api-gateway). (e) TLS: Let's Encrypt via Certbot on host nginx (auto-renewal). (f) Backup: `make backup` runs `pg_dump` → `./backups/gula_<ts>.sql.gz`. (g) Monitoring: `make health`, `make health-deep`, `make status` for operator diagnostics. (h) Repair scripts: `diagnose-droplet.sh` (read-only), `repair-droplet.sh` (destructive — requires human approval). |
| **Rejected Solutions** | AWS EC2 rejected because: cost (2-3x DigitalOcean for equivalent specs), complexity (VPC, security groups, IAM, EBS volumes), and team lacks AWS operational expertise. On-premise rejected because: server procurement takes weeks, power/cooling/space costs, no hardware redundancy, and disaster recovery is complex. Render/Railway rejected because: less control over Docker configuration, managed PostgreSQL may not support the specific PostgreSQL 16 features we use, and data sovereignty concerns (data location may not be controllable). |
| **Trade-offs** | *Positive:* Simple — one droplet, one Docker Compose deployment. Predictable pricing (~$48/month for 4 vCPU/8GB). Fast deployment (a new droplet is ready in minutes). Backup script is simple (pg_dump to local file). Repair scripts provide both safe (diagnose) and aggressive (repair) options. *Negative:* Single point of failure (no HA). Vertical scaling limit (can't exceed droplet specs without downtime — need to resize droplet). No managed database (PostgreSQL runs in Docker — must manage backups, upgrades, and performance tuning ourselves). Frankfurt is not Iraq — data sovereignty is a concern (data physically leaves Iraq). |
| **Evidence** | Current production deployment runs on a single DigitalOcean droplet. `make backup` runs nightly. `scripts/diagnose-droplet.sh` provides read-only diagnostics (safe to run anytime). `scripts/repair-droplet.sh` is destructive (requires human approval — documented in `CLAUDE.md` as "requires human approval"). |
| **Approval** | Engineering Lead, DevOps Lead (2026-01-01) |
| **Implementation Date** | 2026-01-01 |
| **Review Date** | 2026-07-01 |
| **Impact** | Single-droplet deployment for all services. Host nginx terminates TLS. Docker Compose runs inside the droplet. Backup via `make backup` (pg_dump to compressed file). Repair scripts for diagnostics and emergency repair. |
| **Risk** | *High.* Single-droplet deployment is a SPOF. Risks: (a) droplet outage (DigitalOcean host failure) — mitigated by backup strategy (`make backup`, offsite copy needed), (b) resource exhaustion (CPU/memory/disk) — mitigated by monitoring (`/health/deep`), auto-repair (memory GC), and alerting (health alert loop), (c) data loss (disk failure) — mitigated by nightly `make backup` (backup should be copied off-droplet), (d) security breach (droplet compromise) — mitigated by firewall, SSH key auth, and minimal attack surface. |
| **Rollback Strategy** | Migrate to a new droplet: (a) create a new droplet, (b) install Docker + Docker Compose, (c) restore the latest backup (`make backup`), (d) update DNS to point to the new droplet IP, (e) decommission the old droplet after TTL expiry. |
| **Future Re-evaluation Criteria** | Re-evaluate when: (a) the droplet resource usage regularly exceeds 80% (need to vertically scale or split services), (b) uptime requirements exceed single-droplet reliability (need HA — multiple droplets, load balancer, managed database), (c) Iraqi data sovereignty regulations require in-country hosting (need a data center in Iraq, e.g., local hosting provider), (d) the team grows enough to justify managed infrastructure (RDS for PostgreSQL, ElastiCache for Redis). |

## AD-OPS-004: Blue-Green vs Canary Deployment Strategy

| Field | Value |
|-------|-------|
| **Decision ID** | AD-OPS-004 |
| **Problem** | The GULA Platform needs zero-downtime or minimal-downtime deployments for production updates. Lab technicians enter results throughout the day — a deployment that causes 503 errors or connection drops would disrupt patient care. The deployment strategy must balance deployment speed with safety, and support both routine updates and emergency hotfixes. |
| **Context** | Two deployment workflows: `.github/workflows/deploy.yml` (standard deployment) and `.github/workflows/blue-green-deploy.yml` (zero-downtime blue/green). The platform runs on a single DigitalOcean droplet, which constrains the deployment options (limited resources for running two full stacks simultaneously). |
| **Alternatives Considered** | (1) Rolling update — update containers one at a time (not applicable for single-instance). (2) Blue-green — two full environments, switch traffic. (3) Canary — new version receives a percentage of traffic initially. (4) **Blue-green for major releases, simple restart for hotfixes (chosen)** — blue-green when resources allow, direct restart for emergencies. |
| **Chosen Solution** | **Blue-green deployment for major releases, simple restart for patches:** (a) Blue-green: two Compose stacks (blue and green). Deploy the inactive stack, run health checks, switch the api-gateway nginx to the new stack, keep the old stack running for rollback. Requires sufficient droplet resources to run two backend instances simultaneously (addressed by `make scale` and resource monitoring). (b) Simple restart: for emergency hotfixes (security patches, critical bug fixes), stop the current container and start the new one. This causes ~5-10s downtime (acceptable for emergencies). (c) Health check validation: before switching traffic, the new deployment must pass `/health/ready` (DB + Redis + startup) and `/health/deep` (GREEN grade). (d) Rollback: blue-green — switch api-gateway back to the old stack. Simple restart — redeploy the previous image tag. |
| **Rejected Solutions** | Rolling update rejected because: not applicable to a single-instance deployment (rolling requires multiple instances rotating through the update). Canary rejected because: on a single droplet, canary routing requires a load balancer (HAProxy) and extra capacity — it adds complexity without significant benefit over blue-green for current scale. |
| **Trade-offs** | *Positive:* Blue-green provides true zero-downtime deployment. Rollback is instant (switch api-gateway back). Health check validation prevents deploying a broken release. Simple restart for emergencies is fast (redeploy in <1 minute). *Negative:* Blue-green requires 2x backend resources (manageable on current droplet with 8GB RAM, but tight). Blue-green deployment is slower (build + deploy + health check + switch). Simple restart has ~5-10s downtime (acceptable for emergencies but not for routine updates). Automation complexity (blue-green CI workflow, api-gateway switching logic). |
| **Evidence** | `.github/workflows/blue-green-deploy.yml` defines the blue-green pipeline. `config/haproxy/haproxy.cfg` includes backend switching logic for blue-green. `make health` and `make health-deep` validate deployment health. Rollback procedure documented in runbooks. |
| **Approval** | Engineering Lead, DevOps Lead (2026-01-01) |
| **Implementation Date** | 2026-01-01 |
| **Review Date** | 2026-07-01 |
| **Impact** | Major releases use blue-green (zero-downtime). Emergency hotfixes use simple restart (5-10s downtime). CI workflow validates health before switching. Rollback is documented and tested. |
| **Risk** | *Medium.* Blue-green risks: (a) insufficient droplet resources for two full stacks — mitigated by monitoring and scaling up droplet size if needed, (b) database schema change incompatibility between old and new backend — mitigated by backward-compatible migrations (additive only, no destructive changes), (c) api-gateway switching fails — mitigated by manual switch fallback (update nginx config by hand). |
| **Rollback Strategy** | Blue-green: switch api-gateway back to the old stack (immédiate). Simple restart: redeploy the previous Docker image tag (~1 minute). Both rollbacks are documented and tested. |
| **Future Re-evaluation Criteria** | Re-evaluate when: (a) the platform grows to multiple droplets (canary deployment becomes more useful), (b) Kubernetes adoption changes the deployment model (Kubernetes has built-in rolling updates and canary support via service mesh), (c) the blue-green approach becomes impractical due to resource constraints or deployment frequency, (d) the team adopts feature flags that make canary deployments more valuable for testing features with real traffic. |

## AD-OPS-005: Backup & Disaster Recovery Architecture

| Field | Value |
|-------|-------|
| **Decision ID** | AD-OPS-005 |
| **Problem** | The GULA Platform stores patient data (lab results, orders, patient demographics) and system data (users, audit logs, configuration). Data loss is unacceptable — patient records must be recoverable in case of: database corruption, accidental data deletion, ransomware attack, hardware failure, or site disaster (fire, flood at the data center). |
| **Context** | Backup strategy: `make backup` runs `pg_dump` → `./backups/gula_<ts>.sql.gz`. This is a full PostgreSQL dump (all databases, all schemas). Frequency: nightly (cron job or scheduled task). Retention: local backups kept for 30 days. Off-site: backups should be copied off-droplet (to S3-compatible storage or another server) — not yet automated. Disaster recovery: restore backup on a new droplet, update DNS. |
| **Alternatives Considered** | (1) No backup — data lives only on the production DB. (2) `pg_dump` only — full dump nightly (current). (3) WAL archiving (continuous archiving) — PostgreSQL WAL files archived for point-in-time recovery. (4) Managed PostgreSQL (RDS, DigitalOcean Managed DB) — automated backups, point-in-time recovery. |
| **Chosen Solution** | **`pg_dump` nightly + WAL archiving (planned):** (a) Nightly: `make backup` runs `pg_dump` of the entire database, gzip compressed, stored in `./backups/`. (b) Retention: 30 days local (configurable). (c) Off-site: backups should be copied to off-droplet storage (S3-compatible, scp to another server, or backup service). (d) WAL archiving: planned enhancement — continuous archiving enables point-in-time recovery (recover to any point within 5 minutes before a disaster). (e) Redis: Redis persistence (RDB/AOF) for cache data — less critical, can be regenerated from DB. (f) Disaster recovery: provision new droplet → restore latest backup → update DNS → restart services. Recovery time objective (RTO): < 4 hours (for full disaster). Recovery point objective (RPO): < 24 hours (nightly backup). |
| **Rejected Solutions** | No backup rejected because: patient data loss is unacceptable. WAL-only (no `pg_dump`) rejected because: WAL replay requires a base backup anyway; `pg_dump` is simpler and more portable. Managed PostgreSQL rejected because: currently running PostgreSQL in Docker on the droplet — moving to managed DB is an infrastructure change that can be made later without affecting the application. |
| **Trade-offs** | *Positive:* `pg_dump` is reliable, portable, and can be restored on any PostgreSQL version. Gzip compression reduces backup size (typical ~200MB compressed for a mid-sized lab). Backup script is simple and well-understood. *Negative:* RPO of < 24 hours means up to 24 hours of data loss in a disaster (improved by WAL archiving to < 5 minutes). Restore time depends on backup size (a 2GB compressed backup takes ~10 minutes to restore). Off-site backup copy is not automated (risk of losing both droplet and local backup in a site disaster). |
| **Evidence** | `make backup` script in the project Makefile. Backups stored in `./backups/` directory (gitignored). Restoration procedure documented in `DEPLOYMENT.md`. Redis persistence configured (RDB snapshots every 5 minutes, AOF enabled). |
| **Approval** | Engineering Lead, DevOps Lead (2026-01-01) |
| **Implementation Date** | 2026-01-01 |
| **Review Date** | 2026-07-01 |
| **Impact** | Nightly `pg_dump` backups of the full database. 30-day retention locally. Redis persistence configured. DR procedure: new droplet → restore backup → update DNS → restart. RTO: < 4 hours. RPO: < 24 hours. |
| **Risk** | *High.* Current backup strategy has gaps: (a) no automated off-site copy — a site disaster (fire, flood at the data center) destroys both the droplet and local backups (mitigated by manual periodic off-site copy — needs automation), (b) RPO of < 24 hours — up to 24 hours of data loss if the nightly backup is corrupted or the disaster occurs just before the backup window (mitigated by WAL archiving enhancement), (c) restore procedure is untested — we have not done a full DR drill (mitigated by scheduling a quarterly DR drill), (d) backup file corruption — a corrupted backup is not discovered until restore time (mitigated by automated backup verification — compute checksum and compare). |
| **Rollback Strategy** | N/A — backup is a safety net, not a feature that can be rolled back. Enhancements to the backup strategy (WAL archiving, off-site copy) can be added incrementally. |
| **Future Re-evaluation Criteria** | Re-evaluate when: (a) the platform moves to managed PostgreSQL (automated backups, PITR), (b) data volume exceeds 50GB (full `pg_dump` becomes slow), (c) regulatory requirements mandate specific backup/DRSLAs (e.g., RPO < 1 hour for healthcare data), (d) the team implements an automated off-site backup strategy, (e) a quarterly DR drill reveals gaps in the current strategy. |

## AD-OPS-006: Self-Healing 3-Layer Architecture

| Field | Value |
|-------|-------|
| **Decision ID** | AD-OPS-006 |
| **Problem** | Medical laboratories require high availability — DB or Redis failures should not cause complete system unavailability. The platform must detect failures, isolate faulty components, and recover automatically without human intervention. Manual incident response is too slow (incidents often happen at night, on weekends, or when the on-call engineer is showering). |
| **Context** | 3-layer self-healing: Circuit Breaker (`backend/app/core/self_healing.py`), Auto-Repair Engine (`backend/app/core/auto_repair.py`), Adaptive Concurrency (`backend/app/main.py::_adaptive_concurrency_loop`). Health alert loop (60s cycle) scores GREEN/YELLOW/RED and sends alerts to Telegram/Discord/Slack. Degradation levels: NONE → L1_CACHE_HEAVY → L2_READ_ONLY → L3_CRITICAL_ONLY. |
| **Alternatives Considered** | (1) Manual incident response only — on-call engineer handles all failures. (2) External circuit breaker (Istio/Envoy) — service-mesh-level circuit breaking. (3) Fixed concurrency limit — no adaptive adjustment. (4) **3-layer self-healing (chosen)** — application-level circuit breaker + auto-repair + adaptive concurrency. |
| **Chosen Solution** | **Three-layer self-healing:**
1. **Circuit Breaker** (`self_healing.py`): Tracks consecutive failures per service (DB, Redis). States: CLOSED (normal, requests pass), OPEN (failure threshold exceeded, requests rejected), HALF_OPEN (recovery probe in progress). Degradation levels escalate: NONE (normal) → L1_CACHE_HEAVY (writes pass with warning) → L2_READ_ONLY (POST/PUT/DELETE/PATCH rejected — DB circuit open) → L3_CRITICAL_ONLY (only health + auth + kill-switch paths pass — DB storm).
2. **Auto-Repair Engine** (`auto_repair.py`): Background asyncio task (30s poll). Detects and repairs: DB connection pool exhaustion, Redis eviction storm, memory pressure, circuit breaker stuck open, outbox backlog spike. All actions are logged and idempotent. Does NOT modify business data.
3. **Adaptive Concurrency** (`_adaptive_concurrency_loop`): Halves `_MAX_CONCURRENT` on 2 slow DB readings (>300ms). Restores after 3 fast (<150ms). Clinical writes (`/results`, `/orders`, `/samples`, `/critical-alerts`) are exempt — never shed.
4. **Health Alert Loop** (60s cycle): Grades system GREEN/YELLOW/RED. Fires alerts on transitions (GREEN→YELLOW, YELLOW→RED) and every 5 minutes on RED reminder. |
| **Rejected Solutions** | Manual-only rejected because: response time is too slow for clinical systems (a 2-hour outage during off-hours is unacceptable). External circuit breaker rejected because: Istio/Envoy add infrastructure complexity not supported by the current Docker Compose deployment. Fixed concurrency rejected because: it wastes capacity during normal operation and is insufficient during overload (adaptive concurrency provides better resource utilization). |
| **Trade-offs** | *Positive:* System remains partially available during DB/Redis failures (degraded mode instead of complete outage). Automatic recovery reduces MTTR (mean time to repair) from hours to minutes. Clinical writes are never shed — even under load, patient safety operations get through. Health alerting (GREEN/YELLOW/RED) provides immediate visibility into system state. *Negative:* Additional code complexity in the request path (each request passes through circuit breaker checks). Degraded mode behaviour must be tested and documented (operators need to know what works and what doesn't in each degradation level). Circuit breaker parameters (failure threshold, recovery timeout) need tuning for each deployment. |
| **Evidence** | ADR-009 ratified 2026-07-08. All three layers implemented in `backend/app/core/`. Circuit breaker (`self_healing.py`, 458 lines) with: `CircuitBreaker` class (thread-safe, name, threshold, timeout, states), `SystemHealth` (shared health state), `DegradedModeMiddleware` (routes degraded requests), `RecoveryWorker` (background coroutine probes). Auto-repair engine (`auto_repair.py`, 330 lines) with: 5 repair actions (DB pool, Redis eviction, memory, circuit breaker, outbox backlog). Adaptive concurrency in `main.py::_adaptive_concurrency_loop`. Health alert loop in `main.py::_health_alert_loop`. |
| **Approval** | Engineering Lead, Platform Architect, DevOps Lead (2026-07-08) |
| **Implementation Date** | 2026-07-08 (ADR-009 ratified) |
| **Review Date** | 2026-07-08 |
| **Impact** | Circuit breaker prevents cascading failures (if DB is down, writes are rejected early with clear errors, not queued and timed out). Auto-repair fixes common failure modes automatically (no human needed). Adaptive concurrency prevents overload collapse. Health alert loop notifies operators. Clinical writes are always processed. All three layers complement (not replace) monitoring and alerting. |
| **Risk** | *Low.* Self-healing is defensive — the worst case is that healing fails and the system falls back to the same state as without self-healing. Risks: (a) circuit breaker false positive (trips on a transient failure, causing unnecessary degraded mode) — mitigated by configurable failure threshold (default 3), (b) auto-repair makes things worse (e.g., pool drain during high traffic) — mitigated by idempotent actions and policy guard (`_guard_repair()` checks kill switch), (c) adaptive concurrency oscillates (halves and restores repeatedly) — mitigated by hysteresis (2 slow → halve, 3 fast → restore). |
| **Rollback Strategy** | Disable individual self-healing layers: circuit breaker (set threshold to a very high number), auto-repair (set poll interval to a very long time), adaptive concurrency (set to fixed limit). Each layer can be disabled independently without affecting the others. |
| **Future Re-evaluation Criteria** | Re-evaluate when: (a) the platform adds more dependencies that need circuit breaking (external APIs, AI providers, S3 storage), (b) the auto-repair actions registry needs to be extended for new failure modes, (c) the adaptive concurrency algorithm needs to consider more metrics (memory pressure, Redis latency, not just DB latency), (d) the health alert loop needs to integrate with an external incident management system (PagerDuty, OpsGenie). |

## AD-OPS-012: Migration Testing Strategy

| Field | Value |
|-------|-------|
| **Decision ID** | AD-OPS-012 |
| **Problem** | Database schema migrations can fail in production if they: reference tables that don't exist (ordering issue), add non-nullable columns without defaults (breaks existing rows), are not idempotent (fail on re-run), or are not reversible (can't downgrade if the migration has issues). The migration testing strategy must catch these issues before they reach production. |
| **Context** | 47 migration files in `backend/migrations/versions/`. Migration immutability policy (AD-ARC-015): never modify an existing migration, always create a new revision. `CLAUDE.md` documents the mandatory testing procedure. CI pipeline `migration-check` job validates: `alembic upgrade head` on a fresh PostgreSQL 16 Alpine container, required table verification, and `alembic downgrade -1 && alembic upgrade head` (round-trip test). |
| **Alternatives Considered** | (1) No migration testing — apply migrations blindly in production. (2) Test on staging only — apply migrations to a staging DB, assume production will behave the same. (3) **Clean DB + round-trip + guard functions (chosen)** — CI validates on a fresh DB, round-trip ensures reversibility, guard functions ensure idempotence. |
| **Chosen Solution** | **Three-part migration testing strategy:** (a) Clean DB test: `alembic upgrade head` on a fresh PostgreSQL 16 Alpine container in CI. This validates that all 47 migrations (and any new one) run cleanly from a bare database. Required tables are verified after upgrade. (b) Round-trip test: `alembic downgrade -1 && alembic upgrade head`. This validates that the latest migration is reversible. Only the most recent migration is round-trip tested (CI limitation). (c) Guard functions: every migration uses `_has_column()`, `_table_exists()`, `_index_exists()` to check preconditions before executing SQL. This ensures idempotence — a migration can be run multiple times without error. (d) Local test: developers must test on a clean DB before PR: `docker compose down -v && docker compose up -d postgres && docker compose run --rm gula-backend alembic upgrade head`. |
| **Rejected Solutions** | No migration testing rejected because: production DB failures are unacceptable for healthcare data. Staging-only testing rejected because: staging DB may have accumulated schema drift from manual changes, making tests not representative of a fresh production deploy. |
| **Trade-offs** | *Positive:* CI catches migration issues before they reach production. Round-trip test validates reversibility. Guard functions make migrations safe to re-run. Required table verification ensures nothing is silently missing. *Negative:* Only the latest migration is round-trip tested (CI constraint — can't round-trip all 47 migrations). Guard functions add boilerplate to each migration. Clean DB test doesn't validate upgrade from an existing production snapshot (can't catch issues with data-dependent migrations — e.g., backfill that fails on real data). |

| **Implementation Date** | 2026-01-01 |
| **Review Date** | 2026-07-01 |

Risks: (a) data-dependent migration fails on production data (works on clean DB but not on production) — mitigated by `make backup` (can restore) and testing on a staging DB with production-like data, (b) migration takes too long (locks tables, causes downtime) — mitigated by using `CONCURRENTLY` indexes, `NOT VALID` constraints, and breaking long migrations into batches, (c) guard function is incorrectly implemented (doesn't detect the condition) — mitigated by code review and testing. |
| **Rollback Strategy** | If a bad migration reaches production: (a) run `alembic downgrade -1` (if reversible), (b) create a new migration that reverses the bad migration, (c) if irreversible, restore from backup (`make backup`). Never edit the bad migration in-place. |
| **Future Re-evaluation Criteria** | Re-evaluate when: (a) migration count exceeds 100 (CI migration-check takes too long), (b) the team needs to support branching migration histories (multiple active release trains), (c) the CI pipeline needs to test upgrade from a production-like snapshot (not just clean DB), (d) the team adopts a different migration tool or strategy. |

## AD-OPS-015: Alerting & Incident Response Design

| Field | Value |
|-------|-------|
| **Decision ID** | AD-OPS-015 |
| **Problem** | The GULA Platform needs an alerting system that notifies the operations team when things go wrong, and an incident response process for handling production incidents. Alerts must be: actionable (every alert should require a specific response), routed to the right person (Telegram/Discord/Slack), deduplicated (no alert storms), and graded by severity (the team doesn't get paged for minor issues). |
| **Context** | Health alert loop (`_health_alert_loop` in `main.py`): runs every 60s, grades system GREEN/YELLOW/RED, fires alerts on transitions and RED reminders every 5 minutes. Alert webhook: `ALERT_WEBHOOK_URL` configurable for Telegram/Discord/Slack. Additional alert sources: Prometheus Alertmanager (from `config/prometheus/` rules), Grafana alerting (from dashboard panels), and system-level monitoring (disk space, CPU usage, memory). |
| **Alternatives Considered** | (1) No alerting — rely on engineers checking dashboards. (2) Single-channel alerting — all alerts to one channel (e.g., email). (3) **Severity-graded, multi-channel alerting (chosen)** — alerts routed by severity to appropriate channels. |
| **Chosen Solution** | **Severity-graded alerting with multi-channel routing:** (a) Severity levels: GREEN (ok), YELLOW (degraded — notify during business hours, Slack/Telegram), RED (critical — page 24/7, Telegram + phone call). (b) Sources: health alert loop (60s, grades GREEN/YELLOW/RED), Prometheus Alertmanager (metric-based rules: high error rate, high latency, low disk space), Grafana alerting (dashboard-based: business metrics, usage anomalies). (c) Channels: Telegram (primary — instant, push notification on phone), Slack (secondary — team workspace, good for collaboration), Discord (tertiary — some team members prefer it). (d) Deduplication: Alertmanager groups similar alerts, prevents alert storms (e.g., "InstanceDown" fires once, not once per replica). (e) Actionability: every alert has a runbook link in `docs/runbooks/` — operators know exactly what to do. (f) Incident response: RED alert → on-call engineer acknowledges within 15 minutes → investigates → resolves or escalates. Post-incident review within 24 hours. |
| **Rejected Solutions** | No alerting rejected because: the team can't watch dashboards 24/7. Single-channel email rejected because: email notifications are easy to miss (especially at night), have unpredictable delivery times, and can't provide the instant feedback needed for RED alerts. |
| **Trade-offs** | *Positive:* 60s health alert loop catches system-level issues quickly. Prometheus rules catch metric-based anomalies (error rate spikes, latency degradation). Grafana alerts catch business-level issues (sudden drop in result entry rate may indicate a UI bug). Severity grading prevents alert fatigue (engineers are only paged for RED). Multi-channel routing ensures alerts reach the right person. *Negative:* Health alert loop runs in the backend process — if the backend is completely down, the alert loop can't fire (mitigated by Docker healthcheck restart — if the backend is down, Docker restarts it, and the alert loop restarts with it). Alert fatigue is an ongoing risk (too many YELLOW alerts can desensitize the team). Runbooks must be maintained (outdated runbooks are worse than no runbooks). |
| **Evidence** | Health alert loop in `main.py::_health_alert_loop`. `ALERT_WEBHOOK_URL` in `config.py` configures Telegram/Discord/Slack webhook. Prometheus alerting rules in `config/prometheus/`. Grafana alerting in provisioned dashboards (`config/grafana/`). Runbooks in `docs/runbooks/`. Kill switch (`kill_switch.py`) provides emergency stop for autonomous actions if alerts indicate an AI/auto-repair malfunction. |
| **Approval** | Engineering Lead, DevOps Lead (2026-01-01) |
| **Implementation Date** | 2026-01-01 (health alert loop); 2026-07-15 (Prometheus/Grafana alerts) |
| **Review Date** | 2026-07-15 |
| **Impact** | Health alert loop fires alerts every 60s when system is YELLOW, immediately on RED transition, and every 5 minutes for prolonged RED. Prometheus alerts fire on metric thresholds (e.g., error rate > 5% for 5 minutes). Grafana alerts fire on business metric anomalies. All alerts include severity, affected component, and a link to the relevant runbook. Incident response: RED alert → 15-minute acknowledgment → investigation → resolution → 24-hour post-incident review. |
| **Risk** | *Medium.* Alerting risks: (a) alert fatigue — too many alerts, especially YELLOW (mitigated by severity grading and periodic review of alert rules), (b) missed RED alert — engineer doesn't see the notification (mitigated by multi-channel routing and 5-minute RED reminders), (c) runbooks are outdated (mitigated by runbook review as part of incident post-mortem), (d) health alert loop fails to fire (backend process is hung but not crashed) — mitigated by Docker healthcheck restarting hung processes and external monitoring (DigitalOcean monitoring checks from outside the droplet). |
| **Rollback Strategy** | Change alert routing: update `ALERT_WEBHOOK_URL` to a different channel, or update Prometheus/Grafana alert configurations. Alert changes are reversible. |
| **Future Re-evaluation Criteria** | Re-evaluate when: (a) the team grows to require on-call rotations (need scheduling, escalation policies, and a tool like PagerDuty/OpsGenie), (b) alert volume exceeds what the team can reasonably triage (need more aggressive deduplication or auto-remediation), (c) the platform adopts a formal incident management framework (ITIL, SRE practices), (d) the team needs to reduce mean time to acknowledge (MTTA) and mean time to resolve (MTTR) with better alerting and runbooks. |
