## AD-AI-001: Clinical AI Integration Architecture

| Field | Value |
|-------|-------|
| **Decision ID** | AD-AI-001 |
| **Problem** | The GULA Platform needs clinical intelligence features: result interpretation suggestions, anomaly detection, trend analysis, and predictive analytics. These features must integrate with the existing FastAPI monolith without compromising stability, data integrity, or request latency. The AI integration must be asynchronous (non-blocking), provider-agnostic (avoid lock-in), and feature-flag-gated for gradual rollout. |
| **Context** | AI features span: `backend/app/ai/` (monolith-side AI integration), `ai/` (project root — independent AI services and models), `backend/app/routes/ai.py` (AI API routes), `backend/app/core/feature_flags.py` (feature flag gating). External AI providers: Ollama (primary, local LLM inference), OpenAI-compatible APIs (fallback for cloud inference). The AI abstraction layer must support multiple providers and provider switching without code changes. |
| **Alternatives Considered** | (1) Tight coupling with specific AI provider — simple but vendor-locked. (2) Separate AI microservice — independent scaling but adds network latency and deployment complexity. (3) Embedded ML models (ONNX, TensorFlow) — offline capable but model size and GPU requirements are constraints. (4) Monolith AI module with abstraction layer (chosen). |
| **Chosen Solution** | **Dual-location AI architecture:** (a) `backend/app/ai/` — monolith-side AI integration module with provider abstraction, guardrails, approval workflow, and sandbox execution. (b) `ai/` (project root) — independent AI services and models that can be deployed separately for GPU-backed inference. (c) Provider abstraction layer — supports Ollama as primary provider, OpenAI-compatible APIs as fallback. Provider selection via configuration (not code). (d) All AI operations are asynchronous and non-blocking — AI inference runs in background tasks, results are stored and retrieved separately. (e) Feature-flag-gated via `ENABLE_AI_FEATURES` (per-tenant or deployment-wide). |
| **Rejected Solutions** | Tight coupling rejected because: AI provider landscape is evolving rapidly — abstraction prevents lock-in and allows provider switching. Separate AI microservice rejected because: for current scale, monolith integration is simpler and faster; microservice decomposition can follow if AI load demands it (AD-ARC-006 criteria). Embedded ML models rejected because: external AI services provide more flexibility for model updates, don't require GPU hardware in the deployment, and the team can iterate on prompts without model redeployment. |
| **Trade-offs** | *Positive:* AI features available without external service dependencies for basic operations. Abstraction layer allows provider switching without code changes. Asynchronous design prevents AI latency from blocking the main request path. Feature flag allows gradual rollout per tenant. *Negative:* External AI service dependency for advanced features (internet required for cloud inference). Additional latency for AI-enhanced operations (2-30s for complex inference). Need to manage AI service availability and fallback behaviour (circuit breaker prevents cascade). |
| **Evidence** | ADR-006 (Clinical AI Integration) ratified 2026-07-08. `backend/app/ai/` contains `guardrails.py`, `approval.py`, `sandbox.py`, `system_optimizer.py`. `ai/` at project root contains independent services. All AI operations are async and non-blocking. Feature flag gating via `ENABLE_AI_FEATURES`. |
| **Approval** | Engineering Lead, AI Team Lead (2026-07-08) |
| **Implementation Date** | 2026-07-08 (ADR-006 ratified) |
| **Review Date** | 2026-07-08 |
| **Impact** | AI integration lives in two locations: `backend/app/ai/` for monolith-side integration, `ai/` for standalone services. All AI calls are async. Feature flags control availability per tenant. Provider abstraction enables switching between Ollama and OpenAI-compatible APIs. |
| **Risk** | *Medium.* Risks: (a) external AI service latency blocks non-request-path operations (mitigated by timeouts and async execution), (b) AI provider API changes break the abstraction layer (mitigated by provider-specific adapters), (c) feature flag misconfiguration enables AI for a tenant that hasn't consented (mitigated by consent checks before AI inference). |
| **Rollback Strategy** | Disable AI: set `ENABLE_AI_FEATURES=false` globally or per tenant. All AI operations check the flag before executing. Rollback is immediate and graceful. |
| **Future Re-evaluation Criteria** | Re-evaluate when: (a) AI inference volume requires dedicated GPU infrastructure (extract AI microservice), (b) a new AI provider offers significantly better clinical accuracy, (c) regulatory requirements mandate on-premise AI inference (no cloud dependency for patient data). |

## AD-AI-002: AI Guardrails Strategy

| Field | Value |
|-------|-------|
| **Decision ID** | AD-AI-002 |
| **Problem** | Clinical AI can suggest dangerous actions (incorrect interpretations, harmful recommendations, unauthorized operations). The platform must ensure that AI output is always treated as untrusted suggestions, that certain operations are absolutely blocked for AI (never allowed regardless of human approval), and that no AI output can change clinical state without explicit human approval. |
| **Context** | The fundamental rule: "AI = Suggest, Human = Approve, System = Enforce." Implemented in `backend/app/ai/guardrails.py`. `AISuggestion` objects are immutable and always `is_approved=False` at creation. `AIOperationType` classifies operations: `DISPLAY_ONLY` (no approval needed), `ENRICHMENT` (adds context), `SUGGESTION` (requires approval), `BLOCKED` (never allowed). `_ABSOLUTELY_BLOCKED` set: `validate_order`, `cancel_order`, `modify_result`, `delete_patient`, `create_lab_user`, `change_role`, `approve_result`, `write_audit_log`, `export_patient_data`, `send_critical_alert`. |
| **Alternatives Considered** | (1) No guardrails — AI output is trusted, can directly modify data. (2) Post-hoc guardrails — AI can modify data but changes are audited and reversible. (3) Pre-hoc guardrails (chosen) — AI output must pass through guardrails BEFORE any state change. |
| **Chosen Solution** | **Pre-hoc guardrails** with the following design: (a) `AISuggestion` — immutable frozen dataclass, always `is_approved=False` at creation. (b) `AIOperationType` classification — every AI action must be classified before submission. (c) `_ABSOLUTELY_BLOCKED` operations — AI may NEVER perform these, regardless of approval. (d) `_SUGGESTABLE` operations — AI may suggest these, but they still require human approval. (e) `ai_suggest()` — the ONLY way to produce an `AISuggestion`. Raises `AIGuardrailViolation` for blocked operations. (f) Flow: `AISuggestion` → `Guardrail checks` → `ApprovalStore.submit()` → `PendingApproval` → Human approves → `AISandbox.execute()` → Audited execution. (g) Nothing in the guardrails module ever writes to the database or changes application state — it only produces structured, auditable suggestion objects. |
| **Rejected Solutions** | No guardrails rejected because: a single AI hallucination could corrupt patient data, delete records, or issue incorrect clinical guidance — unacceptable for healthcare. Post-hoc guardrails rejected because: even reversible changes leave a window where incorrect data is visible to clinicians, and some operations (e.g., `send_critical_alert`) cannot be "un-sent" even with audit. |
| **Trade-offs** | *Positive:* AI can never directly modify clinical state. Absolutely blocked operations ensure clinical safety (AI can never approve results, cancel orders, or change user roles). The guardrail layer is testable (unit tests for each operation classification). Immutable `AISuggestion` prevents tampering after creation. *Negative:* Additional latency in the AI action pipeline (guardrail check + approval + execution). The `_ABSOLUTELY_BLOCKED` set requires ongoing review (new operations must be classified). Guardrail violations must never be silently caught — they indicate a design violation. |
| **Evidence** | Implemented in `backend/app/ai/guardrails.py`. `_ABSOLUTELY_BLOCKED` set has 10 operations. `_SUGGESTABLE` set has 7 operations. `ai_suggest()` is the single entry point for AI suggestions. `AIGuardrailViolation` is raised for blocked operations and must not be silently caught. The guardrails module is tested in `tests/` with unit tests for each operation classification. |
| **Approval** | Engineering Lead, AI Team Lead, Clinical Safety Officer (2026-07-08) |
| **Implementation Date** | 2026-07-08 |
| **Review Date** | 2026-07-08 |
| **Impact** | Every AI output passes through `ai_suggest()` before it can influence the system. `AIGuardrailViolation` is raised for absolutely blocked operations. Human approval is required for all `SUGGESTION`-type operations. `DISPLAY_ONLY` operations are auto-approved (they don't change state). The guardrail module is the non-negotiable safety layer for all AI integration. |
| **Risk** | *Low.* Guardrails are well-defined and testable. Risks: (a) a new operation is not classified (falls through to `DISPLAY_ONLY` incorrectly) — mitigated by requiring explicit classification for every new operation, (b) guardrail check is bypassed — mitigated by `ai_suggest()` being the single entry point (can't create `AISuggestion` without going through guardrails), (c) `_ABSOLUTELY_BLOCKED` set is missing an operation that should be blocked — mitigated by quarterly review of the blocked set. |
| **Rollback Strategy** | Modifying guardrails is additive (adding new blocked/suggestable operations) — rollback by reverting the change. Removing an operation from `_ABSOLUTELY_BLOCKED` requires careful consideration and is not a simple rollback. |
| **Future Re-evaluation Criteria** | Re-evaluate when: (a) new AI capabilities are added that require new operation classifications, (b) the `_ABSOLUTELY_BLOCKED` set grows beyond 20 operations (classifications become unwieldy), (c) clinical safety review recommends changes to the guardrail policy, (d) regulatory requirements mandate specific guardrail patterns for clinical AI. |

## AD-AI-003: Clinical Decision Support Model Selection

| Field | Value |
|-------|-------|
| **Decision ID** | AD-AI-003 |
| **Problem** | The GULA Platform needs to select AI models for clinical decision support: lab result interpretation, anomaly detection, trend analysis, and predictive risk stratification. Models must be accurate for the Iraqi population (genetic, dietary, and environmental factors differ from Western populations), support Arabic language, and operate within the platform's resource constraints (no dedicated GPU initially). |
| **Context** | Current model stack: Ollama (local LLM inference, CPU-based, Arabic-capable models) for result interpretation text generation, statistical models (rules-based, no GPU needed) for anomaly detection (delta checks, reference range violations, rate-of-change detection), trend analysis (linear regression, moving averages on patient result history), and predictive risk stratification (logistic regression, random forest for outcome prediction). |
| **Alternatives Considered** | (1) Cloud-only LLMs (GPT-4, Claude) — highest accuracy but network dependency, data sovereignty concerns, and cost per inference. (2) On-premise LLMs (Ollama with Llama/Mistral) — local inference, data stays on-premise, lower accuracy than GPT-4 but sufficient for clinical suggestions. (3) Embedding-based models (BERT, clinical-BERT) — fine-tuned for clinical text, lower latency, but require labeled training data and fine-tuning effort. |
| **Chosen Solution** | **Hybrid model stack:** (a) Ollama-based LLMs (Llama 3, Mistral, or Arabic-tuned variants) for interpretation text generation — CPU-based, runs on existing infrastructure, Arabic-capable models available. (b) Statistical/rules-based models for anomaly detection and trend analysis — deterministic, explainable, no training data needed. (c) Logistic regression/random forest for predictive risk stratification — trained on GULA's patient population data (Iraqi demographics). (d) OpenAI-compatible API fallback for complex cases where local models are insufficient. (e) All models are provider-abstracted — switching models does not require code changes. |
| **Rejected Solutions** | Cloud-only LLMs rejected because: data sovereignty (patient data must not leave Iraq), network dependency (lab can't use AI during internet outages), and cost (per-token pricing at scale is expensive). Embedding-based models rejected because: they require labeled training data (expensive to produce for Arabic clinical text), fine-tuning effort for each clinical domain, and they are less flexible than LLMs for general interpretation. |
| **Trade-offs** | *Positive:* Local models work offline (edge agent support). Data never leaves the infrastructure. No per-inference cost. Arabic-language models available for the target population. Provider abstraction allows upgrading models without code changes. *Negative:* Lower accuracy than GPT-4/Claude for complex interpretations. CPU-based inference is slower than GPU-based (2-10s per suggestion). Local models require periodic updates (new model releases). Statistical models are less accurate than deep learning for some tasks. |
| **Evidence** | Ollama is configured as the primary provider. Statistical models in `backend/app/ai/` for anomaly detection and trend analysis. Provider abstraction layer in `backend/app/ai/` supports switching. Feature flag `ENABLE_AI_FEATURES` controls availability. The model stack is documented in `ai/` (project root). |
| **Approval** | Engineering Lead, AI Team Lead (2026-07-08) |
| **Implementation Date** | 2026-07-08 |
| **Review Date** | 2026-07-08 |
| **Impact** | Interpretation suggestions use Ollama-based LLMs (Llama/Mistral). Anomaly detection uses rules-based statistical models. Trend analysis uses linear regression and moving averages. Predictive risk uses logistic regression/random forest. All models run locally (no cloud dependency). OpenAI-compatible API fallback is available for complex cases. |
| **Risk** | *Medium.* Risks: (a) local LLM accuracy is insufficient — mitigated by confidence thresholds (low-confidence suggestions are flagged for human review), (b) CPU-based inference is too slow (mitigated by async execution and timeout handling), (c) population-specific models need retraining with Iraqi data (mitigated by model retraining pipeline in `ai/`), (d) Ollama resource consumption (CPU, memory) affects API performance (mitigated by running AI in the worker process, not the API process). |
| **Rollback Strategy** | Disable AI features: set `ENABLE_AI_FEATURES=false`. Data continues to flow through the platform without AI augmentation. This is the safe fallback if model quality is insufficient. |
| **Future Re-evaluation Criteria** | Re-evaluate when: (a) population-specific model accuracy metrics are established and current models fall below thresholds, (b) GPU infrastructure becomes available for faster inference, (c) an Arabic-specific clinical LLM becomes available (e.g., Arabic-tuned Llama, or a government-provided model), (d) regulatory requirements mandate explainable AI models (statistical models are inherently explainable, LLMs are not). |

## AD-AI-004: AI Approval Workflow

| Field | Value |
|-------|-------|
| **Decision ID** | AD-AI-004 |
| **Problem** | AI suggestions that can modify clinical state must be reviewed and approved by a human before execution. The approval workflow must: prevent stale approvals, require explicit human confirmation for state-changing operations, auto-approve display-only operations (no state change), and provide a clear audit trail for every AI action (suggested, approved, executed). |
| **Context** | Implemented in `backend/app/ai/approval.py`. `ApprovalStore` manages `PendingApproval` objects. States: `PENDING`, `APPROVED`, `REJECTED`, `EXPIRED`, `EXECUTED`. TTL: 30 minutes (`TTL_SECONDS = 1800`). `DISPLAY_ONLY` operations are auto-approved (no state change). `ENRICHMENT` and `SUGGESTION` operations require human approval. `BLOCKED` operations never reach the approval workflow (caught by guardrails). Approval API: `POST /api/ai/approve/{id}`, `POST /api/ai/reject/{id}`, `GET /api/ai/pending`. |
| **Alternatives Considered** | (1) No approval — AI suggestions are immediately executed (dangerous for clinical AI). (2) Auto-approve all — all AI suggestions are trusted (bypasses human review). (3) **Human-in-the-loop approval (chosen)** — suggestions require explicit human approval for state-changing operations. |
| **Chosen Solution** | **Human-in-the-loop approval workflow:** (a) Flow: `ai_suggest()` → `ApprovalStore.submit()` → `PendingApproval` → Human reviews → `ApprovalStore.approve(id, approver)` or `ApprovalStore.reject(id, approver, reason)` → `AISandbox.execute(approval)` → `approval_store.mark_executed(id)`. (b) TTL: 30 minutes — prevents stale approvals from being used later. (c) Auto-approval: `DISPLAY_ONLY` operations (e.g., `summarize_history`, `translate_report`) are auto-approved because they don't change state. (d) Approval tracking: `submitted_at`, `reviewed_at` timestamps, `reviewed_by` (user email/ID), `rejection_reason` for rejected suggestions. (e) Audit: every approval action is logged. |
| **Rejected Solutions** | No approval rejected because: AI can make dangerous suggestions — human review is essential for clinical safety. Auto-approve all rejected because: bypasses the guardrail principle ("AI = Suggest, Human = Approve") and could lead to unauthorized state changes. |
| **Trade-offs** | *Positive:* Human oversight for all state-changing AI operations. TTL prevents stale approvals. Auto-approval for display-only reduces friction. Clear audit trail for compliance. *Negative:* Approval adds latency (minutes to hours depending on reviewer availability). Pending approvals can accumulate if reviewers are busy (mitigated by notification to lab manager). 30-minute TTL may be too short for complex decisions (but prevents misuse of stale approvals). |
| **Evidence** | `ApprovalStore` implemented in `backend/app/ai/approval.py`. Five approval states (PENDING, APPROVED, REJECTED, EXPIRED, EXECUTED). TTL of 1800 seconds (30 minutes). `DISPLAY_ONLY` auto-approved at submission. API endpoints for approve, reject, list pending, and list all. In-memory store for current implementation; production persistence to DB via AuditLog or dedicated table. |
| **Approval** | Engineering Lead, AI Team Lead (2026-07-08) |
| **Implementation Date** | 2026-07-08 |
| **Review Date** | 2026-07-08 |
| **Impact** | Every AI suggestion goes through the approval workflow. DISPLAY_ONLY → auto-approved. ENRICHMENT/SUGGESTION → must be approved by a human. BLOCKED → rejected by guardrails before reaching approval. Approvals expire after 30 minutes. All actions (submit, approve, reject, execute) are audited. |
| **Risk** | *Low.* The approval workflow is well-defined and testable. Risks: (a) in-memory store loses pending approvals on restart — mitigated by TODO in code to persist to DB, (b) 30-minute TTL causes frequent re-submissions for slow reviewers — mitigated by notification system and adjustable TTL, (c) auto-approval for DISPLAY_ONLY is too permissive — mitigated by careful classification (DISPLAY_ONLY operations cannot change state). |
| **Rollback Strategy** | Change approval behaviour: set feature flag to auto-approve all suggestions (emergency only — for testing or if approval workflow is blocking operations). This bypasses human review and should be used with extreme caution. |
| **Future Re-evaluation Criteria** | Re-evaluate when: (a) approval volume exceeds 1000/day (manual review becomes a bottleneck), (b) the team needs tiered approval (lab manager approves, doctor reviews for critical cases), (c) in-memory store is replaced with DB persistence, (d) AI confidence thresholds are established that allow auto-approval for high-confidence suggestions. |

## AD-AI-005: AI Dataset Collection & Privacy

| Field | Value |
|-------|-------|
| **Decision ID** | AD-AI-005 |
| **Problem** | AI models require training data for clinical interpretation, anomaly detection, and predictive analytics. Collecting patient data for AI training raises privacy concerns: data must be de-identified, consent must be obtained, and data must not leave the infrastructure. The dataset collection strategy must comply with Iraqi health data protection law. |
| **Context** | `backend/app/core/ai_dataset_flags.py` controls dataset collection. Consent types: `research` (for AI training). De-identification: PHI fields (name, national ID, phone, address) are removed before data enters training pipelines. Data retention: training datasets have configurable retention periods. Data export: no patient data leaves the infrastructure for training (models are trained on-premise or in-region). |
| **Alternatives Considered** | (1) No patient data collection — AI models trained only on public/ synthetic data. (2) Full patient data collection with consent — de-identified data used for training. (3) **De-identified collection with opt-in consent (chosen)** — only patients who consent to research have their de-identified data used for training. |
| **Chosen Solution** | **De-identified dataset collection with patient opt-in consent:** (a) Consent: only patients with `research = granted` consent have their data used for AI training. (b) De-identification: PHI fields (name, national ID, phone, address) are stripped during data extraction. (c) On-premise training: models are trained on the same infrastructure (no data export). (d) Data retention: configurable retention period (default 90 days for training datasets; feature tables kept for model recalibration). (e) Audit: all dataset extractions and model training runs are logged. (f) Feature flag: dataset collection is gated by `ENABLE_AI_DATASET_COLLECTION` (default: false). |
| **Rejected Solutions** | No patient data rejected because: models trained on public data would not be accurate for the Iraqi population (genetic, dietary, environmental differences). Full patient data collection rejected because: non-compliant with patient consent requirements and data protection law. |
| **Trade-offs** | *Positive:* Patient privacy is respected (opt-in consent, de-identification). Models trained on in-region data reflect the Iraqi population. Audit trail ensures compliance. Feature flag prevents accidental data collection. *Negative:* Research-consent patients are a subset of the total patient population (smaller dataset = lower model accuracy). De-identification must be robust (residual risk of re-identification from lab result patterns). Model training on-premise requires computational resources. |
| **Evidence** | `ai_dataset_flags.py` controls collection. Consent types include `research`. De-identification strips PHI before extraction. Models are trained on-premise (no data export). Audit logging tracks all extractions. |
| **Approval** | Engineering Lead, AI Team Lead, Compliance Officer (2026-07-08) |
| **Implementation Date** | 2026-07-08 |
| **Review Date** | 2026-07-08 |
| **Impact** | Only patients with `research = granted` consent contribute to AI training datasets. De-identification removes PHI before extraction. Models are trained on-premise. Dataset collection is gated by feature flag (default: false). All extraction and training is audited. |
| **Risk** | *Medium.* Risks: (a) de-identification failure leaks PHI into training data — mitigated by automated PHI detection + manual review of sample extractions, (b) model memorizes patient data (model inversion attack) — mitigated by differential privacy techniques and model evaluation for memorization, (c) consent withdrawal after data is in training set — mitigated by excluding withdrawn patients from future extractions (existing models are retrained without their data on the next training cycle). |
| **Rollback Strategy** | Disable dataset collection: set `ENABLE_AI_DATASET_COLLECTION=false`. Existing training data is retained (but not added to). Models trained before disablement continue to work but are not updated with new data. |
| **Future Re-evaluation Criteria** | Re-evaluate when: (a) Iraqi data protection law changes the requirements for AI training data, (b) the research-consent patient subset is too small for accurate model training, (c) a data breach exposes PHI in training data (trigger for immediate review), (d) the team needs to use cloud-based AI providers that require data export (requires separate compliance review). |

## AD-AI-006: Ali Reza Engine Design

| Field | Value |
|-------|-------|
| **Decision ID** | AD-AI-006 |
| **Problem** | The GULA Platform needs an Arabic-first clinical AI engine that can understand Arabic medical terminology, generate clinical interpretations in Arabic, and integrate with the Iraqi healthcare system's language and cultural context. The engine must handle the specific challenges of Arabic NLP: right-to-left text, complex morphology, dialectal variations, and Arabic medical terminology that differs from English equivalents. |
| **Context** | The Ali Reza Engine (named after the influential Iraqi physician Ali Reza) is the platform's primary clinical AI engine. It operates within `backend/app/ai/` and uses the guardrails + approval pipeline. It is designed for: Arabic lab result interpretation (generating Arabic-language clinical notes), Arabic patient history summarisation, Arabic translation of medical reports (English ↔ Arabic), and Arabic terminology mapping (local terms to standard codes like LOINC). |
| **Alternatives Considered** | (1) English-first with Arabic translation — process in English, translate to Arabic. (2) Arabic-first with English fallback (chosen) — process in Arabic natively, fallback to English for terms not recognized in Arabic. (3) Multilingual model — use a model trained on both Arabic and English medical text. |
| **Chosen Solution** | **Arabic-first design with English fallback:** (a) Primary language: Arabic — all clinical interpretations are generated in Arabic. (b) Arabic NLP: uses Arabic-tuned LLMs (via Ollama) that understand Arabic medical terminology, right-to-left text, and morphological inflections. (c) English fallback: for terms not recognized in Arabic (e.g., rare genetic tests named in English), the engine falls back to English with Arabic annotation. (d) Terminology mapping: maps local Arabic lab test names to standard codes (LOINC) for interoperability. (e) Cultural context: interpretations consider Iraqi clinical practice patterns, medication availability, and disease prevalence. |
| **Rejected Solutions** | English-first rejected because: translation adds latency and loses nuance (medical terms have different connotations in Arabic), most lab staff prefer Arabic for clinical notes, and the contextual understanding would be filtered through English (losing Iraqi-specific patterns). Multilingual model rejected because: most available models are English-dominant (Arabic performance is worse), and the training data for Arabic clinical text is sparse. |
| **Trade-offs** | *Positive:* Arabic-native understanding of clinical context. No translation latency. Arabic terminology mapping to standard codes. Cultural relevance ensures interpretations are actionable in the Iraqi healthcare context. *Negative:* Smaller pool of Arabic-capable LLMs compared to English. Arabic NLP challenges (morphology, diacritics, dialect variation). Arabic medical terminology is less standardized than English (variations between Baghdad, Basra, Erbil). Fallback to English may confuse Arabic-only users. |
| **Evidence** | The Ali Reza Engine is under development within `backend/app/ai/`. It uses Ollama with Arabic-tuned models. Terminology mapping connects local Arabic test names to LOINC codes. Feature flag `ENABLE_AI_FEATURES` gates availability. |
| **Approval** | Engineering Lead, AI Team Lead (2026-07-08) |
| **Implementation Date** | 2026-07-08 (development started) |
| **Review Date** | 2026-07-08 |
| **Impact** | Arabic-first clinical interpretations for lab results. Arabic patient history summarisation. English ↔ Arabic medical report translation. Arabic terminology mapping to LOINC. The engine is provider-abstracted (can switch to a better Arabic LLM when available). |
| **Risk** | *Medium.* Risks: (a) Arabic LLM accuracy is insufficient for clinical use — mitigated by confidence thresholds and human-in-the-loop approval, (b) dialectal variation leads to misinterpretation — mitigated by training on Iraqi-specific Arabic medical text, (c) terminology mapping misses local test names — mitigated by manual curation and lab-specific term mapping, (d) RTL rendering issues in HTML/PDF output — mitigated by Arabic-first CSS and PDF generation. |
| **Rollback Strategy** | Disable Ali Reza Engine: revert to English-first interpretation with Arabic translation, or disable AI interpretation entirely. |
| **Future Re-evaluation Criteria** | Re-evaluate when: (a) a significantly better Arabic clinical LLM becomes available (government-provided, or a model trained on Iraqi medical data), (b) accuracy metrics fall below clinical usability thresholds, (c) terminology mapping coverage exceeds 95% of lab tests in active use, (d) the engine needs to support Kurdish or other Iraqi minority languages. |

## AD-AI-007: SAMIR Engine Design

| Field | Value |
|-------|-------|
| **Decision ID** | AD-AI-007 |
| **Problem** | The GULA Platform needs a lab-specific intelligence engine for operational analytics: predictive inventory management (reagent stock-out prediction), instrument maintenance forecasting, workload balancing across lab shifts, quality control pattern detection, and operational cost optimization. These features require statistical analysis of lab operations data, not clinical patient data. |
| **Context** | The SAMIR Engine (System for Autonomous Management, Interpretation, and Reporting) is the operational intelligence engine. It operates on lab metadata: instrument logs, reagent consumption, QC results, workload data, maintenance records. It does NOT access patient clinical data (no PHI). It runs in `backend/app/ai/system_optimizer.py` and `backend/app/ai/` as a separate subsystem from the Ali Reza clinical engine. |
| **Alternatives Considered** | (1) Manual operational analysis — lab managers review dashboards and make decisions. (2) Business intelligence tool (Metabase, Tableau) — visualization-based analysis. (3) **AI-powered operational engine (chosen)** — machine learning models predict inventory needs, maintenance windows, and workload patterns. |
| **Chosen Solution** | **Statistical and ML-based operational intelligence:** (a) Inventory prediction: time-series models (ARIMA, Prophet) predict reagent/supply consumption based on historical usage patterns, seasonality, and patient volume trends. (b) Maintenance forecasting: survival analysis models predict instrument failure probability based on usage hours, error rates, and calibration history. (c) Workload balancing: clustering and queuing theory models predict daily/weekly workload patterns to optimise shift scheduling. (d) Quality control: statistical process control (SPC) charts detect QC pattern shifts before they result in failed runs. (e) Cost optimization: regression models identify cost drivers and recommend efficiency improvements. (f) All models operate on lab metadata only (no patient data). |
| **Rejected Solutions** | Manual analysis rejected because: lab managers have limited time for data analysis, patterns are hard to detect manually, and predictive lead time is short (reagent stock-out detected too late). BI tool rejected because: dashboards require human interpretation, don't provide predictions, and don't automate recommendations. |
| **Trade-offs** | *Positive:* No patient data exposure (only lab metadata). Predictive insights reduce reagent stock-outs, instrument downtime, and workload imbalances. Explainable models (statistical, regression) are easy to audit. Operates independently from clinical AI (no interference). *Negative:* Models require training data from lab operations (may take months to collect enough data for accurate predictions). Seasonal patterns (e.g., Ramadan, Hajj) require special handling. Model accuracy depends on data quality (incomplete instrument logs reduce forecast reliability). |
| **Evidence** | SAMIR Engine under development in `backend/app/ai/system_optimizer.py`. Uses statistical models (ARIMA, Prophet, SPC) for time-series prediction. Feature flag `ENABLE_AI_FEATURES` gates availability. Models trained on lab metadata collected from `Instrument`, `Reagent`, `Maintenance`, `QualityControl`, and `Workstation` models. |
| **Approval** | Engineering Lead, AI Team Lead (2026-07-08) |
| **Implementation Date** | 2026-07-08 (development started) |

| Field | Value |

| **Problem** | Approved AI suggestions must be executed in a controlled, audited environment that prevents AI operations from directly accessing the main database or production state. The sandbox must support: execution of approved operations under audit, rollback of sandbox changes if needed, and clear isolation between sandbox and production state. |
| **Context** | `AISandbox` in `backend/app/ai/sandbox.py` provides the execution environment for approved AI operations. | **Alternatives Considered** | (1) Direct execution — AI operations execute directly on the production database. (2) Sandboxed execution (chosen) — AI operations execute through an audited, isolated execution layer. (3) Preview-only — AI operations generate previews only, no direct execution. |

(c) Isolation: the sandbox does not have direct database access — it uses the same service-layer functions as the API routes (no special privileges). (d) Audit: every sandbox execution is logged with full details (which AI model, what operation, what payload, who approved it, when executed). (e) Rollback: audited operations can be reversed (not automatically — requires human review and manual reversal). | **Rejected Solutions** | Direct execution rejected because: any bug or misconfiguration in the AI module could corrupt production data. Preview-only rejected because: the point of AI is to automate useful operations (suggesting interpretations, flagging anomalies) — preview-only makes AI useless for anything beyond display. |
| **Trade-offs** | *Positive:* Sandbox prevents direct DB writes from AI code. All sandbox operations are audited. Non-rollbackable operations have an extra confirmation step. The sandbox uses the same service-layer code as API routes (consistency). *Negative:* Sandbox creates an additional abstraction layer (must be maintained and tested). Non-rollbackable operation confirmation adds friction. Sandbox does not prevent data corruption from a logically correct but clinically wrong operation (e.g., AI suggests an incorrect interpretation that a human approves). |
| **Evidence** | `AISandbox` implemented in `backend/app/ai/sandbox.py`. Operations: `execute(approval)`, `preview(approval)`. Integration with `ApprovalStore.mark_executed()`. Uses service-layer functions (no direct DB access). Audit logging via `audit_service.log_action()`. |
| **Approval** | Engineering Lead, AI Team Lead (2026-07-08) |
| **Implementation Date** | 2026-07-08 |
| **Review Date** | 2026-07-08 |
| **Impact** | Approved AI operations execute through the sandbox. All sandbox operations are audited. Non-rollbackable operations require additional confirmation. The sandbox uses the same service-layer code as the API (no special privileges). |
| **Risk** | *Low.* The sandbox is a safe execution layer. | **Context** | Models are identified by `ai_model` string in `AISuggestion` (e.g., `ali_reza_1.0`, `samir_1.0`). | **Trade-offs** | *Positive:* Simple, effective model versioning. Complete audit trail (every suggestion records its model version). Provider abstraction enables A/B testing and gradual rollout. Rollback is a configuration change. *Negative:* No automated model accuracy monitoring (accuracy drift must be detected manually or via custom metrics). No experiment tracking (model training runs are not logged in a central registry). Version string convention must be maintained by convention (no automatic version bumping). |
| **Evidence** | `AISuggestion.ai_model` field is a string. Provider abstraction layer maps version strings to inference endpoints. Model version is recorded in audit logs alongside each suggestion. A/B testing is possible via the provider abstraction (not yet implemented). |

| **Implementation Date** | 2026-07-08 |
| **Review Date** | 2026-07-08 |
