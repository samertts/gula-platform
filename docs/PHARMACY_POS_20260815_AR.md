# دفعة POS وسجل العلاج في منصة GULA

**التاريخ:** 2026-08-15

**النطاق:** الصيدلية المؤسسية، المبيعات، المخزون، الفوترة، الصرف، وسجل المواطن

**حالة البيانات:** اصطناعية ومعزولة؛ لا توجد اتصالات بأجهزة أو بوابات دفع أو موردين خارجيين.

## الملخص التنفيذي

أضافت هذه الدفعة طبقة تشغيلية أولى للصيدلية داخل GULA. أصبحت `Pharmacy Operations Workspace` تحتوي على نقطة بيع مؤسسية يمكنها البحث بالباركود أو اسم الدواء، بناء سلة، طلب معرف الفوترة، اختيار المواطن اختياريًا لسجل العلاج، ثم إرسال عملية بيع ذرية إلى backend. العملية تنشئ سجل البيع وبنوده، وتخصم المخزون وفق الدفعة الأقرب انتهاءً، وتسجل حركة مخزون، وتنشئ فاتورة وتسوية دفع اصطناعية، وتكتب `MedicationDispense` لكل بند عندما يتوفر سياق مريض/مواطن.

لم تُنسخ أي ملفات أو واجهات من المشاريع العامة. جرى استخدام أنماط المجال والعقود التشغيلية فقط، ثم إعادة تنفيذها باستخدام بنية GULA الحالية المبنية على FastAPI وSQLAlchemy وAlembic وReact. هذا يحقق إعادة تكوين أصلية، ولا يثبت أن GULA بديل معتمد طبيًا أو ماليًا عن أي منتج خارجي.

## ما تم تنفيذه

| المجال | التنفيذ داخل GULA |
|---|---|
| نقطة البيع | `POST /pharmacy/pos/sales` مع سلة متعددة البنود و`Idempotency-Key` ومنع التكرار عند إعادة الطلب |
| الكتالوج والباركود | بحث `GET /pharmacy/drugs` بالاسم أو الباركود، مع اختيار صنف مؤسسي فعال |
| FEFO | توزيع الكمية على الدفعات الصالحة الأقرب انتهاءً، مع رفض المنتهي والمحجور وغير المتاح |
| المخزون | خصم `StockLevel` و`DrugBatch` وتسجيل `StockMovement` مرجعية إلى البيع داخل نفس المعاملة |
| الفوترة | إنشاء `BillingInvoice` من بنود البيع وربط رقم الفاتورة بسجل البيع، مع تسوية اصطناعية فقط |
| الربح ورأس المال | تخزين المبيعات والتكلفة والربح الإجمالي، وفصل قيمة المخزون المتبقي عن الإيراد |
| التقارير | `GET /pharmacy/pos/summary` للمبيعات والتكلفة والربح والوحدات والنواقص والركود لمدة قابلة للتحديد |
| سجل المواطن | `MedicationDispense` لكل بند مصروف عند توفر `citizen_id` أو سياق مريض صالح، مع معرف البيع والدفعة والصلاحية في metadata |
| واجهة المواطن | تبويب `العلاجات المصروفة` في `CitizenWorkspacePage` عبر `GET /citizen-platform/me/medication-dispenses` |
| العزل | مسارات POS تستخدم `require_institutional_permission` وتطبق `lab_id` على البيع والمخزون والاستعلامات |
| حواجز frontend | فتح مسارات القراءة والكتابة المعتمدة فقط، مع إبقاء بقية الكتابات التشغيلية محظورة حتى اعتماد عقودها |

## التدفق الذري للعملية

```text
Barcode / drug search
        ↓
Institution-scoped catalog validation
        ↓
FEFO allocation against non-expired, non-quarantined batches
        ↓
Create sale + sale lines
        ↓
Create billing invoice + synthetic settlement
        ↓
Decrease stock and batch quantities
        ↓
Write stock movement
        ↓
Write MedicationDispense for citizen/patient context
        ↓
Audit event + idempotent response
```

تُجرى جميع عمليات الكتابة في خدمة واحدة قبل `commit` المسار. إذا فشل التحقق من الكمية أو الفاتورة أو سجل الصرف، لا تُعتمد العملية الجزئية. ويمنع مفتاح idempotency إعادة خصم المخزون أو إنشاء فاتورة ثانية عند إعادة إرسال الطلب نفسه.

## الاستفادة الأصلية من المشاريع العامة

استُخدم نمط OpenBoxes في الفصل بين المخزن والموقع وتسجيل حركات المخزون والتحويلات بدل تعديل كمية صامت. [1] واستُخدم نمط تطبيق الصرف في OpenMRS في فصل سياق الوصفة عن عملية الصرف والاحتفاظ بحالة صرف قابلة للتتبع، ثم أعيد تمثيله داخل GULA بعقود `PharmacySaleLine` و`MedicationDispense`. [2]

استُخدمت مبادئ GNU Health في ربط الوصفة بالمريض والدواء والجرعة والمدة والوحدات، وفي جعل حركة المخزون قابلة للرجوع إلى مصدر سريري أو تشغيلي. [3] [4] كما استُخدمت أنماط OpenMRS Stock Management الخاصة بالدفعات، الصلاحية، التحويل، التسوية، حدود إعادة الطلب، والتنبيهات كخريطة توسعة مستقبلية للنظام الموجود في GULA. [5]

واستُخدم نمط OpenEMR العام في ربط السجل الصحي بإدارة الممارسة والفوترة، مع إبقاء تفاصيل التكلفة والربح مقيدة بالصلاحية وعدم عرضها في سجل المواطن العام. [6] هذه الاستفادة هي نقل للمفاهيم وليس نسخًا للكود أو أسماء الواجهات أو تصميم المنتج.

## الضوابط والحدود الحالية

تُعد عملية الدفع الحالية **تسوية اصطناعية داخلية**؛ ولا يوجد بها اتصال ببطاقات أو محافظ أو بوابة دفع. كما أن الطباعة الحالية تعتمد على واجهة المتصفح، بينما الطباعة الحرارية المباشرة عبر Gateway محلية تبقى ضمن دفعة لاحقة. ولا تشمل هذه الدفعة بعد التأمين والمطالبات أو الشراء الكامل من الموردين أو المزامنة مع جهاز حقيقي.

لا يُنشأ سجل مواطن إذا لم يقدم النظام معرف مواطن أو مريض قابلًا للربط. لذلك يجب على المؤسسة أن تمرر معرف المواطن الوطني المعتمد عند صرف علاج لمواطن حتى يظهر في تاريخه. أما بيع OTC مجهول الهوية فيظل سجلًا تجاريًا ومخزنيًا دون ربط شخصي، تجنبًا لإنشاء سجل صحي بلا هوية موثوقة.

تحتوي نماذج `MedicationDispense` على معرفات عابرة للنطاقات. أبقيت قيود العلاقات المرجعية في migrations، بينما يستخدم ORM معرفات scalar في بيئة الاختبار متعددة metadata حتى لا يخلط بين `EHRBase` و`NationalBase`. لا يخفف ذلك قيود قاعدة البيانات الإنتاجية التي تُطبقها migrations.

## الدفعات التالية المقترحة

الدفعة التالية ينبغي أن تضيف أوامر الشراء والاستلام والموردين، لأن POS الحالي يستهلك مخزونًا موجودًا ولا ينشئ بعد دورة توريد كاملة. بعدها تضاف المرتجعات التجارية وربطها بعكس الفاتورة وحركة المخزون، ثم التأمين والمطالبات، ثم الطباعة المباشرة عبر Gateway المؤسسية. وبعد تثبيت هذه العقود يمكن إضافة قواعد التنبؤ بالنقص وكشف الركود المتقدم، مع إبقاء جميع العمليات ضمن المؤسسة والمخزن والفرع والصلاحية المناسبة.
