# تنفيذ مسار العيادة الطبية في GULA

## الملخص

أضيفت بوابة آمنة لمسار العيادة الطبية داخل `frontend-v3` تحت `/clinic-operations`. صُممت الصفحة باعتبار العيادة نقطة تنسيق للموعد والوصول والزيارة والطلبات وخطة الرعاية، لا باعتبارها نظام حجز منفصلاً أو بديلاً عن السجل السريري. يبقى backend هو المصدر النهائي للهوية والتفويض والحالات والتوثيق والتوقيع والتدقيق.

## ما تم تنفيذه

تقدم الصفحة وضع Demo اصطناعياً ومعزولاً يعرض المواعيد، الاستقبال والانتظار، المرضى ضمن السياق، شاشة Encounter، الطلبات والنتائج، خطة الرعاية، صندوق التنبيهات، ودور علي رضا كمرشد داخل الواجهة. أزرار طلب المختبر والأشعة والوصفة والإحالة وإغلاق الزيارة معطلة في Demo حتى لا توحي بوجود كتابة سريرية حقيقية.

في Live تقرأ الصفحة مساحات العمل من `GET /niam/workspaces`، وتقبل فقط مساحة غير شخصية مرتبطة بمنشأة بحالة فعالة أو موثقة أو معتمدة. تفعيل السياق يتم عبر `POST /niam/workspaces/{workspace_id}/switch`. بعد ذلك تستخدم الواجهة بوابة القراءة السريرية canonical الموجودة:

| المجال | العقد | الحالة |
|---|---|---|
| المرضى | `GET /api/v1/clinical/patients` | قراءة محدودة بعد Clinical Context وAuthorization |
| الطلبات | `GET /api/v1/clinical/orders` | قراءة محدودة بعد Clinical Context وAuthorization |
| المواعيد والانتظار | لا يوجد عقد واجهة عيادة موحد آمن مستخدم هنا | محجوب |
| Encounter والتوثيق | لا يوجد عقد كتابة frontend آمن مستخدم هنا | محجوب |
| الوصفات والإحالات وخطة الرعاية | تحتاج state machine وتفويضاً مستقلاً | محجوبة |
| التنبيهات الحرجة | تحتاج تسليم وتأكيد وتصعيد وتدقيق | محجوبة |

## الفصل بين الموعد والزيارة

تعرض الواجهة صراحة أن `Appointment` لا يساوي `Encounter`. قد يُحجز الموعد ولا يحضر المواطن، وقد يصل مريض دون موعد في حالة طارئة، وقد يبدأ Encounter بعد التحقق من الهوية والسياق. لذلك لا تقوم الصفحة بتحويل الحجز إلى زيارة ولا تعتبر الدفع أو التأمين دليلاً على حضور أو إكمال الخدمة.

## الحراسة والعزل

أضيفت سياسة دفاعية لمسار `/clinic-operations` تشمل الأدوار الموجودة فعلياً: الإدارة، الطبيب، الموظف، الفني، و`demo_viewer`. المواطن لا يرى لوحة عمليات العيادة؛ وصوله إلى المواعيد والسجل الصحي يبقى في المساحات المواطنية المحكومة. هذه الحراسة دفاعية فقط، ويبقى التحقق النهائي خادمياً.

لا تعرض الصفحة `patient_id` أو الهاتف أو الرقم الوطني من قراءات العيادة، ولا تتيح بحثاً حراً خارج Clinical Context. كما لا تنشئ Professional Identity أو Membership أو Role أو Permission من frontend، ولا تمنح الطبيب وصولاً لمجرد اختيار workspace.

## الوظائف المحجوبة عمداً

تبقى عمليات البحث عن طبيب وحجز الموعد وإعادة الجدولة والإلغاء وcheck-in وtriage وفتح Encounter وكتابة الشكوى والتاريخ والعلامات الحيوية والفحص والتشخيص والطلبات والوصفة والإحالة وخطة الرعاية والمتابعة والتوقيع والإغلاق، إضافة إلى Break-Glass وTelemedicine وChat السريري والإجراءات والحقن والتأمين والدفع والشكوى، بحاجة إلى عقود خادمية مستقلة أو غير موصولة من هذه الموجة.

كل كتابة مستقبلية يجب أن تفرض علاقة مريض وسياقاً سريرياً وتفويضاً مهنياً ونطاق مؤسسة ونسخة أو `If-Match` و`Idempotency-Key` ومسار حالات واضحاً وسجل تدقيق غير قابل للحذف. لا يجوز استخدام Last Write Wins لتعارضات Encounter أو التشخيص أو الحجز، ولا يجوز أن يحول علي رضا اقتراحاً إلى تشخيص أو وصفة أو صلاحية.

## دور علي رضا

يظهر علي رضا كمرشد للتنقل وشرح حقول النظام والتذكير بالبيانات الناقصة وتلخيص ما يملك المستخدم صلاحية رؤيته. لا يوقع، ولا يغير التشخيص، ولا يصدر وصفة، ولا يفتح صلاحية، ولا يتجاوز Consent أو Authorization، ولا يقرأ كل بيانات المريض بناءً على طلب نصي غير مصرح.

## الاختبارات

تمت إضافة اختبارات لمسار العيادة تثبت عزل Demo عن API الحي والكتابة السريرية، وعدم قراءة المرضى والطلبات قبل تفعيل workspace، وإخفاء `patient_id`، وحجب المواعيد وEncounter والوصفة والإحالة في Live. كما أضيف اختبار لسياسة التنقل لمنع المواطن من رؤية بوابة العيادة.

## الحدود التشغيلية

هذه الموجة لا تثبت جاهزية إنتاج، ولا تكاملاً حكومياً أو تأمينياً أو مع بوابة دفع أو مزود فيديو أو أجهزة قياس حيوية. كما لا تفتح Offline Encounter أو queue synchronization؛ تلك تحتاج تخزيناً مشفراً ومزامنة ذات تعارض domain-specific وتدقيقاً وإعادة تحقق خادمية. الفحوص المحلية لا تستبدل فحوص GitHub البعيدة أو اختبار PostgreSQL staging ببيانات اصطناعية.
