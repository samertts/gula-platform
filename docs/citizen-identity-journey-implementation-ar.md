# تنفيذ مسار الهوية والمواطن في GULA

## الغرض

يمثل هذا المستند تحويل المسار المرفق إلى تنفيذ واقعي داخل GULA دون ادعاء وجود تكاملات غير متاحة. يعتمد التنفيذ على مبدأ **شخص واحد، حساب موحد، سياقات ومساحات عمل منفصلة**. لا تصبح الواجهة مصدراً للهوية أو الصلاحية؛ الخادم هو صاحب القرار في التحقق، العلاقة الصحية، العضوية، الموافقة، وسياق المؤسسة.

> لا يعني ظهور بطاقة أو مرحلة في الواجهة أن التحقق الحكومي أو مطابقة الوجه أو إنشاء السجل الطبي قد تم فعلياً. كل مستوى غير موصول بعقد خادمي واضح يظهر بوصفه غير مفعّل أو يتطلب عقداً خادمياً.

## ما تم تنفيذه الآن

أصبحت صفحة `/my-record` هي **مركز التحكم بالهوية ومساحات العمل**. تعرض الصفحة ملخص حساب GULA، وحالة الحساب المنعكسة من الجلسة، ومراحل التحقق بصياغة صادقة، والموافقات التي يعيدها الخادم، ومساحات العمل التي يعيدها عقد NIAM. لا تعرض الصفحة الرقم الوطني أو المعرف الصحي الخام، ولا تنشئ حساباً أو Person أو NHID أو عضوية أو ترخيصاً مهنياً من الواجهة.

في الوضع الحي، تقرأ الصفحة قائمة المساحات من `GET /niam/workspaces` والموافقات من `GET /consents/me`. تبديل مساحة العمل يمر عبر `POST /niam/workspaces/{workspace_id}/switch`. إلغاء موافقة نشطة يمر عبر `POST /consents/{consent_id}/withdraw` ثم تعيد الصفحة القراءة من الخادم. وفي الوضع التجريبي لا تُرسل أي قراءة حية؛ تظهر بطاقة اصطناعية للعرض فقط.

تم أيضاً إصلاح حاجز عميل الواجهة ليسمح بتجديد الجلسة `POST /auth/refresh`، وإضافة اختبار يمنع عودة هذه المشكلة. بقيت الكتابات السريرية والإدارية وعمليات التسجيل الحكومي خارج الحاجز ما لم يوجد لها عقد صريح.

## مطابقة المسار مع النماذج الحالية

| مجال المسار | التنفيذ الحالي | الحد الأمني |
|---|---|---|
| هوية الشخص والحساب الموحد | حساب GULA والجلسة ومساحات NIAM المنعكسة في `/my-record` | لا يستخدم الهاتف أو الرقم الوطني أو الجهاز كمفتاح Person داخل الواجهة. |
| مساحة المواطن | `/citizen` مع عقد `citizen-platform/me/*` الحالي | تبقى CitizenRelationship وscope الخادمي شرطاً؛ لا يفتحها الدور المحلي وحده. |
| المساحات المهنية | تعرض فقط إن أعادها الخادم مع `professional_type` وmembership/context | لا ينشئ frontend مساحة لطبيب أو صيدلي من role أو اسم أو import. |
| الموافقات | عرض الموافقات النشطة وسحبها عبر عقد NIAM | لا تعرض الواجهة معرفات الحسابات للعميل، ولا تمنح موافقة جديدة من دون مسار grant خادمي معتمد. |
| تبديل السياق | يمر عبر `switchWorkspace` الخادمي | لا توجد حالة سياق محلية تمنح صلاحية. |
| Demo | بيانات اصطناعية معزولة وقراءة فقط | لا يستدعي `/niam/workspaces` أو `/consents/me` في Demo. |
| مساعد علي رضا | يبقى مرشداً تفسيرياً في الواجهة | لا يستطيع اتخاذ قرار Authorization أو الوصول إلى قاعدة البيانات. |

## مراحل التحقق

تعرض الواجهة أربع حالات مفهومة: حالة حساب GULA، وثيقة الهوية وOCR، NFC/الوجه الحي، والتحقق الحكومي. حالة حساب GULA مأخوذة من session contract، بينما المراحل الأخرى تظهر `غير مفعّل` لأنها تحتاج عقوداً خادمية وخدمات تحقق وقراراً قابلاً للتدقيق. لا تعتبر الواجهة قراءة OCR دليلاً حكومياً، ولا تعتبر بصمة الجهاز هوية الشخص.

التنفيذ الصحيح عند اعتماد هذه الخدمات مستقبلاً يجب أن يحفظ أدلة التحقق في `VerificationRecord` أو نموذج مكافئ، ويصدر مستوى ثقة منفصلاً مثل `PROVISIONAL` أو `GOVERNMENT_VERIFIED`. لا يجوز ترقية المستوى من JavaScript أو من نتيجة OCR محلية وحدها.

## مساحات الخدمات الصحية

تظهر صفحة المركز روابط آمنة إلى المساحة الصحية عند انعكاس مساحة مواطن نشطة أو مقيدة من الخادم. وتبقى عناصر الأجهزة والجلسات، الأسرة، الوثائق، والتأمين في حالة `يتطلب عقداً خادمياً` لأن العقود الحالية لا توفر قراءة ذاتية كافية أو قد تتطلب نطاقاً قانونياً خاصاً.

هذا القرار مقصود. لا تُستخدم endpoints إدارية أو مؤسسية لتمثيل «من شاهد بياناتي؟»، ولا تُعرض بيانات الجلسات أو الأجهزة التفصيلية من endpoint لا يملك عقداً citizen-self. يلزم لكل سطح لاحق endpoint مستقل يفرض ownership/relationship وminimum disclosure وaudit.

## الفجوات التي تحتاج Backend أو تكاملاً خارجياً

| القدرة المطلوبة في المسار | سبب عدم تفعيلها الآن | متطلبات الاعتماد |
|---|---|---|
| Phone OTP | مسار auth الحالي يعتمد عقد login/password ولا يوجد عقد OTP citizen مكتمل في هذا الفرع | rate limit، challenge/expiry، audit، منع enumeration، وربط session آمن. |
| OCR للبطاقة | لا يوجد endpoint تحقق مواطن ذاتي يخزن evidence ويصدر قراراً | خدمة معتمدة، تشفير، retention، مراجعة fraud، وقرار خادمي لا من المتصفح. |
| NFC | يحتاج adapter interface وSDK أو قارئ خارجي معتمد | attestation، توافق أجهزة، fallback، وعدم جعل NFC شرطاً وحيداً. |
| Face/liveness | لا يوجد عقد capture/verification | موافقة صريحة، anti-spoofing، معالجة biometric data، retention، ومراجعة قانونية. |
| Government verification | لا يوجد اتصال مفوض بوزارة الداخلية | عقد حكومي، authorization، data-sharing agreement، SLA، وتدقيق نتيجة المصدر. |
| NHID/health record discovery | النموذج الحالي يفصل حساب/Person/Relationship ولم يُضف endpoint citizen summary شاملاً | ownership واضح، عدم كشف identifiers، deduplication/HITL، وaudit. |

| My Sessions | endpoint الحالي account-scoped ويعيد metadata محدودة ويتطلب account_id | session self contract، account binding من الخادم، terminate-all مع reason وaudit. |
| Who viewed my data | audit الحالي organization-scoped | endpoint citizen access-history يخفي payload ويعرض الغرض/الجهة/الوقت وفق policy. |
| Family/guardian | علاقة ولي الأمر ليست ملكية للطفل | GuardianRelationship وlegal scope وtransition عند بلوغ الاستقلال. |
| Emergency break-glass | لا يُفعّل من واجهة المواطن الحالية | clinician authorization، reason required، emergency dataset محدود، وaudit/alert. |
| Insurance/documents/radiology/vaccination | endpoints الحالية ليست كلها citizen-self approved | عقد read منفصل لكل domain مع relationship/consent وminimum disclosure. |

## قواعد غير قابلة للتفاوض

يبقى `Role` مختلفاً عن `Profession`، و`Permission` مختلفة عن `Role`، و`Consent` ليست بديلاً عن `Authorization`. كما أن مساحة الطبيب لا تمنح الوصول إلى سجل مواطن؛ يلزم سياق سريري أو CitizenRelationship وscope مناسب. لا يجوز استخدام التطابق الاسمي أو بصمة الجهاز لإنشاء Person أو دمج سجلات.

كل كتابة مستقبلية، بما فيها grant/withdraw أو تسجيل جهاز أو طلب تصحيح، تحتاج server-side authorization، version/If-Match عند قابلية التعديل، idempotency حيث يوجد side effect، وسجلاً تدقيقياً immutable. أما السجل الطبي فلا يحذف تدميرياً؛ تصحيح البيانات ينشئ نسخة أو طلب تصحيح مع سبب وأثر.

## الاختبارات المرتبطة

اختبارات MyRecord تثبت عزل Demo، الاعتماد على workspaces الخادمية، عدم عرض `national_id` أو `health_id` الخام، تبديل السياق عبر endpoint الخادمي، عرض الموافقة الخادمية، سحب الوصول عبر endpoint المحدد، وفحص axe. اختبارات `client.writeBarrier` تثبت السماح فقط بـ`/consents/me` وwithdraw و`/auth/refresh` ضمن العقود، مع استمرار رفض الكتابات غير المصنفة.

## الخلاصة

تم تنفيذ **الطبقة المرئية الآمنة** من المسار: مركز هوية ومساحات، عرض صادق لمراحل التحقق، موافقات قابلة للسحب، ارتباط بالسجل الصحي الحالي، وعزل Demo. أما OCR/NFC/face/government verification/NHID/الأجهزة والجلسات/الأسرة/الوصول التاريخي والطوارئ فهي ليست placeholders تُخفي نقصاً؛ بل قدرات محكومة تحتاج backend contracts وتفويضاً وموافقات وتشغيلاً قبل إظهارها كميزات فعالة.
